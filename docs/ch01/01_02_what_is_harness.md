# 1.2 Harness：模型之外的运行系统

## 1.2.1 模型负责生成，外壳负责落地

要理解 Harness 这个词，先看清模型实际站在哪一层：

> **模型负责生成内容，或者生成一次动作请求。访问网络、读取文件、记住昨天的对话、决定删不删数据，都发生在模型外面。**

它不会自己打开你的电脑。给它文字，它可以接下一段文字；给它图片，它可以描述那张图；在支持工具调用的接口里，它还可以返回「请调用某个函数」这样的结构化请求。请求本身仍然只是一段输出。真正把请求变成一次查询、一次修改、一条记忆的，是外面的运行系统。

那些能读代码、能改文件、能查资料的 AI 产品，干活的就是这层系统。它叫 Harness。

## 1.2.2 模型决定上限，外壳决定产品

这是本书最重要的一个区分，也是本章要记住的类比：

> **模型是发动机，Harness 是整台车。**

发动机提供动力，它决定这台车的动力上限。方向盘、刹车、仪表盘、车门锁，以及「这车能不能上路、敢不敢让别人开」，由整车决定。

因此：

> **Harness = 模型权重之外、把 LLM 组织成可运行 Agent 的那层系统。**

模型决定能力上限：推理、上下文长度、工具调用、是否看得懂图片，这些都算。Harness 决定这些能力如何被组织、约束，并交付成一个产品。两边都起作用。同一个模型装进不同外壳，仍然可以成为差别很大的产品：

| 模型 | 装进什么外壳 | 变成的产品 |
| --- | --- | --- |
| 同一个 Claude | 网页对话外壳 | Claude.ai（聊天） |
| 同一个 Claude | 终端编码外壳 | Claude Code（会读代码、改文件、跑测试） |
| 同一个 GPT | 网页对话外壳 | ChatGPT |
| 同一个 GPT | 编码代理外壳 | Codex |

## 1.2.3 产品架构上的五个部件

**本书把 harness 分成五个部件。** 这是产品架构的清单，也是后面目录的组织方式：

| 部件 | 它负责回答 | 本书章节 |
| --- | --- | --- |
| **Agent 循环** | 什么时候继续、什么时候停 | 第 3 章 |
| **能力层** | 它能做什么、懂什么方法 | 第 4、5 章 |
| **上下文与会话** | 它这次能看见什么、跨会话记得什么 | 第 6 章 |
| **权限与沙箱** | 它被允许做到什么程度 | 第 15 章 |
| **客户端** | 用户从哪儿跟它说话 | 第 11、20 章 |

五个部件都在模型权重之外。换一台发动机，车还在；但循环和能力接口要按新模型的调用方式做适配。会调 API，只是让发动机点着了火。离「能上路、能载人、敢让别人开」，中间隔的就是这五个部件。

后面还会再遇到两张清单。三张清单说的不是同一层：

| 清单 | 它在说哪一层 | 包含什么 |
| --- | --- | --- |
| **Harness 五部件** | 整个产品 | 循环、能力层、上下文与会话、权限与沙箱、客户端 |
| **运行时四件套** | 各家产品拆开后都能看见的内核 | 循环、能力注册表、会话日志、执行策略 |
| **循环内部五部件** | 第 3 章那个循环里面的零件 | 状态载体、执行器、终止条件、熔断器、权限策略 |

这一张是整台产品。运行时四件套里的「执行策略」，就是这里的权限与沙箱，再加上执行环境。客户端是同一套运行时的不同入口：接终端是命令行，接网页是控制台，接手机是随身的审批端，不接界面就是给别人调用的服务。所以很多架构图不单列客户端。第 11 章会把它做出来。

第 3 章那张清单是循环里面的零件。权限策略在那里先留空，第 15 章再装上。

模型本身还要学，但只学它的脾气：它为什么有时会一本正经地编造、为什么输入越长越慢、为什么同一个问题两次答案可以不一样。知道这些，你才知道该配什么档位的车。这些在下一章一次讲完。换模型时，循环和工具调用要经过一层统一接口，代码只跟这个接口说话。这一层也在第 2 章落地。

## 1.2.4 能力层先记住两个抽屉

五个部件里，最直接决定「它到底能帮你干多少事」的是能力层。这里最容易混的是两样东西。

**第一层：工具（Tool）——它能请求哪些动作。**

查天气、读文件、执行命令、搜索网页，每一个动作都是一个工具。例如 `get_weather(杭州)`：给出城市，返回天气。

工具可以是一个本地函数，也可以是一次远程 API，还可以经 **MCP** 做成独立服务再挂进来。MCP 解决的实际问题是：能力可以单独发布、单独升级，调用方按同一套协议去用。工具少、都是你自己写的短函数时，本地函数就够。MCP 是一条可选的路，不是每接一个工具都必须走的路。第 4 章展开。

**第二层：技能包（Skill）——它知不知道该怎么做好。**

会查天气，不等于会安排一趟出行；会写代码，不等于会按你们团队的规范写提交信息。这类章法由技能包承担：

- 团队提交信息的书写规范
- 发版的标准流程
- 某类报告必须包含的章节结构

在技术上，一个技能包通常是 **一个目录加一份 `SKILL.md`**：写给模型看的方法说明。Agent Skills 是一项公开规范，Claude Code、Codex、Cursor 等主流产品都提供了各自的支持。你写的方法说明，有机会在不同 Agent 之间复用。具体格式、版本和安全边界以规范站点为准，第 5 章再落地。

两层解决的问题不同：

```text
工具解决："它能不能做这个动作"      ← 会查天气 ≠ 会安排出行
技能包解决："它知不知道该怎么做好"   ← 会写代码 ≠ 会按团队规范写
```

还有一个值得先知道的加载方式：启动时可以只读每个技能包的名字和一行描述，真正要用到时再读正文。这样能力可以继续增加，未命中的说明不会占满这一次的上下文。这是渐进式加载，第 5 章会写成真正的加载器；它是一种常用设计，不是所有产品的默认实现。
