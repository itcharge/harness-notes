# 3.1 ReAct 与循环的解剖：五个抽屉

先把这个循环的来历讲清楚。它不是一个拍脑袋的设计，而是有论文来源、又被所有现代产品沿用至今的结构。

2022 年，一篇叫 **ReAct** 的论文给出了一个朴素但关键的观察：人在解决复杂问题时，不会「一口气想完全部再做」，而是 **边做边想** —— 先想一步，动手试一下，看看结果，再决定下一步。

论文把这个过程写成三段：

```text
Thought（想法）     →  现在该做什么？先查一下天气。
Action（行动）      →  调用 get_weather(上海)
Observation（观察） →  返回：上海，小雨，18~24℃
（带着「下雨」回到 Thought）
```

上面是示意。**这个「Thought → Action → Observation」的三段循环，就是 Agent 的骨架。** 本书的循环就照这三段写：想一步，做一步，把结果放回去，再想。第 1 章说的受控循环，就是这一圈再加上两种停法：模型自己给出回答，循环退出；步数到了上限，循环被切断。

从 2022 年的论文到今天的 Claude Code、Codex，这一圈一直没变。变的是圈上多挂了一些功能。拿 Claude Code 帮你改代码来说：

- **改文件之前先问你一句**：这是在「做」之前加了一道审批，第 15 章会写
- **一次同时读三个文件**：这是一次「做」里执行好几个工具，第 11 章会写
- **对话太长时，把前面的内容压成一段摘要**：这是在下一次「想」之前给记录瘦身，第 6 章会写

这些功能都挂在某一步的前后。拆掉它们，剩下的仍是那一圈：模型决定下一步，程序去执行，结果交回给模型。

## 3.1.1 想法不必再打印出来

ReAct 原文那个年代，模型只会回一段话，不会单独告诉你「请调用哪个函数」。论文只好规定它把想法和动作写成两行字：

```text
Thought: 用户问天气，我需要调用天气工具
Action: get_weather(上海)
```

程序再从这段话里找出 `Action` 那一行，才知道该执行什么。

第 2 章已经换成了另一种返回。你把工具清单和问题一起发给模型，它回来时多带一个字段，名字叫 `tool_calls`。里面直接写着函数名和参数，比如 `get_weather`、城市是上海。程序读这个字段就行，不用再从一段话里抠 `Action:`。

它可以回答了，这个字段就是空的，回来的是给用户看的那段话。所以本章代码里没有 `Thought:` 这一行。

> 思考的台词可以不印出来。留下的是「想 → 做 → 看」：决定写在 `tool_calls` 或最终回答里，结果写回消息列表。

带推理通道的模型，内部仍可能有一段思考。那一段由模型在这一次调用里产生。本章的循环只使用两样返回：`tool_calls`，以及最后的回答文本。

判断依据也可以写进提示词，那是第 2 章的五个零件。循环负责的是另一件事：把工具结果放回消息，让模型带着新信息再决定一次。

## 3.1.2 和现在的写法对照

| ReAct 论文 | 本章代码里 | 真实 harness 里 |
| --- | --- | --- |
| Thought（想法） | 这一轮的决定。需要调工具时是 `tool_calls`，需要收尾时是最终回答 | 模型的决策。有的产品还能看到一段推理 |
| Action（行动） | 按名字调用 `TOOLS` 里的函数 | 工具执行 |
| Observation（观察） | 追加一条 `{"role": "tool", ...}` | 工具结果 |

各家给这三步起的名字不一样，顺序是一样的：先决定，再去做，再把结果交回去。

下一节我们将这三步封装进一个 `for` 循环，反复执行，实现基础的控制流程。但是也有不少框架不用循环，而是直接将这一逻辑画成流程图，实现节点之间的流转。比如第 14 章会介绍的 LangGraph，就是用「构建图」的方式实现：整个流程只是两条路径，节点和分支一目了然。

```text
       ┌─ 可以回答了 ──► 结束
问模型 ─┤
       └─ 还要查资料 ──► 执行工具 ──► 把结果送回「问模型」
```

左边决定下一步，右边真的去执行。本章先写那个 `for` 循环，不画这张图。

## 3.1.3 五个抽屉，这一章装四个

这一圈要能转起来，得先回答五个问题。下一节的代码回答前四个，最后一个先空着。

| 问题 | 书里的叫法 | 下一节写在哪 |
| --- | --- | --- |
| 做到哪一步了？ | 状态载体 | `messages`：问过的话、调用过的工具、返回的结果，按顺序记在这张列表里 |
| 谁去真的做？ | 执行器 | `TOOLS`：模型点了哪个名字，就从这张表里取出对应的函数来执行 |
| 怎样正常停下来？ | 终止条件 | `if not msg.tool_calls`：模型没有再要工具，就把回答交出来 |
| 一直转个不停怎么办？ | 熔断器 | `MAX_STEPS`：最多转这么多圈，到了就停 |
| 做之前要不要先问人？ | 权限策略 | 这一章先不问。第 15 章再写 |

在下一节的代码中，我们会把表里这五个名字，变成一次完整运行的步骤顺序：想、记、停、熔断、做、看。

「终止条件」和「熔断器」都会停止调用，但是这两种停法不一样：

- **正常停：** 事情办完了。比如你问「上海天气怎么样」，它查了一次，不再要工具，直接回答「上海：晴，26℃」。
- **强制停：** 它还想继续查，可是已经转满 `MAX_STEPS` 圈（下一节写成 8 圈）。程序不再让它查，直接回一句「步数超限」。

如果只有第一种停法，它可能查完还要再查。一次提问会变成十几次调用，每次调用都要付钱。所以先规定最多转几圈。这个上限只管「转了多少次」。第 10 章再补两种停法：一次调用等太久就停；失败了不要马上重试，隔一会儿再试。

### 第五个抽屉为什么空着

权限策略这一章先不写。

下一节只有 `get_time` 和 `get_weather`。它们返回写死的字符串，不能改文件，也不能碰到真实数据。模型点了哪个名字，循环就执行哪个，中间不问你。在「只有自己用、工具只读」的这一步，空着可以。

第 1 章 1.3 节说过，自主性带着三份成本：钱、时间、结果不确定。工具一旦可以改文件、跑命令、动真实数据，执行前问不问人，就得有一份明确的答案。

后续会在 3 个地方补上「权限策略」：
- 第 4 章：每个工具写明自己能干什么，比如只能看，还是会改文件
- 第 11 章：会改文件、会花钱的动作，执行前先问你
- 第 15 章：把「哪些必须问」写成一套规则，并加上沙箱。就算它想动不该动的东西，也碰不到

> 本章先让流程跑通。两个工具目前只返回固定的字符串，即使用错了也不会造成损失，所以暂时无需向你确认。等到工具具备删文件、花钱等能力时，再加上「执行前先征求你的同意」的机制。是否具备这个机制，也决定了这个系统能否被放心地交给别人使用。

在第 14 章对比 Codex、LangGraph 和 DeepSeek Harness 时，我们依然以本节提出的五个核心问题为分析框架。对于 LangGraph，这五个问题也能一一对应到其将循环流程以图形化方式呈现的模型上。
