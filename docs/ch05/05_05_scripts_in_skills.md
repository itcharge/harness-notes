# 5.5 技能包里的脚本：确定性部分不该即兴发挥

## 5.5.1 让模型临场发挥会出错

拿「新软件发一版」当例子。发布前通常要走一套固定步骤：改版本号、写更新日志、打 git 标签、推送。其中有一步很死板、也很关键——核对 `pyproject.toml` 和 `CHANGELOG.md` 里的版本号是否一致。对不上就停，不然发出去的包元信息是错的。

如果交给模型照着描述做，它每一轮都会 **自己写一段代码去解析这两个文件**。写十次成功七次左右：`CHANGELOG.md` 的标题有几种格式变体，正则松一点就漏、紧一点就错。

问题的性质要看清：**这不是模型不够强，而是这件事本来就不该由概率性的东西来做。** 版本号一致性检查是纯确定性判断——没有歧义、没有例外、输入格式固定。**确定的事，就该用确定的东西表达。**

所以它该进 `scripts/`。

## 5.5.2 什么写成脚本

一个判断标准，两句话：

> **能用一段代码稳定地做完，且做完之后「下一步做什么」不需要再判断——进 `scripts/`。**
> **需要在多个选项之间取舍、需要读上下文才知道该怎么做——留在 `SKILL.md` 正文。**

按这条标准过一遍发版流程：

| 步骤 | 放哪 | 为什么 |
| --- | --- | --- |
| 检查版本号三处一致 | `scripts/` | 纯判断，输入固定，失败条件明确 |
| 生成 CHANGELOG 条目骨架 | `scripts/` | 格式化任务，模板固定 |
| 判断这次改动该标 `minor` 还是 `patch` | 正文 | 要看改了哪些提交，是语义判断 |
| 决定要不要跳过某次发版 | 正文 | 取决于人的意图，模型无权决定 |
| 打标签、推送 | 正文 | 不可逆动作，必须先问用户 |

规律很清楚：**脚本承担确定性与易错性，正文承担判断与授权。**

## 5.5.3 一个真实脚本

把上面那条检查做成脚本，放进技能包：

```bash
#!/usr/bin/env bash
# skills/release-runbook/scripts/check_versions.sh —— 版本号一致性检查
set -euo pipefail

version=$(grep -m1 '^version' pyproject.toml | cut -d'"' -f2 || true)
changelog=$(grep -m1 '^## \[' CHANGELOG.md | sed 's/.*\[\(.*\)\].*/\1/' || true)

if [ -z "$version" ] || [ -z "$changelog" ]; then
  echo "没找到版本号：请确认 pyproject.toml 有 version 字段、CHANGELOG.md 有 '## [x.y.z]' 一行。"
  exit 2
fi

if [ "$version" != "$changelog" ]; then
  echo "版本不一致：pyproject.toml = $version，CHANGELOG.md = $changelog"
  echo "下一步：先改 CHANGELOG.md 的版本号，再重新运行本脚本。"
  exit 1
fi
echo "版本一致：$version"
```

三处细节：

- **`set -euo pipefail`**：任何一步失败立即退出，变量的未定义也算失败。脚本进了自动化链路，静默失败比崩溃危险得多。**但要留意 `pipefail` 的副作用**：`grep` 没匹配到会返回 1，`set -e` 会在你打印「下一步」之前就把脚本掐断——所以上面两行取值都带了 `|| true`。
- **不一致时打印「下一步」**：这是第 4 章那条「好错误 = 发生了什么 + 可能原因 + 下一步」的延续。**脚本的输出也是喂给模型的观察结果**，它写得清楚，模型下一轮的动作就准。
- **两个退出码表达两件事**：`exit 2`（输入没找到）与 `exit 1`（找到了但不一致），模型据此能分清该去补文件、还是该改版本号。第 7 章会讲退出码的完整语义。

技能包这一侧，`SKILL.md` 只需写清「什么时候跑它、跑完看什么」：

```markdown
---
name: release-runbook
description: 按团队流程执行一次发版：核对版本号、生成 CHANGELOG 条目、提交并打标签。当用户说要发版、打版本、release、准备发布时使用。
compatibility: 需要 git 与 bash；版本号同时写在 pyproject.toml 与 CHANGELOG.md
allowed-tools: Bash(git:*)
metadata:
  author: harnex-book
  version: "1.1"
---

# 发版手册

## 步骤

1. 跑 `scripts/check_versions.sh`。退出码非 0 就停下来问用户，不要自己改版本号。
2. 版本一致时，按 `references/changelog-template.md` 生成这一版的条目草稿给用户看。
3. 用户确认后，再提交、打标签、推送——这三步都要先给命令。

## 不要做

- 不要修改 `pyproject.toml` 的版本号来「修好」不一致。版本号是人定的。
- 不要在用户没确认时推送。推送不可撤销。
```

注意步骤 1：正文只写了 `scripts/check_versions.sh` 这个路径，**没有把脚本源码贴进来**。回想 5.3——`scripts/` 属于第 3 层，是拿去 **执行** 的，不是拿来 **阅读** 的。模型加载这份手册时，上下文里只多这一行路径；那几十行 bash 本身不进上下文，所以说「零成本」。

## 5.5.4 脚本能省多少字

回到 5.3 节那个数字，落到具体例子上。

`check_versions.sh` 不到 20 行、约 150 token。它替代了什么？没有它，`SKILL.md` 里就得写清「怎么取版本号、`CHANGELOG.md` 的标题有哪几种格式、正则怎么写」——这段文字本身几百 token，而且 **模型读完还要现场生成代码，那部分代码会作为一次工具调用进上下文**，又是一两百 token。

真正的差距在 **重复执行** 上。脚本每跑一次只进一两行输出；而现场生成那条路，每一轮都要重读一遍文字、重生成一遍代码。**脚本的成本是常数，即兴发挥的成本是常数乘以次数。**

| 做法 | 首次 | 第 N 次 | 出错率 |
| --- | --- | --- | --- |
| 正文描述 + 模型现场写代码 | 散文约 300 token + 生成代码约 150 token | 每轮重来 | 约 3/10 |
| 正文指向 `scripts/` | 脚本进正文 0 token（只写路径） | 只进输出约 20 token | 0（代码确定） |

一句话总结这张表：**把确定性搬到脚本里，省下的不只是 token，还有「每次都要重新赌一次」的那部分方差。**

## 5.5.5 允许哪些工具只是建议

`release-runbook` 的 frontmatter 里有一行：

```yaml
allowed-tools: Bash(git:*)
```

它的意思是：**这个技能包声明自己只需要 `Bash` 工具里 `git` 开头的命令。** 作用是告诉模型「你在这个技能包里应该用哪些工具」，帮它收敛选择范围——尤其当技能包正文提到多个工具时，这一行能减少误用。

但必须立刻补上后半句：

> **`allowed-tools` 是技能包自己写的。技能包自己说的权限，不算数。**

这一点和上一章 MCP 的结论完全一致：**MCP server 自称「我需要 fs:write」，不代表你就得给；技能包自称「我只用 git」，不代表它真的只会用 git。** 真正的授权在 harness 那一侧——注册表里的 `scopes`，以及第 15 章的审批档位。规范也把它标为**实验性**，各实现支持程度不一。

换句话说：`allowed-tools` 是一个**声明**，用来帮模型做选择；它不是一个**开关**，用来控制模型能做什么。这两件事的混淆，是 5.8 节要处理的安全问题的入口。

顺带交代一个接口：这一节一直在说「跑脚本」，但 Harnex 现在还不会执行命令——`shell` 是第 7 章的主角。**技能包这一侧的准备（`scripts/` 目录、`allowed-tools` 声明、正文只写路径）已全部就绪**；等第 7 章把 `shell` 接进注册表，它们立刻具备执行能力，一行都不用改。

## 5.5.6 三个常见错误

**巨型 `SKILL.md`。** 正文超过 500 行，第 2 层的成本就开始失控——它「触发即全量加载」，一个 1500 行的技能包会一次吃掉近 2 万 token。**正文该拆进 `references/`**；判断标准不是行数，而是「这些内容是不是每次都需要」——完整规范、字段表、历史变更，都不是。

**把密钥写进技能包。** API key、内部地址、测试账号，写进 `SKILL.md` 或脚本都是灾难，而且是三重灾难：随上下文进模型、随目录进 git、随分发进别人的机器。技能包要走 git 的话，**密钥只能从环境变量读**，`compatibility` 里写清需要哪些变量。

**把依赖藏起来。** 脚本依赖 `jq`、`docker` 或某个 Python 包，却没写进 `compatibility`——别人装上之后，脚本会在第一次执行时以最含糊的方式失败。**它不是文档，是安装门槛的声明。**
