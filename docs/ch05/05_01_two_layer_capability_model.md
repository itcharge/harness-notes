# 5.1 两层能力模型：工具管动作，技能包装方法

## 5.1.1 工具装不下的规矩

先把上一章那个失败场景拆细。

你让 Harnex「把本周的工作整理成周报」。它手上的 `fs_read` 能翻日志、`fs_write` 能落盘，能力上是够的。它缺的是这几件事：

- 周报只分三类：进展、风险、待办，每条必须能归进其中一类
- 「进展」必须是已完成且能指出依据的事；没验证的写「待确认」，不许写「已完成」
- 每条风险必须带对策，没有对策的不许上周报
- 上周遗留的风险要写最新状态，不能原样复制上周的原话
- 写完先给用户看一眼，确认后再落盘

这五条没有一条是「动作」。它们全是「做法」。

**动作和方法是两种东西。** 动作可以有很多个，每个都短小、确定、自带参数；方法则是一整套判断规则，只有在特定场景下才需要，而且往往同时涉及好几个动作。把它们混在一起，是上一章之后最容易犯的错。

## 5.1.2 工具和技能包的对照

|          | 工具（Tool）           | 技能包（Skill）              |
| -------- | ------------------ | ------------------------ |
| 回答什么问题   | 「能不能做这个动作」         | 「这件事该怎么做」                |
| 主要解决     | **一件事**            | **一类事**                  |
| 什么时候进上下文 | 清单常驻（JSON Schema）  | 只有 `name` + `description` 常驻，正文按需加载 |
| 谁执行      | 代码执行，返回值确定         | 模型按步骤执行，中间有判断            |
| 典型内容     | `fs_read`、`shell`   | 周报口径、发版流程、代码评审标准、某领域的操作手册 |
| 分发形态     | MCP server + 清单     | 一个目录 + `SKILL.md`         |
| 上一章 / 本章 | 第 4 章               | 第 5 章                     |

一行边界：**工具是动词，技能包是手艺。**

「读一个文件」是动词——它需要参数、有返回值、成功失败一目了然，模型看到名字就知道怎么调。

「按团队口径写周报」是手艺——它由若干动作串成（确认日期、翻日志、分类、套模板、等确认），中间要判断，而且判断标准只有你们团队知道。你没法把它做成一个工具，因为它不是一个动作；你也没法把它塞进 `description`，因为 `description` 是给模型「决定要不要用」的，不是给模型「照着做」的。

## 5.1.3 三条走不通的老办法

在技能包出现之前，团队里的「方法」只能放在三个地方。三个都不好用。

**第一条：塞进 system prompt。** 最直觉的做法——把周报口径整段写进系统提示，它不就知道了？

问题有三个。**一是成本**：system prompt 每次请求都要重新发一遍，一个 2000 token 的口径，跑一万次就是两千万 token，而其中九成九的对话根本不需要写周报。**二是膨胀**：规范会越来越多，提交规范、发版流程、评审标准、部署检查单……每加一条都往所有请求上摊。**三是没法分发**：它和你的 harness 绑死了，换个产品、换台机器，得重新贴一遍。

**第二条：写成 wiki 页或 README。** 便宜、可版本化、人能读。但**模型读不到**。它只存在于你的浏览器标签里，除非你每次手动把内容复制进对话——那你就变成了加载器，而且要自己判断什么时候该粘。

**第三条：微调一个模型。** 把规范喂进权重里。这条路在一些场景确实有效，但代价是：改一条规则要重训一次、没法按需开关、没法给不同用户不同规范、还得为每次实验付钱。**把易变的流程固化成权重，是拿最贵的工具干最轻的活。**

技能包是第四条路：**方法写成一个文件，平时只暴露一行描述，需要时才把正文读进来。** 它同时拿到了三个好处——可版本化（就是一个目录，进 git）、可分发（别的 harness 也认这个格式）、低成本（不触发就不占上下文，5.3 节会算这笔账）。

## 5.1.4 流程写成可执行文件

这里有一件事值得单独说：技能包不只解决了「模型不知道」，它还顺手解决了一个更老的工程问题。

团队里的 runbook（发版手册、故障处理流程、上线检查单）过去只有两个形态：**给人读的文档** 和 **给人执行的脚本**。人读的那份会过期——代码改了，文档没人改，半年后它就成了错误信息的来源。而脚本只能承载完全确定的那部分，中间需要判断的步骤写不进去。

技能包正好卡在两者之间：**它是给模型读的文档格式，读者是模型。**

这件事的后果比它看起来大。文档第一次有了「被读取后立刻被执行」的通道——而执行者会 **容忍不完整**：你写「如果版本号不一致，停下来问用户」，它真的会在那一步停下来问你，不需要你把每个分支都写成 `if`。**写得像文档，跑起来像脚本。** 这是技能包和普通文档最根本的区别。

## 5.1.5 为什么光有工具协议不够

到这里你可能会问：上一章不是已经有 MCP 了吗？把周报口径做成一个 MCP server，模型调它不就行了？

不行，而且失败的原因很典型。

MCP 的三种能力是 `tools`、`resources`、`prompts`——它们封装的是「**有什么可以做**」和「**有什么可以读**」。而周报口径要求的是「**什么时候该做、按什么标准做、做错了怎么补救**」。这三件事没有一个是 MCP 的接口能表达的：

- 你不能把「没验证的事不许写已完成」写成参数
- 你不能让 `tools` 清单常驻而不付 JSON Schema 的代价
- 你更不能要求模型先读一份 `resources` 再决定调哪个工具——那需要一段「指导模型在不同情况下怎么选」的散文，而散文正是技能包的主体

反过来说也成立：**技能包装不了动作。** `SKILL.md` 里可以写「把周报存进 `reports/` 目录」，但写文件这个动作必须由 `fs_write` 来做。技能包是 **给模型看的说明**，它自己不动手。

两层的关系，一句话：

```text
工具（MCP）        技能包（SKILL.md）
   ↓                    ↓
给模型动作            给模型方法
   ↓                    ↓
「你能做什么」          「这件事你们是怎么做的」
   ↓                    ↓
可插拔                 可插拔
```

两层都是可插拔的，合起来才叫 **能力层**。下一节先不写代码，只把 `SKILL.md` 这个格式看明白——它比你想的短，十分钟足够。
