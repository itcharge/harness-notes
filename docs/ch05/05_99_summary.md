# 小结与验收

## 本章小结

1. **动作和方法是两种东西。** 工具回答「能不能做这个动作」，技能包回答「这件事该怎么做」。工具是动词，技能包是手艺。
2. **技能包让 runbook 第一次有了可执行的格式。** 它是给人读的文档格式，但读者是模型，执行者会容忍不完整——「如果版本号不一致，停下来问用户」不需要写成 `if` 也能跑。
3. **`SKILL.md` 只有一个硬约束：根目录下必须有这个文件（全大写）。** frontmatter 两个必填字段（`name`、`description`），四个可选（`license`、`compatibility`、`metadata`、`allowed-tools`）。`name` 必须与父目录名一致。
4. **渐进式披露是这套格式能成立的根本原因。** 第 1 层元信息常驻（约 100 token/包），第 2 层正文触发才读（5000 token 以内），第 3 层资源按需取用。**50 个技能包的常驻成本约 5000 token，是全部加载的十八分之一。**
5. **脚本是零上下文成本的例外。** 脚本被执行的，不是被阅读的——只有输出进上下文。读一个 400 行脚本要 4000 token，跑它只看输出只要 20 token。
6. **`description` 是唯一必然常驻模型视野的文本**，因此是整个格式里杠杆最高的两行字。前半句说「做什么」，后半句说「什么时候用」，并把用户真会说的词写进去。
7. **确定性进 `scripts/`，判断留在正文。** 能靠一段代码稳定做完、且做完不需要再判断的步骤，都该下沉；需要在多个选项间取舍的，留在 `SKILL.md`。
8. **知识层永远排在执行层与权限层之后。** 技能包带知识，不带权力——它不能修改权限、不能扩大执行能力、不能覆盖系统提示红线。`allowed-tools` 是建议，不是授权。

## 动手任务

1. **写你自己的第一个技能包**：挑一件你每周都要向 AI 重复解释的事（团队的代码评审标准、值班交接的写法、一份内部系统的操作流程）。要求：`description` 前半句说做什么、后半句说何时用；正文有独立的「边界情况」一节；至少引用一个 `references/` 文件。用 5.4 节的加载器把它装起来，确认启动清单里出现了它。

2. **做一次「巨型技能包」的成本实验**：把任务 1 那个技能包的正文人为扩到 800 行，看启动清单的字符数有没有变化（应该没有），再跑一个会触发它的任务，看这一轮总 token 涨了多少。然后把它拆成正文 + `references/`，重跑同一个任务对比数字。**把两次的 token 数写进笔记——这是你对第 3 层成本的第一次实测。**

3. **跑通触发测试集**：把 5.7 节的 10 个用例填进 `evaluate.py`，跑一遍记录通过数。然后照着失败项改 `description`，再跑一遍。**把「改前 / 改后」两张结果表都留下**——这是回归测试的第一条基线。

4. **故意写一个坏技能包**：让 `description` 宽到「帮助完成各种日常任务」。跑触发测试集，看 5 个反向用例里有几个被它抢走。**亲眼看到 over-triggering 的代价**，比读十遍描述都管用。

5. **走一遍安装审计清单**：从 `anthropics/skills` 或社区里挑一个你确实想要的技能包，在**一个空目录、只读注册表**的环境里先跑它，按 5.8 节那五步逐项过一遍，写下每一项的结论。确认无问题后再放进你的真实技能目录。

## 验收清单

- [ ] `SkillPackLoader` 落地：启动时能扫出全部技能包，且**不读任何正文**
- [ ] 启动清单里每个技能包只占「名字 + 描述 + 路径」三行
- [ ] 自研技能包 ≥2 个，其中至少一个带 `references/`、一个带 `scripts/`
- [ ] 技能包的 `name` 与目录名不一致时，加载器会跳过并打印提示（亲手试一次）
- [ ] 触发测试集通过：5 个正向 + 5 个反向用例全对
- [ ] 主循环与第 4 章相比，**除多了一个 `system` 参数外零改动**
- [ ] （里程碑）Harnex 启动加载 ≥5 个技能包，未触发场景下的额外 token ≈ 清单开销，数字写进 trace

## 本章的常见误区

- **把方法论塞进 system prompt**：常驻成本高、改一条要重启、换个 harness 就得重贴。
- **把技能包当成「文档」写**：技能包的读者是模型，它需要步骤和约束，不需要背景介绍和客套话。
- **正文写成巨型文档**：正文是「触发即全量加载」的，超过 500 行就该拆进 `references/`。
- **描述过窄**：只覆盖自己测试时用的那种说法，用户换句话它就再也不触发——而且不报错。
- **描述过宽**：什么任务都抢，正文反复污染上下文，还挤掉别的技能包的位置。
- **让模型即兴写确定的代码**：版本号比对、格式校验这类事，交给脚本，不要每轮现写一遍。
- **密钥写进技能包**：随上下文进模型、随目录进 git、随分发进别人的机器，三重泄露。
- **依赖不写进 `compatibility`**：别人装上后脚本以最含糊的方式失败。
- **以为 `allowed-tools` 是权限开关**：它是技能包自己的声明，判断权必须留在 harness。
- **装第三方技能包不审计**：技能包是提示注入面——你邀请了一段陌生人写的指令常驻在你的 Agent 里。

## 自测题

1. 工具和技能包的本质区别是什么？请各举一个只有对方做得了的例子。
2. 渐进式披露的三层各加载什么、各在什么时候加载？为什么说常驻成本是「按包数线性增长，但斜率只有全量加载的十八分之一」？
3. 什么内容该放 `scripts/`，什么必须留在 `SKILL.md` 正文？请给出判断标准，并用「版本号一致性检查」和「判断这次发版该标 minor 还是 patch」各套一次。
4. 为什么脚本的上下文成本接近零，而 `references/` 里的文档不是？这个差别对技能包的设计有什么影响？
5. 系统提示、技能包、工具返回结果三者冲突时，优先级顺序是什么？为什么？
6. 如何给一个技能包写触发测试？正向用例和反向用例各考察什么？为什么两种失败的成本不对称？
7. 为什么说「技能包不能替代沙箱与审批」？如果某个技能包的正文要求模型跳过审批，正确的做法是什么？

## 本章术语速查（中英对照）

| 中文 | 英文 | 一句话解释 |
| --- | --- | --- |
| 技能包 | Skill / Agent Skill | 一个目录 + `SKILL.md`，把方法论封装成按需加载的知识包 |
| 能力层 | Capability Layer | 工具层 + 技能包层的合称，两层都可插拔 |
| 渐进式披露 | Progressive Disclosure | 元信息常驻、正文触发才读、资源按需取用的三层加载 |
| 元信息 | Frontmatter Metadata | `SKILL.md` 头部的 YAML 块；唯一常驻模型视野的内容 |
| 触发 | Activation / Trigger | 任务与 `description` 匹配，正文被读进上下文 |
| 误触发 | Over-triggering | 描述过宽，不该加载时也加载；浪费 token |
| 漏触发 | Under-triggering | 描述过窄或含糊，该加载时想不起来；安静地不生效 |
| 触发测试集 | Trigger Eval Set | 正反各半的用例集，测召回与精度 |
| 技能包加载器 | Skill Pack Loader | 扫描技能目录、生成清单、按需取正文的 harness 组件 |
| 脚本 | Bundled Script | `scripts/` 下的可执行代码；只进输出，不进上下文 |
| 参考资料 | Reference | `references/` 下的按需文档；读了才花 token |
| 预授权工具 | `allowed-tools` | 技能包声明自己要用的工具；实验性，只是建议不是授权 |
| 提示注入 | Prompt Injection | 本无权威的内容混进有权威的位置；技能包是它的新载体 |
| 技能包坏味道 | Skill Smell | 描述过宽、正文过长、缺错误处理等常见缺陷 |
