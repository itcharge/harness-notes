# 5.3 渐进式披露：为什么装 50 个技能包也不怕

## 5.3.1 装很多个会怎样

先把问题摆出来。假设你有 50 个技能包，平均每个 `SKILL.md` 正文 1800 token。如果全部塞进上下文：

```text
50 × 1800 token ≈ 90,000 token
```

九万 token，还没算你的系统提示、对话历史、工具清单、文件内容。多数模型的上下文窗口在 128k–200k 之间——**光技能包就吃掉一半，而且其中 49 个这次根本用不上。**

这就是「知识越攒越多」的必然结局：一份文档化的方法库，如果用「全部常驻」的方式接入，第一次扩容就会撞墙。

渐进式披露（progressive disclosure）解决的就是这件事。它不是优化技巧，而是这套格式能成立的根本原因。

## 5.3.2 分三层加载

| 层级 | 加载什么 | 什么时候加载 | 成本 |
| --- | --- | --- | --- |
| **第 1 层 · 元信息** | frontmatter 里的 `name` 与 `description` | 启动时，**永远在** | 每包约 100 token |
| **第 2 层 · 指令** | `SKILL.md` 的 Markdown 正文 | 任务与某个描述匹配时 | 每包 5000 token 以内 |
| **第 3 层 · 资源** | `references/` 里的文档、`scripts/` 里的脚本、`assets/` 里的文件 | 正文指向它、或任务确实需要时 | 文档：读到才算；脚本：**零成本**（见下） |

关键在于 **第 1 层和第 2 层之间那道门槛**。启动时模型看到的，只有每个技能包的一个名字加一段描述——刚好够它判断「这次要不要用」。判断为「要用」，正文才被读进来；判断为「不用」，那个包在这次的上下文里就只值 100 token。

重算一遍那 50 个技能包：

```text
50 × 100 token ≈ 5,000 token
```

从九万降到五千，**十八分之一的成本换来同样的可发现性**。

这个规模感可以再放大一点：

| 技能包数 | 全部加载 | 渐进披露（常驻） | 差距 |
| --- | --- | --- | --- |
| 5 | 9,000 | 500 | 18× |
| 20 | 36,000 | 2,000 | 18× |
| 50 | 90,000 | 5,000 | 18× |
| 200 | 360,000（撑爆） | 20,000 | 18× |

最后一行是这个设计真正的分量：**装到 200 个包，常驻成本才 20000 token，仍然装得下。** 用「全部常驻」的方式，你在第 50 个包就撞墙了；渐进披露把撞墙的位置往后推了四倍以上，而且推得很远——**成本随包数线性增长，但斜率是常驻那一层的 1/18。**

Anthropic 自己的文档里有一句话把这件事说透了：

> **上下文窗口是公共资源。**

这句话值得停一下。上下文窗口不是「越大越好用的空间」，它是有预算的。系统提示要占、工具清单要占、对话历史要占、读进来的文件要占——技能包也是来抢这块预算的一方。**任何常驻内容都在向所有请求收税。** 所以设计技能包时该问的第一个问题不是「这段内容有用吗」，而是「它值得常驻吗」。

## 5.3.3 脚本不占上下文

第 3 层里有一个特例，值得单独讲。

`references/` 里的文档被读进来，是要花 token 的——`spec.md` 有 3000 token，读进来就得付 3000 token。但 `scripts/` 里的脚本不一样：**脚本是被执行的，不是被阅读的。**

```text
读一个 400 行的 Python 脚本         → 约 4000 token
跑同一个脚本，只看它的输出         → 约 20 token
```

相差两个数量级。原因很直白：模型需要知道「怎么用这个脚本」，不需要知道「这个脚本内部是怎么写的」。前者写在 `SKILL.md` 正文里，后者留在文件系统上。

这条推论是 5.5 节的起点：**凡是确定性的、易错的、重复的步骤，都该从「让模型即兴写」变成「让模型调用已有脚本」。** 收益不只是省 token，更是把一段概率性的操作换成一次确定的执行。

不过也要说清楚代价：脚本进了执行层，就要面对命令执行的全部风险——权限、沙箱、超时、退出码语义。这些是第 7 章与第 15 章的事。**第 3 层的「零成本」是上下文成本，不是工程成本。**

## 5.3.4 平时只留两行说明

把上面这些推到底，会得到一个有点反直觉的结论：

> **`name` 和 `description` 是整个格式里杠杆最高的两行字。**

因为它们是 **唯一必然常驻模型视野** 的内容。技能包的正文写得再好，如果描述没能让模型在正确的时刻想起它，那段正文永远不会被读。更麻烦的是，这件事在正文里补救不了——正文写「请务必在提交代码时使用我」没用，因为正文没被加载的时候，模型看不见这句话。

于是技能包的失效方式变得很不体面：它不报错，不警告，只是 **安静地不生效**。你装了一个包，测试时随手写的任务触发了它，一切正常；上线后用户说的是另一种说法，它就再也不出现了。5.7 节整节都在处理这个问题。

一个具体的对照，同一个技能包的三种描述：

```yaml
# 太窄：只覆盖你调试时用的那种说法
description: 生成周报。

# 太宽：什么都沾，什么都抢
description: 帮助处理工作汇报相关的各种事情。

# 刚好：说清做什么 + 什么时候用 + 带上会出现的词
description: 按团队口径把本周工作整理成一份周报。当用户提到周报、weekly、本周总结、整理这周做了什么时使用。
```

第三种写法的两句话是有分工的：**前半句是「做什么」，决定模型知道它存在时能不能用；后半句是「什么时候用」，决定模型在这一刻想不想得起它。**

最后补一个实测数字：Anthropic 的文档写了——**20 个已安装的技能包合计约 2000 token。** 换算下来每包 100 token，和我前面的估算一致。也就是说，一个团队装二十个包，常驻成本大致等于一段中等长度的系统提示。**这个量级，才让「知识库」这件事变得可负担。**

## 5.3.5 和下一章的关系

渐进式披露是 **上下文工程** 的第一个具体案例，而它只是一个开始。

它做的事是「按需加载」——内容先放在磁盘上，需要时才搬进上下文。但搬到上下文之后呢？一轮对话结束后，读进来的 `SKILL.md` 正文还留在历史里，二十轮之后它还在那里占着位置，而任务早就做完了。这时候需要的就不是「加载策略」，而是「清理策略」。

第 6 章要处理的就是这一类问题：会话日志怎么记、上下文满了怎么压缩、什么东西该在什么时候从上下文里退场。**这一章你学到的是「如何少花」，下一章讲「花掉之后怎么收回来」。**

现在可以动手了。下一节给 Harnex 装上技能包加载器——为了让第一个版本就能跑起来，我们只实现第 1 层和第 2 层，第 3 层留到 5.5 节。
