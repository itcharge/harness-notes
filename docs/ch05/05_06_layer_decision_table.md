# 5.6 决策表：能力该放进哪一层

## 5.6.1 四层各管什么

学完工具和技能包，最常见的问题变成了另一个：**手上这个东西到底该放哪层？**

四层的能力，各有明确的职责边界：

| 层 | 放什么 | 判断依据 | 典型例子 |
| --- | --- | --- | --- |
| **工具（MCP）** | 改变状态的动作、需要确定执行的操作 | 它「做什么」：有参数、有返回值，可能改变状态 | 读文件、跑命令、发消息、调 API |
| **技能包（SKILL.md）** | 可重复的流程、规范、方法论、领域 SOP | 它说「怎么做」，中间有判断 | 提交规范、发版流程、评审标准 |
| **系统提示（system prompt）** | 全局人设与红线 | **每一次对话都必须成立** | 「不确定就说不确定」「破坏性操作必先确认」 |
| **检索（第 8 章）** | 海量、会变的事实性知识 | 量大、更新频繁、只有一部分用得上 | 产品手册、工单历史、代码库内容 |

一句话的记忆法：

> **工具是动词，技能包是手艺，系统提示是底线，检索是资料。**

注意这四层 **没有替代关系**，任何一层都不能越权去做另一层的事。而它们的共同点也值得说一句：后三层都是在回答「上下文里该放什么、什么时候放」——这正是第 5、6、8 三章连在一起的原因。

## 5.6.2 按顺序问五个问题

拿到一个需求，从上往下依次问，第一个回答「是」的就是它该去的地方。

```text
1. 它会改变外部状态吗？（写文件、发消息、改数据、提交代码）
   → 是：工具。它必须有明确的参数、确定的返回值、可声明的权限。

2. 它是「每一次对话都必须成立」的吗？
   → 是：系统提示。比如安全红线、输出语言、不可越过的边界。

3. 它是「这件事该怎么做」的一整套流程或标准吗？
   → 是：技能包。它需要按需加载，还需要能被版本化、被分发。

4. 它是「一堆事实」，量大且会变，但每次只需要其中一部分吗？
   → 是：检索。第 8 章处理。

5. 四个都不是：这个需求大概不该自动化。
   → 回到第 1 章 1.3 节的选型顺序，先想想它值不值得做。
```

顺序不能乱。最容易搞错的是把第 1 问和第 3 问调换——先想「这是不是一套方法」，就会把带副作用的动作写进技能包。**只要它改变状态，它就必须是工具，哪怕它只占整个流程的一小步。**

## 5.6.3 例子：每周五发周报

本章开头那个例子，在这里正好拆一遍。这句话里有四件性质完全不同的事：

| 需求里的部分 | 去哪层 | 判断过程 |
| --- | --- | --- |
| 把本周的提交记录、合并的 PR、关闭的工单拉出来 | **工具** | 它要去读别的系统，是动作。只读、不改状态，但仍然是工具——因为它是一个动作，不是一套做法 |
| 团队规范的周报口径：什么算「进展」、什么算「风险」、给谁看写多细 | **技能包** | 这是方法，需要判断（一条改动算进展还是风险），而且换团队就换一套 |
| 「给客户看的那份发出前必须我确认」 | **系统提示** | 红线。它必须在每一次对话里都成立，不能因为「这次没触发周报技能包」就失效 |
| 成员名单、项目代号对照、当前迭代编号 | **检索** | 事实，会变，量大，每次只用到几条 |

接着把周报这件事本身做完，它还需要两样东西：**一个「发出去」的工具**（改变状态，不可撤销），和 **技能包里的正文步骤**（先拉数据、再分类、再按模板写、最后等确认）。

于是「每周五发周报」这个需求，落成了：2 个工具 + 1 个技能包 + 1 条系统提示红线 + 1 份检索语料。**四个层都用了，没有一个层能独自承担它。**

这就是这张决策表的实际用法：**它不是让你给需求选一个层，而是让你把一个需求拆到四个层里去。**

## 5.6.4 两种放错地方的情况

**错位一：把该做成工具的东西写成技能包。**

症状是「模型每次都现场做一遍」。

比如「查数据库」。如果你写一个技能包，正文是「用 Python 连 PostgreSQL，执行 SQL，把结果整理成表格」，那么模型每一轮都会自己写一段连接代码——连接串从哪来、字段名对不对、结果怎么分页，全都在赌。**十次里有三次会错，而且每次错的地方还不一样。**

正确做法是把「执行一条只读 SQL」做成工具（或技能包里的脚本），技能包正文只写「查哪些表、口径怎么算、结果怎么给用户看」。**确定的部分沉到工具，判断的部分留在技能包。**

**错位二：把该做成技能包的东西写成工具。**

症状是「工具列表膨胀，但什么都没变好」。

比如把「代码评审标准」做成一个 `get_review_rules()` 工具。看起来挺正规——模型调用它，返回一篇标准。但问题在于：**返回的那篇标准还是会进上下文，一点都没省。** 而且你丢了技能包真正的价值——「什么时候该用哪条标准」「发现违规时怎么办」这些判断，本来该写在正文里，现在没有了。

判据很清楚：**工具返回的是「数据」，技能包提供的是「做法」。** 一个返回固定文本的工具，通常只是把一份文档伪装成了接口。

## 5.6.5 两边冲突时听谁的

四层之间会打架。两种情形必须提前说清。

**系统提示压过技能包。** 技能包可以写「提交前给用户看一眼命令」，但**不能写「这种情况可以跳过确认」**。红线在系统提示里，知识层无权改写它。这条的工程含义是：**技能包的加载不能覆盖系统提示**——两者的顺序是先系统提示、后技能内容，而不是反过来。

**工具的执行结果压过技能包的预期。** 技能包写「用 `git log` 拿最近的提交」，但工具返回了「不是 git 仓库」。这时候以工具的结果为准，技能包里的流程应当被中止或改道，而不是硬走。**观察结果永远比计划新。**

这两条背后是同一个原则，第 15 章会把它讲完：

> **知识层永远排在执行层和权限层之后。技能包可以建议怎么做，但不能决定能做什么。**

| 优先级 | 层 | 冲突时的行为 |
| --- | --- | --- |
| 最高 | 权限与审批（第 4、15 章） | 决定「能不能做」，其余各层无权覆盖 |
| 高 | 系统提示红线 | 决定「必须遵守什么」，技能包不可改写 |
| 中 | 工具返回的真实结果 | 决定「实际发生了什么」，优先于任何计划 |
| 低 | 技能包正文 | 提供「怎么做的建议」 |

现在你有了四层怎么分的判据，也有了一个具体需求怎么拆的演练。剩下两个问题：**怎么知道一个技能包真的能用**，以及 **怎么安全地装别人的技能包**。这两件事分别是 5.7 和 5.8 的主题。
