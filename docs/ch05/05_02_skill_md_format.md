# 5.2 SKILL.md：十分钟掌握格式

## 5.2.1 一个目录就是一个技能包

技能包就是一个普通目录。约定只有一条：**根目录下必须有一个 `SKILL.md`**，文件名全大写。

```text
weekly-report/                ← 目录名必须与 frontmatter 里的 name 一致
├── SKILL.md                  ← 必需：元信息 + 指令
├── references/               ← 可选：按需加载的参考资料
│   └── spec.md
├── scripts/                  ← 可选：可执行脚本
└── assets/                   ← 可选：模板、图片、示例数据
```

三个可选目录的分工是这套格式里最需要理解的部分，5.5 节会展开。先记住它们的定位：

| 目录 | 放什么 | 什么时候进上下文 |
| --- | --- | --- |
| `scripts/` | 确定性的、易错的步骤，写成代码 | **永不进**。只有它的输出进上下文 |
| `references/` | 需要时才查的详细文档（完整规范、字段表、领域资料） | 正文引用到它、模型主动去读时 |
| `assets/` | 模板文件、图片、示例数据 | 被用到时 |

其余的目录随便你建——规范里明确写了「任何额外的文件或目录都允许」。这三个只是惯例，不是限制。

## 5.2.2 文件头写什么

`SKILL.md` 由两部分组成：YAML frontmatter（写在两行 `---` 之间）与 Markdown 正文。

```markdown
---
name: weekly-report
description: 按团队口径把本周工作整理成一份周报。当用户提到周报、weekly、本周总结、整理这周做了什么时使用。
license: MIT
metadata:
  author: harnex-book
  version: "1.0"
---

# 周报助手

（正文……）
```

字段一共六个，按规范：

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| `name` | **是** | 1–64 字符。只能用小写字母、数字、连字符；不能以连字符开头或结尾，不能有连续两个连字符，不能含保留字 `anthropic` / `claude`，不能含 XML 标签，**且必须与父目录名一致** |
| `description` | **是** | 1–1024 字符，非空。要说清「做什么」和「什么时候用」 |
| `license` | 否 | 许可证名，或指向包内许可证文件的路径 |
| `compatibility` | 否 | 1–500 字符。环境要求：目标产品、需要的系统命令、网络访问等 |
| `metadata` | 否 | 任意键值对，常用于 `author`、`version` |
| `allowed-tools` | 否 | 空格分隔的工具列表，声明本技能包预先获准使用的工具。**实验性字段** |

关于 `name` 的约束，最常踩的坑是这几条：

```text
name: PDF-Processing      ✗ 不允许大写
name: -pdf                ✗ 不能以连字符开头
name: pdf--processing     ✗ 不能有连续连字符
name: pdf_processing      ✗ 不能有下划线
name: pdf-processing      ✓
```

目录名和 `name` 必须一致，这条不是洁癖。加载器的扫描逻辑是 `*/SKILL.md`——**路径即身份**，两者不一致时，模型无法确定该信任哪一个。

`description` 的 1024 字符上限看起来很宽，但真正重要的是另一件事：**它是唯一常驻模型视野的文本**。5.3 节会把这条推到底。

## 5.2.3 一个完整例子

现在把引言里那个场景做成真的技能包。`skills/weekly-report/SKILL.md`：

```markdown
---
name: weekly-report
description: 按团队口径把本周工作整理成一份周报。当用户提到周报、weekly、本周总结、整理这周做了什么时使用。
license: MIT
metadata:
  author: harnex-book
  version: "1.0"
---

# 周报助手

## 步骤

1. 先调 `now` 确认今天的日期，算出本周的范围；再 `fs_read` 列出 `notes/` 目录，把本周的日志读一遍。不要凭对话内容猜本周做了什么。
2. 按下面的口径表，把每条记录分到「进展 / 风险 / 待办」。
3. 按 `assets/template.md` 的结构写，保存到 `reports/` 目录，文件名用 ISO 周号，如 `2026-W44.md`。
4. 把写好的周报给用户看一眼，得到确认后告诉用户文件路径。

## 口径表

| 分类 | 什么时候用 |
| --- | --- |
| 进展 | 本周完成、且能指出依据（日志、文件、验收记录）的事 |
| 风险 | 会拖慢自己或影响别人的事，每条必须带对策 |
| 待办 | 下周打算做的，写清目标而不是动词 |

## 边界情况

- 日志里没有的事，不要凭印象补。宁可空着，标「待确认」。
- 上周遗留的风险：写最新状态，不要原样复制上周的原话。
- 拿不准该不该写进周报的事故：先问用户，不要自作主张。
- 同一件事涉及多个项目：写在主要项目下，不要重复出现。
- 不要修改日志原文来「凑」进展。日志是记录，不是素材。

完整的口径定义与措辞规范见 `references/spec.md`。
```

二十六行的正文，加上八行的 frontmatter。`weekly-report` 到这里就写完了——没有代码、没有 schema、没有配置文件。

三处设计值得单独点出来：

- **步骤写的是「先做什么、再做什么」**，而不是「你应该是一个严谨的周报写手」。模型不需要人设，它需要流程。第 2 章讲 prompt 五零件时那条结论在这里同样成立：**任务和约束比语气重要。**
- **边界情况单独成节。** 这一节是技能包性价比最高的部分。复制上周的原话、凭印象补进展、自作主张写事故——这些是真实世界里的坑，写进去一次，之后每一次调用都躲开。
- **末尾留了一个引用。** 完整口径有几千字，但它只在「需要确认某条口径的确切措辞」时才有用。所以它进 `references/spec.md`，正文只在最后一行提一下路径。

## 5.2.4 选填项什么时候写

**`license`** 只有你要把技能包发给别人才需要。内部自用的包可以不写——但如果你准备开源，现在就写，以后补很麻烦。

**`compatibility`** 在技能包对宿主机有要求时写。比如：

```yaml
compatibility: 需要 git 与 bash；版本号同时写在 pyproject.toml 与 CHANGELOG.md
```

它是给「安装前的人」看的，不是给模型看的。所以它应该写**环境缺什么会坏**，而不是罗列所有依赖。

**`metadata`** 放你自己的键。最常见的是 `version`——技能包会迭代，改完一版要能标出来，5.7 节讲版本回归时会用到。

**`allowed-tools`** 只在技能包会自己跑命令时才有意义。它是一份**建议清单**，不是授权——5.5 节先讲怎么用它，5.8 节再讲它在安全上的分量。

## 5.2.5 为什么跟开放标准

`SKILL.md` 是 Anthropic 起头、但已经交出去的格式。2025 年 10 月 16 日随 Claude Skills 发布，同年 12 月作为开放标准公开；不到一年，接入它的客户端就超过了 70 个，横跨 Claude Code、ChatGPT、Codex CLI、Cursor、Gemini CLI、VS Code、GitHub Copilot。

这意味着三件具体的事：

1. **你现在写的 `weekly-report`，在别的 harness 里能直接用。** 不用改格式、不用写适配层。
2. **别人写好的技能包，你也能装。** 官方仓库（anthropics/skills）里有文档处理、数据分析等一批现成的包，社区还有更多——5.8 节会讲怎么安全地装。
3. **格式稳定。** 一个连字段名都被规范钉死的格式，比某家产品的私有配置格式更值得投入时间。

顺带说清楚一件事：规范是开放的，**但各家实现有私有扩展**。比如 Claude Code 额外支持 `disable-model-invocation`（禁止自动触发，只允许用户用 `/` 手动调用）、`user-invocable`、`argument-hint` 这些字段，Codex 则用另一套配置文件控制自动触发。这些字段不在标准里，换产品就不生效——**核心的两个字段到哪里都一样，扩展字段只属于某一家。** 写技能包时，这个区分决定了你要不要用它们。
