# 10.6 量化：成功率是可测量的

## 10.6.1 感觉稳了不算数

前五节做完，你会有一个很强的感受：**它好像靠谱了。**

这个感受不可信。原因在 10.1：它是个非确定性系统，同一句话问两次，结果可能不一样。而你对它的印象，只来自最近那几次。最近三次都成功，你会觉得「稳了」。可真实的成功率可能是 70%，只是你恰好没赶上那 30%。

打个比方，这就像「自我感觉良好」。真要知道身体怎么样，得去验个血，看化验单上的数。本章最后要做的事就是这个：把「稳了」变成一个数。做法是**固定一批任务，重复跑很多次，数成功和失败。**

要算出一个有意义的数，需要三样东西：

**一、一个固定的任务集。** 任务集就是拿来反复测的一批任务。它必须固定住，因为变化的任务集测不出变化——每次都比不同的东西，数字没有可比性。

**二、每个任务重复多轮。** 跑一次成功，不构成任何证据。**重复是为了把非确定性平均掉**：一个任务跑五次，你才能看到它「五次里错一次」这种真实面貌。

**三、每类失败分开数。** 只说「成功率 87%」没有行动价值。加上分布就完全不同——「87% 成功，13% 里 9 个百分点是超时、4 个百分点是 schema 不合规」：前者回去看 10.3，后者回去看 10.2。

## 10.6.2 二十个任务从哪来

骨架的里程碑是「固定 20 个任务的测试集，重复 5 轮」。这 20 个不是凭空编的：

> **从你真实用过、并且它翻过车的任务里来。**

这和第 8 章那个做法是同一个——**题库来自你最近几次它答错的地方。** 自己编的任务会不自觉地偏向「它擅长的形状」。而你真实踩过的坑，恰恰落在分布的尾巴上：不常出现，但一出现就翻车。

选任务时记住两条：

- **每个任务都要有一条硬判据。** 判据就是判断标准，也是这一节能成立的前提。这里要的不是「写得好不好」，而是「文件存在吗、测试过吗、退出码是 0 吗」。退出码就是程序结束时返回的号码，0 表示成功。
- **覆盖本章的几种坏法。** 有意放进会触发 schema 校验的、会超时的、会中途失败的、会崩在半路的任务。测试集的价值不在于好看的成功率，在于**它能撞出哪些坏法**。

## 10.6.3 用外部结果判断成败

这是本书反复出现的一条优势，到这里再收一次。

判断「这次成功了吗」有两种方式：

- **软信号**：让模型自己说「做完了」，或者让另一个模型打一个 1–5 分。
- **硬信号**：有没有一个外部事实可以判定。

软信号的问题是 9.3 说过的——**它也是模型在判断，也可能判错**，而且没有校准。它给的分和真实好坏之间，没有一把公认的尺子可以对照。硬信号没有这个问题。

回到体检那个比方：一个是病人自己说「我好多了」，一个是化验单上的读数。后者不听谁的意见，只看仪器测出什么。而 Harness 这类任务的天然优势是：**绝大多数目标的完成状态都有硬信号。**

| 任务 | 硬判据 |
| --- | --- |
| 删掉未使用的 import | `pytest -q` 退出码 0，且 `import` 行数减少 |
| 重命名一个文件并改引用 | 旧路径不存在、新路径存在、测试退出码 0 |
| 把这批数据分成三类 | 条数对得上，且每条都在 `enum` 内 |
| 修一个 failing test | 该用例退出码从 1 变 0 |

表里两个词顺手解释掉。`enum` 是「允许的那几个值」，`failing test` 是「跑不过的那条测试」。

一个任务配一个判定函数，就这么简单：

```python
# harnex/reliability/bench.py —— 每个任务一条硬判据：返回 True 就是成功，None 是判不成
import subprocess


def check_import_cleanup(cwd):
    """跑一遍测试。返回 True / False / None：None 表示这条判据没跑起来。"""
    # shell=True 才让 "pytest -q" 这一整串当成命令执行；capture_output 把输出收起来，不刷屏。
    finished = subprocess.run("pytest -q", shell=True, cwd=cwd, capture_output=True)
    # 127 = 这台机器没装 pytest；5 = 一个测试都没收集到。
    # 两种都是「判不成」，不能算任务失败，交回 None 让调用方记成 check_error。
    if finished.returncode in (5, 127):
        return None
    # 判的是退出码，不是输出文字。模型说「我做完了」不算数，这里才算。
    return finished.returncode == 0

# 用法：print(check_import_cleanup("codes/ch10/harnex_v0.8"))
# 预期输出：True（测试全过）、False（有测试没过）、None（环境里没有 pytest，判不了）
```

这段代码短得不像话，要害却全在最后一行：**成功不由模型宣布，由测试的退出码宣布。** 它有三个返回值：做成了、没做成、判不了。第三种单独记：**判据坏了不算失败**。这也是为什么本章的评测比「写一篇好文章」那类任务的评测更早成熟。**harness 的反馈来自它运行的环境，而运行环境天然会给出可判定的结果。** 第 13 章会把这一条发展成完整的评测体系。

## 10.6.4 跑一百次

```python
# harnex/reliability/bench.py（续）—— 固定任务集 × N 轮：统计成功率与失败类型分布
def run_suite(tasks, run_once, rounds=5):
    """tasks 是 [{"name":..., "goal":..., "check":...}] 的清单。
    run_once(goal) 返回 {"ok": True/False/None, "kind": 失败类型}。"""
    total = 0
    passed = 0
    kinds = {}

    for round_no in range(rounds):
        for task in tasks:
            total = total + 1
            outcome = run_once(task["goal"])

            ok = outcome["ok"]
            if ok is None:
                # 判据自己没跑起来（比如脚本崩了）。这不是任务失败，单独记一笔。
                kinds["check_error"] = kinds.get("check_error", 0) + 1
                continue
            if ok:
                passed = passed + 1
                continue

            # kinds.get(k, 0) 的意思是「没有这个 key 就先当 0」，省掉一次 if。
            kind = outcome.get("kind")
            if not kind:
                kind = "unknown"
            kinds[kind] = kinds.get(kind, 0) + 1

    if total > 0:
        rate = round(passed / total, 3)
    else:
        rate = 0.0
    return {"total": total, "passed": passed, "rate": rate, "failures": kinds}


if __name__ == "__main__":
    # 一个假的跑批函数：凡是 goal 里带「崩」的，都当成超时失败。
    def fake_run_once(goal):
        if "崩" in goal:
            return {"ok": False, "kind": "timeout"}
        return {"ok": True, "kind": None}

    tasks = [
        {"name": "写报告", "goal": "写一份周报", "check": None},
        {"name": "改配置", "goal": "会崩的那一件", "check": None},
    ]
    print(run_suite(tasks, fake_run_once, rounds=2))

# 预期输出（一行）：
# {'total': 4, 'passed': 2, 'rate': 0.5, 'failures': {'timeout': 2}}
```

20 个任务 × 5 轮 = 100 次。跑完你会拿到两行东西：

```text
成功率：92/100 = 92.0%
失败分布：timeout 4 / schema_violation 2 / precondition_failed 2
```

**这两行才是本章「有用」的证据。** 它们的价值不在绝对值，在**对比**。把本章的改动一条条加进来，每加一条重跑一次，看那条曲线往哪走。

## 10.6.5 次数少时数字会晃

100 次样本能支撑什么结论、不能支撑什么结论，要说明白。

成功率 92% 时，如果你再跑 100 次，结果大概仍在 92% 附近，但不会正好又是 92。按二项分布估算，100 次样本下 92% 附近的 95% 置信区间大约是 ±5 个百分点。

「二项分布」这个词可以先跳过，看它算出来的意思就够了：一共试 100 次，每一次不是成就是败，光是这一点，就会让「92 次成功」这个结果自带波动。换一批 100 次，可能 88 次，也可能 95 次。**95% 置信区间 ±5 个百分点**说的是：真实水平大概率落在 87% 到 97% 之间。这个「大概率」，是九成半。这有两个直接用途：

- **别追小数点。** 「92.0% 比 91.5% 好」这个结论，在 100 次样本里不成立。那 0.5 个百分点很可能只是抽样噪声，也就是换一批样本就会变的那点波动。
- **看得到方向就够了。** 本章的改动如果能把它从 70% 推到 88%，这个差距远远超出噪声，值得信；如果是从 91% 到 92%，那还看不出来，需要更多样本，或者干脆接受「这点差别不重要」。

还有一条更根本的限制：**测试集是你自己选的。** 它测的是「在你选的这 20 个任务上的成功率」，不是「它可靠了」。换 20 个任务，数字会变。还是体检那个比方：只查了五项，五项正常不等于全身没病。这一点第 13 章会展开。**评测集的代表性，也就是这批任务能不能代表你真实的活儿，永远比分母的大小更值得警惕。**

## 本章到此：v0.8

前九章每加一样能力，版本号往前走一格。这一章不一样：**它没有给 Harnex 加任何新功能。**

它给的是一圈护栏：输出被 schema 约束、失败被分类处理、超时和重试有上限、状态能从检查点恢复、失败能说清、成功率能测量。能力清单没变，**但同一件任务的成功率变了——这才是 L2 的开始。**

L2 是这本书阶段三的达标等级，第 13 章才正式达标；这里说的是「开始」。阶段三还有五章，走的都是这个方向：可观测与成本、评测、沙箱与审批、团队化。它们和本章的关系是——**本章让失败「可处理」，后面几章让失败「可看见、可衡量、可预防」。**

下一章先解决「看得见」：你现在只知道它失败了，还不知道**它是怎么一步步走到失败的**。
