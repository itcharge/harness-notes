# 小结与验收

## 本章小结

1. **同一句话问三遍，可能给你三个不一样的答案。** 同一个分类任务跑三次，你可能碰上本章的三种坏法：
   - 程序崩了
   - 字段对不上
   - 看着对其实错
2. **这不是哪个设置没调好，是你要长期相处的一种条件。** 温度（控制随机程度的旋钮）调到 0，也只是让它更稳，不会让两次一模一样。计算机存的小数是近似值，浮点加法不满足结合律（先加谁后加谁，结果会差一丁点）；显卡也不顺着一个个加。它把一堆数分成几份同时加。分几份、按什么顺序合，每次都可能不同。
3. **目标换了：不再要求它不犯错，改成要求它错了能被发现、能被恢复。** 前九章一直在往车上加装备，这一章装的是刹车。**装备清单没变，翻车的次数变了。**
4. **失败分三类：可重试、可修正、不可恢复。** 怎么分？不看错误长什么样，只看**再试一次有没有可能变好**。
5. **三类各由谁来判，也不一样。** 可重试由环境判：退出码、状态码、有没有超时。退出码就是程序结束时返回的号码，0 表示成功。可修正由 schema（写清字段和格式的说明）和校验器判。不可恢复由外部事实判。**没有一类是模型自己说行不行。**
6. **认不出来的失败，按最坏情况处理。** 分类器这时返回 `abort`（中止）。认不出来，多半说明你还没把这类失败想清楚。
7. **约束解码和校验器各管一段，两个都不能省。** 约束解码是生成时就不许写出不合格式的内容，能省掉一大半格式失败。但它要靠服务端（真正跑模型的那台机器）支持，而且**只管结构合不合规，不管内容对不对**。
8. **写 schema 有三条原则。** 字段少而必要；能用枚举（允许的那几个值）就不用自由文本；必填还是可空，写清楚。再配一条习惯：`additionalProperties: false`。不写它，模型会自作主张，加上你没要的字段。
9. **用枚举，等于把判断标准从模型的措辞搬进了代码。** 顺带还多一个指标：落到「其他」的有多少。
10. **校验的结果是一份数据，不是一次报错中断。** `validate()` 返回一张错误列表。这张表既是「过没过」的判定，也是下一轮要喂回模型的内容。
11. **让它重试时，喂回去的必须是报错原文。** 只说「格式不对，请重试」，模型学不到任何东西，下一轮大概率再错一次。
12. **防御性解析只补最常见的几种毛病。** 补得越多，改错的机会越多。**一个悄悄改错的字段，比一次当场解析失败更麻烦**：后者你立刻知道，前者会一路流进下游。
13. **三条修法各要付代价。** 重新请求：可能再犯一次。局部修补：可能改出新错。降级加标记（放弃格式、收下散文，并标明这条不合规）：下游得有人来看。重试次数用完走第三条，但**必须留痕**。
14. **超时（给一个动作定最晚完成时间）分四层，里层必须比外层短。** 写反了会怎样？外层的时间一到就把里层掐了，里层的信息全丢。
15. **只重试幂等的动作。** 幂等的意思是：做一次和做十次，结果一样。`POST`（提交、新建）不是幂等的。要么不重试，要么给它一个幂等键。幂等键就是一个字符串，专门标识「这一件具体的事」。不然「重试」就成了「重复执行」。
16. **只会按倍数等待的退避，是惊群的帮手。** 惊群指一群客户端同时醒来重试，把尖峰又顶回去。要加抖动（在等待时间里掺一点随机），才能把请求摊开。**退避管「别太频繁」，抖动管「别同时」。**
17. **重试 2 次，通常比 5 次强。** 等待只是把活往后挪，活还在。真正把活变少的，是换一条路走。
18. **熔断管「这一阵子」，重试管「这一次」。** 熔断（连着失败就先停手）断开时一个请求都不发，钱就省在这儿。但断开必须上报，不能悄悄停着。
19. **检查点写在动手之前，不写在之后。** 副作用就是真正改了外面世界的动作：写文件、发请求、提交订单。日志里有一条「我准备做」，却找不到配对的「做完了」。这条悬空记录就在告诉你：崩溃发生在这一步中间。
20. **幂等键标识「这一件具体的事」，不是「这一类事」。** 拿 `uuid4()`（每次生成都不一样的随机串）当键，等于没有键。
21. **重放之所以安全，靠的是短路**：查账本发现做过，就直接返回上次的结果，不做第二次。
22. **恢复要用 `resume()`，不是从头重放（replay）。** 做法是读清单的投影（从流水账里推出来的当前状态）和账本，拿到「下一步做什么」。**不是回放「之前发生过什么」**，那样会把自己做过的副作用再做一遍。
23. **检查点只给「重做一次要付代价」的动作。** 读文件、查数据这类读操作不用设：它们没有副作用，重做一遍结果也一样。
24. **给模型看的错误，和给人看的失败报告，是两份东西。** 前者要短，要直接指向下一步动作。后者要能重建现场：哪一步、期望什么、实际什么、建议怎么办。
25. **好报告只讲事实，不替人下判断。** 人要拿主意，需要的是范围，不是结论。
26. **报告有三个读者：现在的你、三天后的你、接手的人。** 后两个最容易被忘掉。
27. **成功率是能测出来的**。跑一次成功，不构成证据。前提是三件事：
    - 任务固定
    - 多跑几轮
    - 失败分类数
28. **题目要从你真实踩过的坑里出。** 硬判据就是程序能直接判真假的标准。这正是它在 Harness 上管用的原因：**它给出的反馈来自真实使用，不来自谁的印象。**

## 动手任务

1. **亲手造出本章的三种坏法。** 同一个分类任务跑三遍，刻意把温度调高，让差异更容易冒头。三次返回都原样存下来，逐条标它属于可重试、可修正、还是不可恢复。**三遍都成功怎么办？温度再调高，字段加到 15 个，重来一遍。**

2. **给你的 schema 做一次「减字段」。** 挑一个正在用的 schema，字段砍到「下游真的会读」的那几个。**记下改之前和改之后的首次成功率**（第一次就跑通的比例）。这个对比通常会让你对「字段多，成本高」有切身体感。

3. **量一次重试的代价。** 挑一个会超时的任务，把重试次数从 5 调到 2，同一个任务跑 10 次。记两个数：**总耗时**和**成功率**。如果成功率没掉、耗时掉了一半，你就亲眼看见「重试 2 次好过 5 次」了。

4. **演示一次断点恢复。** 拿 10.4 那个改过的 5 步任务，跑到第 3 步。这一步是个写操作，做到一半时用 `kill -9` 掐掉进程。重启后跑 `resume()`，看三件事：
   - **从对的步骤接着做**
   - **前两步没被重做**
   - **清单和实际对得上**

5. **验一次幂等。** 故意把同一个 `run_effect()` 连着调两次。第二次的返回值里应该有「已执行过，直接返回上次结果」这句，而文件内容只能改过一次。**再把 key 换成 `uuid4()`，看它怎么坏**——你会得到两份改动。

6. **给一次真实的失败写报告。** 翻出你最近一次真正卡住的任务，按 10.5 的七个字段填一遍。**如果「实际什么」那一栏你只能写出一句话，说明当时没留证据。** 回头去你的 harness 里，把这条证据的采集补上。

7. **跑一次 100 次。** 不用等完整测试集建好，5 个任务 × 20 轮，凑够 100 次也算。跑完记下成功率和失败分布，**然后把本章任意一条护栏拆掉，再跑一遍**。两条曲线的差，就是这一章在你手上的实际价值。

## 阶段三开场：L2 的第一步

本章是阶段三的第一章。前三个阶段各管什么，一张表就能对上：

| 阶段 | 目标 | 判断标准 |
| --- | --- | --- |
| 一（1–3 章） | 跑起来 | 它能回一句话 |
| 二（4–9 章） | 能接活 | 你有一件真实的事，会主动丢给它做 |
| 三（10–14 章） | 可靠可观测 | 同一批任务跑 100 次，成功率可量化、失败可归因 |

L2 不是某个功能，是一种做事方式的转变。**从「我觉得它还行」，变成「我有一组数说明它还行」。**

本章只做出了这组数的最小版本：一个 20 任务的测试集，一份失败分布。把它做成体系，是第 13 章的活；让它能被看见、成本可控，是第 12 章的活。**但地基在这一章就打好了：失败不分类，就找不到原因；没有硬判据，成功率就不可信。**

## 本章的常见误区

- **把温度调到 0 当成问题解决了**：它只是让波动少一点，不保证两次一致。可靠性靠机制，不靠参数。
- **只做校验，不写重试提示**：校验器发现了错，错误却扔了。这等于把「可修正」降成「不可恢复」。
- **提示里只说「格式不对，请重试」**：模型学不到东西，下一轮大概率重犯。
- **schema 写了十几个字段，还全设必填**：每多一个字段，就多一次格式翻车的机会。
- **防御性解析写成万能修复机**：改错的字段悄悄流进下游，比一次解析失败更难发现。
- **降级了却不留痕**：下游会把一条散装结果当成合规数据，制造出「看着对其实错」。
- **只给工具设超时**：一次「重试 × 工具超时」的组合，够烧掉一个晚上。
- **里层超时比外层长**：里层那份配置从来没生效过，你还以为它有保护。
- **不加分辨地重试所有失败**：对「文件不存在」重试五次，是花钱确认一件早就知道的事。
- **重试非幂等的动作**：写文件失败后直接重试，写进去五份——骨架里那个事故就是这么来的。
- **只重试，不换招**：同样的参数试五次全失败，问题在方法选错，不在参数。
- **熔断断开却不出声**：人以为任务慢，其实它根本没在干活。
- **检查点只在任务开始时存一次**：恢复等于重跑，这一节白做。
- **检查点写在动作之后**：进程在动作完成和落盘之间崩掉，这条记录就丢了。
- **幂等键用随机数**：每次重放都是新 key，账本完全认不出来。
- **恢复时从头重放**：把自己做过的副作用再做一遍——重放不是恢复。
- **把校验失败当异常抛出去**：整个会话终止，模型连一次改的机会都没有。
- **给模型和给人共用一份错误**：两边都读不到自己要的东西。
- **报告里替人下结论**：它掌握的信息比你少，却替你做了决定。
- **跑一次成功就宣布稳定**：只跑一次的结论不成立。

## 自测题

1. 三类失败（可重试 / 可修正 / 不可恢复）各自怎么处理？为什么分类不看错误文本？
2. 三类各由谁判？为什么「让模型自己说行不行」在三类里都站不住？
3. 温度设成 0，为什么还是不能保证两次推理完全一致？说出至少两个实现层面的原因。
4. 约束解码和校验器各守哪一段？有了约束解码，为什么还要留着校验器？
5. schema 的三条原则是什么？`additionalProperties: false` 挡掉的是哪类问题？
6. 校验器为什么返回错误列表，而不是抛异常？带路径的错误（`$.items[37].category`）比一句「校验失败」好在哪？
7. 三种修复策略各适合什么样的失败？「降级」为什么必须留痕？
8. 分层超时为什么必须「里层比外层短」？举一个顺序写反之后出事的例子。
9. 为什么「重试 2 次」通常好过「重试 5 次」？这和 9.3 的重试预算说的是同一件事吗？
10. 只会按倍数等待的退避，在什么场景下会变成故障的一部分？抖动解决的是哪个问题？
11. 熔断器的三态分别是什么？为什么 open 状态下「不发请求」才是它省钱的地方？
12. 幂等为什么是断点恢复的前提？举一个不幂等的操作，再给它设计一个幂等键。
13. 检查点为什么写在有副作用的动作之前？「有 begin 没 done」说明了什么？
14. 恢复为什么用 `resume()` 而不是从头重放？这两个动作在代码上差在哪一行？
15. 哪些动作该设检查点、哪些不该？那条判据是什么？
16. 模型能读的错误，和人能读的失败报告，差别在哪？为什么必须分成两份？
17. 一份失败报告有哪几个字段？「建议」那一栏为什么要克制？
18. 成功率怎么测才有意义？跑一次成功为什么不算证据？
19. 100 次样本下，「92.0% 比 91.5% 好」为什么站不住？
20. 用你自己的话说：本章为什么可以给 Harnex 编 v0.8，还不算「加了新功能」？

## 本章术语速查（中英对照）

| 中文 | 英文 | 一句话解释 |
| --- | --- | --- |
| 非确定性 | Non-determinism | 同一个问题问两次，答案可能不一样，这是推理这一层带来的性质 |
| 结构化输出 | Structured Output | 让模型照着你给的格式写，而不是想怎么写就怎么写 |
| 约束解码 | Constrained Decoding | 生成时就按 schema 卡住能写什么，结构上写不出不合规的内容 |
| JSON 模式 | JSON Mode | 只保证输出是合法 JSON，不保证符合你那份 schema |
| 校验器 | Validator | 写完再查一遍，返回错误列表而不是抛异常 |
| 防御性解析 | Defensive Parsing | 容忍代码块包裹、尾随逗号、全角符号这类常见畸形 |
| 局部修补 | Repair | 把校验错误喂回模型，只让它改不合规的那几处 |
| 降级 | Fallback | 放弃结构、收下散文，并**标记**这条结果不合规 |
| 分层超时 | Layered Timeout | 单次调用 / 单次工具 / 子任务 / 整个任务四层，里层短于外层 |
| 指数退避 | Exponential Backoff | 失败后等一会儿再试，等待时间按倍数变长 |
| 抖动 | Jitter | 在等待时间里掺随机，避免多个客户端同时重试 |
| 惊群 | Thundering Herd | 一大批客户端同时醒来重试，把尖峰又顶回去 |
| 熔断器 | Circuit Breaker | 连着失败就断开、冷一会儿、放一个请求探路的三态开关 |
| 幂等键 | Idempotency Key | 标识「一件具体的事」的唯一字符串，用来安全地重试 |
| 检查点 | Checkpoint | 动手之前先落盘的一条进度记录 |
| 副作用账本 | Effect Ledger | 记下每个副作用的 begin / done，用来判断它做过没有 |
| 断点恢复 | Resume | 从检查点回到「下一步做什么」，而不是回放历史 |
| 重放 | Replay | 从头重跑一遍事件流；没做幂等就会产生重复副作用 |
| 失败报告 | Failure Report | 给人看的失败说明，含轨迹路径与失败类型 |
| 硬信号 | Hard Signal | 由外部事实给出的可判定结果，比如退出码、文件在不在 |
| 软信号 | Soft Signal | 由模型自评或打分给出的判断，可能判错，也没有刻度 |
| 成功率 | Success Rate | 任务固定、跑够轮数之后，通过次数占多少 |

## 延伸阅读

- **OpenAI《Introducing Structured Outputs in the API》**——10.2 那组数字的出处：`strict: true`、复杂 schema 评测的 100% 对比，以及 JSON mode 与 Structured Outputs 的区别
- **Marc Brooker《Exponential Backoff And Jitter》**（AWS Architecture Blog，2015）——退避与抖动的原始模拟；他的后续文章《What is Backoff For?》讲了那句「退避只是把工作往后挪」
- **Stripe 的幂等键文档**——`Idempotency-Key` 头、UUID、24 小时窗口；10.4 那个账本就是这套思路的自建版本
- **本书第 6 章（会话日志）**——检查点和账本都建在它的两条不变式上；不变式二在这里第一次用来做「恢复」，而不是「发消息」
- **本书第 12 章（可观测性与成本）**——本章解决「可处理」，它接着解决「可看见」：轨迹、token 看板、链路耗时预算
