# 10.4 状态持久化与断点恢复

## 10.4.1 进程中途停了

第 9 章末尾留下了一个具体的问题。

要看懂它，先交代两个词。**进程** 是程序跑起来以后，活在内存里的那一份。**内存** 是它干活时随手用的工作台，一崩、一断电，台面就全空了。磁盘不一样，写进去的东西一直躺在那儿。

你睡前丢给它一个 5 步任务。它跑到第 3 步，网络抖了一下，进程崩了。第 6 章的会话日志还在。磁盘上那份 JSONL（一行一条记录的日志文件）完好无损。里面有用户的指令，有 20 轮工具结果，有那张清单。

**但你打开它，接着做不了。**

问题不在「历史没了」。真正的缺口是：**「进度」和「已完成的事」不在日志里。**

- **进度不在。** 清单确实写进了日志（9.2 的 `todo_update`）。但「第 3 步已经做到一半」这件事，只存在崩溃前那块工作台上。
- **副作用不在账上。** 「副作用」是改动了外面世界的事：写了文件、发了请求、提交了订单。第 1、2 步改过的文件是真的改了。日志里记的是「调用了 `apply_patch` 并返回成功」。它没有一张清单，回答不了**「哪些副作用已经落到世界上」**。
- **重放是危险的。** 最直觉的恢复方式是「把日志从头按顺序再执行一遍」，这个动作叫重放。但第 1 步那次文件改写会 **再执行一次**。如果它是「往配置里追加一行」，你就得到了两行。

所以断点恢复要补的，不是「更完整的日志」。它要补的是**日志里缺的两类事件：检查点，和副作用账本。** 检查点是一句「我准备动手做这件事」；账本记的是每件事有没有开头、有没有收尾。

## 10.4.2 动手前先记一笔

先解决第一个。检查点的规矩和直觉相反：

> **检查点要写在有副作用的动作之前，不是之后。**

原因还是崩溃的时机。如果检查点写在动作之后呢？进程可能在「动作完成」和「检查点落盘」之间崩掉。这条记录就丢了。恢复时你不知道这一步做过没有，只能重做，于是又回到重复副作用的问题上。

写在之前，意思就清楚了。日志里有「我准备做 X」，却没有配对的「X 做完了」。这说明崩溃就发生在 X 中间。**这一步的状态是「不确定」**，恢复时要按幂等的方式重做或核对。（幂等：同一件事做一次和做十次，结果一样。）

这道题前面出现过，只是形式不同。第 6 章讲 `append()` 时那条规矩是「**先落磁盘，再回内存**」。理由一模一样：**在你动手之前，先把意图写下来。**

## 10.4.3 每个改动单独记账

第二个问题更实际：怎么知道某个副作用做过没有。

答案是给每个有副作用的动作一个 **幂等键**，也就是一个字符串，专门标识「这一件具体的事」。注意，不是「这一类事」。有了键，就能落一本账：

```python
# harnex/reliability/checkpoint.py —— 副作用账本：动手前记 begin，成功后记 done
# 这里的 log 就是第 6 章的 SessionLog：append() 往里加一行，events() 读回全部。
class Ledger:
    """副作用账本。key 标识一件具体的事，不是一类事。"""

    def __init__(self, log):
        self.log = log

    def done(self, key):
        """这件事已经成功做过吗？"""
        for event in self.log.events():
            if event["kind"] == "effect_done" and event["key"] == key:
                return True
        return False

    def begin(self, key, note):
        # 动手之前先落一条 begin。崩在中间时，这条没有配对的 done 就是证据。
        self.log.append("effect_begin", key=key, note=note)

    def commit(self, key, result):
        self.log.append("effect_done", key=key, result=result)

    def last(self, key):
        """取上一次成功的结果，供重复执行时直接返回。"""
        # 从后往前找：同一个 key 理论上只有一条 done，倒着找最快碰到。
        for event in reversed(self.log.events()):
            if event["kind"] == "effect_done" and event["key"] == key:
                return event["result"]
        return None

# 用法（要先有一个第 6 章的 SessionLog）：
#   ledger = Ledger(log)
#   ledger.begin("send-mail-42", note="给客户 42 发确认信")
#   ledger.commit("send-mail-42", "ok")
#   print(ledger.done("send-mail-42"))    # True
#   print(ledger.last("send-mail-42"))    # ok
```

`key` 怎么取，是这一节唯一需要动脑的地方。它必须满足一条：**同一件该做的事，每次算出来的 key 相同；两件不同的事，key 不同。**

几个例子：

| 动作 | 好的 key | 为什么 |
| --- | --- | --- |
| 给 `src/a.py` 打补丁 | `patch:src/a.py:<原文哈希>` | 同一处修改重放时 key 不变 |
| 往 `log.txt` 追加一行 | `append:log.txt:<内容哈希>` | 同一行内容不会追两次 |
| 调一次「发邮件」接口 | `mail:<收件人>:<正文哈希>` | 关键：绝不能是随机数 |

表里那几个 `<…哈希>` 是占位符。说说哈希是干什么用的：把一段内容丢进去，算出一串短字符。内容一样，算出来就一样；内容差一个字，结果就面目全非。它不存内容本身，只用来回答一件事：这两段是不是同一段。

最后一行是反面教材。`uuid4()` 是个每次调用都生成新随机串的函数。如果 key 用了它，每次重放都是新 key。账本认不出来，重复副作用照做——**随机 key 等于没有 key。**

## 10.4.4 做过的不要再做

有了账本，执行一个动作就有了固定写法：

```python
# harnex/reliability/checkpoint.py（续）—— 幂等执行：做过就返回上次结果，没做过才动手
# 参数里的 *args 是「把后面的参数原样收进来」，再原样转交给 action。
def run_effect(ledger, key, action, *args):
    """幂等地执行一个有副作用的动作。崩溃后重放，不会重复执行。"""
    cached = ledger.last(key)
    if cached is not None:
        return "（已执行过，直接返回上次结果）" + cached

    # note 只留前 200 字：日志是给人扫的，整段参数塞进去会把它淹掉。
    ledger.begin(key, note=repr(args)[:200])

    try:
        result = action(*args)
    except Exception as exc:
        # 失败就不写 done。日志里留下一条没有配对的 begin，下次一看就知道要重做。
        return f"错误：{key} 执行失败：{exc}"

    ledger.commit(key, str(result))
    return str(result)
```

三处细节：

- **`cached is not None` 走短路。** 短路的意思是提前返回，后面的代码不跑了。这就是重放安全的全部秘密——**重放时不做第二次，直接返回第一次的结果。** 返回值前面那句「已执行过」不是客套，它在日志和对话里都留下了一条可读的痕迹。
- **失败时只写 `begin`，不写 `done`。** 于是日志里会出现「有 begin 没 done」的悬空记录。恢复时的规则很简单：**悬空的 key 按没做过处理，重做一次。** 代价是它可能做了一半，所以动作本身要尽量幂等。
- **异常被兜住，转成文本。** 还是 4.2 那条铁律。

这个「先记账再执行」的写法，就是 10.3 里那个支付接口幂等键的原样搬运。区别只在那边是服务端记账，这边是我们自己记账。

## 10.4.5 从上次停下的地方继续

现在可以写恢复逻辑了。它的形状和「重放整个日志」完全不同：

```python
# harnex/reliability/checkpoint.py（续）—— 任务级恢复：回到「下一步要做什么」，不回放历史
def resume(ledger):
    """从日志里恢复出一个任务的进度视图：哪些做完了、下一步是什么。"""
    events = ledger.log.events()

    # 先收「已经落地的副作用」有哪些 key，后面拿它给每一步对账。
    done_keys = set()
    for event in events:
        if event["kind"] == "effect_done":
            done_keys.add(event["key"])

    items = project_todos(events)          # 9.2 的清单投影：最后一条 todo_update
    steps = []
    for item in items:
        effect_key = item.get("effect_key")
        recorded = False
        if effect_key in done_keys:
            recorded = True
        steps.append({
            "id": item["id"],
            "task": item["task"],
            "status": item.get("status", "todo"),
            "effect_key": effect_key,
            "recorded": recorded,
        })

    # 「下一步」就是第一条还没做完的。恢复要的是这个，不是把历史重放一遍。
    pending = []
    for step in steps:
        if step["status"] != "done":
            pending.append(step)

    next_step = None
    if pending:
        next_step = pending[0]

    return {"steps": steps, "pending": pending, "next": next_step}

# 用法（依赖第 9 章的 project_todos 和第 6 章的 SessionLog）：
#   view = resume(ledger)
#   print(view["next"])   # {'id': 3, 'task': '改配置', 'status': 'doing', ...}
```

关键差别在这两行上：

- **它读的是 `project_todos()` 和账本，不是 `project()`。** 两个函数读的是同一份日志，只是各挑各的。`project()` 产出的是「要发给模型的消息列表」；恢复需要的是「这件事走到哪了」。**同一个日志，两种取法，用在两个地方。** 这就是第 6 章不变式二那句「记录只有一份，用途随意」的具体兑现。
- **恢复的产物是「下一步做什么」，不是「之前发生过什么」。** 拿到 `pending` 之后，`run_task()` 从 `next` 开始往下跑就行。前面已完成的步骤不会被重新执行。

工程上还有一个现实问题：**恢复的时候，上下文要不要带？** 上下文是每次发给模型的那段对话内容，带得越多越贵。答案是不用全带。清单本身就是一份压缩过的进度摘要（9.2）。把它注入系统提示（开头那段设定身份和规矩的话）。再补一句「你正在从一次中断中恢复」，模型就能接着做。真正需要的历史——比如第 2 步查到的那份依赖清单——如果落在文件里，就让它重新读一次。这比塞进上下文更省。

## 10.4.6 记多密，以及恢复不了什么

最后是一道取舍题：记多密。

**太粗**（只在任务开始时存一次）：恢复等于重跑，这一节全部白做。这正是骨架里记的那个错误模式。

**太细**（每一个动作都存）：日志迅速膨胀。而且大量检查点描述的是「读到一半」「算到一半」，这些状态不值得恢复。

常用的做法是 **按「有副作用的动作」画线**。一条检查点对应一件会改变世界的事：一次文件写、一次提交、一次外部调用。读操作——读文件、跑一个只读查询、搜一段代码——不需要检查点。**它们没有副作用，重做一次的成本只是时间，而结果一定一样。**

一条判据就够了：

> **只给「重做一次会有代价」的动作设检查点。**

把第 9 章那个 5 步任务按这条判据改造一遍：列出依赖（读，不设）、找引用点（读，不设）、改 `package.json`（写，设）、跑测试（读，不设）、删零引用条目（写，设）。**五步里只有两个检查点**，而这已经足够让「任意步骤崩溃后可续跑」。

说清边界，免得把它当成万能药：

- **恢复只到检查点。** 检查点之间的动作会重做。「有副作用但无法幂等」的动作（比如「给用户发一条通知」）要另作处理。要么改成能按幂等键重做的样子，要么别放在两次检查点中间。
- **恢复不修复「错误的进度」。** 如果崩溃前模型已经走偏了，恢复只会把偏差接着跑下去。那是 9.3 自检的活。
- **恢复不是评测。** 「这次恢复了」和「它变可靠了」是两件事；后一件事要交给 10.6 的重复测量。

进程能救回来了。剩下一个问题：救不回来的时候，怎么把话说明白。
