# 10.5 失败的可解释性：两套受众

## 10.5.1 给模型看的错误

上一节把任务从崩溃里救了回来。救不回来的时候，本章还欠着一句话：**怎么把失败说清楚。**

第 4 章有一条铁律，也就是一条不许破的规矩。工具永远返回字符串（一段文字），永远不抛异常（抛异常：报错并中断）。配套的「好错误」写法是：

```text
错误：路径 'src/main.py' 不存在。
请先用 fs_read(path='src') 看看实际有哪些文件。
```

这条错误写得很好，但注意它是写给谁的。**「请先用 fs_read」是说给模型听的指令。** 它是下一步行动，不是给人看的说明。

本章前面几节做的事，都在服务这个读者：退避、熔断、修复循环，全是让 **机器** 继续往下走。但有一类情况跑不完这条流水线。重试耗尽、熔断断开、不可恢复类失败（重试也改不了结果的那一类），走到这里都停住了。这时候任务停了，**它要跟人说话。**

跟人说话得换一种写法。这一步的产物，可以想成一张 **报修单**。机器坏了，你在单子上写清四件事：哪台、什么现象、试过什么、现场在哪儿。写完贴给下一个来修的人。这一节要说的就是这件事：**给模型看的错误，和给人看的失败报告，是两份不同的东西。** 换句话说，同一件失败，有两个读者。

## 10.5.2 人和程序要的不一样

| | 模型可读错误（4.2） | 人可读失败报告（本节） |
| --- | --- | --- |
| 谁读 | 下一轮对话里的模型 | 你、三天后的你、接手的人 |
| 目标 | 让它改对、继续走 | 让人能重建现场、决定怎么办 |
| 长度 | 越短越好 | 该有的都得有 |
| 时间观 | 只有「现在」 | 「几点、多久、几次」 |
| 关键字段 | 下一步怎么做 | 哪一步、期望什么、实际什么 |

差别最大的是**时间观**。模型活在当前上下文里（这一轮发给它的那段内容）。它不需要知道「这件事发生在 19:42、重试了 3 次、花了 47 秒」。而这些恰是人最需要的东西。**因为人要判断的不是「下一步做什么」，而是「要不要相信这个结果」和「我该不该重跑」。** 报修单上不写时间，修理工就分不清是昨天坏的还是上周坏的。

把这两份说明混着用，后果是双向的。给人的报告写成「请用 fs_read 重试」，人读了等于没读。给模型的错误里塞上时间戳和重试次数呢？每一轮都在烧 token（模型按字计费，多写就多花钱）。而这些信息模型用不上。

还有一处差别在 **触发时机**，也就是什么时候生成。模型可读错误每失败一次就产生一条，一轮里可能出现三次；失败报告只在 **任务转交给人的那一刻** 生成一份。前者是流水线里的零件，后者是一个句号。

## 10.5.3 失败报告里写什么

骨架给了四个字段，也就是单子上必须有的四栏。每一栏对应人的一个具体问题。

**一、哪一步。** 不是「任务失败了」，是「停在第 3 项『把调用点从 requests 改成 httpx』」。有清单（第 9 章那份待办列表）的话，直接报清单里的编号和标题。这一句同时给了 **进度**。

**二、期望什么。** 这一步本来应该达成什么。把 9.4 那个 `done_when` 拿出来原样用。那是当初写下的一句验收条件，写明什么算这一步做完。**它当初是为了让模型能自检（自己核对做没做对），现在顺手成了给人看的验收标准。** 同一个设计，第二次派上用场。

**三、实际什么。** 真实观察到的结果，带证据。**这一条最关键，也最容易写坏**：写「测试失败」是废话；写「`pytest -q`（跑测试的命令）退出码 1（非 0 就是没通过），失败用例 `test_client.py::test_pool`，报连接泄漏」才有用。

**四、建议怎么办。** 整条流水线已经试过重试、试过换方法、试过熔断。那些尝试的结论必须在这里写下来。不写，接手的人就会把它们全部重来一遍。

## 10.5.4 一次失败，两份说明

同一张单子要出两份：一份是给程序读的字段表，一份是排好版给人读的文字。

```python
# harnex/reliability/report.py —— 失败记录：一份结构化，一份人读
import time


def classify_kind(attempts):
    """从尝试记录里定出这次失败的类别，喂给 10.6 统计。"""
    # 从后往前找：最后一次尝试最能说明这次为什么没做成。
    for attempt in reversed(attempts or []):
        # 用记录里当时就写下的 kind。那是失败发生那一刻从工具返回里认出来的，不是事后猜的。
        if attempt.get("kind"):
            return str(attempt["kind"])
    # 一条都没有就返回 unknown。它不是「没有失败」，是分类器没认出来。
    return "unknown"


def build_failure(step, expected, actual, attempts, advice, log_path):
    """构造失败记录。它同时是给人看的报告，和 10.6 统计用的样本。"""
    return {
        # 这里用 time.time() 而不用 monotonic：人要读的是「几点几分」，得是墙上时间。
        "ts": round(time.time(), 3),
        "step_id": step["id"],
        "step_task": step["task"],
        "expected": expected,
        "actual": actual,
        "attempts": attempts,             # [{"method":..., "why":..., "kind":...}, ...]
        "advice": advice,
        "kind": classify_kind(attempts),  # 10.1 的失败分类，喂给 10.6
        "log_path": log_path,             # 完整轨迹在哪，给人足够线索
    }


def render_human(failure):
    """把失败记录渲染成一段人读的文本。"""
    lines = []
    for index, attempt in enumerate(failure["attempts"]):
        lines.append(f"  {index + 1}. {attempt['method']} —— {attempt['why']}")
    if lines:
        tried = "\n".join(lines)
    else:
        tried = "  （没有重试记录）"

    return "\n".join([
        f"任务中止，停在第 {failure['step_id']} 项「{failure['step_task']}」。",
        f"期望：{failure['expected']}",
        f"实际：{failure['actual']}",
        f"失败类型：{failure['kind']}",
        f"试过什么：\n{tried}",
        f"建议：{failure['advice']}",
        f"完整轨迹：{failure['log_path']}",
    ])

# 渲染出来的样子（这里把记录手写出来，就不必真跑一遍流水线）：
# 任务中止，停在第 3 项「给客户发确认信」。
# 期望：邮件发出，返回 message-id
# 实际：SMTP 连接超时，重试 2 次都失败
# 失败类型：timeout
# 试过什么：
#   1. 直连 SMTP —— 30 秒超时
#   2. 换备用端口 —— 仍然超时
# 建议：这一项依赖的网络出口需要人工确认；后面的第 4、5 项没动
# 完整轨迹：sessions/2026-11-07.jsonl
```

`classify_kind()` 干的是另一件事：它不重新算一遍分类，只把当时记下的 `kind` 取出来。**失败的那一刻认得最准**，事后从结果倒推，多半只能推出一句「反正没成」。取不到就记 `unknown`。一堆 `unknown` 说明分类器覆盖得不够，不等于没有失败。

刚才那个 `render_human()` 负责的就是后半份。它把记录里的各个字段填进模板，拼成一段能读的文字。「渲染」这个词说的就是这件事。它的输出长这样：

```text
任务中止，停在第 3 项「把调用点从 requests 改成 httpx」。
期望：14 个文件的调用点全部改完，pytest -q 退出码 0
实际：pytest -q 退出码 1；失败用例 test_client.py::test_pool，
      报连接泄漏；另有 3 个文件用了 requests.Session 保持连接池
失败类型：precondition_failed
试过什么：
  1. 直接替换 import —— 失败：Session 没有对应写法
  2. httpx.Client() 逐个替换 —— 失败：连接泄漏，2 个用例挂
  3. 装 httpx-aiohttp 适配层 —— 失败：版本不兼容
建议：这 3 个文件的连接池用法需要人工决定是改成 Client 还是保留 requests。
      第 4、5 项没动，前后依赖关系不受影响。
完整轨迹：sessions/20261011-231842.jsonl
```

这份报告和第 9 章那份 abort（中止）说明是同一个东西的两代。9.3 那份已经有三样（做到哪了、卡在哪、试过什么）。这一节加了两样：**失败类型**和**轨迹路径**。前者让 10.6 能统计——所以它必须取自 10.1 那三份名单，临时起个名字，统计就对不上号了。后者让人能自己往下挖。轨迹就是那一轮的完整事件记录，也就是第 6 章那份日志。

## 10.5.5 内部细节别给用户

给人看的报告要 **说清事实，不要替人下判断**。看这两句建议：

```text
坏：建议回滚这次修改。
好：这 3 个文件的连接池用法需要人工决定是改成 Client 还是保留 requests。
    第 4、5 项没动，前后依赖关系不受影响。
```

第一句越界了——它替人做了决定。而它掌握的信息恰恰比人少：它不知道自己没看到的那部分代码。报修单上写一句「必须换主板」，等于让修理工别看了、照办就行。第二句把 **判断所需的事实** 摆出来：卡点是什么、影响范围到哪。**人做决定需要的是范围，不是结论。**

## 10.5.6 三个人各看哪一份

最后一条，也是这一节真正的用意：**一份失败报告不只写给你。**

- **写给现在的你**：要不要重跑、要不要改提示。
- **写给三天后的你**：「那次失败到底是哪一步」——三天后你只记得「它没做出来」。
- **写给接手的人**：他不看你的对话历史，只看这份报告和轨迹文件。

三个里，后面两个更常被忽略，也更容易被 10.6 那种「跑 100 次」的批量任务放大。**一次批量跑出 8 个失败，你会先读那 8 份报告，而不是先去看 8 条轨迹。** 报告的职责，就是在你不看轨迹的前提下，把 8 个失败分成「同一个原因」和「各不相同」。要做到这一点，报告里的字段就得是固定的、可比的、能把同一个原因的归成一堆。**这也是它同时能当统计样本的原因。**

说清楚失败之后，还剩最后一个问题：**你怎么知道这些改动真的让事情变好了？**
