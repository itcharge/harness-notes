# 10.3 超时、退避与熔断

## 10.3.1 三种超时一起设

上一节把输出关进了笼子。可笼子管得住格式，管不住外面那台机器。这一节对付另一类失败：格式全对，对面在抖。

第 7 章给 shell 工具（让模型执行命令的那个工具）加了超时。超时是干什么用的？给一个动作定一个最晚完成时间，到点就不等了，直接算失败。那时管的是**一个动作**。到了长任务，超时是分层的，层数不够就会出事：

| 层级 | 管什么 | 典型值 |
| --- | --- | --- |
| 单次模型调用 | 一次 `chat()` 挂住 | 60–120 秒 |
| 单次工具执行 | 一条命令、一次请求 | 10–300 秒 |
| 单个子任务 | 清单里的一项 | 几分钟 |
| 整个任务 | 一整段任务 | 十几分钟到几小时 |

少任何一层的后果都是具体的：

- 少了 **单次调用** 超时，一次卡住的请求会让整个循环停在那里，你在终端看到的是「不动了」。（卡住：请求发出去了，对面一直不回。）
- 少了 **工具** 超时，就是 7.1 那三类「不会结束的命令」。
- 少了 **子任务** 超时，它会在同一项里反复重试。哪怕有 9.3 的预算，那预算也是按次数算的，不是按时间。
- 少了 **任务** 超时，前几层全部通过，加起来仍然可能是半个通宵。**你睡前丢给它一个任务，早上起来发现它还在第 3 步。**

有一条容易写错的规矩：**内层超时必须比外层短。** 工具超时 300 秒、子任务超时 120 秒，工具那 300 秒就从来没生效过。子任务在 120 秒时就把它掐了。**分层超时的意义在于「谁先发现」。外层先发现，内层那部分信息就丢了。**

## 10.3.2 只有可能变好的才重试

10.1 那张分类表，在这里变成做法。

**只重试可重试类和可修正类。** 对不可恢复类的重试，是在花钱确认一件你已经知道的事——文件不存在，再试五次还是不存在。

还有一条更根本的：**只重试幂等的动作。** 幂等的意思是：同一个动作做一次和做十次，结果一样。GET（取数据）和 DELETE（删数据）按约定是幂等的，重试安全。POST（提交、新建）不是：第一次请求服务端已经处理成功，回包（对方的回应）却在路上丢了。这时你的重试，会在真实世界里再执行一次。这就是骨架里记的「重试放大事故」的机制。

真实支付接口的做法是 **幂等键**：客户端为一次操作生成一个唯一 ID，随请求发出去。服务端记住它，同一个 ID 再来，直接返回上次的结果，不再执行。这个思路在 10.4 会被搬到 Harnex 自己的工具调用上。「重放」和「重试」面对的是同一个问题。

## 10.3.3 一次比一次等得更久

知道该重试了，还有一个细节：立刻重试，还是等一会儿？

朴素的重试是立刻再来，连试三次。这在单机上无害。可一旦失败的原因是 **对面扛不住了**，它就变成了帮凶。你的三次重试，是对面收到的第四、五、六次请求。

所以重试要等，而且 **越等越久**：

```python
# harnex/reliability/retry.py —— 退避 + 抖动：等的时间要随机，不是 2 的幂
import random


def backoff(attempt, base=0.5, cap=30.0):
    """第 attempt 次失败之后，该等多少秒。返回的是一个随机数，不是一个固定值。"""
    # 这一轮的上限：0.5、1、2、4……但封顶在 cap。
    ceiling = min(cap, base * (2 ** attempt))
    # 在上限之内随便取一个：多个客户端才不会在同一秒一起醒来。
    return random.uniform(0, ceiling)


if __name__ == "__main__":
    # 每次运行的值都不一样，但一定落在后面注释说的范围里。
    print(round(backoff(0), 3))      # 0 到 0.5 之间
    print(round(backoff(3), 3))      # 0 到 4 之间
    print(round(backoff(20), 3))     # 0 到 30 之间，cap 封住了
```

这个写法来自 AWS 那篇经典分析（Marc Brooker，2015）。他们把「纯指数退避」和三种加抖动的版本放在一起模拟。抖动（jitter）就是在等待时间里掺一点随机。结论是：纯指数退避是「明显的输家」；而**全抖动**——也就是上面这种「在上限内均匀随机」——在客户端总工作量上表现最好，而且最好写。

为什么「随机」比「按时翻倍」更好？看一个具体场景。你同时跑了 20 个任务，同一个 provider（提供模型服务的公司）在同一秒抽了一下，20 个任务同时失败。

- **纯指数退避**：20 个都在 0.5 秒后重试，20 个请求又同时到达；再失败，20 个都在 1 秒后重试。**你只是把同一堵墙往后挪了 0.5 秒。**
- **全抖动**：20 个各自在 0 到 0.5 秒之间随机等，请求被摊平到整段窗口里。

这个现象叫惊群：一群客户端同时醒来，一起撞同一堵墙。退避解决的是「单个客户端别太频繁」，抖动解决的是「多个客户端别同步」。**两个问题，两个手段。**

## 10.3.4 重试次数要少

前面都在讲「怎么等」。更重要的是「等几次」。

这里有一条可以直接用的经验：**重试 2 次通常好过重试 5 次。**

理由不是省调用，是**重试的期望收益在下降**。第一次失败，多半是抖动，重试有希望。第二次失败，是抖动的可能性已经明显小了。到第五次，你重试的对象更可能是一个稳定的错误，而不是一次偶然的抖动。而每一次尝试都要付出时间、token（模型写字的最小单位，也按它计费）。还有一件事在 Agent 场景里更关键：**它占着这一步不放。**

Brooker 后来补过一句很锐利的话：**退避只是把工作往后挪，它不会让工作消失。** 一百个请求要处理，退避只是把它们摊到更长时间里，该做的一百次还是得做。真正把工作删掉的是 **不重试**：认定这条路不通，换一条。

这一条和 9.3 的重试预算对得上——那边限的是「同一方法两次」，说的其实是同一件事的另一面：

> **重试的职责是「渡过短暂的抖动」，不是「把这条路试通」。试不通，就换方法。**

所以在 Harnex 里，`retry` 和 `replan` 是两件事（9.3 的 `action` 四个值）。退避管 `retry`；`retry` 用完就转 `replan`。

## 10.3.5 连着失败就先停

重试次数管住了单次动作。但还有一层：**整个依赖都挂了的时候，你的每一个子任务都会去撞同一堵墙。**

设想 provider 出了持续故障。你的任务有 12 个子任务，每个都按「重试 2 次」的预算去敲，一共 36 次失败调用。全部计费，一次都不会成功。你付了钱，什么也没得到。

熔断器管的就是这件事：同一堵墙连着撞几次，就先别撞了。连续失败到阈值（事先定好的那个次数）就 **断开**，后面的调用直接原地失败，不发起网络请求。冷却（先安静等一段）之后，放一个请求出去探路，探通了才恢复。

```python
# harnex/reliability/retry.py（续）—— 熔断器：三态，冷却后放一个请求探路
import time


class Breaker:
    """连续失败到阈值就断开；冷却之后只放一个请求出去试探。"""

    def __init__(self, threshold=3, cooldown=30.0):
        self.threshold = threshold     # 连着失败几次就断开
        self.cooldown = cooldown       # 断开之后先冷静多少秒
        self.fails = 0
        self.opened_at = 0.0
        self.state = "closed"          # closed 通 / open 断 / half_open 试探

    def allow(self):
        """现在能不能发起一次调用？"""
        if self.state == "closed":
            return True

        if self.state == "open":
            # monotonic 是只往前走、不受系统改时间影响的钟，量间隔必须用它。
            waited = time.monotonic() - self.opened_at
            if waited >= self.cooldown:
                self.state = "half_open"
                return True            # 只放这一个出去，探通了再全面恢复
            return False               # 冷却没到，一个请求都不发，钱就省在这

        return True                    # half_open：这一次探路放行

    def record(self, ok):
        """每次调用回来都记一笔。成功或失败，决定状态往哪边走。"""
        if ok:
            self.fails = 0
            self.state = "closed"
            return

        self.fails = self.fails + 1
        # 探路那次也失败，或者失败次数到阈值，就断开。
        if self.state == "half_open" or self.fails >= self.threshold:
            self.state = "open"
            self.opened_at = time.monotonic()


if __name__ == "__main__":
    breaker = Breaker(threshold=3, cooldown=30)
    for i in range(3):
        breaker.record(False)          # 模拟连着失败三次
    print(breaker.state)               # open
    print(breaker.allow())             # False：冷却期还没过

# 预期输出（两行）：
# open
# False
```

三态各自的含义：

- **closed**：正常，调用直接放行。
- **open**：断开，调用原地失败。**这段时间一次网络请求都不发**——这就是省钱的地方。
- **half_open**：冷却结束，放一个请求出去。成功了回到 closed，失败了立刻回到 open。

熔断和重试的分工是清楚的：**重试管「这一次」，熔断管「这一阵子」。** 一次调用失败重试两次，是重试的活。连续三个子任务都在同一个依赖上失败，那是熔断的活。

还有一个必须配套的动作：**熔断断开时要上报，不能静默。** 一个不吭声的熔断器会让人以为是任务慢，其实是它根本没在做。断开时至少留下三样：断开的时刻、连续失败了几次、最后一次的真实错误。

## 10.3.6 重试也在花钱

到这里可以看清一件事：**第 1–9 章所有机制的成本，都是「一次」的成本**——一次调用、一次工具、一份上下文。从这一节起，成本变成了 **乘出来的**：

- 重试次数 × 单次调用成本
- 子任务数 × 重试次数 × 单次调用成本
- 再乘上「熔断没做好」的那部分——它们全部计入，收益为零

这也正是第 12 章要有一个 token 看板（一块盯着用量和花费的面板）的原因。但在这之前，本节这三样已经能挡住最贵的一类事故。分层超时、有上限的退避、熔断，三样加起来挡的就是这件事：**一个晚上烧光预算，换来一句「任务失败」。**

超时和熔断处理的是「还活着但走不通」。下一节处理更狠的一种：**进程直接没了。**
