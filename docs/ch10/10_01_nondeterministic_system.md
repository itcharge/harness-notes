# 10.1 你面对的是一个非确定性系统

## 10.1.1 同一句话，三次结果不同

Harnex 是这本书一路搭出来的那个 AI 助手：会自己动手，不只回话。第 9 章结束时，它能接长活了——一次跑很多步，跑很久。于是你真的开始用它，比如这个：

```text
你> 把这 200 条客户反馈按主题分类，输出成一张表。
```

前九章的任务大多有一个共同点：**做错了你立刻知道。** import（引用别人代码的那一句）没删掉，打开文件一看就知道；测试挂了，退出码不是 0——退出码是程序结束时交回的号码，0 代表成功。这类任务的成败由外部世界裁决，Harnex 骗不了你。

分类任务是另一回事。它跑了三次，三次都「完成了」：

- **第一次**：JSON 少了一个右括号。JSON 是一种通用的数据写法，少一个闭合的括号，整段就读不出来。解析当场抛异常，会话终止。你看到一段 traceback（程序崩掉时打出的一串记录）。
- **第二次**：格式对了，字段名却从 `category` 变成了 `分类`。你的下游脚本（读完这张表接着干活的程序）读到的是 `KeyError`。这个报错的意思是「找不到这个字段」。
- **第三次**：格式和字段名全对。但第 37 条本该是「物流」的反馈被归进了「其他」。**它没崩，它只是错了。**

三次是本章的三种坏法：崩、对不上、看着对其实错。这就是接下来要一起处理的东西。

## 10.1.2 不能要求每次都对

前面九章，你一直在给 Harnex **加能力**。技能包、记忆、shell（命令行）、检索、清单——每加一样，它能干的活就多一类。说白了是往车上加装备。这一章装的是刹车：**不再加能力，只消灭翻车。**

第 9 章末尾给 L1 定过一条达标标志：「你有一件真实的事，会主动丢给它做」。L1 是这本书的一个达标等级，做到就算过关。可一旦你真这么用了，你关心的就不再是「它能不能做」，而是「它十次里能做对几次」。

而这件事有个绕不过去的前提：**同一个输入，模型不会给你同一个输出。**

有人第一反应是「那把温度调成 0」。温度是控制随机程度的旋钮，调到 0，就是每次都挑最有把握的那个字。这么做确实让它更稳定，但 **不保证完全一致**。

原因不在提示词，在推理实现本身。计算机里的小数存的是近似值，两个小数相加会舍掉一丁点。更麻烦的是，先加谁、后加谁，会让误差换个位置。数学上 (a+b)+c 和 a+(b+c) 该相等，计算机里不一定。这就叫「浮点加法不满足结合律」。

显卡也不顺着一个个加：它把一堆数分成几份同时加，最后再合起来。分几份、按什么顺序合，每次都可能不同。这就是 GPU 上的归约顺序、批处理的批次组成、并行计算怎么切分造成的差别。

同一句话、同一份权重、同样的温度，两次推理在数值上就可能不一样。差一点点通常看不出来；偶尔正好差在岔路口，它就拐上了另一条路。

同一句话问两次，答案可能不一样，这件事有个名字，叫 **非确定性**。**它不是配置问题，是你要长期共处的环境条件。**

接受它之后，判断标准就换了：

> 不能要求它「不犯错」，只能要求它「错了能被发现、能被恢复」。

这一句是整章的立场。下面所有手段，都是在给这句话配执行细节。

## 10.1.3 失败分三类

「它又抽风了」不是一句能处理的话。要处理，先得分清是哪一种抽风。

按**处理方式**分，失败只有三类：

| 类型 | 典型样子 | 处理策略 |
| --- | --- | --- |
| **可重试** | 网络抖动、429/5xx、超时 | 等一会儿再来一次，同样的请求 |
| **可修正** | 字段名写错、参数类型不对、格式不符 | 把错误信息喂回去，让它改一次 |
| **不可恢复** | 文件不存在、前提不成立、权限不够 | 停下来，说清楚卡在哪 |

（429 是「请求太密」，5xx 是「服务器自己出错」，都是服务器回的错误码。）

注意这个分类的依据**不是错误长什么样，而是「重试有没有可能成功」**。

同一个「连接失败」，如果只是网络抖了一下，那就可重试；如果是撞上一个根本不存在的域名，重试一百次也一样——那是前提错了。判断的关键不在错误文本，在**你知不知道重试会不会改变结果**。

三类失败的出口也不同：

- 可重试的，交给 10.3 的退避与熔断（退避：等一会儿再试，越等越久；熔断：连着失败先停手）。重试次数要有限，否则它会把预算烧在一条死路上。
- 可修正的，交给 10.2 的校验加修复循环：查一遍，不对就让它改，再查一遍。这类失败占比最高，也最容易自动化处理。
- 不可恢复的，交给 10.5；它的价值不在「恢复」，在「说清楚」。

## 10.1.4 谁来判断对错

三类失败要能被分开，前提是有人知道「刚才那次算不算失败」。这里有一条从 7.1 节延伸下来的规矩：

**这个判断不能交给模型。**

看第三次那个例子。它把 37 条反馈归错了类，回复却是「已完成，200 条反馈已分类」。它没有说谎——**它判断不了自己错没错**，因为它手上没有一把能对照的尺子。

尺子只能来自外部：

```python
# harnex/reliability/failure.py —— 三类失败的判定：依据是「重试能不能改变结果」
# 三份名单：把认识的失败名归好类，分类结果才是可复现的。
RETRYABLE = {"timeout", "connection_reset", "rate_limit", "server_error"}
FIXABLE = {"schema_violation", "bad_argument", "invalid_json"}
FATAL = {"not_found", "permission_denied", "precondition_failed"}


def classify(kind):
    """把一个失败名换成处理动作：retry 重试、repair 改一改再试、abort 停下报告。"""
    # 判断顺序有讲究：先看还能不能重试，再看能不能改，最后才认输。
    if kind in RETRYABLE:
        return "retry"
    if kind in FIXABLE:
        return "repair"
    if kind in FATAL:
        return "abort"
    # 认不出来的，按最坏情况处理：停下来，交给人看。
    return "abort"


# 这一段直接跑就行：python failure.py
if __name__ == "__main__":
    print(classify("timeout"))
    print(classify("bad_argument"))
    print(classify("not_found"))
    print(classify("谁也没见过这个错"))

# 预期输出（四行）：
# retry
# repair
# abort
# abort
```

`kind` 从哪来？来自 **工具返回和接口状态**，不来自模型的自述。具体是：进程退出码、HTTP 状态码（服务器回的那个号码）、校验器的报错、文件是否存在。这些就是第 7 章那类硬信号——程序能直接判真假的结果。

最后那个 `return "abort"` 是刻意的：**未知的失败按最坏的情况处理。** 分类器认不出的东西，多半是你还没想清楚的东西。让它停下来，比让它猜要安全。

## 10.1.5 三类失败分别谁来判

再往下想一层，三类的判定主体其实不同。这也正是它们能分开处理的原因：

- **可重试** 由 **环境** 判定：退出码、状态码、超时。它不需要读懂内容，只看一次交互有没有走完。
- **可修正** 由 **schema 和校验器** 判定：schema 是一份事先写好的格式说明，专门用来卡住输出长什么样。它查结构对不对、值在不在枚举里（枚举：允许的那几个值），看的是形状，不是意思。
- **不可恢复** 由 **外部事实** 判定：路径在不在、权限够不够。它问的是世界，不是模型。

三类里没有一类是「模型说自己行不行」。这不是巧合——**凡是能被模型自述替代的判断，都已经在开头那个分类例子里失败了。**

## 10.1.6 这一章做的三件事

三类失败对应三套手段，也就是本章剩下五节的组织方式：

1. **把输出约束成结构**（10.2）。可修正类失败的绝大多数，根子在下游要解析一段自由文本。让它别产出自由文本，这类失败就少一大半。
2. **把失败当作常态处理**（10.3、10.5）。超时、退避、熔断管「怎么重试」；失败报告管「重试不动了怎么交代」。
3. **把状态做成可恢复的**（10.4）。前面九章的能力全活在一个进程里；程序一关，能力全部归零。

还有一件不算手段、但决定这一章有没有意义的事：**你得能测量**（10.6）。「稳定多了」不是结论，「100 次里成功 92 次、失败集中在超时」才是。

先做第一件。它管的是本章出现频率最高的那类失败：**格式跑偏。**
