# 2.1 模型是什么：一个无状态函数，外加 token、参数与上下文窗口

第 1 章结尾把同一件事问了两遍。一遍随口问：「杭州有什么值得去的？」另一遍写清了角色和限制：你是在杭州生活了十年的本地向导，要带一位 65 岁、腿脚不便、不喜欢人多的长辈玩三天；每天最多两个景点，午饭晚饭都要给出，不确定的信息直接说不确定。后一种回答更具体，也更少编造。

这两个说法差在哪，2.2 节再拆。我们先来看清：你每次发话，接话的到底是个什么东西。了解清楚之后，很多困惑会自动消失。

下面就是第 1 章实验一的那几行，文件在 [`codes/ch01/01_99_01_first_call.py`](../../codes/ch01/01_99_01_first_call.py)。问的是前一种说法。DeepSeek 和通义千问都兼容 OpenAI 的 SDK，换供应商只改三处：Key 的环境变量、`base_url`、`model`。

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
)

resp = client.chat.completions.create(
    model="deepseek-flash",
    messages=[{"role": "user", "content": "杭州有什么值得去的？"}],
)
print(resp.choices[0].message)
```

输出大致是这样（省略了值为空的字段）：

```text
ChatCompletionMessage(
    content="杭州值得去的地方很多，比如西湖、灵隐寺、西溪湿地……",
    role="assistant",
    reasoning_content="用户想知道杭州景点，可以按湖、寺、湿地几类来答……",
)
```

先看 `content`：一段文字，没有订单，没有查过天气。`reasoning_content` 是 DeepSeek 默认开着的思考过程，也只是文字，有的供应商不返回这个字段。

再看 `role="assistant"`。一段回复为什么要标「谁说的」？因为下一次调用时，你得把这段话连同之前的提问一起发回去，模型要靠 `role` 分清哪句是用户问的、哪句是它自己答的。

这两点合起来，就是本节要讲的事：**模型不是一个会记事的「人」，而是一个函数。**

```text
回复 = f(这一次发过去的全部消息)
```

这是一个 **无状态函数**：给一份输入，算出一段输出，调用就结束了，什么都不留。下一次调用，又从零开始。

> 把它想成一台自动售货机：投币、选货、出货。交易结束，机器不记得上一个顾客买了什么。你再投币，一切都是新的。

有人管它叫「纯函数」，这个说法只对一半。纯函数要求同样的输入必得同样的输出，模型做不到，原因见下面第三条。记住「无状态」就够了。

## 2.1.1 三条推论

- **推论一：记忆要由你来做。**

你觉得「AI 记得我」，是因为程序在每次请求时，把之前的对话重新塞了回去。模型那边从来没存过任何东西。第 6 章的会话管理，就建在这一条上。

- **推论二：能塞多少，就能记多少。**

既然历史要每次重新塞进去，一次调用能装多少内容就成了硬上限。超出的部分，要么报错，要么被丢掉。第 6 章讲怎么在上限里挑出该留的。

- **推论三：同样的输入，不保证同样的输出。**

模型是按概率挑下一个词的，不是确定性程序。所以「试一次没问题」不能说明它可靠，第 13 章要用整章讲评测。

这三条后面会反复用到：会话、上下文、评测，都是从这里长出来的工程问题。

## 2.1.2 token 和上下文窗口

推论二说的「能装多少」，要用两个词来量。

**token**：模型处理文字的基本单位，可以粗略理解成「字词碎片」。一个英文单词通常是一到两个 token；中文怎么切因模型而异，一个汉字大约零点几到一个多 token。token 既是 **计费单位**，也是 **长度单位**，所有长度限制都按它算。

**上下文窗口（context window）**：一次调用里，模型能「看到」的最大 token 数（输入 + 输出合计）。超过这个数，要么报错，要么被迫丢掉一部分内容。

这里要建立一个直觉：

> **上下文窗口是「桌面」，不是「抽屉」。**

桌面再大，摊开的也只是这一次干活的材料。活干完，桌面清空，东西不会自动收进抽屉，因为模型本来就没有抽屉。

由此有两个容易踩的坑：

- **长上下文 ≠ 长记忆**：窗口大，只说明这一次能摊开更多材料，不说明它记住了上一次。
- **中间容易被忽略**：材料一长，模型对开头和结尾看得比较清楚，对中间段落容易漏看。关键信息埋在一万字中间，很可能被跳过。这是第 6 章上下文工程要处理的第一个问题。

**动手试一下**：把同一份材料从 500 字加到 8000 字，把答案藏在中间，问同一个问题，对比几次回答。窗口还远没满，答案就可能开始变差。

## 2.1.3 三个常用参数

写代码时，你迟早会碰到这三个参数。先知道它们各自管什么。

| 参数            | 管什么    | 建议                                |
| ------------- | ------ | --------------------------------- |
| `temperature` | 输出的随机性 | Agent 场景先用 0：工具调用、结构化输出都要稳定  |
| `max_tokens`  | 输出上限   | 留够余量。截断比报错更危险：返回看着正常，内容却断在半句 |
| 结构化输出开关       | 返回格式约束 | 需要程序解析时打开（2.3 节展开）                |

关于 `temperature`，值得多说一句。调高 `temperature`，会让输出更「有创意」，但也让格式也会更不稳定。工具调用（2.3 节）要求模型输出一段严格的 JSON，温度一高，字段名和括号就可能出错。所以凡是要交给程序接着处理的输出，都压到低温。

两点提醒。一是各家支持的参数不完全一样，比如 DeepSeek 开着思考模式时，`temperature` 不生效；以供应商文档为准。二是思考过程也占输出额度，`max_tokens` 给少了，可能思考完就没位置写答案。

> **一句话记住**：参数只管「它这次怎么说话」，不管「它能不能办事」。但说话的方式坏了，后面办事的链路也会跟着出错。
