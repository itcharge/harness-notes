# 2.2 怎么把话说清楚：五零件、一叠消息与四个常见错误

2.1 节看过了接话的是什么东西：给它一叠消息，它算出下一段，调用结束，什么都不留。现在回到那两次提问。

一遍是：「杭州有什么值得去的？」

另一遍写清了这些：你是在杭州生活了十年的本地向导；带一位 65 岁、腿脚不便、不喜欢人多的长辈玩三天；每天最多两个景点；午饭和晚饭都要给出；按「上午 / 午饭 / 下午 / 晚饭」四行输出；不确定的信息直接说不确定。

后一种更好用，也更少编造。差别就是它把五个零件补齐了。写 prompt 时，先把这五项对一遍：

| 零件       | 作用         | 例子                            |
| -------- | ---------- | ----------------------------- |
| **角色**   | 决定它用什么视角说话 | 「你是一位在杭州生活了十年的本地向导」           |
| **任务**   | 说清要它做什么    | 「推荐一份三天行程」                    |
| **输入**   | 给足材料，别让它猜  | 「带 65 岁的长辈，腿脚不便，不喜欢人多」        |
| **约束**   | 划边界、定红线    | 「每天最多两个景点；不确定的信息不要编」          |
| **输出格式** | 决定结果好不好用   | 「按上午 / 午饭 / 下午 / 晚饭四行输出，每天一段」 |

## 2.2.1 五个零件，缺了会怎样

缺哪一项，结果通常就坏在哪：

- **缺任务** → 它不知道你要的是一份行程、一张清单，还是一段介绍
- **缺输入** → 材料不够，它就靠猜。猜出来的，就是编的
- **缺约束** → 它往「专业、全面、详细」上写，写出来的却不是你要的
- **缺输出格式** → 一大段散文，填不进行程表
- **缺角色** → 口吻跑偏，本地人的建议写成了百科词条

> 写完觉得不对劲，先对这五项，先别急着加形容词。缺的那一项，多半就是原因。

## 2.2.2 消息分三层

第 1 章实验三把角色放进 `system`，其余要求放进 `user`。2.1 节的调用里，发出去的也不是单独一句话：

```python
messages=[{"role": "user", "content": "杭州有什么值得去的？"}]
```

`messages` 是一个列表。一次调用里，常见的是这三层。`system` 像一直生效的规矩，`history` 像会议记录，`user` 是你现在这句话。

```text
① system    长期规则：你是谁、底线是什么、输出什么风格
② history   前面几轮的问答。模型自己不记得，是程序攒起来再发回去的
③ user      这一次的具体要求
```

| 层          | 放什么                              | 放错了会怎样                         |
| ---------- | -------------------------------- | ------------------------------ |
| `system`   | 稳定的规则、人设、红线                      | 把「这次要三天行程」塞进来，下一轮换了任务也甩不掉      |
| `history`  | 之前的 `user` / `assistant`，成对放回去   | 不放的话，它每一轮都是白纸                  |
| `user`     | 这一次的任务、材料和格式                     | 每次都把 `system` 重写一遍，规则就漂了        |

程序上一轮拿到的 `role="assistant"`，这一轮要放进 `history` 再发回去。2.1 节说的「记忆要由你来做」，指的就是这件事。

**动手看一次**：把完整的 `messages` 打印出来。它就是一个普通的 Python 列表，一层一层摞上去。

## 2.2.3 三个好用的写法

五项齐了之后，下面三种写法还能再稳一截。改几行字就能试。

**技巧一：给角色，同时给目标。**

「你是资深测试工程师」只定了口吻。加上目标，它才知道往哪使劲：

```text
你是资深测试工程师。我的目标是让这段代码在线上不因边界输入崩溃。
请审查下面这段代码的边界问题。
```

**技巧二：给示例（few-shot）。**

输出要固定的样子时，与其写「专业一点」，不如给一两个「输入 → 期望输出」。例子能照着写，形容词各有各的理解。

```text
把下面的需求改写成用户故事：
输入：用户可以修改自己的昵称
输出：作为已登录用户，我希望修改个人昵称，以便展示个性化信息。

现在改写：用户可以导出自己的全部数据
```

**技巧三：让它先思考，再回答（思维链）。**

在复杂判断前加一句「先列出你的判断依据，再给结论」。准确率通常会有可感知的提升。

在 Agent 场景里，这个技巧还有额外价值：**思考过程本身就是可观测的中间产物。** 当 Agent 答错时，我们能顺着它的「依据」看出它哪一步偏了。

我们在 2.1 节见过 `reasoning_content`：有的模型会自己先想一段，那段不一定出现在 `content` 里，格式也各家不同。你在 prompt 里要求的依据，是写进回复、你能直接核对的那一部分。

## 2.2.4 四个常见错误

**错误一：把 prompt 当许愿池。**

「请专业、严谨、全面、细致、深入地分析……」—— 形容词堆了一屏，没说清要做什么。换成「只列出问题，不要改写代码」，它知道该交什么。

**错误二：指令互相打架。**

「尽量详细，但要简短。」「要严谨，也要活泼。」模型只能猜你想站哪边，猜错不怪它。

**错误三：期待它记得上一轮。**

不做历史拼接，模型每一轮都是白纸。「它怎么又忘了」，从来不是模型的问题，是程序没有把历史塞回去。

**错误四：指望 prompt 解决一切。**

Prompt 只能改善「这一轮它说得好不好」。能不能真的去查天气、做没做错、允不允许做、要花多少钱，分别是后面的能力层、可靠性、权限和成本要管的。

> **本章要建立的边界意识**：Prompt 是「说好话」的功夫，Harness 是「办成事」的工程。第 1 章把界限放在「模型生成，外壳落地」—— **prompt 再好，也只是发动机的点火钥匙。**
