# 12.6 与用户侧的观测回路

## 12.6.1 前面的数字是给自己看的

12.5 结尾留了一句：还有一半没算，也就是用户那一侧。前五节攒下三样东西。trace 是轨迹，把日志按「谁属于谁」排成一棵树（12.1）。成本看板把 token 折成钱，按任务、按技能各加一遍（12.3）。延迟预算表把一次任务的时间摊开，看花在哪一段（12.5）。

这三样服务的都是同一个读者：**你，写这个程序的人。**

但 Harnex 最终要有人用。用户那一边发生的事，前五节一个字都没记：

- 他在哪一步关掉了页面？
- 他点了「再试一次」几次？
- 他有没有在任务跑到一半时，直接新开一个会话重问一遍？

这三个问题不是「用户体验」的边角料。**它们是观测里最难得的一类信号**——记的是**真实用户的失败**，不是你从测试集里挑出来的失败。测试集就是你提前出好的一批题，是你自己挑的（10.6 已经说过）。

## 12.6.2 用户看到的进度也算数据

先说一件免费的事。

11.6 是给网页控制台补体验的一节。它当时处理过三个空档：模型还没开口、工具正在跑、审批在等人点。那三处当时各填了一样东西——一行「正在执行 pytest…已 3.2 秒」、一张待办清单、一段工具输出。填这些，是怕人以为程序卡死。

这三样东西同时是**观测数据**。那句「已 3.2 秒」里的 3.2 不是界面自己另算的。它来自 trace 里 `tool` 节点的 `duration_ms`——一个字段，记的是这次工具执行花了多少毫秒。

也就是说，**服务端到用户这条线是免费的**：这个数你早就量过了（12.1），显示出来只是顺手。11.6 说「两个数都要进轨迹」，说的正是这件事——**界面显示的数，和看板统计的数，是同一个数。**

## 12.6.3 用户中途离开

反方向那条线才是新的：**从用户到服务端。**

用户「走了」这件事，在有界面的系统里是一个**明确的事件**。他关掉标签页算走了，点了「取消」算走了，新开一个会话重问一遍也算走了。而在终端里（那个只能打字、只能看字的黑框框），你连他走没走都不知道。

要把「他走了」记下来，只需要一个 `cancel`。日志里每一行都带一个 `kind`，用来说明这一行记的是什么事，`cancel` 就是其中一种。这个类型 11.5 的协议里已经有了：

```python
# harnex/observability/funnel.py —— 任务完成率：把技术成功率和用户放弃率合成一个数
# 只用标准库，不用 pip 装。
def completion_rate(events):
    """按轮次看最终去向：做完了、失败了、还是用户走了。"""
    outcome = {}                        # turn_id → 这一轮最后是什么状态
    for event in events:
        kind = event["kind"]
        if kind == "turn_done":
            status = event.get("status", "done")
            outcome[event["turn_id"]] = status
        elif kind == "cancel":
            outcome[event["turn_id"]] = "cancelled"      # 用户中途走了
    done = 0
    cancelled = 0
    for status in outcome.values():
        if status == "done":
            done += 1
        if status == "cancelled":
            cancelled += 1
    total = len(outcome)
    if total == 0:
        rate = 0.0
    else:
        rate = round(done / total, 3)
    return {"total": total, "done": done, "rate": rate, "cancelled": cancelled}
```

喂三段进去（一段做完了、一段失败了、一段取消），返回 `{'total': 3, 'done': 1, 'rate': 0.333, 'cancelled': 1}`。

这段代码按轮次（一轮是用户说一句、它答完）记下每一轮的最后去向。看到 `turn_done`，就取它的 `status`；看到 `cancel`，就记成 `cancelled`。

`cancel` 不需要新协议，11.5 那张表里已经有了它。**这一节做的事只是：让它在统计上有位置。**

## 12.6.4 任务做完的比例

现在得到本章最后一个指标，也是最该被放在首页的那一个：

> **任务完成率 = 做完了的任务 ÷ 所有被提交的任务。**

分母里有三类：做完了、失败了、用户中途走了。前两类 10.6 已经量过，算出来的叫**技术成功率**——程序没报错、任务被判成功的那些，占前两类的多少。第三类是新加的。

为什么它比技术成功率更该上首页？因为：

> **harness 类产品的留存，等于用户的成功率。**

留存就是用户下次还来不来。技术成功率 92% 听起来不错。但如果另外还有 20% 的用户在半路不耐烦走了，那么对一个真实用户来说，**成功率是 92% 乘上 80%，约 74%。** 这两个数是拿来说明关系的例子，不是实测。

那 18 个百分点不体现在任何一行报错里。它只体现在：**这个人下次不打开它了。**

## 12.6.5 中途离开多半不在模型

这里有一个反直觉、但很实用的结论。

看到完成率低，第一反应通常是「模型不行，换个更强的」。可要是把放弃率拆开看（放弃率就是中途走掉的人占多少），**它更多指向体验，而不是模型**：

- 用户放弃，常常发生在**那三处空窗**——首字之前、工具执行中、审批等待中（11.6）。他放弃的原因是「我以为它死了」，不是「它答得不好」。
- 用户放弃，还常发生在**看不见进度**的时候。11.6 定过一条线：**超过 2 秒没有新东西，就得有东西填。** 一直有更新，他就接着等；一静过这条线，人就开始自己下结论，然后走。

所以 11.6 那三处空窗，每消灭一处，放弃率通常就掉一截——**因为它们治的正是「用户以为它死了」这个误会。** 这也解释了 11.6 和这一章为什么要连着读：**一边修体验，一边数放弃率，中间靠观测数据把两头接上。**

## 12.6.6 用这些数字指导下一次改

到这里，这一章那条回路可以画完了：

```text
trace（12.1）→ 归因分类（12.2）→ 改哪一格（归因表）
    ↑                                    ↓
用户侧完成率（12.6）← 跑批对比（10.6）← 改动
```

图里那一步「跑批对比」来自 10.6：把同一批题反复跑一遍，数成功了几次。这条回路转完一圈，你才第一次能说：**「我知道它为什么好、为什么坏」**，而不是「我感觉它最近还行」。

这条回路和 10.6 那条是同一件事的两头：**10.6 从技术侧数成功率，这一节从用户侧数完成率。** 两头一起看，才是这个系统真实的健康状况。

## 这一节的边界

- **没有做用户行为分析**（点了几次、停在哪个界面）。那要在网页上埋点——事先在页面里放几个记录点，用户一碰就记一笔。这属于产品分析，不是 harness 内核的事。
- **没有做满意度反馈**（点赞、点踩）。它是另一种软信号：没有硬对错，好坏只能靠人判断。第 13 章会把它接到评测里。
- **没有做多用户的完成率对比。** 那要有账号体系，是第 16 章的事。

## 本章到此：v0.10

这一章给 Harnex 加的是**观测能力**：trace、成本看板、延迟预算表。这三样不改内核的判断，只让已经发生的事变得可查。唯一动了真实行为的是**模型分级路由**（12.4）。同一件事可能由更小的模型完成，所以那一格的成败率要单独盯。

所以版本号给 **v0.10**，并且**第 10 章那组可靠性指标必须重跑一遍**——路由改了「谁来做」，它可能影响成功。

可查不等于可衡量。下一章（第 13 章）把这一章的产出变成评测：**trace 里的分类、跑批里的成功率、用户侧的完成率，都是它的输入。**
