# 小结与验收

## 本章小结

这一章的主线只有一句：让已经发生的事变得可查。下面 36 条按正文顺序排，一条一句结论。

1. **trace 不是新存储，是 `SessionLog` 的第三个投影。** 先认两个词。`SessionLog` 是第 6 章那个会话日志，一行记一件事的流水账。投影就是同一份记录换个角度照出来的一份样子，删掉还能重新照。日志里能拼出树，只因为每条 span 事件都带了 `parent_id`——记着「我属于谁」的那个字段。加一个字段，不是加一个系统。
2. **判据一句话：能随时从日志重建的，是投影；不能的，是新的事实。** 判据就是判断用的那条线。所以 trace 库可以删了重放，你永远不会遇到「日志和看板哪个是真的」。
3. **一棵树上只需要五类节点**：`turn` / `llm` / `tool` / `approval` / `compact`。它们分别记一轮任务、一次模型调用、一次工具执行、一次等审批、一次压缩历史。后两类最容易被漏掉，也都有一次「意外好用」的时候。
4. **耗时要在现场记，不能事后算。** span（跨度）是树上一段有始有终的工作。它成对写：`span_start` 记开始，`span_end` 记结束。异常路径也要落 `span_end`，不然那一段永远悬着。
5. **trace 写 SQLite，不是继续塞 JSONL。** JSONL 是一行一条的文本文件，往后追加很合适。要做汇总，就得用能 `GROUP BY` 的东西：SQLite 是单文件数据库，`GROUP BY` 的意思是「按某个字段分组，再分别加总」。
6. **标准工具是同一个形状。** OTel 是 OpenTelemetry，一套通用的记录规范，各家平台都认。它的 `invoke_agent` / `chat` / `execute_tool`，就是本章的 `turn` / `llm` / `tool`。手写一遍才知道平台替你做了什么。
7. **失败要展开成一条路径，而不是一个点。** 「搜索 0.18 秒」「模型去猜文件」，这些不正常的形状比报错信息更早暴露问题。
8. **模型的补救动作，是它自己知道信息不足的证据。** 一条不断「猜文件」的 trace，就是检索被截断的信号。
9. **截断必须显式告知。** `{"hits": 12, "truncated": true, "total_if_unlimited": 37}`。返回里没有这个字段，模型只知道少，不知道少多少。
10. **失败分五类**：`tool_error`（工具报错）/ `retrieval`（检索没找到）/ `reasoning`（想错了）/ `context_lost`（上下文丢了）/ `permission`（没权限）。**分类的依据是「各自指向一个不同的修法」。**
11. **用规则分类，不用模型。** 规则确定、可复现、能批量跑。模型分类既可能判错，又破坏了省钱的初衷。
12. **归因分类是评测与告警的前置条件。** 归因是找出「哪一步、因为什么」失败，告警是出了问题自动通知你。不分类的「感觉变差了」，既不能定位，也不能设阈值（超过某条线就报），还没法验证改动。
13. **成本看板是 trace 的几种 `GROUP BY`**，不是另一份存储。按会话、按任务、按技能，三个口径共用一份数据。口径就是算一个数时用的定义和算法。
14. **技能本身不烧 token，烧的是它引出的后续推理。** token 是模型算长度、也算钱的单位。所以「哪个技能最贵」= 这个技能下面那一整枝里，所有 `llm` 的成本之和。
15. **单价放配置，未知模型返回 0。** 猜出来的成本比没有成本更危险。
16. **80% 的钱花在 20% 的场景**，而那 20% 反复是三类：长上下文、低效检索、大输出。
17. **月度预测必须带上假设。** 「按当前日均外推」这句话是必需的。外推就是拿最近的日均乘剩下的天数；而「剩下的日子和前面一样」这个假设，通常不成立。
18. **token 数是估算。** 不同 provider 的 tokenizer 切法不同，缓存计费规则也不同。tokenizer 就是把文字切成 token 的那把尺子。标题里该有「估算」两个字。
19. **三招按「省得多」乘「风险低」排序**：模型路由 > 缓存 > prompt 瘦身。最安全的一招反而排最后，因为它是日常。
20. **路由的判据不是「任务重不重要」，是「这一步需不需要那么强的模型」。** 大量格式转换、提取、分类、简单编辑都不需要。
21. **长不等于难。** 长文档摘要是信息压缩，小模型做得不差。反倒「短输入、要多方案权衡」才需要前沿模型。
22. **路由决策必须进 trace。** 不是不许误伤，是不许不知情地误伤。
23. **升级路径要有次数上限。** 「小的升中的、中的升大的、大的再回去问小的」是打转的另一种写法。
24. **缓存是「要么白拿、要么白白错过」的。** 前缀是每次请求开头那段固定内容。错过的唯一方式，就是把每次都不一样的东西放了进去。
25. **缓存失效灾难比「没命中」严重得多。** 没命中只是少省钱。串味是甲用户的内容出现在乙用户的回答里。
26. **判据：这一段的字节，在下一次请求里还会一模一样吗？** 一模一样就是一个字都不差。会就往前放，不会就往后放。
27. **工具结果只缓存幂等的、不随时间变的调用。** 幂等就是同样的调用跑几次，结果都一样。缓存一个不幂等的调用，等于让「第二次」执行了「第一次」的结果。
28. **单轮 1 秒不等于多步 7 秒。** 多步 E2E 是超线性的：整条链的耗时比各段相加涨得更快。多出来的是三处——prefill 递增累加、串行技能、一轮多技能。
29. **延迟要报五个口径**：TTFT / TPOT / tool_ms / 单轮 E2E / 多步 E2E。前四个是组件指标，量的是某一段；最后一个是结果指标，量的是整件事。
30. **先归因再开药。** 预算表告诉你哪一格亮红灯，不同格开不同的药。**prefill 那一格的药就是省钱三板斧**——同一个动作，两个收益。
31. **别在错的环节使劲。** TTFT 超标却去换更快模型：decode 快了 20%，prefill 纹丝不动。decode 是一个字一个字往外吐的那一步。
32. **两条 SLO，不是一个。** SLO 是「这个指标不许差过某条线」。单轮问答和多步任务的组成不同，用同一条只会「怎么都对」或「怎么都错」。
33. **用户看得见的进度本身就是观测数据。** 界面显示的和看板统计的，是同一个数。
34. **用户「走了」是最难得的信号**——它是真实用户的失败，不是你测试集里挑出来的。
35. **任务完成率 = 做完了 ÷ 所有被提交的**（分母含失败与取消）。**harness 的留存 = 用户的成功率**：92% 技术成功率遇上 20% 中途放弃，对用户就是 74%。这组数是举例，拿来说明关系的。
36. **优化「中途放弃」往往不在模型侧。** 它更多地指向那三处空窗——用户以为它死了，不是它答得不好。

## 动手任务

小结给的是结论，这九件事是让结论落地的。每一件都能在你自己的日志上做，做完都该有一个数、或者一条 trace 可以指给人看。

1. **手写一遍 trace，再对照一个平台。** 按 12.1 落一份 SQLite。跑完一个多步任务后打开树，逐节点看输入输出与耗时。**再去看 LangSmith 或 Langfuse 的文档**，写下一句「它多做了什么、逼我按什么形状来」。

2. **故意造一次「少了一半」。** 把某个搜索工具的默认 `limit` 调到很小，而且不告知截断。`limit` 就是「一次最多返回几条」。然后跑一个需要全量的任务。**再打开 trace，找出「模型在猜文件」那一段**——亲眼看一次这个形状。

3. **给五类失败各造一个样本。** `tool_error` 用跑一个必然失败的命令。`retrieval` 用上面那个截断。`permission` 用一次被拒的审批。`reasoning` 用一个不该信小模型的任务。`context_lost` 触发一次压缩。**五条 trace 摆在一起，检验你的 `classify_failure()` 准不准。** 那是 12.2 里那个分类函数。

4. **算出你的 80/20。** 用 `cost_by_tool()` 跑最近一周的 trace，看排行榜第一名是谁。这个函数按技能把成本加起来。**如果第一名不是 `search_code` 或某个读大文件的技能，想想为什么**——它可能揭示了一个你没意识到的贵点。

5. **把预测和实际对一对。** 月初记下预测值，月末看真实账单。**误差超过 30% 时，去找那个「使用方式变了」的事件**——它就是你预测失准的原因。

6. **上线模型路由，并把决策打进 trace。** 加上 12.4 那个 `routing` 事件后，**重跑 10.6 的跑批**（把同一批题再跑一遍）。成功率掉了吗？成本降了多少？两条曲线都要有数。

7. **做一次缓存命中率体检。** 在 trace 里给每个 `llm` 节点记下 `cached_in`，也就是这次有多少输入是命中缓存的。命中率接近 0，就回头查前缀里是不是有每轮都在变的东西（时间戳是最常见的元凶）。

8. **把一次任务的耗时摊开。** 拿一个你觉得「慢」的任务，跑 `budget_table()`。**先只看表格、不猜原因**，写下哪一格超标；然后再去改。改完复跑，看那一格有没有降。

9. **算一次真正的完成率。** 把 `cancel` 事件数出来，和 10.6 的技术成功率放一起。**如果两者差得远，去看那些被取消的任务停在哪一步**——它多半不是模型的问题。

## 本章在阶段三里的位置

阶段三（L2）的主线是「可靠可观测」。三章各管一段：

| 章 | 管什么 | 一句话 |
| --- | --- | --- |
| 第 10 章 | 可处理 | 错了能被发现、能被恢复 |
| 第 11 章 | 可用 | 同一件事做起来顺手 |
| **第 12 章** | 可看见 | 轨迹、成本、延迟都能查 |

这一章有一处和第 11 章对称的性质：**它加了三样东西，却没有一样改动「做什么」的判断。** trace、看板、预算表，管的都是「已经发生的事怎么被读」。`run_turn()` 里那些决定走哪条路的代码，一行没动。

唯一的例外是模型分级路由。它改的是「谁来做」，所以本章在版本号旁边加了一条附注：**第 10 章那组可靠性指标必须重跑。**

可看见之后，下一件事是可衡量。这一章所有的分类、成功率、完成率，都会成为第 13 章评测体系的输入。

## 本章的常见误区

下面每一条，都是读完这一章之后仍然容易犯的。

- **把 trace 当成第二份数据。** 一旦两份真相并存，「日志和看板对不上」就是必然。
- **只记文本，不记 token 与耗时。** 成本与延迟从此无从归因——这是错误模式里那条。
- **耗时靠「下一条事件的时间」去凑。** 多轮和并行下全是错的，还会掩盖真正卡住的那一段。
- **只写 `span_start` 不写 `span_end`。** 工具一挂就留下悬空节点，占比算不平。
- **trace 全量落盘不做采样。** 采样就是按比例只存一部分。短时间内能跑，量上来之后存储会失控。
- **把 trace 里的提示词原样落盘。** 用户数据进了观测存储，就是一次合规事故——合规指的是符合法规，用户内容不该随手存。
- **只看报错不看形状。** 「模型在猜文件」这类信号不报错，但比报错更早暴露问题。
- **截断了不说。** 模型只知道少、不知道少多少，于是绕着走。
- **给失败分类时让模型来判断。** 它可能判错，而且每次失败都烧一次钱。
- **不分类就说「变差了」。** 这句话既不能定位，也不能设阈值。
- **把预测当成承诺。** 不说假设的预测，月底对不上账时会显得很不可信。
- **把单价写进业务逻辑。** 模型一换，就要满仓库改价格。
- **未知模型猜一个价。** 假装的精确比诚实的粗略更危险。
- **缓存前缀里塞用户内容。** 省钱没省成，先出了串味事故。
- **缓存不幂等的调用。** 第二次执行了第一次的结果，比没缓存危险得多。
- **路由误伤无人察觉**——错误模式里那条。正解不是不许误伤，是不许不知情地误伤。
- **升级路径不设上限。** 小的升中的、中的升大的、大的再问小的，就是打转。
- **只优化平均值。** 平均 1.5 秒达标，P95 是 30 秒——最难受的恰好是最重要的用户。
- **在错的环节使劲。** TTFT 超标却去换模型：decode 快了 20%，prefill 纹丝不动。
- **技能没有超时。** 一条 30 秒的命令卡死链路，循环还会把它放大 N 倍。
- **多步任务只测单轮延迟。** 单轮 1 秒，7 轮加串行技能，就是用户等一分钟。
- **把多步 E2E 线性外推。** prefill 是递增累加的，这个假设不成立。
- **用一条 SLO 管两种形态**——结果要么怎么都对，要么怎么都错。
- **只看技术成功率。** 中途放弃的那部分人不在任何一行报错里，但他们会走。
- **把放弃率全归给模型。** 它往往先指向空窗，而不是模型能力。

## 自测题

每一题都能在正文里找到依据。答不出来时，回去看对应那一节，比记答案有用。

1. 手写 trace 后再看 LangSmith 这类平台，你能说出它多做了什么、少做了什么吗？
2. 为什么 trace 库可以随时删掉重建？这个性质依赖日志里的哪个字段？
3. 五类节点里，哪两类最容易被漏掉？漏掉之后会失去什么信息？
4. 为什么耗时必须现场记、不能事后算？10.1 和 11.3 各留了什么教训？
5. 模型分级路由的风险是什么？怎么兜底，也就是出了问题拿什么顶上？
6. 为什么「路由决策进 trace」是路由安全的必要条件，而不是加分项？
7. prompt 缓存命中依赖什么条件？哪些内容绝不能放进前缀？
8. 「能缓存的」和「绝不能缓存的」调用，判据是哪一条？
9. 80/20 成本分析怎么定位「最贵的 20%」？为什么第一名常常让人意外？
10. TTFT 超标时你的排查顺序是什么？为什么先看 prefill，而不是先换模型？
11. 为什么一个 7 步任务不能把「单轮 1 秒」顺着推成「任务 7 秒」？多出在哪三处？
12. 延迟预算表里，哪一格是 Agent 特有的？为什么它没有通用解法？
13. 为什么延迟要报五个口径？组件指标和结果指标各用来干什么？
14. 为什么单轮问答和多步任务要各定一条 E2E SLO？
15. 归因分类为什么必须用规则而不是模型？两个理由分别是什么？
16. 五类失败各自指向什么修法？举出一对「指向同一修法、所以该合并」的假想类别。
17. 「任务完成率」和「技术成功率」的差别在哪？为什么前者更该上首页？
18. 92% 的技术成功率遇上 20% 的中途放弃，对用户意味着什么？
19. 用户放弃通常和什么有关？为什么说它「往往不在模型侧」？
20. 为什么成本看板可以不带存储？它的数据从哪里来？

| 成本看板 | Cost Dashboard | 按会话/任务/技能聚合的 token 与费用 |

| 前缀缓存 | Prompt Caching | 复用字节一致的前缀，跳过重复 prefill |
| 缓存失效灾难 | Cache Contamination | 用户相关内容进了前缀，导致会话串味 |
| 模型分级路由 | Model Tiering / Routing | 按步骤难度把请求分给不同档位的模型 |
| 级联 | Cascade | 小模型先答、过不了校验再升级的路子 |
| 首字时延 | TTFT | 单次调用到第一个可见 token |
| 单 token 间隔 | TPOT (Time Per Output Token) | decode 速度，决定整段输出多久 |
| 多步端到端 | Multi-step E2E | 整个任务从开始到结束的耗时 |
| 耗时预算表 | Latency Budget | 把任务耗时按阶段摊开算占比的表 |
| 服务等级目标 | SLO | 对某个指标定的目标线（如 P95 ≤ 90s） |
| 分位数 | Percentile | P50/P95/P99；延迟一律报分位数而非平均 |
| 任务完成率 | Task Completion Rate | 做完了的 ÷ 所有提交的（含失败与取消） |
| 取消 | Cancel | 用户中途离开产生的事件，是最难得的观测信号 |
| 观测回路 | Observability Loop | 观测 → 归因 → 改动 → 跑批 → 回看观测 |
