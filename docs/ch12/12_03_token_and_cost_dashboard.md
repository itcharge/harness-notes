# 12.3 Token 与成本看板

## 12.3.1 账单只告诉你花了多少

上一节最后一句说，要「把它变成钱」。这一节就干这件事，第一步是让钱看得见。

月底你收到一张 API 账单。API 是模型厂商对外提供服务的接口。账单上的钱是这么来的：你每调用一次模型，厂商按这次用掉的 token 收一次费。上个月是 340 美元，这个月是 610。

涨了 79%。然后呢？**然后你什么都做不了。**

你不知道是哪一个任务变多了、是哪一类调用变贵了，还是某一天有个循环失控烧了 40 美元。账单给的是**一个总数**。一个总数不是信息，是结论。它把你和原因之间的一切都抹掉了。

要让钱可管，得先能回答三个问题：

- 哪个**会话**最贵？会话就是一次连续的对话，从你开口到收工。
- 哪个**任务**最贵？任务是这一轮，你交给它的那件事。
- 哪个**技能**最贵？技能是它调用的那个工具，比如搜代码、读文件。

## 12.3.2 三种算法，同一份数

三个问题，看起来要存三份数据。好消息是：它们不需要三份存储。

能省下来，是因为原料本来就有。12.1 记的 trace 里，每个 `llm` 节点都带着两个数：送进去多少 token，写出来多少。**成本看板就是同一份 trace 的几种 `GROUP BY`。** 看板是一块把数字摊开的页面，本章要的只是它底下那几步加法。`GROUP BY` 是数据库里的一句指令，意思是「按某个字段把记录分堆，一堆一堆分别算」。

按会话聚合，是「这个会话花了多少」。聚合就是把一堆数字并成一个，比如加起来。按任务聚合，是「这一轮的子树加总是多少」。子树是树上某一节往下长的整枝；按任务算，等于把这一轮下面所有节点加起来。按技能聚合稍微绕一点：技能本身不烧 token，**烧的是它引出的后续推理**。

最后那条要单独说，因为它最反直觉：「`search_code` 花了 0 美元」是错的。技能真正的成本，是**它把多少 token 送进了下一轮上下文**。一个返回 5 万字的搜索，自己一分钱不花，却让之后每一轮 prefill 都贵一截。prefill 是模型开口之前，把收到的全部上下文重新读一遍的那一步。读得越多，这一步越贵。

## 12.3.3 费用等于用量乘单价

说了这么多「成本」，公式其实只有一句：钱 = 用掉多少 × 每单位多少钱。先把这句话写成函数。

有一件事要在这里就定死：**单价放配置，不写进业务逻辑。** 配置是单独一份设置，改它不用碰代码。

```python
# harnex/observability/cost.py —— 单价放配置：模型换得比代码快
# 只用标准库，不用 pip 装。这段没有任何网络请求。
PRICES = {                                  # 美元 / 百万 token
    "gpt-4o":      {"in": 2.50, "out": 10.00, "cached_in": 1.25},
    "gpt-4o-mini": {"in": 0.15, "out": 0.60,  "cached_in": 0.075},
}


def cost_of(model, tin, tout, cached_in=0):
    """把一次调用折成美元。未知模型不猜价：记 0 并单独告警。"""
    price = PRICES.get(model)
    if price is None:
        return 0.0                          # 表里没有的模型，宁可记 0 也不猜
    fresh = tin - cached_in
    if fresh < 0:
        fresh = 0                           # 缓存数比输入还大，说明数据脏了
    fresh_cost = fresh * price["in"]
    cached_cost = cached_in * price["cached_in"]
    output_cost = tout * price["out"]
    return (fresh_cost + cached_cost + output_cost) / 1e6
```

顺手调一次：`cost_of("gpt-4o", 4200, 210, 3800)` 返回 `0.00785`，不到一美分。

三个细节都不是装饰：

- **`cached_in` 单开一列。** 命中缓存的价格只有未命中时的一半（12.4 会讲）。缓存是「这段内容之前算过，这次直接拿结果」；命中就是这次真用上了。把两者混在一起，你会得出「缓存没用」的错误结论。
- **未知模型返回 0，而不是猜一个价。** 猜出来的成本比没有成本更危险。它会让看板显示出一种不存在的精确。
- **单价放配置。** 模型名字和价格一年能变好几轮。把价格写进函数体，就是给自己埋一张「三个月后对不上账」的罚单。

「哪个技能最贵」就是在这个基础上做一次子树求和：

```python
# harnex/observability/cost.py（续）—— 哪个技能最贵：把每个 tool 子树下的 llm 成本加起来
def _walk_for_cost(node, owner, totals):
    """沿树往下走。owner 记「当前在谁手下」，进了 tool 就换人。"""
    if node["node"] == "tool":
        owner = node["name"]                      # 进入子树，换主人
    if node["node"] == "llm" and owner:
        tin = node.get("tokens_in") or 0
        tout = node.get("tokens_out") or 0
        cost = cost_of(node["name"], tin, tout)
        totals[owner] = totals.get(owner, 0.0) + cost
    for child in node["children"]:
        _walk_for_cost(child, owner, totals)


def cost_by_tool(trace):
    """技能本身不烧 token，烧的是它引出的后续推理。"""
    totals = {}
    for root in trace["roots"]:
        _walk_for_cost(root, None, totals)
    return totals
```

`owner` 沿着树往下传。一旦走进某个 `tool` 的子树，那里面所有 `llm` 的成本就算在这个技能头上。跑出来通常是这样一张表：

```text
技能成本排行（上周）
1. search_code       $18.40    ← 返回内容太长，把上下文撑大了
2. fs_read           $ 6.20
3. run_command       $ 2.90
4. todo_update       $ 0.00
```

**第一名往往让人意外。** 而「意外」正是看板该给你的东西。

## 12.3.4 钱主要花在哪

三个问题都答完了，钱就摊开了。摊开之后，你会看到一条比想象中更陡的分布：**通常 80% 的钱花在 20% 的场景上。** 而 Harnex 这类系统里，那 20% 反复是同样的三类：

| 贵点 | 为什么贵 | 表面症状 |
| --- | --- | --- |
| **长上下文** | 每一轮都要重新 prefill 全部输入 | 越聊越贵，成本随轮数上涨 |
| **低效检索** | 检索塞了一大堆用不上的块进上下文 | `search_code` 类技能霸榜 |
| **大输出** | 把整段编译日志、整个文件读进了上下文 | 某几次调用的 `out` 特别大 |

这三类的共同点是：**它们都不是「模型贵」，而是「你给它看的东西太多」。** 这个判断很重要。它把成本问题的方向，从「换个便宜的模型」掰回「管好你喂进去的东西」。而后者才是真正的大头，12.4 的三板斧正是在这三格上动刀。

## 12.3.5 估计下个月的账单

「钱花在哪」已经有答案了。看板还该回答第二个问题：**照这样下去，月底会花多少？**

```python
# harnex/observability/cost.py（续）—— 月底预测：它是外推，不是承诺
def forecast_month(llm_spans, day_of_month):
    """按当前日均外推 30 天。假设「从今往后和过去一样」——通常不成立。"""
    spent = 0
    for span in llm_spans:
        tin = span.get("tokens_in") or 0
        tout = span.get("tokens_out") or 0
        spent = spent + cost_of(span["name"], tin, tout)
    days = day_of_month
    if days < 1:
        days = 1                        # 1 号才开始跑，除零会炸
    per_day = spent / days
    projected = per_day * 30
    return {"spent": round(spent, 2),
            "per_day": round(per_day, 2),
            "projected": round(projected, 2)}
```

这个算法叫外推：拿已经发生的速度，往后推还没发生的那一段。它有一处天生站不住：**它假设剩下的日子和前面的日子一样。**

所以用法上有一条纪律：**报预测时，必须同时报它的假设。** 「本月已花 220 美元，日均 20，按此推算月底 600」。这句话里，「按此推算」四个字是必需的。它公开承认了假设：剩下的日子和前面一样。

这个假设什么时候会崩？很明确：**当你的使用方式在变的时候。** 你刚把 Harnex 接进一个每天跑批的流程，日均就会跳；你刚上线模型路由，日均就会掉。所以预测旁边应该放一条曲线，画出日均随时间怎么走。这样「速率是不是在变」一眼可见，而不是只放一个孤零零的数字。

## 12.3.6 多个模型分开记账

前面五节都默认只有「一个模型」。可你一旦开始用两个、三个，记账就得跟着变。

这一节有一处「如果早先没做，现在就得回头补」的地方。**多模型记账要求 adapter 层统一 usage 结构。** adapter 层是夹在中间的一层代码，专门把各家不同的接口翻译成同一套。usage 是厂商在返回里附带的一组数字：这次用了多少 token。

第 2 章的 `call_model` 是所有模型调用的唯一出口。这是全书一直守的纪律：模型调用只有一个入口。它必须把不同 provider 的返回**归一化成同一组字段**。provider 是提供模型服务的厂商，比如 OpenAI、Anthropic。归一化就是不管各家用什么字段名，统一改成同一套。

```python
{"text": "...", "tokens_in": 4200, "tokens_out": 210,
 "cached_in": 3800, "model": "gpt-4o-mini"}
```

一旦归一化了，看板就不关心底下是谁。成本函数只认 `model` 和那三个 token 数。反过来，要是每家返回的字段各不相同，成本统计就得先判断「这是哪一家」。代码里会堆满 `if provider == ...`。那种写法**每次上新模型都要改一遍**。

这条要求，其实是全书一条老纪律在这一章的又一次兑现。**把差异收在边界上，里面就只剩一种形状。**


**token 数是估算，不是精确值。**

两个原因。不同 provider 用不同的 tokenizer，同一个字符串算出的 token 数不一样。tokenizer 就是把文字切成 token 的那把刀。缓存 token 的计费规则各家也不同：有的把写缓存单独计价，有的不额外收费。

所以看板的标题里应该有「估算」两个字，而不是一个精确到分的数字。这个提醒和第 10.6 那条「别追小数点」是同一个道理。**一个诚实的粗略数字，好过一个假装精确的数字**。后者会让你为了 0.3% 的波动去做无意义的优化。

## 这一节的边界

- **没有做实时看板。** 本节只到「数据能算出来」。真正的界面，是在 12.1 那个 SQLite 上加几个查询、再画几张图。前端仍是 11.5 那套协议驱动。
- **没有做预算强制。** 「花超了就停」是另一件事，属于第 16 章的配额与限流。配额就是给一个上限，用超了不许再用。
- **只看 LLM 成本。** 基础设施、数据库、向量库的钱不在这里。向量库是给检索用的那种数据库。
