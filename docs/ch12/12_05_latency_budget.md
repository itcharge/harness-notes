# 12.5 延迟工程：链路耗时预算表

## 12.5.1 从一步慢，到整条链路慢

11.1 定了两个指标：TTFT 和 E2E。这两个词先说明白。TTFT 是从你按下回车，到屏幕上冒出第一个字。E2E 是从你按下回车，到它把整段话说完。不过 11.1 量的是 **一次调用**。

真实的 Harnex 任务不是一次调用，是**一条链**。第 9 章那种多步任务，由若干次模型调用加若干次工具执行串起来。链的耗时不是各段简单相加，**它比相加涨得还快。** 这种「涨得比相加更快」有个说法，叫超线性。

「单轮 1 秒，7 轮就是 7 秒」这个推算错了。错在三处：

1. **每一轮的 prefill 都在涨。** prefill 是模型开口之前，先把收到的全部内容读一遍那一步（11.1）。历史一轮比一轮长，第 7 轮要读的东西比第 1 轮多得多。所以时间是越加越快地累积，不是每轮加一样多。
2. **技能之间有先后依赖。** 有些活必须等前一件做完才能开始，比如先搜到文件，才能读它。11.3 只解决了能同时跑的那些；有这种依赖的，仍然要排队。
3. **有的轮次要跑好几个技能。** 一轮里调三个工具，这三个的耗时都得算进去。

所以一个「单轮 1 秒」的任务，多步跑完，用户可能等一分钟。**多步任务的延迟得单独量、单独定基线。** 基线就是先定下一个「正常该多快」的数，以后拿它来比。

## 12.5.2 先约定五个时间

要单独量，第一步是把口径钉死。延迟工程最容易犯的错，是拿两个口径不同的数互相比较。比如把单轮那 1 秒，和多步那 1 秒当成一回事。五个口径在这里定下来：

| 指标 | 含义 | 归谁管 |
| --- | --- | --- |
| **TTFT** | 单次调用到首字 | 体感（11.1） |
| **TPOT** | 每输出 token 的平均间隔 | decode 速度，决定整段生成多久 |
| **tool_ms** | 单次工具执行 | 技能 |
| **单轮 E2E** | 一次「用户说一句、它答完」 | 交互 |
| **多步 E2E** | 整个任务从开始到结束 | 用户对这件事的耐心 |

前四个是**组件指标**，最后一个是**结果指标**。组件指标量的是一段，结果指标量的是整件事。诊断看前四个，定基线看最后一个。

**它们都要按 P50/P95/P99 报。** P95 是把耗时从小到大排队，95% 的请求比这个数快。P50 是中位数，也就是排在正中间的那个数。P99 是那条线，只有 1% 的请求比它慢。11.1 已经说过为什么不用平均。一次 30 秒的卡顿，混进 100 次 1 秒里，平均值只涨到 1.3 秒，看着完全正常。

TPOT 值得单独说一句。它和 TTFT 分工不同。**TTFT 决定「它开始理我了」，TPOT 决定「它说话有多快」。** 一段回答你感觉等了多久，约等于 TTFT 加上「输出多少 token 乘 TPOT」。token 是模型算长度也算钱的单位（12.3 讲过）。所以「输出写太长」在延迟上的代价是能算出来的，不是一句「感觉慢」。

## 12.5.3 先找到慢在哪

口径有了，接下来要回答「时间花在哪」。做法很机械：**把一次任务的耗时按阶段摊开，算占比。** 摊出来的那张表，就是耗时预算表。

```python
# harnex/observability/latency.py —— 把一次 trace 摊成耗时预算表
# 只用标准库，不用 pip 装。
def _accumulate(node, totals):
    """沿树累加每一类节点的耗时。"""
    name = node["node"]
    duration = node["duration_ms"] or 0
    totals[name] = totals.get(name, 0) + duration
    for child in node["children"]:
        _accumulate(child, totals)


def _percent(row):
    return row[1]


def budget_table(trace):
    """返回 [阶段, 占总耗时百分比]，从大到小。"""
    totals = {}
    for root in trace["roots"]:
        _accumulate(root, totals)
    total = sum(totals.values())
    if total == 0:
        total = 1                        # 全是 0 时别除零
    rows = []
    for name, duration in totals.items():
        percent = round(duration * 100 / total)
        rows.append([name, percent])
    rows.sort(key=_percent, reverse=True)
    return rows
```

一个 7 步任务跑出来是这样。`prefill` 与 `decode` 由每个 `llm` 节点的内部拆分得出。怎么拆的，本节不展开。

```text
阶段            耗时    占比
prefill（×7）   9.8s    52%
tool（×9）      5.6s    30%
decode（×7）    3.2s    17%
overhead        0.2s     1%
总计           18.8s
```

**这张表的作用只有一个：告诉你该动哪一格。** 一格就是表里的一行。

| 超标的格子 | 说明什么 | 开哪副药 |
| --- | --- | --- |
| **prefill** | 你喂进去的东西太多 | 瘦身、缓存、压缩（← 就是 12.4 三板斧） |
| **decode** | 输出太长，或模型太大 | 限制输出长度（schema、要它别写废话）、模型路由 |
| **tool** | 某个技能慢 | 超时（10.3）、并行（11.3）、缓存、预取 |
| **循环次数** | 不是某一步慢，是它绕远了 | 改规划与终止条件（第 9 章） |

两处容易混的，单独说：

- **decode 那格的「模型太大」**，说的是模型本身的速度差别。同一句话，慢的那个要花更久说完。
- **schema** 是一份字段清单，规定输出长什么样。用它限长度，是让模型只填该填的字段，不写多余的话。

## 12.5.4 省钱和变快有时是一件事

表的第一行值得停下来看。**prefill 超标的药，就是 12.4 的三板斧。** 这不是巧合。缓存和瘦身省的是 token，降的也是 TTFT。**它们省掉的正是 prefill 的工作量**。所以上一节和这一节在这一格上完全重合。**同一个动作，两个收益。记账上分两笔。**

最后一行不一样，它是 **Agent 特有的**。普通网站不会「因为绕远了 5 步而变慢」，Agent 会。它多绕一步，就多一次模型调用、多一轮 prefill。「循环次数超标」这一格没有对应的通用手段。它要改的是**规划本身**，也就是「决定下一步做什么」那一套。这也是第 9 章为什么要先于本章。

## 12.5.5 别在不慢的地方使劲

第 9 章那条讲的是绕远。还有一种错，是把慢归错了地方。

错误模式是一类反复出现的错法。其中就有那条：**TTFT 超标，本来是 prefill 的问题，却去换更快的模型。** 换完 decode 快了 20%，prefill 纹丝不动，用户等的时间几乎没变。

这条错之所以常见，就是因为没有这张表。换模型是最容易想到的动作，而它恰好**只动 decode 那一格**。如果瓶颈在 prefill（在 Agent 里通常都是），换模型就是白花钱。

预算表存在的意义，就是**在你动手之前，先逼你看一眼是哪一格亮红灯。**

## 12.5.6 给普通情况和慢情况各定一个目标

表能指认哪一格慢，但「快慢」还得有个准。这就是基线，而且要定**两条**，不是一条：

- **单轮问答的 E2E P95**：比如不超过 5 秒。它主要由 TTFT 加 decode 决定。
- **多步任务的 E2E P95**：比如不超过 90 秒。它主要由 prefill 累加、工具耗时、循环次数决定。

为什么不能只定一条？因为两者的组成完全不同。拿 5 秒去卡多步任务，它永远超标，这个目标不现实。拿 90 秒去卡单轮问答，它永远达标，这个目标没意义。**一条 SLO 用在两种形态上，只会得到「怎么都对」或「怎么都错」。** SLO 就是服务等级目标，也就是「这个指标不许差过某条线」。

基线定完，最后一条纪律说的是这张表该在什么时候看。

它不是在任务**进行时**用的。你不需要实时盯着它。它是在**下次有人问「为什么慢了」**时用的：

- 打开最近一批 trace，跑一遍 `budget_table()`；
- 看占比排序，和上次比，哪一格涨了；
- 那一格就是答案。

所以它该被存下来、被比较，而不是每次重新摸一遍。12.1 的 trace 库让这件事变便宜。`budget_table()` 是一次查询，不是一次考古。

## 这一节的边界

- **没有做实时告警。** 「某一格持续超标就报警」是第 13 章和运维的事。
- **没有做端到端自动优化。** 从「哪一格亮红灯」到「改哪行代码」，仍然是人的判断。
- **没有覆盖外部依赖的延迟。** 网络、第三方 API 的抖动不在本节口径里，它们要单独量。

到这儿，这一章把「看得见」做完了：轨迹、成本、延迟，三样都查得到。但还有一半没算——**用户那一侧的观测**。
