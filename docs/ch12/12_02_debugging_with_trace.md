# 12.2 用 trace 排查一个真实 bug

## 12.2.1 它说做完了，结果不对

上一节把记录仪装上了。装上不是为了好看，是为了出事那天能回放。

先看清一个最常见的麻烦：真实的失败很少是程序当场崩掉。崩掉反而好办——屏幕上有红字报错，程序收工时报一个非零的退出码，比如 `exit 1`。退出码就是程序结束时交给系统的一个数字。0 表示一切正常，别的数字表示出了事。

难办的是另一种：**它做完了，看起来对，其实少了一半。**

这种失败长什么样？下面这条指令，你大概率真下过。代码里的 TODO 是一种标记，表示这里还有事没做完。

```text
你> 把这个仓库里所有的 TODO 注释整理成一张表，标上文件和行号。
```

它跑了一会儿，给你一张表：**12 条。** 挺整齐，格式也对。

你随手翻了两个源文件——光这两个里就有 5 个 TODO。你数了数全仓库，**37 个。**

你没报错可看，没有失败的退出码，也没有任何一条线索。手上只有一张「看着挺合理」的表。

## 12.2.2 顺着树往下看

「看着挺合理」的东西没法查。要查，得先有一个能逐段对着看的东西。12.1 拼好的那棵树，就是干这个用的。打开它，长这样：

```text
turn 整理 TODO ........................ 32.4s
├─ llm gpt-4o ......................... 3.1s   in 4.2k / out 210
│  └─ tool search_code ............... 0.18s   args {"pattern": "TODO"}
├─ llm gpt-4o ......................... 6.8s   in 5.1k / out 640
│  ├─ tool fs_read src/a.py .......... 0.02s
│  └─ tool fs_read src/b.py .......... 0.02s
└─ llm gpt-4o ......................... 4.9s   in 6.9k / out 1180  → 输出那张表
```

先认清这棵树的三层。最外面的 `turn` 是这一轮任务。中间的 `llm` 是每一次模型调用。最里面的 `tool` 是每一次工具执行。右边是耗时和用量。`in` 是这一次送进去多少 token，`out` 是模型写出来多少。`args` 是调用工具时填的参数。

两处立刻不对劲：

- **第一个 `search_code` 只用了 0.18 秒、返回 12 条。** 一个扫全仓库的搜索不该这么快——除非它根本没扫全。
- **第二次 `llm` 调用里，模型自己去读了两个文件。** 它在**手动补**：发现搜索结果太少，就猜了几个可能藏着 TODO 的文件去翻。

第二个信号很关键，也最容易漏。**模型的「补救动作」，是它自己知道信息不足的证据。** 一条健康的 trace 是「搜索 → 汇总」。这一条是「搜索 → 不够 → 猜文件 → 再猜」。**它绕着走了**，最后那张表就是在绕路里凑出来的。

## 12.2.3 问题出在参数上

绕路是症状。症状让你定位到某一段，病因却还在更里面。把第一个 `tool` 节点的参数展开：

```json
{"pattern": "TODO", "limit": 12}
```

问题在这。`search_code` 的实现里，`limit` 的默认值是 **12**。`limit` 就是「最多给几条」。这是当初写代码时为了防大输出随手设的，7.2 讲过为什么要防大输出。模型从来没传过这个参数，因为它**不知道有这个参数**。工具的 description 里一个字都没提。description 就是工具的说明书。模型看不到代码，只能照这份说明书来用。

于是链条是这样的：

1. 工具默认只返回前 12 条。
2. 工具描述没告诉模型「默认有上限」。4.2 那条「什么时候不该用它」被漏掉了。
3. 模型拿到 12 条，隐约觉得少，但**没有任何硬信号告诉它「你被截断了」**。7.2 说过：截断必须显式告知。硬信号就是程序能直接判出来的信号，不靠感觉去猜。
4. 它靠猜文件来补。补到的当然不全。

**修复有两条，第二条才是根因：**

- 把默认 `limit` 提到足够大，或者干脆默认全量。
- **在返回结果里把截断说出来**：`{"hits": 12, "truncated": true, "total_if_unlimited": 37}`。三个字段分别是「命中几条」「有没有被截断」「不限量的话一共有几条」。只要模型看得见这几个字段，它就知道要追问。

改完重跑，37 条。

## 12.2.4 看清失败是什么样

病修好了，回头看看这次排查花了多少力气。你没翻几百行日志，没加 `print`（插一句打印语句，看它到底跑成了什么样），没重跑五次。你只做了一件事——**把失败展开成一条路径，然后看哪一段不对劲。**

这就是 trace 相对「一条报错信息」的全部价值。报错是一个**点**，trace 把这个点还原成**线**。而线的形状本身就告诉你哪出了问题。「搜索 0.18 秒」这个形状不对，「模型去猜文件」这个形状更不对。

顺带一条纪律：**修完之后，`truncated` 必须留在 trace 里。** 它是这个案例里最值钱的信息。下次再撞上同类问题，你希望第一眼看到的就是它，而不是再排查四十分钟。

## 12.2.5 失败分五类

树上的毛病修完了。可你手上还只是一次具体的事故。下次换一种坏法，这套办法又得从头摸一遍。要能反复用，得把失败分成几类。

先问：上面这个案例属于哪一类？答案不是「搜索坏了」——**搜索没坏，它忠实地执行了默认值。** 真正的毛病是「工具的约定没写清，截断也没说」。

要系统地归因，先得有这份名单。归因就是找出「哪一步、因为什么」失败的。全书到这里，反复出现的失败可以归成五类：

| 类别 | 特征 | 修法在哪 |
| --- | --- | --- |
| **工具失败** `tool_error` | 工具报错、超时、返回码非 0 | 改工具本身（第 7 章） |
| **检索失败** `retrieval` | 检索跑了但空手而归、或被截断、或明显不相关 | 改检索策略（第 8 章） |
| **推理错误** `reasoning` | 工具都对、信息都全，**判断错了** | 改提示、改模型、改路由（12.4） |
| **上下文丢失** `context_lost` | 信息曾经在上下文里，后来被压缩吃掉了 | 改压缩策略（第 6 章） |
| **权限拒绝** `permission` | 审批被拒、`guard` 挡下 | 改审批策略（第 11、15 章） |

分这五类有一条共同依据：**它们各自指向一个不同的修法。** 如果两类失败指向同一个修法，它们就该是一类。**分类不是为了整齐，是为了让每一类后面都挂着一个动作。**

回到这次事故：按这张表的口径，它落在 `retrieval` 那一格。工具没坏，是检索被截断了。

## 12.2.6 用固定规则分类

五类定好了，还剩一个问题：谁来打这个标签？

这里再兑现一次全书那条线索：**把判断从模型手里拿走。**

```python
# harnex/observability/diagnose.py —— 用规则给一次失败归因：把「感觉」换成「哪一类」
# 只用标准库，不用 pip 装。
def classify_failure(trace):
    """返回五类之一。规则是启发式的（按现象猜），但一个错的分类也好过没有分类。"""
    denied = False
    tool_error = False
    lost_context = False
    truncated = False
    for node in trace["index"].values():
        status = node["status"]
        if status == "denied":
            denied = True                        # 有人挡了一下
        if node["node"] == "tool" and status == "error":
            tool_error = True                    # 工具自己报的错
        if node["node"] == "compact" and node.get("lost_used_info"):
            lost_context = True                  # 压缩吃掉了还要用的东西
        if node["node"] == "tool" and node.get("truncated"):
            truncated = True                     # 检索被截断或空手而归
    # 顺序就是优先级：一次失败同时像两类时，先报靠前的那一类
    if denied:
        return "permission"
    if tool_error:
        return "tool_error"
    if lost_context:
        return "context_lost"
    if truncated:
        return "retrieval"
    return "reasoning"                           # 其余：工具都对，判断错了
```

把 12.1 那棵树传进去，返回的是一个字符串，比如 `retrieval`。

顺序不是随意的：**从最硬的信号往下排**。`denied` 和 `error` 是确定的。`lost_used_info` 和 `truncated` 要读字段。落到最后的 `reasoning` 是「把确定性的都排除了，剩下就是它」。

函数抬头那句说明里写着，这些规则是**启发式**的。启发式就是「按经验定的规矩」，不是严格推出来的，所以不一定对。

为什么不用模型来分类？两个理由：

- **它也是模型，也可能判错**（9.3 那条）。而这里的规则是确定的、可复现的、能写进测试的。
- **分类是要被大批量跑的**（10.6 那种 100 次跑批，跑批就是把同一批任务反复跑）。第 13 章的回归也一样，改完要拿老题重跑一遍。给每一次失败都调一次模型，这笔成本本身就破坏了「省钱的初衷」。

规则会误判。一个 `reasoning` 可能其实是伪装得很好的 `retrieval`。但**一个会误判的分类，好过一个没有分类的「变差了」**。前者能让你去看五格里最像的那一格，后者只能让你重新感受一遍。

分类这件事，到这里本来可以收尾了。但还有个更基本的问题没回答：这份力气为什么值得花。

**为什么非得分类。** 因为「感觉变差了」永远修不好。它既不能定位，也不能设阈值，还不能判断改动有没有效。阈值就是一条线，超过就报警。

一旦分成五类，三件事立刻变成可能：

- **能数。** 比如这个月 `reasoning` 类 9 次、`retrieval` 类 14 次。数字摆出来就能比。
- **能设阈值。** 「`retrieval` 失败率超过 5% 就报警」——阈值需要一个分母和一个类别。分母就是一共跑了多少次。
- **能验改动。** 改了检索策略，重跑跑批，看 `retrieval` 那一类的计数有没有真的下降。这就是 10.6 的做法。

第 13 章的评测体系、10.6 的成功率跑批，还有将来的告警规则，**喂给它们的都是这五类**。所以这一节看着是在「修一个 TODO 的 bug」。其实它是在**给整条观测链定义最小可用的词汇表**。

## 这一节的边界

- **分类是启发式，会错。** 上面说了——它给的是一个起点，不是一个判决。
- **只覆盖「任务失败」这一层。** 一次任务可能同时出现两类失败（检索截断 + 推理跑偏）。本节只取最硬的那个信号；多标签归因留到第 13 章。多标签就是一次打上两个以上的类别。
- **没有自动修复。** 本节只到「知道是哪一类」，从类别到改哪一行仍然是人做的决定。

有了分类，接下来把它变成钱：同样的 token，花在哪一类任务、哪一类技能上。
