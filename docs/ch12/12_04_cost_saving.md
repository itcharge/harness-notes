# 12.4 省钱三板斧

## 12.4.1 先做哪一件

上一节把账算清了：钱花在哪、月底大概多少。下一步就是把油钱压下来。

能下手的地方有三处，这本书叫它们三招。**模型分级路由**（routing），按活的难易给每一步挑模型。**缓存**，算过一遍的不重算。**prompt 瘦身**，把每轮发出去的话写短。

三招都能省钱，代价却不一样。路由会误伤，把难活派给了不够强的模型。缓存配错，会把别人的对话混进来。瘦身几乎没风险。所以排序不能只看省多少——**不按技术含量，按「省得多」乘「风险低」**。省多少、风险，两个都要看，所以相乘。

| 做法 | 省多少 | 风险 | 动手成本 |
| --- | --- | --- | --- |
| 模型分级路由 | 最多 | 中高（有误伤） | 中 |
| 缓存 | 多 | 中（配错会串味） | 低 |
| prompt 瘦身 | 中 | 低（几乎无副作用） | 低 |

**注意第三行：最安全的一招反而排最后。** 这一行是 **prompt 瘦身**。prompt 就是提示词，每轮发给模型的那段话。它省得最少、见效最慢，但唯一没有副作用。所以它是前两招之后一直要做的日常。

## 12.4.2 简单任务用便宜模型

### 判据不是「任务重不重要」

「这个任务重不重要」听着像标准，其实没法执行。

能执行的是另一个问法：**这一步需不需要那么强的模型？**

按强弱分三档就够：`small` / `mid` / `frontier`，从最便宜排到最贵。最上面那档是前沿模型，最强也最贵。

按这个问法过一遍，大部分步骤的答案都是「不需要」。占多数的是**格式转换、信息提取、分类、简单编辑**——答案明确，只把内容搬来搬去。真正需要前沿模型的，是**决定下一步做什么、在几种可能里挑一个**的那些步骤。

```python
# harnex/llm/routing.py —— 三档 tier 映射到模型 id：模型名只出现在配置里
# 只用标准库，不用 pip 装。
TIERS = {"small": "gpt-4o-mini", "mid": "gpt-4o", "frontier": "gpt-4o"}


def pick_tier(step):
    """决定这一步用哪一档。从便宜往贵排，先匹配先返回。"""
    kind = step["kind"]
    if kind in ("classify", "extract", "format"):
        return "small"                       # 结构化的小活，小模型够用
    if step["input_tokens"] > 20000:         # 两万 token 以上算长输入
        return "small"                       # 长文档摘要：长不等于难
    if step["needs_multi_step"]:
        return "frontier"
    return "mid"
```

两个决定值得停下：

- **`TIERS` 是配置，不是硬编码。** 硬编码就是把模型名直接写死在代码里。上层只说「这一步要 `frontier`」，从不说「用 gpt-4o」。明年换模型，改一行 `TIERS`，不是改十处调用。
- **`input_tokens > 20_000` 给 `small`。** `input_tokens` 是这一步送进去多少 token。这条反直觉，但有依据：**长不等于难**。把一份长文档缩成三句话，是信息压缩，小模型做得不差。

### 风险：路由误伤，而且你不一定看得见

路由最大的风险，一句话说完：**把难任务分给了小模型，错误率悄悄上升，而没人察觉。**

它为什么「悄悄」？因为小模型不报错。它不崩，也不会说「我不行」。它只给你一个 **看着对、其实错** 的结果——就是 12.2 那种最难查的失败。所以有一条配套不能省：

> **路由决策必须进 trace。**

```python
# run_turn() 里挑完档位后，顺手把这次决策也写进日志：
log.append({"kind": "routing",
            "span_id": llm_id,          # 挂在这次 llm 调用上
            "tier": tier,               # 选了哪一档
            "model": TIERS[tier],       # 实际用哪个模型
            "why": reason})             # 为什么这么选，如 "kind=extract"
```

进了 trace，第 13 章的评测就能把「tier」（档）和「成功率」摆在一起看。这时你能真的回答「小模型把哪一类任务拉低了」，而不是笼统地感觉「最近差点意思」。

对付误伤的正解是：**不是不许误伤，是不许不知情地误伤。**

### 兜底与参照

第二件配套是 **升级路径**：结果过不了校验，就升一档重来。10.2 的 `validate()` 是现成的判据，它照一份字段清单核对返回，对不上就返回一串错误。

这条路叫级联（cascade）：先让便宜的试，不行再往上换。它比「一次路由到位」安全，因为失手还有第二次机会。

但要接回 9.3 那条：**升级要有次数上限。**「小的失败升中的、中的升大的、大的再回去问小的」，这是打转的另一种写法。现实里的配置是：**最多升一档，升一次不过就按失败处理**。

公开的实测里有两个数。**RouteLLM**（LMSYS，2024-07）在 MT Bench 上用 95% 的 GPT-4 质量，换来**最多 85% 的成本下降**。**FrugalGPT**（Stanford，2023）用级联，声称最多降 98%。MT Bench 是一份公开的模型考卷，benchmark 就是这类考卷。

但这两个数都是在自家考卷上跑出来的。**你能省多少只能自己测**：加路由前后各跑一轮跑批，看成本与成功率两条曲线。跑批就是把同一批任务反复跑（10.6）。

## 12.4.3 能复用的结果先存着

### prompt 缓存：11.1 讲过一半，这里讲钱

11.1 讲缓存，为的是降 TTFT，也就是按下回车到冒出第一个字那段时间。同一件事还有另一半：**它也省钱。**

机制 11.1 说过：上一轮和这一轮的**开头一个字节都不差**，服务端就不重算那一段。用上了叫命中，被复用的开头那一段叫前缀。

下面是几个计费事实，以 OpenAI 2024-10-01 上线的自动缓存为例。计价按 token 算，token 是模型算长度、也算钱的单位（12.3 讲过）。

| 事实 | 数值 |
| --- | --- |
| 生效门槛 | 提示超过 **1024 token** 自动开启，无需改代码 |
| 命中折扣 | 缓存命中的输入 token **打 5 折**（输出不变价） |
| 最小粒度 | 从 1024 起，按 **128 token** 递增 |
| 缓存寿命 | 无活动 **5–10 分钟**后清除，最长保留 1 小时 |
| 附带效果 | 长提示的 TTFT 最多降 **80%** |

**注意「无需改代码」。** 缓存不是你「上线」的功能：要么白拿，要么白白错过。错过的方式很具体——把每次都不一样的内容放进前缀。前缀一变，整段作废。

### 缓存失效灾难：串味

错误模式指一类反复出现的错法，其中就有那条：**把用户相关内容加进缓存前缀，所有会话串味。**

串味指**甲的上下文出现在乙的回答里**。同事 A 刚问完项目预算，同事 B 一开口就听见「预算 30 万」。

它比「没命中」严重得多：没命中只是少省点钱，串味是把别人的话端给了你。分界线很清楚：

| 属于前缀（所有人一样，可缓存） | 不属于前缀（每个会话不同） |
| --- | --- |
| 系统提示、行为规范 | 用户这轮说的话 |
| 技能清单与工具定义（第 5 章） | 本会话的历史 |
| 固定的 few-shot 示例 | 待办清单（第 9 章） |
| —— | 任何结果、任何时间戳 |

表里那个 few-shot 示例，就是给模型看的几个样例题，让它照着格式答。

**判据一句话：这一段的字节，在下一次请求里还会一模一样吗？** 会，就往前放；不会，就往后放。11.1 那条规矩是「前缀里不能夹时间戳」。这里多了第二个理由。它不只毁性能，还毁隔离。隔离就是各用各的。

### 技能结果短时缓存：只缓存该缓存的

第三种缓存最小：同一工具、同样参数调了两次以上，第二次直接返回第一次的结果。

```python
# harnex/tools/cache.py —— 工具结果短时缓存：只缓存幂等的、不随时间变的调用
# 只用标准库（hashlib / json），不用 pip 装。
import hashlib
import json


def cache_key(tool, args):
    """参数要排序后再序列化，否则键序不同会算成两次调用。"""
    blob = json.dumps(args, sort_keys=True, ensure_ascii=False)
    digest = hashlib.sha256(blob.encode()).hexdigest()
    short = digest[:16]                  # 16 位够用，键短一点好看
    return tool + ":" + short
```

注意那句备注：参数要**排序后**再序列化（把参数变成一串字符）。不排序的话，参数顺序一变，同一份参数就算成两次调用。

但有一条硬边界，写错即灾难：**能缓存的是 `fs_read`、`search_code` 这类同样参数短时间内结果不变的；绝不能缓存的是 `run_command`（`git status` 两次可以不同）、任何有副作用的调用、任何带时间的查询。** 副作用就是这个动作会改动外面的世界，比如写文件、提交代码。

判据是 10.3 那条的同款：**只缓存幂等的、结果不随时间变的调用。** 幂等的意思是，同一个动作做一次和做十次，结果一样。缓存一个不幂等的调用，等于让「第二次」执行了「第一次」的结果，比没有缓存危险得多。

## 12.4.4 把提示词写短

第三招最朴素，也最没有副作用。前两招都有误伤风险，这一招是纯赚。所以它该最后做，并且长期做：**前两招是「项目」，这一招是「日常」。**

三处：

- **系统提示审计。** 系统提示就是每轮固定发给模型的总要求。把它原样打印，逐段问：**「删掉它，模型会变差吗？」** 经验是，一半以上是「历史遗留 + 重复强调」——同一件事用三种说法讲了三遍。
- **技能描述精简。** 第 5 章定了 `description` 上限 1024 字符。`description` 是技能的说明书，模型看不到代码，只能照它决定用不用。但「能到 1024」不等于「该到 1024」。清单里每个技能都写满，加总就是每轮几百 token。每次调用还要重新 prefill，把这批内容重读一遍，11.1 算过这笔账。
- **历史压缩回看。** 第 6 章的压缩会生成摘要。定期问：**「这条摘要现在还有用吗？」** 一条三天前的摘要，如果后面再没被引用过，它就在吃钱。

## 12.4.5 每做一件就再测一遍

三招的落地方式，和 10.6 那条完全一致。**每加一招，把跑批重跑一次。同时看两条曲线：成本，和成功率。**

只降成本不看成功率，是把「省钱」做成了「换钱」。花更少的钱得到更差的结果，然后在下个月的用户流失里还回去。**两条曲线一起往好的方向走，才叫优化。**

## 这一节的边界

- **没有做语义缓存**——语义缓存按意思匹配，问法不同、意思一样也算命中。它省得更多，但准确与隔离更难保证，容易踩串味。
- **没有做批处理折扣**——攒一批请求一起算，厂商给更低的单价。但它和「实时 Agent」的形态冲突，用户等不了。
- **没有做微调**。微调是拿自己的数据再训一个小模型。用它替代分级路由是另一条路，成本结构完全不同。

钱和 token 都管住了。下一节管第三样：**时间**。
