# 9.1 长任务的三种失控方式

## 9.1.1 短任务为什么不容易坏

前面几章，Harnex 接的都是「一句话任务」。Harnex 是一个 Agent，也就是一个能自己决定下一步做什么的程序。真正做决定的是里面的模型，那个能读会写的 AI。它干活一轮一轮来：看一眼当前的情况，决定做一个动作，拿到结果，再看一眼。做一个动作就是调一次工具，读文件、跑命令都算。

它每一轮眼前那些东西，叫上下文（context）。你的话、它自己说过的话、工具返回的结果，都堆在里面。模型做判断只看这一堆，别处它看不见。

短任务有一个共同的好处：**目标就在最近一条消息里。**

> 把 src/uploader.py 里的重试次数从 0 改成 3，然后跑一下测试。

它往下翻几条消息就能看见这句话，不需要「记住」任何东西。目标是摆在眼前的，不是记在脑子里的。

长任务不是这样。

> 帮我把项目里所有没用到的依赖找出来，清理掉，然后确保测试还能过。

依赖（dependency）就是项目借来用的外部代码包。光第一步「找出没用到的依赖」就不轻松。它得先知道依赖清单在哪、测试怎么跑。还得知道哪些包是运行到一半才加载的。十几轮、十几次工具调用跑不掉。**可目标只是开头那一句话，第三轮之后就被十几条工具结果压在了底下。**

「长任务」没有一条精确的轮数线。但有个好用的判断办法：**这句话，下一轮还要不要拿出来对照？** 短任务的目标用完就扔，测试一绿，这句话就作废。长任务的目标要在几十轮里反复拿出来看。**只要一个目标要被反复引用，它就有被埋掉的风险。**

拿开车比一下。短任务像下楼买瓶酱油，目标只有「楼下那家店」，走两步就到。长任务是开两天的长途，目的地一次都没变，可路上要过几十个路口，还要应付修路和绕行。你得把目的地一直摆在眼前，不能靠「我记得」。

这一节先把这类任务会怎么坏讲清楚。三种坏法，都能在第 6 章的会话日志里一条一条读出来。会话日志就是它每做一步都追加一条记录的文件，事后能回放。

## 9.1.2 走偏

先看一条真实的轨迹，也就是它从头到尾每一步的记录。最左边是第几轮。中间是谁在说话：`user_message` 是你。`assistant` 是模型。`tool_result` 是工具交回的结果。右边是内容。`fs_read` 是读文件的工具，`apply_patch` 是改文件的工具。

```text
T0   user_message     「给 README 加一段安装说明」
T1   assistant        fs_read(path="README.md")
T2   tool_result      README 全文（88 行）
T3   assistant        fs_read(path="package.json")        ← 只想确认包名
T4   tool_result      package.json 全文
T5   assistant        fs_read(path=".npmrc")
T6   tool_result      错误：'.npmrc' 不存在
T7   assistant        fs_read(path=".")
T8   tool_result      目录列表（31 项）
T9   assistant        fs_read(path="scripts/build.sh")
T10  tool_result      构建脚本
...
T18  assistant        apply_patch(path="scripts/build.sh", old=..., new=...)   ← 在改构建脚本
```

用户要的只是给 README 加一段说明。模型第 3 轮只想确认包名。第 5 轮发现 `.npmrc` 不存在。第 9 轮开始看构建脚本。第 18 轮已经在改 `scripts/build.sh` 了。

**每一步单看都合理，连起来跟原始目标毫无关系。** 这是走偏最迷惑人的地方。它不是拐了一个大弯，是连着拐了十几个小弯。

## 9.1.3 来回打转

走偏是目标一点点漂走。还有一种是原地踏步：它连漂都不漂，就在同一个地方转圈。

```text
T4   assistant        fs_read(path="config/app.yaml")
T5   tool_result      配置全文
T6   assistant        shell(command="pytest -q")
T7   tool_result      命令失败（exit 1）…2 failed…
T8   assistant        fs_read(path="config/app.yaml")     ← 和 T4 一模一样
T9   tool_result      配置全文（和 T5 一样）
T10  assistant        shell(command="pytest -q")          ← 和 T6 一模一样
T11  tool_result      命令失败（exit 1）…2 failed…
T12  assistant        fs_read(path="config/app.yaml")     ← 第三遍
```

`shell` 是跑命令的工具。命令跑完会交回一个数字，叫退出码，0 表示成功，别的数字表示失败。`exit 1` 就是失败。

同样两个动作，来回三遍。每一轮它都在「看一眼当前状态」。可它没记下「上一轮我看过了，结果是这样」。

这些结果确实躺在它的上下文里。工具返回的东西一条接一条堆着，可「这是新信息」和「这是我刚看过的」长得一模一样。**手里没有一张进度表，它就分不清新的和旧的。**

## 9.1.4 假装做完了

```text
T11  assistant        shell(command="pytest -q")
T12  tool_result      命令失败（exit 1）…1 failed, 3 passed…
T13  assistant        「已清理未使用的依赖，并确认测试全部通过。」
```

这是三种里最危险的一种。

注意一个细节：它没读错工具结果。T12 就摆在它眼前。日志里记着这条事件，说明那一轮它确实收到了。问题出在收尾：**它把「我做了这件事」和「这件事做成了」说成了同一句话。**

第 7 章 7.5 节讲过这个机制：模型收尾时要给一个结论。它手里最顺手的材料是自己的话，不是三轮前那个退出码。**长任务把这个坑放大了**——中间隔了十几轮，那条信息离得更远。

## 9.1.5 三种坏法是同一个原因

把三条轨迹叠在一起看：

- **走偏** = 目标丢了
- **打转** = 进度丢了（不知道自己做到哪）
- **假完成** = 验收丢了（没有「做成了没」的判据）

丢的东西不一样，根子是同一个。问题出在 harness 上。harness 就是包在模型外面的那层程序。模型负责决定，它负责真的去做，也负责把每一步记下来。**它每一轮只盯着「当前上下文」重新决定下一步。** 而目标、进度、验收这三样，恰好都不在「当前上下文」里。

## 9.1.6 三种坏法，麻烦在哪

麻烦程度，取决于**你什么时候发现它**。

| 坏法  | 什么时候暴露        | 代价                      |
| --- | ------------- | ----------------------- |
| 走偏  | 结果不对时         | 白做了一段时间；成果本身是好的，只是不是你要的 |
| 打转  | 看着终端时         | 和走偏差不多，而且重复调用一直在烧时间和钱   |
| 假完成 | **你依赖它的结论之后** | 前面所有推断作废，而且你不知道该往回退到哪一步 |

走偏和打转都是 **看得见** 的。你盯着屏幕，能看见它在改一个八竿子打不着的文件，或者第三次读同一个配置。假完成不一样。它最后一条消息干净、自信、有结论。**等你下次用它的时候，才知道那结论是空的。**

而且三种坏法会互相喂大。走偏之后目标更模糊，更分不清哪条结果是新的，打转就容易发生。打转耗掉的轮数越多，离目标越远，收尾时越想说一句「已完成」了事。**它们不是三个独立的小毛病，是同一件事在三个阶段的不同样子。**

## 9.1.7 不是「忘了」，是「看不见了」

有个常见说法要改一改。模型不是「忘了」。「忘」意味着它曾经记得、后来丢了。

要查这件事，得先知道一条规矩，书里叫不变式：程序跑到哪一步，它都必须成立。第 6 章立了两条。第一条叫「模型可见即已记录」。意思是：它这一轮能看见的东西，日志里一定有。`seq` 是每条日志事件的序号。从头读一遍那一轮的 `seq`，能看见「把所有没用到的依赖找出来」还写在里面。**它没丢，只是被压在了下面。**

## 9.1.8 加一句提醒，管三轮

那在系统提示里写一句「请注意，你的原始目标是……不要偏离」，行不行？系统提示就是每一轮都摆在最前面的那段话，告诉它「你是谁、该怎么干活」。

管三轮。原因还是那个：叮嘱也是一段文字，也会被后来的工具结果一层层盖住。而且它每轮长得都一样，看几遍就成了背景噪音。

要一直管用，得满足两个条件：**每一轮都在眼前；说的是事实，不是要求。** 按这两条筛一遍，需要常驻的就三样：

- 目标：一句写死的任务描述（常量，改不了，也占不了几个字）
- 进度：一张会变的状态表——**做到第几项了、还剩什么**
- 验收：每一项的完成标准，加上最近一次检查的结论

三样凑齐，就是一张 **待办清单**。下一节就做它。

做法上有个关键选择。清单不能是程序内存里的一个变量，得和第 6 章的会话日志站在同一边。

回头看，这三条轨迹摆得这么整齐，靠的不是我读了模型的思考过程。靠的是 **每一步都留下了一条日志事件**。

这是第 6 章那两条不变式第一次收到回报。正因为「模型可见即已记录」，我们才能说清它每一轮眼前到底有什么。放在长任务上，这条性质更值钱。**一个跑了 30 轮的任务，你唯一能重建现场的方式就是日志。**
