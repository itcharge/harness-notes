# 9.3 自我反思与中途修正

## 9.3.1 谁来宣布做完

9.2 留下的清单有一个洞。`update_todo(status="done")` 是模型自己调的。**它可以在事情没做成的时候调它**——9.1 那个假完成就是这么发生的。

第 7 章 7.5 节讲过机制：模型要做的事是「给一个结论」。只要没人逼它回头看证据，它就会拿自己说的话当证据。

所以每一项做完，要插一道 **独立的检查**。检查拿这一项声明的 `done_when`，去比对刚才那些工具调用的实际返回。「独立」指的是不采信模型自己的说法，只采信工具交回的东西。

这道检查有两个硬要求：

1. **输入是工具的返回原文**，不是模型的复述。拿复述去核对，等于让它自己给自己打分。
2. **产出是一句结构化的结论**，不是自由发挥。结构化就是按固定几个字段写：成没成、为什么、下一步怎么办。自由发挥的话，程序没法照着它分岔。分岔就是按结论选不同的下一步。

第 2 章的结构化输出在这里第二次派上用场——第一次是 9.2 的规划。

## 9.3.2 自检：拿证据对标准

这道检查写出来就是一个函数。给它子任务、完成标准、工具返回，它回一句结论。

```python
# harnex/planning/reflect.py —— 自检：拿完成标准比对工具结果，输出结构化结论
import json

PROMPT = """你是执行者，不是评委。只根据下面给出的【工具实际返回】判断这一步是否达成目标。

子任务：{task}
完成标准：{done_when}

【工具实际返回】
{evidence}

只输出 JSON：
{{"ok": true 或 false,
  "why": "一句话说明判断依据",
  "action": "continue" 或 "retry" 或 "replan" 或 "abort"}}

规则：
- 证据里没有的东西，一律视为没做到。
- 不确定就填 ok=false、action=retry，不要猜。"""


def _to_text(prompt: str) -> str:
    """把 prompt 交给模型，只取文本——复用第 3 章的 chat()。"""
    return chat([{"role": "user", "content": prompt}]).content


def reflect(task: str, done_when: str, evidence: str) -> dict:
    """一次模型调用，返回 {"ok","why","action"}；解析失败时保守地判为未通过。"""
    reply = _to_text(PROMPT.format(task=task, done_when=done_when,
                                   evidence=evidence[:4000]))
    try:
        parsed = json.loads(reply)
        if not isinstance(parsed, dict):
            raise ValueError("返回的不是一个对象")
        if parsed.get("action") not in ("continue", "retry", "replan", "abort"):
            raise ValueError("action 非法")
        return {"ok": bool(parsed["ok"]),
                "why": str(parsed.get("why", "")),
                "action": parsed["action"]}
    except (ValueError, KeyError, json.JSONDecodeError):
        return {"ok": False, "why": "自检结果无法解析，按未通过处理", "action": "retry"}
```

三处值得多说一句：

- **`evidence[:4000]` 截断。** `[:4000]` 的意思是只取前四千个字符。自检是往上下文里再塞一份工具结果，不设上限会和 6.2 那张预算表打架。上下文就是这一轮摆在模型眼前的那堆内容。四千字符足够判断「文件建了没、测试过了没」。
- **提示里写「你是执行者，不是评委」。** 这句是防和稀泥，也就是防它给出一个含糊、谁都不得罪的结论。评委习惯给个印象分（「基本完成」），执行者只认「这一步到底成没成」。把它按在证据上，结论才硬。
- **解析失败时返回 `ok=false`。** 解析失败有两种。回复根本不是 JSON，或者能解析、但不是一个对象（比如以方括号开头的列表）。两种都按「没通过」处理。代码里因此先查一句 `isinstance(parsed, dict)`。**宁可多跑一轮，也不要放过一个假完成。**

## 9.3.3 证据从哪一段算起

`reflect()` 的第三个参数是一段文本。哪几条工具返回该塞进去？

最省事的做法是「这一项开始以来所有的工具返回」。听着对，其实有两个毛病。第 5 项自检时还会看见第 1 项的结果，越往后干扰越多。而且一超过四千字符就被截断，真正相关的那几条反倒被挤掉。

所以得划一条起点：**从这一项被标成 `doing` 那一条 `todo_update` 开始，往后所有的 `tool_result`。** 翻日志时从后往前找，撞见第一条「把这一项标成 doing」的事件就停。

模型要是没标 doing 就直接标 done（这种事常有），那就退一步。用「这段任务至今的全部工具返回」，靠四千字符兜住。

## 9.3.4 接进主循环

这套检查插在哪？一句话：**卡在「标 done」落盘之前。** 落盘就是把状态写进日志，写进去就作数了。

```text
模型调 update_todo(index=3, status="done")
  → 先别动清单，把这一项拦下来
  → 取第 3 项标 doing 之后的全部工具返回，跑一次 reflect()
  → ok=true  ：放行，写 done
  → ok=false ：打回 failed，把 why 写进备注，让模型重来
  → 预算用完：abort，交出报告
```

位置不能挪。**落盘之后再检查，清单上已经写着「已完成」，模型下一轮看见的就是「我做完了」。** 假完成不但没治住，还多了一条日志替它作证。

## 9.3.5 重试、改计划、放弃

`action` 的四个值里，`continue` 之外的三个都是「没成」的处理：

- `retry`：换参数，同一方法再来一次（换路径、加 `--force`、缩小范围）
- `replan`：换方法，或者承认这一项拆错了，回去改清单
- `abort`：停下，如实报告

关键在最后一条。**会放弃的 Agent 才可信。**

理由不是道德，是算术。同一次失败，两条路各要付什么：

| 处理方式 | 你当下付出 | 你后来付出 |
| --- | --- | --- |
| 诚实放弃（abort） | 读一段「第 3 步失败，试过 A 和 B，都卡在 X」 | 接手，五分钟后解决 |
| 假完成 | 什么都不用做，看起来一切顺利 | 三小时后发现结论是错的，前面所有推断作废 |

**假完成的成本不是「多花了时间」，是「你踩着一个错的前提继续干活」。** abort 的成本只是被打断一次。所以一个死活不放弃的 Agent 不是更努力，是**把失败推迟到了你发现之前**。

开长途也是这个理。半路抛锚，靠边停下说清楚，比硬说「到了」省事得多。

但重试不能没有上限。给三个数（经验值，可以按任务调）：

```python
# harnex/planning/reflect.py（续）—— 重试预算：把「再试一次」变成有数的东西
MAX_SAME_METHOD = 2     # 同一方法最多重试 2 次
MAX_SWITCH = 1          # 换方法最多 1 次
MAX_REFLECT = 20        # 整段任务的自检总次数上限


class Budget:
    """记每一次尝试，到点就拦。"""

    def __init__(self):
        self.same_method = {}
        self.switches = 0
        self.reflects = 0

    def allow_retry(self, method: str) -> bool:
        self.same_method[method] = self.same_method.get(method, 0) + 1
        return self.same_method[method] <= MAX_SAME_METHOD

    def allow_switch(self) -> bool:
        self.switches += 1
        return self.switches <= MAX_SWITCH

    def allow_reflect(self) -> bool:
        self.reflects += 1
        return self.reflects <= MAX_REFLECT
```

为什么同一方法要限两次？**两次都没用，第三次大概率也没用。** 失败的原因往往不在参数细节上，而是方法选错了。限次数真正的作用是**逼它换方法**，不是省调用。

## 9.3.6 放弃时要说清楚

`abort` 不是一句「任务失败」。它要交出三样东西，让人觉得「接着做」是有可能的：

```text
任务中止，停在第 4 项「改调用：逐个核对超时与异常写法」。
已完成：第 1 项（调用点清单，14 个文件）、第 2 项（httpx 已装）、第 3 项（import 已全部替换）
卡在哪：14 个文件里有 3 个用了 requests.Session 保持连接池，
        httpx 的等价写法需要显式创建 Client 并管理生命周期，
        改完一处就会破坏另外两处的连接复用，测试直接报连接泄漏。
试过什么：A. 直接替换 import（失败：Session 无对应写法）
          B. 用 httpx.Client() 逐个替换（失败：连接泄漏，2 个用例挂）
          C. 试过装 httpx-aiohttp 适配层（失败：版本不兼容）
```

**「试过什么」这一行是重点。** 没有它，接手的人会把你踩过的坑再踩一遍。这一整段不用多写一行代码。它是 `reflect()` 的 `why` 一条条攒起来的，加上清单里那几条 `failed` 备注。

## 9.3.7 和「动作后验证」怎么分工

这里容易和第 6、7 章那个「动作后验证」混。它们是两层，套着用：

| | 动作后验证（第 7 章） | 自我反思（本节） |
| --- | --- | --- |
| 问的问题 | 这个动作的结果对不对？ | 这一步推进了原目标吗？ |
| 看什么 | 文件在不在、退出码是不是 0、内容改对没有 | 这一项的 `done_when` 达成没有 |
| 管多大 | 一次工具调用 | 一个子任务（可能含好几次调用） |
| 没成怎么办 | 找回正确结果，重做这个动作 | 重试 / 换方法 / 放弃 |
| 谁来判 | 工具返回里带来事实 | 一次专门的自检调用 |

顺序是固定的：**先验证动作，再反思子任务。** 文件都没建成，谈不上这一项做完了。

## 9.3.8 反思也不能保证做对

本节这套东西仍然是「软」的。`reflect()` 的判断也是模型做的，也可能给出一个错的 `ok=true`。它比「模型自己说 done」强在三点。一是看证据，不看复述。二是结论结构化。三是失败默认判否。

但**真正过硬的判据只能来自外部**。判据就是「凭什么说它对」的那条标准。外部指的是这些：跑一遍测试、看渲染结果、第 13 章的评测集、第 19 章每一步截图。

本节能保证的是：**假完成从「必然发生」降到「偶尔发生」。** 而且每次自检都留下一条能查的证据链。剩下的那一部分，是后面几章的活。
