# 9.4 什么才算「规划好了」：可检验性与粒度

## 9.4.1 写得出「怎样算做成」

9.2 的清单里留了一列 `done_when`，意思是「做到什么样算完」。9.3 的自检，就是拿这一列当尺子。这一列怎么写，直接决定整张清单管不管用——**清单的质量，就压在这一列上。**

标准只有一句：**每一项都得能写出一句「怎么知道它成了」。写不出来的，那不是子任务，是愿望。**

差在哪，对照着看：

| 坏 | 好 |
| --- | --- |
| 检查依赖是否正常 | 跑 `npm ls --depth=0`，退出码 0 且输出里没有 `extraneous` 行 |
| 优化一下代码结构 | `pytest -q` 全绿，且改后 `src/parser.py` 的行数小于改前 |
| 看看文档写得好不好 | 列出 README 里每个 `##` 标题，逐个判断它下面有没有一句能独立读懂的开头 |
| 让构建能过 | `npm run build` 退出码 0，且 `dist/` 非空 |

左边四项听着更「专业」，模型却拿它们没办法。右边四项把判断的对象从 **形容词** 换成了 **事实**。而形容词，正是模型最容易自我满足的地方。「优化好了」「写得挺清楚」，全凭它自己一句话。

拿开车打比方，这就是路线单上写什么。「往南边走」不算一项，开出一百公里也没法说自己到了没有。「A 出口下高速」才算，下了就是下了。

右边那几条命令不必逐字读懂。看共同点就够了：每一条都能跑出个结果，成没成一眼看得出来。比如退出码是 0 还是非 0（0 就是成功），用例全过还是有挂的，目录空不空。

注意第三行。不是所有子任务都能变成一条命令。但「列出标题、逐个判断」这件事干得下去，「写得好不好」干不下去。`##` 是 Markdown 里的小标题记号。Markdown 是写文档用的一套简单标记。`##` 打头的那一行就是小标题，有标题可列，就有了能下手的对象。**可检验不等于全自动**，它只要求「有一个能看得见的产出」。

## 9.4.2 细到一个动作

清单几项合适？经验值：**3–7 项。**

- **多于 7 项**：多半是还没拆到「动作」那一层。像「整理所有测试文件」这种条目，本身还得再拆，不该跟别的步骤并排站着。
- **少于 3 项**：这件事大概不需要计划，直接做。为什么，下一小节算这笔账。

「动作」是能直接开工的那一步。「阶段」是还得再拆一层的大块，它自己里面还套着好几步。

怎么分？**看你这一项能不能对应到一两次工具调用，或者一轮以内的思考。** 能，就是动作级。要是这一项自己还要想半天怎么做，那它是阶段，不是动作。

看个反例：

```text
1. 分析项目结构
2. 重构代码
3. 优化性能
4. 完善文档
```

这不是计划，是**主题列表**。四项里没有一项能直接开工，每个主题拆开都能写成一份像样的清单。把它们并排放在一张单子上，只能说明还没拆。

## 9.4.3 小事不必列长计划

上一节说「少于 3 项就别列计划」，是因为规划本身要花时间，而且成本不止一种：

- 多一次模型调用（让模型先写出一张清单）
- 清单每轮都要进上下文（几十到一百多 token，还会分走注意力）
- **它自己也会走偏**——一个错误的计划，能把本来简单的任务带进沟里

所以先问一句：**这件事需要计划吗？** 三条信号指向「需要」：

1. 跨多个文件、或多个系统
2. 步骤之间互相咬着（后一步要用前一步的产出）
3. 中途失败的代价高（发布、迁移、删数据）

三条都不沾（比如「帮我看下这个函数是干嘛的」），直接做。**给单步任务出计划，等于出门买瓶酱油还先画一张全线路线图。**

清单还有一份隐藏收益：**它让任务可以被打断。** 中途停下来，三天后接着做，读一遍清单就知道自己走到哪了。路线单上划掉的那几项，就是做完的。交给别人也一样，每项都写着「做到什么算成」，不用去问原作者。

## 9.4.4 计划可以改

允许改。因为干活时知道的信息，总比规划时多。第 3 步做完才发现依赖是运行到一半才加载的，那第 4 步就该换。

`set_todos` 是整张覆盖的（9.2 的设计）。每回提交的都是新的一整张，不是改一格。模型要重排清单，再调一次就行，没有技术障碍。但要立一条规矩：**改计划要留痕。**

留痕这件事，日志已经替你办了。`todo_update` 是事件，每份快照都落在日志里。剩下要做的是**回头看**。把一份任务里所有 `todo_update` 按 `seq` 排开。这样两种修改一眼就能分开：

- 改动是因为拿到了新信息：第 4 步从「跑测试」改成「先装缺失的依赖」
- 改动是因为忘了原目标：第 4 步从「跑测试」改成「顺便把 CI 配置也整理一下」

第二种就是 9.1 的走偏。它换了个说法，管自己叫「我在更新计划」。**日志里有没有新证据，是这两者的唯一区别。**

## 9.4.5 同一个任务的两种计划

任务：**把项目从 `requests` 迁移到 `httpx`。** 这两个都是发网络请求的库，前者用得久，后者是新一代的替代品。

坏的一版：

```text
1. 找出所有用到 requests 的地方
2. 替换成 httpx
3. 跑测试
```

问题在三处。第 1 项没有完成标准——找到哪些算找全？第 2 项是阶段不是动作。替换要动 import、动调用、动超时参数、动异常类型，每样都可能失败。第 3 项没说「过了算什么」。

好的一版：

```text
1. 找调用点：rg -l "import requests|requests\." 列出全部文件，产出文件清单
   完成标准：清单里的文件数 = rg 统计出的文件数
2. 装依赖：pip install httpx，再确认 pip freeze 里同时出现 httpx
   完成标准：python -c "import httpx" 退出码 0
3. 改 import：对第 1 项清单里每个文件做一次 apply_patch
   完成标准：rg "import requests" 只剩 0 处
4. 改调用：逐个核对超时与异常写法（httpx 的语义与 requests 不同）
   完成标准：rg "requests\." 只剩 0 处
5. 跑测试：pytest -q
   完成标准：退出码 0，且用例数不少于改前
6. 收尾：删掉 requirements.txt 里的 requests 行
   完成标准：pip freeze 里不再有 requests
```

六项，每项都能对应一两次调用。第 3、4 项要对清单里每个文件各调一次，属于「批量项」，仍算动作级。每项都有看得见的产出。

那几条命令不必逐字读懂，看共同点就行。每一项都收在一个能核对的结果上。文件数对得上，import 搜出来是 0 处，退出码是 0，用例数不少于改之前。`rg` 是一个在文件里搜文字的命令，和 `grep` 干的是同一件事，只是更快；`pip freeze` 列出当前装了什么包。

这份清单要是断在第 4 步，下一个接手的人读一遍就知道走到哪了。**这是好计划最容易被忽略的收益：它不只给模型看，也给「检查这件事的人」看。**

## 9.4.6 三个标准一起用

| 判据 | 问法 | 不满足时 |
| --- | --- | --- |
| 可检验 | 能写出「怎么知道它成了」吗？ | 这不是子任务，是愿望——重写 |
| 粒度 | 对应一到两次调用吗？ | 太大：它是阶段，要再拆；太小：合并或去掉 |
| 必要性 | 这事需要计划吗？ | 不需要——直接做，别开清单 |

清单、自检、粒度，这三样做的是同一件事——**把「它做了」变成「它做成了」。而且做得怎么样，别人能复查。**
