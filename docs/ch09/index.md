## 一句话的任务，和要做二十分钟的任务

Harnex 是一个 Agent，也就是一个能自己决定下一步做什么的程序。它是前面几章一路搭出来的。你给它一句话，它自己挑工具、走几步，把事办完。工具是它能做的动作，读一个文件、跑一条命令，都算一次工具调用。

从第 3 章到第 8 章，它接的都是「一句话任务」：删一个 import（代码里引用别的包的那一行）、跑一次测试、查一段代码、写一个文件。这些任务有一个共同的省心之处——**目标就在最近一条消息里。** 它往下翻几条就能看见，不用记。

现在换一个：

```text
你> 帮我把项目里所有没用到的依赖找出来，清理掉，然后确保测试还能过。
```

依赖（dependency）就是这个项目借来用的外部代码包。光第一步「找出没用到的依赖」就够它忙一阵。它得先弄明白依赖清单放在哪，测试怎么跑，哪些 import 是运行到一半才加载的。整件事至少十几轮、十几次工具调用，中间还要读一堆文件。**目标是开场那句话，而它会在第三轮之后被十几条工具结果埋在下面。**

这两种任务的区别，就在目标离你有多远。下楼买瓶酱油，目标只有「楼下那家店」，不用写路线单。开两天的长途是另一回事。目的地一次都没变，可路上要过几十个路口。你得把它一直摆在眼前，不能靠「我记得」。

这一章补的就是这件事：让目标一路上都摆在眼前。这也是 L1 阶段的最后一块能力。L1 是这本书五级达标线里的第二级，第 4 到第 9 章都在爬这一级。**爬完这一级，Harnex 才算接得住长任务。**

## 本章要做的事

**第一件，看清长任务会怎么坏。** 走偏、打转、假完成——三种失控，都能在第 6 章的会话日志里逐条读出来。会话日志就是它每做一步都追加一条记录的文件，事后能回放。三种坏法看着不一样，根子是同一个。

**第二件，做一张每轮都看得见的清单。** 既然病根是「该看的东西被埋住了」，那就让它一直露在外面：任务 → 有序子任务 → 逐项勾销。关键在于清单**存在日志里、每轮由投影重建**，而不是内存里的一个变量。投影这个词听着唬人，做法很朴素。每次都从日志里最后一条清单记录，重新算出「现在这张清单长什么样」。

**第三件，给「做完了」加一道检查。** 清单只回答了「走到第几项」，没回答「这一项真做完了吗」。所以 `done` 不能由模型一个人说了算，要用工具的实际返回去比对。还有一件更重要的事：**会放弃的 Agent 才可信。**

上面三件事讲完，你应该能做到四件事：

1. 说出长任务的三种失控方式，并指出它们共同的机制
2. 手写一张随任务推进的待办清单，并说清为什么它必须是日志事件，不能是内存变量
3. 写出一个好的子任务（它的完成标准长什么样），并说清规划这件事本身要付什么代价
4. 用四条标准判断一个任务该不该拆给多个 Agent，并给出一个「看起来该拆、其实不该拆」的例子

**前置**：这一章要用到前面四样东西。

- 第 4 章的 `ToolRegistry`：一张登记工具的表格，写着每个工具叫什么、干什么用、参数长什么样。9.2 里那两个清单工具就是普通工具，登记进去就能调。
- 第 5 章的技能包：一个文件夹加一份 `SKILL.md`，把「这类事该按什么章法做」写在里面，Agent 需要时再读。规划方法就写在这一层。
- 第 6 章的会话日志与 `project()`：日志只增不改，`project()` 从日志里算出这一轮该看见什么。清单就是日志里多出来的一种事件。
- 第 7 章的「动作后验证」：做完一个动作，回头读一遍结果，确认真的达成了。9.3 的自检，就是它在每一项子任务上的推广。

> **关于多 Agent**：这一章 **不做** 多 Agent。多 Agent 就是让好几个 Agent 分工办同一件事。多数业务场景不该拆。规划首先是一个 Agent 自己要做的事。什么时候该拆，判断标准在 9.5 节给出；拆开之后怎么让它们互不干扰（隔离），留到第 15 章。
