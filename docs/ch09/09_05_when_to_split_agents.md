# 9.5 何时才该拆多 Agent

## 9.5.1 多数任务不要拆开

9.4 说完「怎么样才算规划好了」，一个 Agent 的规划能力就齐了。清单、自检、重试、放弃，四样都在它自己一个人的上下文里完成。**会规划了，下一个念头自然是：把活儿分给几个 Agent，是不是更强？**

这一章**不给**这个能力。理由不是「多 Agent 难做」，而是 **多数业务场景不该拆。**

先澄清一个常见的混淆。拆多 Agent 不是「更强的规划能力」，它是另一件事。**把一个 Agent 的上下文切成几份，每份各跑各的。**

拆开能换来三样好处。几个 Agent 能同时在跑，这是并行。彼此看不见对方在干什么，这是隔离。各自还能拿不同的权限。

要付的代价也有三样。状态得在几份之间搬来搬去，这是状态传递。出了错得查是哪一环的问题，这是归因。钱要花好几份。

两边都算清楚，才轮到考虑拆。而「这个任务流程很长」不在好处那一栏。

全书立场就这一句：**多 Agent 不进主线，判断标准就是下面四条。** 主线始终是一个 Agent 加一套更强的 harness。真要拆，安全前提是第 15 章的沙箱（关起门来跑的隔离环境）和第 16 章的隔离。本书到此为止，不再单开一章。

## 9.5.2 四条标准，至少占两条

判断一个任务该不该拆，依次问四件事：

**一、需要完全不同的工具或权限吗？**
一个只读的分析角色、一个能写能发布的执行角色——它们不该共用一张工具表。工具表就是登记这个 Agent 能调哪些动作的那张表。

**二、能真并行，而且互不干扰吗？**
注意是「同时做、互不影响」，不是「轮流做」。排队干的活，分给几个 Agent 还是排队干。区别只是多付了几份系统提示的钱。系统提示就是每轮摆在最前面、告诉它「你是谁、该怎么干活」的那段话。

**三、一个上下文装不下吗？**
两边的中间产物加起来超过窗口，就该分。窗口是模型一次能看进去的内容上限。这是 6.2 节那笔预算账的扩展：一个装不下，就分几个，各装一部分。

**四、需要隔离验证吗？**
生成者负责写，审查者负责挑毛病。审查者不能看见生成者的推理过程。**只要它看得见，它就是在审自己的思路**，独立性归零。

**至少占两条**才考虑拆。只占一条，通常有更省事的办法。第一条，多半给工具加个权限声明就够（第 4 章的 `scopes`）。第三条，压缩和检索能撑住（第 6、8 章）。压缩是删掉冗余只留要点，检索是按需取回几段。

加分项：**拆开后各分支的结果能独立验收。** 独立验收的意思是，每份结果自己就能验对错，不用等别人拼起来。要是每份结果都得等别人回来才算数，拆完反而添了新的牵挂。

## 9.5.3 步骤多不等于要拆

「先调研、再写方案、再改代码、最后跑测试」——听起来像四个角色。逐条对一遍：

- **工具**：四个阶段都用 `fs_read` / `apply_patch` / `shell`，**同一套**
- **并行**：方案得等调研完，代码得等方案定，**一条线串到底**
- **上下文**：阶段之间要传的，正是前面查到的信息，拆开还得重新打包一遍
- **隔离**：不需要，后一步本来就该看见前一步怎么想的

四条一条不沾。它是一个**单 Agent 的清单**，不是四个 Agent。**流水线不等于多 Agent**——流水线是一环接一环过手，后一环等前一环完工。

真正的多 Agent 信号，和「看起来像」的对照：

| 看起来像 | 实际是 |
| --- | --- |
| 「调研 → 方案 → 编码 → 测试」 | 单 Agent 的顺序清单 |
| 「审查者不参与编写，只读最终代码」 | 真该拆（判据四：隔离验证） |
| 「同时处理 200 个文件，每个文件独立处理」 | 真该拆（判据二：真并行 + 独立上下文） |
| 「用最强的模型做少量决策，用便宜的模型做大批量改写」 | 不构成理由——单 Agent 内按步骤做模型路由即可（12.4 节） |
| 「任务步骤多、要跑半小时」 | 不构成理由——步骤多恰恰说明该用清单 |

判断误区的根子是同一个：**把「任务复杂」当成了「任务可以并行」。** 复杂只说明需要规划，不说明需要几个上下文。

## 9.5.4 拆开要多付的代价

四笔账，都是拆完之后才冒出来的。

**状态怎么传。** 两个 Agent 不共享内存——各跑各的，谁也不知道对方手里攒了什么。想让它知道，只能靠发消息或者写文件。传什么、传多细，是一道新题：传少了对面缺料，传多了等于把上下文又抄一份。

**出错算谁的。** 单 Agent 出问题，你看一条轨迹（它从头到尾每一步的记录）。三个 Agent 就是三条轨迹。你得先把它们的时间顺序摆到一起。这样才能回答「这一步是甲判断错了，还是乙给的信息错了」。

**成本是几倍，不是一份。** 每个 Agent 都要各带一份系统提示、工具清单、技能清单。6.2 那张预算表直接乘以 Agent 数。并行看着省时间，可合并结果、处理冲突都不便宜。

**隔离多半是假的。** 在提示里写一句「你是审查者，请客观评审」，隔离程度为零。生成者的推理过程还在同一份上下文里。**真正的隔离得落在进程和权限边界上，那是第 15 章的事。**

## 9.5.5 什么时候真的该拆

它也不是从没对过。Anthropic 是一家做 AI 模型的公司，Claude 就是它家的。公开的工程复盘里，他们讲过 Research 功能背后那套多 Agent 系统。主 Agent 拆出几个子 Agent，让它们并行检索，各自压缩结果回传。子 Agent 就是主 Agent 派出去干活的那几个小的。

他们内测发现，这套架构在开放式研究题上**比单 Agent 高出约 90%**。代价也写在同一篇里。**多 Agent 的 token 消耗约是普通对话的 15 倍**。单 Agent 是 4 倍。他们自己的解释是，多 Agent 之所以有效，靠的正是这一点。**它让「在这道题上多烧些 token」变成可行的做法。**

所以适用场景很窄，而且能列清：

- **能切开的批量活**：200 个文件各自独立处理，天然并行、上下文不交叉。
- **生成和验证必须分开**：审查者看见生成过程就会被带跑，看不见才判得独立。这套分工在 Anthropic 的《Building Effective Agents》里叫 evaluator-optimizer。中文写作评估者–优化者，就是一个写、一个挑。
- **信息量超过一个窗口**：子 Agent 各读一块，各自压缩。主 Agent 只面对压缩后的结论。
- **权限必须真的不同**：一个能读生产库、一个只能读代码。这种差别要在进程和凭据层面成立。凭据就是账号和密钥这类能证明身份的东西，一句提示写不出这种差别。

值得注意的是，同一份材料里还有那句**反向**的话。多数编码任务真正能并行的部分比研究少。而且当时的模型还不擅长临场协调和派活。**发布这套架构的公司，自己也在说「大多数情况别拆」。**

共同点很清楚：**拆开是因为「合在一起会出问题」，不是因为「分成几份看起来更快」。** 前者是真需求，后者是错觉。

## 本章到此：L1 达标

这一章给了 Harnex 三样东西。一张**每轮都能看见的清单**，管目标与进度。一次**拿证据说话的自检**，管验收。一把**判断该不该拆的尺子**，管分不分家。三样都在单个 Agent 的上下文里完成。

**L1 达标的意思就在这里**：你手上的 Harnex 已经能接一个真实的多步任务。中途失败，它会重试或者老实报告。产出能验证。而且你知道它在哪些地方靠不住。

靠不住这件事，下一章正面处理。你睡前丢给它一个任务，早上来收结果。可它要是半夜在第 6 步崩了，进程没了，清单和历史是不是也没了？**下一章就让它扛得住崩溃。**
