# 小结与验收

## 本章小结

1. **短任务的目标就在最近一条消息里，长任务不是。** 一句话任务里，模型每一轮往下翻几条就能看见那句指令。十几轮的任务里，目标会被十几条工具结果埋在下面。
2. **判断一个任务算不算「长」，不用数轮数。** 只要问一句：这个目标还要不要被反复引用？要反复拿出来对照的目标，就有被埋掉的风险。
3. **三种失控：走偏、打转、假完成。** 走偏是目标丢了，打转是进度丢了，假完成是验收丢了。根子是同一个：这三样都不在「当前上下文」里。
4. **模型不是「忘了」，是「看不见了」。** 那句话还在日志里，只是被后面十几条工具结果压到了底下。**「在日志里」和「这一轮还看得见」是两件事。**
5. **三种坏法暴露的时机不一样。** 走偏和打转，你盯着输出就能发现。假完成要等你信了它的结论才露出来——到那时候，前面所有推断都得作废。
6. **解法不是「提醒」，是「让它一直看得见」。** 在提示里加一句「别忘了原始目标」，撑不了三轮。要一直管用的东西，必须每轮都在视野里。它带的还得是事实，不是要求。
7. **清单得是日志里的一条条事件，不能是内存里的一个变量。** 变量有三个毛病：进程一崩就没了；每一轮要人手动拼进上下文；事后没法照着它重演一遍。做成 `todo_update` 事件就不一样，当前状态由投影算出来。投影就是从日志里最后一条记录，重新算出「现在这张清单长什么样」。
8. **存整张，比只记改动省心。** 每次写的都是整张清单，这叫全量快照；只写这次改了什么，叫增量差分。`project_todos()` 只取最后一条。清单最多几十项，这点重复换掉的是一整类「状态漂移」的 bug。所谓状态漂移，就是清单上的状态和真实情况慢慢对不上。
9. **清单是「每轮重新画出来的」，不是「被记住的」。** 所以「计划只存在第一轮上下文里」这个错误做法，从结构上就行不通。
10. **清单顺手治了打转。** 它把「我做过了什么」从十几条散落的工具结果，压成一份随时能读的进度摘要。**「当前」和「已读」因此分得清了。**
11. **`done` 不能由模型一个人说了算。** 每完成一项，拿 `done_when` 去比对工具的实际返回。输入必须是证据原文，也就是工具交回来的原话。输出必须是结构化结论，也就是按固定的几个字段写。证据只算「这一项被标成 `doing` 之后」的工具返回，不是整段任务的产出。检查还要卡在「标 done」落盘之前。落盘就是写进日志；等它写进去了再查，清单上已经写着 done，查了也白查。
12. **自检提示要写「你是执行者，不是评委」。** 只请它「评估执行」，会得到「基本完成」这类含糊、谁都不得罪的结论。
13. **会放弃的 Agent 才可信。** 假完成的代价不是多花时间，是让你拿着错的前提继续干活。诚实放弃只是打断你一次。
14. **重试要有预算**，就是事先定好的次数上限。同一方法两次，换方法一次，到点就转 abort。限次数真正的作用是**逼它换方法**：两次都没用，第三次也不会用。
15. **放弃时要交出三样东西**：做到哪了、卡在哪、试过什么。第三样最容易被忽略，也最省接手人的时间。
16. **规划和验证是两层。** 动作后验证问「这个动作的结果对不对」。自我反思问「这一步推进了原目标吗」。顺序是先验证、后反思。
17. **反思也是软校验。** 软的意思是，判的人还是模型自己，只是判得更有依据。硬判据只能来自外部。比如测试、渲染结果、第 13 章的评测集、第 19 章的每步截图。
18. **好子任务的判据只有一句**：能写出「怎么知道它成了」。写不出来的是愿望，不是任务。
19. **粒度到动作级，3–7 项。** 粒度说的是每一项拆到多细，动作级就是能直接开工。每项能对应一到两次工具调用，或者一轮以内的推理。超出这个量，说明还停在「阶段」那一层。
20. **规划本身有成本**：多一次模型调用、每轮都占一份 token。还有一种风险是计划本身错了，把简单任务带进沟里。单步任务直接做。
21. **计划是草稿，但改计划要留痕。** 留痕就是每次都留下记录。日志里所有 `todo_update` 排开一看就能分清。这次修改是有新证据，还是把走偏说成了更新计划。
22. **流水线不等于多 Agent。** 「调研 → 方案 → 编码 → 测试」这四步，四条标准一条不沾。它是单 Agent 的清单。
23. **四条标准至少满足两条才考虑拆**，四条是：工具或权限不同；真并行且独立上下文；单上下文装不下；需要隔离验证。
24. **拆开是因为「合在一起会出问题」，不是因为「分成几份看起来更快」。** 前者是真需求，后者是错觉。

## 动手任务

1. **制造一次走偏，再治它。** 挑一个你上次做了一半就放弃的任务，把当时的对话翻出来，或者翻日志。找出「哪一步开始偏离目标」的 `seq`（`seq` 就是日志里每条事件的序号）。然后**重跑一次**，这次一开始就 `set_todos` 四项。对比两次的结尾——大概率第二次花的轮数更少，就做完了。

2. **数一次「清单的开销」。** 在你的 harness 里加一行打印。把每轮注入的 `render_todos()` 文本长度记下来。跑完一个六项的任务后求和。**用它除以这一轮的总输入 token，得到那个比例。** 这个数字会让你以后再看到「要不要加个常驻提示」时有个参照。

3. **手工演示一次假完成。** 故意让某个子任务失败：把一个 `pytest` 目标改成不存在的用例。**先不加自检**，看模型最后怎么总结。再加 `reflect()` 重跑一次。对比两次的差异，特别看一件事：没有自检时，它的总结里有没有一个字提到那个失败。

4. **给一条 abort 写「试过什么」。** 拿 9.3 那段的格式，把你上一次真正卡住的任务填进去。**如果填不出「试过什么」这一栏，说明当时其实是在打转，不是在尝试换方法。**

5. **给小清单补完成标准。** 取 9.4 的坏例子（`1. 分析项目结构 / 2. 重构代码 / 3. 优化性能 / 4. 完善文档`），把其中一项重写成动作级的、带完成标准的子任务。**要求是：重写后的一项，你能直接上手做，不用再想。**

6. **对一个真实需求做四次判断。** 拿你手上三个需求，用 9.5 那张表逐条打勾。**必须有一个是「看起来该拆其实不该拆」的**，并写清它是哪条标准没满足。

## 阶段二收口：L1 达标

第 4–9 章走完，Harnex 已经变了样。它原来只是一个能对话、能调两个工具的循环。现在成了**一个你每天真的在用的工具**。

下面这张表把六章的能力串了一遍。每一项的细节都在对应的那一章里，这里只看它给 Harnex 添了什么。

| 章 | 补上的能力 | Harnex 变化 |
| --- | --- | --- |
| 4 | 工具注册表、描述工程、MCP | v0.2：循环只认识注册表，工具可插拔 |
| 5 | 技能包加载器 | v0.3：方法论可分发，不占常驻预算 |
| 6 | 会话日志、压缩、长期记忆 | v0.4：有了记性，也学会了忘 |
| 7 | shell 与白名单守卫 | v0.5：能动手了，且知道边界在哪 |
| 8 | 向量检索、Agentic RAG | v0.6：会自己找资料 |
| 9 | 清单、自检、重试预算 | v0.7：**接得住长任务** |

L1 是这本书五级能力线里的第二级，意思是「个人自用」。它的达标标志不是一张功能清单，而是这一条：

> 你有一件真实的事，会主动丢给它做，而不是先自己做好再拿它收尾。

如果你已经在这么用它，L1 就达标了，哪怕它在某些任务上偶尔翻车。**知道它会在哪翻车，本身就是这一阶段的一部分。**

进入阶段三之前，请确认这四件事：

- [ ] **能接多步任务**：一个 5+ 步骤的真实任务，全程无干预跑完，产出可验证
- [ ] **失败会说话**：卡住时能重试、能换方法、能诚实放弃并说清卡在哪
- [ ] **有据可查**：每段任务都有日志，能回放出它每一轮看到了什么
- [ ] **知道边界**：能说清它在哪些任务上不可信（这一条比前三条重要）

阶段三（L2：可靠可观测）要解决的正是最后一条。**崩溃后能不能恢复、出错时能不能看见、成本花在哪、怎么衡量它变好了没有？**

## 本章的常见误区

- **把目标当成「模型该记住的东西」**：它不是失忆，是视野被埋。要改的是每轮看到什么，不是让它「多记一点」。
- **清单放在内存变量里**：进程一崩就全没了。而且「每轮记得把它拼进消息」这件事本身就会漏。漏一次，就退回到没有清单的状态。
- **清单只记改动（增量差分）**：省下的 token，换来一整类状态对不上的 bug。清单要写全量。
- **用提醒代替机制**：在系统提示里反复写「别忘了原始目标」，前几轮有用。后面就成了没人再注意的背景杂音。
- **让模型自己复述结果再自检**：拿复述当证据，等于让它给自己打分。必须用工具返回原文。
- **自检提示写成「请评估这次执行」**：会得到「基本完成」这类结论。程序照着它没法决定下一步。
- **重试没有上限**：把预算烧光之后还是失败，而且用户全程不知道。
- **同一方法一直重试**：两次没用，第三次也不会用——问题通常在方法选错，不在参数。
- **abort 只写「任务失败」**：不写「试过什么」，接手的人会把坑再踩一遍。
- **把「退出码 0」当子任务完成**：那是动作后的验证，不是子任务级的反思。两层要分开做。
- **给五分钟的事出七步计划**：规划有成本，而且错误的计划会把简单任务带进沟里。
- **清单里写着「重构代码」「优化性能」**：那不是子任务，是主题。模型对它们无法判断成了没有。
- **把「流程长」当「该拆多 Agent」**：流水线不等于多 Agent。顺序执行分给几个 Agent，也还是顺序执行。
- **靠提示词实现「隔离」**：在提示里写「你是审查者」不构成隔离。真正的隔离在进程和权限边界上（第 15 章）。

## 自测题

1. 三种失控（走偏 / 打转 / 假完成）分别丢的是什么？它们共同的机制是什么？
2. 为什么说模型不是「忘了」？这个说法和第 6 章哪条不变式有关？
3. 为什么清单不能放在内存变量里？至少给出三个理由，并说明每个理由对应前面哪一章的哪条原则。
4. 清单为什么要写全量快照而不是增量差分？这个选择牺牲了什么、换来了什么？
5. 为什么 `reflect()` 的输入必须是工具返回原文，而不是模型对结果的复述？
6. 自检解析失败时为什么默认判「未通过」？反过来默认判通过会怎么样？
7. 「会放弃的 Agent 才可信」——从用户信任和成本两个角度各解释一次。
8. 为什么同一方法重试要限两次？限次数真正的目的是什么？
9. 动作后验证和自我反思分别回答什么问题？为什么顺序不能反？
10. 好的子任务的判据是什么？给出一个「看起来像子任务其实是主题」的例子，并把它改写成动作级。
11. 规划有哪三项成本？举一个「不该开清单」的真实需求。
12. 拆多 Agent 的四条标准是什么？为什么要求「至少满足两条」？
13. 「审查者只看最终代码、不参与编写」满足了哪条标准？为什么用提示词说「你是审查者」不算？
14. 用你自己的话说：L1 达标的标志是什么？

## 延伸阅读

- **Anthropic《Building Effective Agents》**——workflow（把步骤预先串好的固定流程）和 agent（自己决定下一步）差在哪。orchestrator-workers 与 evaluator-optimizer 两种模式最早是在这里定义的。还有那句「先用最简单的做法」
- **Anthropic《How we built our multi-agent research system》**——9.5 那组数字就出自这里：约 90% 的提升、约 15 倍的 token。它也讲了多 Agent 在什么情况下**不**值得
- **本书第 13 章（评测体系）**——本节的反思是软校验，硬判据在那里。一份能重跑的题库，比一次自检可靠得多
- **本书第 15 章（沙箱与审批策略）**——真正的隔离在这里：进程边界、权限边界。不是提示词里的一句「你是审查者」
- 上一章：第 8 章 检索增强。它让 Harnex 会查资料，但每次伸手只拿到零散片段。本章把这些片段接成了能走完的长任务
