# 8.3 检索质量的三处改动

上一节末尾那个失败模式——「库里明明有，却没召回」——是检索系统最常见的病。下面三处改动，各治一面。

## 8.3.1 切块时带上来源

先看一个具体场景。一份产品手册里写着：

```text
该限制已提升到 10000。
```

这句话被单独切成一块之后，就成了一个**孤儿**：什么限制？哪个产品？什么时候的事？向量只看这一段文字，语义确实是模糊的——「提升到 10000」这几个字，和用户问的「每月的请求上限是多少」，在语义空间里未必靠得近。

修法很直接：**在每块前面贴一句它的出处。**

```text
【产品手册 / 计费 / 请求限制】
该限制已提升到 10000。
```

就这一句，召回结果会明显不一样。Anthropic 那篇讲 Contextual Retrieval 的文章量过这个改动的分量：给每块补上一小段上下文，正确答案 **不在前 20 条** 里的比例从 5.7% 降到 3.7%；再加一路关键词索引，降到 2.9%；最后叠上重排，降到 1.9%。

| 配置 | top-20 检索失败率 | 相对基线 |
| --- | --- | --- |
| 只有嵌入（基线） | 5.7% | — |
| 嵌入 + 块级上下文 | 3.7% | −35% |
| 再 + 关键词索引 | 2.9% | −49% |
| 再 + 重排 | 1.9% | −67% |

（指标是「正确答案没进前 20 条」的比例，越低越好。）

注意第二行的分量：**光是把出处补上，就吃掉了三分之一的失败。** 这比换更贵的嵌入模型便宜得多，也更有效。

具体要带哪些元数据？三个必带：

- **来源文件**——答案最终要指回原文，没有它就是无源之水
- **位置**（章节标题或行号）——让人能跳过去核实
- **时间**——同一份规范常有两版，得能分清新旧

还有一类系统要带 **权限范围**。检索是在「全部文档」里做的，但用户只能看其中一部分；这类过滤必须在 **检索之前** 做，靠检索后过滤会把不该看的原文带进上下文。这是第 16 章多用户场景的硬约束，本章先不展开。

补上下文有两种做法：人工写（每块贴一个标题路径，成本低、够用），或让模型读整篇文档后为每块生成一句（更准，但每块都要花一次模型调用）。**先做人工版**——很多场景下它已经够好，而且一分钱模型费都不花。

## 8.3.2 关键词和向量一起搜

向量有一个系统性短板：**它不擅长精确匹配。**

看个例子。技术支持库里有一条，写的是：

```text
错误码 TS-999 表示上游连接池耗尽，请检查 max_connections 配置。
```

用户问「TS-999 是什么错误」。

向量检索会返回一堆 **关于错误码的通用说明**——「错误码用于标识…」，因为那些段落和这个问题在语义上确实接近。而真正管用的那一行，反倒可能排到第 30 位。原因不难理解：`TS-999` 这个字符串，嵌入模型没见过几次，它在语义空间里的位置是漂的。

换成关键词检索（BM25 一类），这条一击即中——它比的就是字符串。

反过来也一样。你问「怎么让测试跑得快」，库里有一段讲 `pytest-xdist` 并行执行，通篇没有「快」字。向量能找到它，关键词找不到。

**两种方法擅长的事不重叠，所以两个都要。** 这就是混合检索的全部理由。走到这一步，你会认出它就是 6.6 节 `keywords()` 的正式版：那时关键词方法抓不住「测试」和「pytest」的关系，向量补上了这一块；而向量抓不住 `TS-999`，关键词补上了另一块。两边合起来才完整。

合并两路结果用 **RRF（Reciprocal Rank Fusion，倒数排名融合）**：

```python
# harnex/retrieval/hybrid.py —— 关键词与向量各召回一份，按名次融合
def rrf(rank_lists: list[list[dict]], k: int = 60) -> list[dict]:
    """rank_lists 里每个元素是一路检索的有序结果，元素需含 text 字段。"""
    scores: dict[str, float] = {}
    seen: dict[str, dict] = {}
    for lst in rank_lists:
        for rank, item in enumerate(lst):
            key = item["text"]
            scores[key] = scores.get(key, 0.0) + 1.0 / (k + rank + 1)
            seen[key] = item
    pairs = [(score, text) for text, score in scores.items()]
    pairs.sort(reverse=True)
    return [seen[text] for _, text in pairs]
```

三处设计值得看：

- **只看名次，不看分数。** 两路的分数量纲完全不同——余弦落在 −1 到 1，BM25 没有上界。直接加权比大小会失真，按名次融合就不用量纲对齐。这是 RRF 存在的全部理由。
- **同时出现在两路的结果会被自然抬高**，因为它在两个循环里各加了一次分。这正是「两边都认它」该有的待遇。
- **常数 60 是经验值**，作用是压一压第 1 名和第 2 名的分差，免得某一路的第一名把另一路的意见全压掉。

## 8.3.3 先多取几条，再精选

前两处改的都是 **进到召回里的东西**：一处让每块文本自己说清来历，一处让召回同时走两条路——关键词一条、向量一条。最后一处不一样：它不动召回，只对召回之后的**排序**下手。

做法是把召回放宽到 20 到 150 条，再让一个重排模型逐条打分，只把最高的三五条交给模型。为什么值得多这一步？因为这背后是两类不同的模型：

| | 嵌入模型（召回用） | 重排模型（精筛用） |
| --- | --- | --- |
| 结构 | 双塔：query 和 doc 分开编码 | 交叉：把 (query, doc) 一起送进去 |
| 速度 | 快（doc 可以预先算好） | 慢（每一对都要算一次） |
| 准度 | 粗（两者没有交互） | 细（能看到两者怎么对上） |

双塔必须先把两边各自编码好才能比，所以 query 里「到底在问什么」这层信息，没法参与对 doc 的编码。重排模型没有这个限制：它读的是「这个问题 + 这段文字」这一对，能直接判断两者对不对得上。代价是慢——所以它只能用在少量候选上。

这就是 **两阶段** 的由来：**粗召回用便宜的方法捞一大把，精筛用贵的方法从中挑出几条。** 候选从上万条降到几十条，贵的模型只看这几十条。

回到 8.3.1 那组数据：重排是最后一刀，2.9% → 1.9%。它砍掉的比例和块级上下文差不多（都约三分之一），却**最省事**——不改切块、不重建索引，只在查询末尾加一步。而且排序这一环只有它能碰：切块和混合检索决定「候选里有没有对的」，重排决定「对的能不能排到前面」。

## 8.3.4 三处改动的先后

这三处不是任选其一，是有先后的：

1. **先修切块**——它是地基。改起来最麻烦（要重灌索引），但收益最大，而且另外两处改动的成效，都建立在块本身完整、可辨认之上。
2. **再上混合**——中等成本，补掉向量在精确匹配上的盲区。
3. **最后加重排**——增量最小、最省事，随时能加，也只影响查询耗时。

**先问「对不对」，再问「排得靠不靠前」。** 三处改动正是按这个顺序铺开的：切块决定语义对不对，混合决定该出现的有没有出现，重排决定出现的顺序对不对。

到这儿，检索的**质量**问题处理完了。但还有一件更根本的事没动：这三处改得再到位，整套流程也是**写死在代码里**的——每次都检索，检索一次就答。下一节把「什么时候检索、检索几次」这层判断，从代码里交还给模型。
