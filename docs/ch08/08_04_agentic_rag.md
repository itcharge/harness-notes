# 8.4 Agentic RAG：把检索变成技能

## 8.4.1 每次都查的三个问题

前三节做出来的东西有个共同结构：**用户提问 → 检索一次 → 拼进上下文 → 回答。** 这条流水线写死在代码里，每一步都不变。它带来三个问题。

**它总是检索。** 用户说「把刚才那段话改得更正式一点」——这也走一遍检索。查出来的段落和这句话毫无关系，塞进上下文只是稀释。

**它只检索一次。** 用户问「A 模块的维护者在哪个团队？那个团队还负责哪些服务？」——这一问要跨三篇文档、走三步：A 模块 → 张伟 → 基础设施团队 → 服务清单。可它只有一个 query，而串起这三步的那个名字（张伟），用户压根没提。

**它不问「够了没」。** 检索固定返回 4 块，代码不知道这 4 块够不够回答问题，也不知道再多查一轮有没有用。

这三个问题根子上是一件事：**「要不要查、查什么、查几轮」这些判断，本该由模型来做，却被写进了代码。**

## 8.4.2 让模型决定要不要查

改法只有一步：**把检索做成一个工具。** 它和第 4 章的 `fs_read` 没有本质区别——进了注册表，模型就知道手里有这么个东西；用不用、怎么用，每轮由它自己定。

一对比就清楚了：

| 决策 | 朴素 RAG（写死在代码里） | Agentic RAG（模型每轮决定） |
| --- | --- | --- |
| 要不要检索 | 总是 | 看问题——闲聊或不查也能答时不查 |
| query 是什么 | 用户原话 | 可以是改写、拆解后的子问题 |
| 检索几轮 | 1 轮 | 直到信息足够 |
| 什么时候停 | 拿到 k 条就停 | 自己判断「够不够回答」 |

最后一行变化最根本。朴素 RAG 里，「足够了」这个判断**根本不存在**——它没有「够不够」这个概念，因为流程是固定的。而在 Agentic 里，「停」成了模型主动做的一个决定：每拿到一批结果，它都要掂量「这些能回答了吗，还是得再查一轮」。

**这不是「更准的检索」，是把一层决策权交了出去。**

## 8.4.3 一次查不到的问题

拿那个问题跑一遍。答案分散在三篇文档里，一条链子三环：

```text
team.md       A 模块由张伟维护。
teams.md      张伟在基础设施团队。
services.md   基础设施团队负责订单、支付、网关三个服务。
```

**朴素 RAG** 把整个问题原样丢进检索：「A 模块的维护者在哪个团队？那个团队负责哪些服务？」回来的 4 块里，多半有讲维护者的、有讲服务清单的，中间那一环（张伟在哪个团队）却没被召回——问题里根本没有「张伟」这个名字，检索没理由去找它。模型手里缺了这环，只能猜「那个团队」是哪一个。**结构上它就补不上**：一次检索只有一次机会，而这条链子要三步才走得完。

**Agentic RAG** 的轨迹是这样：

```text
轮 1  search_docs({"query": "A 模块 维护者"})
      → [1] 来源：team.md　A 模块由张伟维护。
轮 2  search_docs({"query": "张伟 所在团队"})
      → [1] 来源：teams.md　张伟在基础设施团队。
轮 3  search_docs({"query": "基础设施团队 负责的服务"})
      → [1] 来源：services.md　基础设施团队负责订单、支付、网关三个服务。
轮 4  不再调用工具，直接作答
      → A 模块由张伟维护，他在基础设施团队，该团队负责订单、支付、网关三个服务。[1][2][3]
```

（每轮结果各自从 `[1]` 起编号，进上下文时按轮次累加：最后那句里的 `[1]` `[2]` `[3]`，分别指前三轮拿回来的那三块。）

关键在第 2 轮：它的 query 里出现了「张伟」——这个词 **不在用户的问题里**，是第 1 轮的检索结果带回来的。**「用上一轮的结果构造下一轮的查询」这个动作，朴素 RAG 从结构上就做不到**，因为它的 query 只能来自用户输入。

这就是「多跳」的含义：一次回答需要几段信息接力，而接力棒必须能在检索之间传下去。

## 8.4.4 检索就是一个普通工具

`search_docs` 没有任何特殊之处，它和第 4 章的任何工具一样：

```python
# harnex/retrieval/search_tool.py —— 把检索做成一个工具
from retrieval.rag_min import embed, top_k

CLIENT = None                            # 由装配代码注入：能算向量的那个 client
INDEX: list[dict] = []                   # 同上：8.2 建好的索引，启动时塞进来


def search_docs(args: dict) -> str:
    """在知识库里检索相关段落。args: {query: str, k?: int}"""
    query = str(args.get("query", "")).strip()
    if not query:
        return "错误：query 不能为空。"
    k = int(args.get("k", 4))
    if CLIENT is None or not INDEX:
        return "知识库还没接上索引，检索不了。先建一次索引，再问我。"
    hits = top_k(embed(CLIENT, [query])[0], INDEX, k=k)
    if not hits:
        return "没有找到相关段落。可以换个关键词再试，或直接用 fs_read 打开原文件。"
    blocks = []
    for i, h in enumerate(hits, 1):
        blocks.append(f"[{i}] 来源：{h['source']}（相关度 {h['score']:.2f}）\n{h['text']}")
    return "\n\n".join(blocks)
```

`CLIENT` 和 `INDEX` 是留给外面的两个口子，启动时两行就接上：`search_tool.CLIENT = client`（能算向量的那个）、`search_tool.INDEX = json.load(open("index.json", encoding="utf-8"))`（8.2.5 存下的那份）。不接也不算错，工具会照实回「索引还没接上」——比抛一个 `NameError` 好得多。

注册时的描述才是关键——它决定模型会不会用、怎么用：

```python
# harnex/tools/build_registry.py 片段 —— 第 8 章：检索类工具归一组
def retrieval_tools(add) -> None:
    """一个查文档，一个查源码。装配线里加一行 retrieval_tools(add)。"""
    add(_tool(
        name="search_docs",
        description=(
            "在项目知识库里检索相关段落，返回带编号和来源的原文。"
            "当你被问到项目文档、规范、历史决策相关的问题，"
            "而当前上下文里没有这些信息时使用。"
            "如果问题涉及多个概念的关联，分几轮检索："
            "先查最直接的那个概念，再用它返回的关键词构造下一轮的 query。"
            "闲聊、或答案就在当前对话里时，不要调用它。"
        ),
        properties={
            "query": {"type": "string", "description": "检索用的关键词或短句"},
            "k": {"type": "integer", "description": "返回几块，默认 4"},
        },
        handler=search_docs,
        scopes=["kb:read"],
        required=["query"],
    ))

    add(_tool(
        name="code_search",
        description=("在仓库里按正则精确搜索代码，返回「文件:行号:内容」。"
                     "知道要找的符号名或字符串时优先用它——它比向量检索准，"
                     "也比一层层读文件快。不知道叫什么、只知道大概意思时，才用 search_docs。"),
        properties={
            "pattern": {"type": "string", "description": "正则或字面量"},
            "glob": {"type": "string", "description": "限定文件名，如 '*.py'"},
            "max_results": {"type": "integer", "description": "最多返回几条，默认 30"},
        },
        handler=code_search,
        scopes=["repo:search"],
        required=["pattern"],
    ))
```

（`code_search` 的实现、以及它为什么值得单独占一个工具，都放在 8.5。）

两个工具各申请一个范围：`kb:read` 管知识库，`repo:search` 管源码。**不合成一个 `search`**——真要分别授权时，「能查文档、不能翻源码」是一句人会提的需求；合成一个，就再也分不开了。

描述里那句「分几轮检索、用上一轮的关键词构造下一轮」值得单说。**多跳是模型的能力，但它需要被提示出来。** 只写「在知识库里检索」，模型很可能查一次就作答——不是因为做不到，而是没人告诉它可以多轮。这和第 4 章 4.2 的结论一致：**描述决定模型会不会用、以及怎么用这个工具。**

## 8.4.5 引用靠格式，不靠自觉

看返回格式里那些 `[1]` `[2]`。它们不是装饰。

「答案必须能指回原文」这件事，要是只靠吩咐模型「记得说明来源」，它多半给你一句模糊的「根据文档」。做成结构就可靠得多：**检索结果自带编号，提示里要求答案标注编号，返回给用户的清单里附上「[N] 对应哪个文件」。** 三件事一起做，引用才有落点。

Harnex 能校验到什么程度？可以做一层**软校验**：答案里一个 `[N]` 都没出现，就提示它重来一次——纯靠字符串匹配，做得到。但它**判不了「引用的编号对不对」**：答案标了 [1]，[1] 是不是真撑得起那句话，得人来看，或者另配一套自动评分。**后者是第 13 章的活。**

「结构能兜住哪一半、兜不住哪一半」这个划分，到第 17 章的企业知识库问答会变成硬需求——那时答案要给客户看，引用错了是要担责的。

## 8.4.6 多查几轮要花什么

Agentic 不是白得的。同一道单跳题（「默认超时是多少」），朴素 RAG 一次检索、一轮回答就完了；Agentic 要先调用一次工具、拿到结果、再决定作答，**至少多绕一个循环**。多出来的这几轮，是延迟，也是 token。

所以它的收益 **随问题复杂度上升**：单跳事实题上它没优势甚至更差，多跳题和「本不该检索」的题上它明显更好。这个权衡值不值得，不该靠感觉——下一节把它量出来。
