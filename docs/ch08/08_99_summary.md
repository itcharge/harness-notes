# 小结与验收

## 本章小结

1. **模型答不出来有三类原因。** 知识截止日期、私有文档、规模太大——前两类是「不知道」，第三类是「来不及」。病因不同，出口却是同一个：别指望它记住，让它需要时去查。
2. **幻觉不是犯懒，是工作方式使然。** 模型生成的是「最像答案的文字」，不是「核查过的事实」；它没有一个「我不知道」的开关。「承认不知道」需要被专门训练或提示才会出现。
3. **那类「以前对、现在错」的答案最麻烦**，因为它照样答得笃定，看不出破绽，你不查就发现不了。
4. **微调改的是「怎么做」，检索改的是「知道什么」。** 语气、格式、领域术语适合微调；会变的事实永远不进权重——否则改一次价格就要重训一次模型，而且新旧事实会在权重里打架。
5. **小知识库不必上检索。** 20 万 token（约 500 页）以下，整份塞进上下文配合缓存更简单。工程第一原则是别为不存在的规模付代价。
6. **最简的 RAG 一行检索逻辑都没有**，就是「把资料拼进消息」——而其中最容易被忽略的一句是「资料里没有的直接说没有」，没有这句，模型会用自己的记忆补全。
7. **向量检索只有三个零件**：切块、嵌入、相似度。只有切块是自己决定，另外两个是现成模型和一行公式，所以调优大半落在切块上。
8. **切块是地基。** 只把「固定字数切」改成「按逻辑主题边界自适应切」，检索 F1 能从 0.24 涨到 0.64。地基没打好，后面再怎么补都救不回来。
9. **用余弦而不是直线距离**，因为检索只关心方向（语义），不关心长度（文本长短）。
10. **切块时要把「它从哪来」带上。** 「该限制已提升到 10000」在原文里有意义，单独成块就成了孤儿。补一句出处，top-20 失败率就从 5.7% 降到 3.7%——这一步的性价比高于换更贵的嵌入模型。
11. **向量和关键词擅长的事不重叠。** 向量抓不住 `TS-999` 这种精确串，关键词抓不住「测试」和 `pytest-xdist` 的关系。两个都要，用 RRF 按名次融合。
12. **重排是「最省事的一刀」。** 它不改索引、不改切块，只在查询末尾加一步；但排序这一环只有它能碰。
13. **三处改动有序**：先修切块（地基），再上混合（补盲区），最后加重排（增量最小）。
14. **朴素 RAG 的三个死板**：总是检索、只检索一次、不问「够了没」。根子是同一件事——「要不要查、查什么、查几轮」这些判断被写进了代码。
15. **Agentic RAG 不是「更准的检索」，是把决策权交出去。** 它让模型每轮自己决定是否检索、用什么 query、检索几轮、何时停。收益随问题复杂度上升，成本同向上升。
16. **多跳问题需要接力棒。** 「用上一轮的结果构造下一轮的查询」这个动作，朴素 RAG 从结构上就做不到——它的 query 只能来自用户输入。
17. **多跳是模型的能力，但需要被提示出来。** 工具描述里不写「可以多轮检索」，模型多半只查一次就答。
18. **引用溯源靠结构，不靠自觉。** 结果带编号 + 提示要求标注 + 返回附来源清单，三件事一起做，引用才有落点。harness 只能软校验「有没有引用」，判不了「引用对不对」。
19. **代码库检索里精确匹配优先。** 代码结构化且高冗余，大量问题问的是位置而不是意思，`rg` 毫秒级就能给出确定答案，比向量更准。三种退出码要分清：**0 是有匹配，1 是没匹配，2 是正则写错了**——把 2 当成「没找到」返回空串，模型会把「搜坏了」当成「搜过了」。
20. **代码检索的降级链**：能说清符号名用 `rg`，只能描述意图用向量召候选，拿到候选读原文确认。终点永远是精确的原文，不是最像的段落。
21. **没有度量就没有方向。** 十道题的评测已经足够让你在方案之间做一次有依据的选择——但题库版本化、评分自动化、回归对比是第 13 章的活。

## 动手任务

1. **建一个自己的最小知识库。** 挑 10 篇你手头的文档，用 8.2 的 `index_docs` 灌进去，然后问三个你**已经知道答案**的问题。**先别急着看回答质量**，先看检索返回的 5 块里有没有那一段——这一步能让你分清「检索错了」和「问答错了」。

2. **亲手制造一次「切块毁掉语义」。** 找一篇带表格或代码块的文档，用 8.2 的 `chunk()` 切一遍，把切出来的块打印出来看。**找出至少一个被切断的完整单位**，然后给切块规则加一条「表格/代码块不可切」的例外，重跑一遍对比。

3. **给每块补上出处，量一次差别。** 在 `index_docs` 里给每块前面加一句「【文件名 / 章节】」，用同一批问题分别跑加与不加的两版。**记录前后 top-5 命中率**——你大概率会看到比想象中明显的差距。

4. **手工演示一次多跳。** 拿 8.4 那个「A 模块的维护者在哪个团队、该团队负责哪些服务」的题，自己分三轮手写 query（不改任何代码），把每轮结果贴出来。**然后回答一个问题：如果只能在代码里写死一次检索，你会怎么写这个 query？** 你会发现怎么写都缺一半。

5. **对比「该不该检索」。** 用 8.6 的题库，跑一遍闲聊类的题（「谢谢你」「你好」）。**看朴素 RAG 做了什么**——它检索回来了什么、这些内容进了上下文对回答有没有影响。这一步能让「不该检索」这个抽象的失败模式变得具体。

6. **在真实代码库上用一次降级链。** 挑一个你熟悉的仓库，问三个问题：一个符号名你确定的、一个你只知道意图的、一个「谁调用了它」的。**分别用 `rg`、向量、以及你手上能用的符号工具各试一次**，记录哪个方法在哪类问题上赢了。

## 本章的常见误区

- **用微调记事实**：把「上周的价格」训练进模型，改一次价格就要重训一次，还会新旧打架。
- **小知识库硬上检索**：三份文档也去搭向量库，换来一堆基础设施和一个新的失败模式。
- **切块只按字数**：把完整表格、代码块、章节切开，检索到也答不对。
- **块不带出处**：「该限制已提升到 10000」不知道说的是哪个限制——语义模糊的块必然召回不准。
- **只用向量**：查 `TS-999`、错误码、函数名这类精确串时，硬上语义检索是自找的。
- **向量替代一切**：代码库里明明 `rg` 毫秒级能给出确定答案，却去算相似度拿回一堆「都很像」的块。
- **检索必然触发**：闲聊、改写、追问也去查库——又慢又贵，还可能把无关内容带进上下文。
- **只检索一次**：多跳问题的答案分散在多处，一次检索结构上拿不全。
- **工具描述不写「可以多轮」**：多跳是模型的能力，但它需要被提示出来，否则多半只查一次。
- **答案无引用**：模型把检索内容「消化」后自由发挥，用户无法核实——引用得靠结构，不能靠它的自觉。
- **以为 harness 能校验引用**：它能查「有没有 `[N]`」，查不了「`[N]` 对不对」，后者要靠人看或自动评分。
- **拿「感觉更准」当结论**：不建题库、不分组对比，你没法知道 Agentic 在哪些题上其实是亏的。

## 自测题

1. 模型答不出来有哪三类原因？为什么「以前对、现在错」的答案比「明显不知道」更危险？
2. 什么情况下该微调而不是检索？为什么「会变的事实」永远不该进权重？
3. 知识库多小的时候可以直接全塞进上下文？这个界限背后是什么代价在起作用？
4. rerank 为什么值得做？它和向量检索是替代还是互补？为什么它只能用在小批量候选上？
5. 混合检索里为什么要按名次（RRF）融合，而不是把两路分数加权相加？
6. Agentic RAG 和朴素 RAG 的本质区别是什么？为什么说它不是「更准的检索」？
7. 为什么代码检索里「精确匹配优先」经常是对的？举一类向量检索明显更差的问题。
8. 引用溯源靠什么实现——靠模型自觉还是靠结构设计？harness 能校验到哪一步，校验不了什么？

## 本章术语速查（中英对照）

| 中文 | 英文 | 一句话解释 |
| --- | --- | --- |
| 检索增强生成 | RAG | 先查资料再回答，把「知道什么」从权重里挪到可核查的文档上 |
| 外挂知识 | Retrieval / External Knowledge | 模型需要时去查的资料，替代不了也无需写进权重 |
| 幻觉 | Hallucination | 生成「最像答案的文字」而非核查过的事实 |
| 切块 | Chunking | 把长文档切成语义完整的小块，检索的基本单位 |
| 嵌入 | Embedding | 把文本转成定长向量，语义相近则坐标靠近 |
| 余弦相似度 | Cosine Similarity | 比两个向量夹角，只关心方向不关心长度 |
| 上下文检索 | Contextual Retrieval | 给每块补一句出处，显著降低召回失败率 |
| 元数据 | Metadata | 附在块上的来源、位置、时间、权限等字段 |
| 混合检索 | Hybrid Retrieval | 关键词（BM25）+ 向量两路召回，互补盲区 |
| BM25 | BM25 | 基于词频与文档长度的关键词排序函数，擅长精确匹配 |
| 倒数排名融合 | RRF | 按名次而非分数合并多路结果，省去量纲对齐 |
| 重排 | Rerank | 对少量候选逐条精打分，用交叉模型换精度 |
| 双塔 / 交叉 | Bi-encoder / Cross-encoder | 分开编码快、一起编码准；召回用前者，精筛用后者 |
| 朴素 RAG | Naive RAG | 固定流程：检索一次、拼进上下文、回答 |
| 智能体式检索 | Agentic RAG | 由模型决定是否检索、查什么、查几轮、何时停 |
| 多跳 | Multi-hop | 一次回答需要几段信息接力，后一跳用到前一跳的结果 |
| 引用溯源 | Citation / Attribution | 答案标回原文段落，靠结构设计而非模型自觉 |
| 符号检索 | Symbol Search | 按「定义/引用」这类结构关系查代码，非文本匹配 |

## 延伸阅读

- **Anthropic《Contextual Retrieval》**——8.3 那张失败率表的出处，也讲了「20 万 token 以下直接全塞」这条界限
- **《Comparative Evaluation of Advanced Chunking for RAG in LLMs for Clinical Decision Support》**（Bioengineering，2025）——8.2 那个「F1 从 0.24 涨到 0.64」的出处：同一个模型、同一批问题，只换了切块策略
- **Datawhale All-in-RAG**——中文系统课程，从切块到重排按顺序过一遍（见 `extra/tutorials-collection.md`）
- **BM25 与 RRF 的原始论文**——想弄清排序融合为什么有效，回到定义比看二手解释快
