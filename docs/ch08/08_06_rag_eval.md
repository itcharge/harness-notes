# 8.6 评测一小步：朴素 RAG vs Agentic RAG

## 8.6.1 为什么要先量一下

上一节收在一句话上：这套东西到底好不好用。

只靠感觉答，你会得到一句笼统的话——「Agentic 更聪明」。这话没法拿去做决定：什么时候值得为它多付那几轮循环？单跳的问题上，它是不是纯浪费？都说不清。

**想知道答案，只能让两者跑同一批题，再把结果摆在一起看。** 哪怕只有 10 道。

## 8.6.2 十道题，分三类

评测的第一步不是写代码，是出题。每题记三样：**问题、期望来源（可以是一组）、答案里必须出现的关键词**。

```python
# harnex/retrieval/evaluate.py —— 十题对照，手工评分
import asyncio

from retrieval import search_tool
from retrieval.rag_min import embed, top_k

CASES = [
    # 单跳事实题：答案就在一段里
    {"q": "配置里默认的超时是多少秒？", "source": ["config.md"], "must": "30"},
    {"q": "项目使用的测试框架是什么？", "source": ["dev.md"], "must": "pytest"},
    {"q": "日志默认保留几天？", "source": ["ops.md"], "must": "7"},
    # 多跳题：答案分散在多篇文档里，来源写一列
    {"q": "A 模块的维护者是哪个团队？该团队还负责哪些服务？",
     "source": ["team.md", "teams.md", "services.md"], "must": "基础设施"},
    {"q": "处理订单的服务由哪个团队维护？它用的是哪个数据库？",
     "source": ["teams.md", "arch.md"], "must": "Postgres"},
    {"q": "上次故障复盘提的改进项，现在是哪个团队在做？",
     "source": ["incident.md", "teams.md"], "must": "基础设施"},
    # 不该检索的题：答案就在对话里，或根本不需要检索
    {"q": "把上面那句话改成更正式的说法。", "source": None, "must": None},
    {"q": "你好，我们接着刚才那个问题聊。", "source": None, "must": None},
    {"q": "把刚才找到的超时值乘二，写进 config.md。", "source": None, "must": "60"},
    {"q": "谢谢你，先到这里。", "source": None, "must": None},
]
```

三类题各有各的用处：

- **单跳题** 是基线，看两者在「本该都答对」的场景下有没有差别
- **多跳题** 是 Agentic 的主场，看它能不能靠多轮把跨文档的信息接起来
- **不该检索的题** 是朴素 RAG 的结构性弱点——它没法不检索，这一组专门把这块短板摆出来

**三类还要分开算，别混成一个总分。** 混在一起你只看到「10 比 5 强一倍」，看不见单跳那三题一分没多赚、检索次数倒是翻了倍——而后者恰恰是你做决定时要看的地方。

`source` 为什么是一列？**单跳题的答案只从一篇里来，多跳题的答案本来就是拼出来的。** 上面那道 A 模块的题，要同时引到 `team.md`（谁维护）、`teams.md`（在哪个团队）、`services.md`（团队还管什么）——三篇缺一篇，引用就不算过。8.4.3 那三轮轨迹走的正是这条路。

`must` 是「答案里必须出现哪个关键词」：最笨的判据，却是能全自动跑的那一层。更细的活——引的那篇撑不撑得起那句话、答案全不全——还得人看。

## 8.6.3 题从哪来

这十道题不该是你坐在桌前编出来的，**它们应该来自真实的失败**。

最好的来源，是你最近几次用它时「它答得不对」的那几个提问。把原话记下来，补上「正确答案该是什么、该出自哪篇文档」，就是一道题。这样每道题都对应一个**真实发生过的错误**，改完之后你能明确回答「这一类修好没有」。

比这更差的做法，是照着文档封面编题——「项目的许可证是什么」这种，答案就在第一页，什么检索都能命中，测了等于没测。**好的题是那些你心里没底、它上次答错的题。**

十道就够起跑。题库的价值不在多，在于每一道都指向一个具体的失败场景；等它长到几百道，才是第 13 章那套自动化的用武之地。

## 8.6.4 两种做法跑同一批题

```python
# harnex/retrieval/evaluate.py（续）
def ask(client, prompt: str) -> str:
    """一句话问模型、取回文本。"""
    resp = client.chat.completions.create(
        model="deepseek-flash",
        messages=[{"role": "user", "content": prompt}],
    )
    return resp.choices[0].message.content


def strategy_naive(client, question: str) -> tuple[str, int]:
    """检索一次就答。返回 (答案, 检索轮数)。"""
    hits = top_k(embed(client, [question])[0], search_tool.INDEX, k=4)
    context = "\n\n".join(h["text"] for h in hits)
    prompt = f"根据下面的资料回答问题。\n\n{context}\n\n问题：{question}"
    return ask(client, prompt), 1


def strategy_agentic(client, question: str) -> tuple[str, int]:
    """交给模型自己决定检索几次。执行逻辑就是第 3 章那个循环，这里一行都没重写。"""
    from build_registry import build_registry
    from loop.agent import run_turn
    from session.log import SessionLog

    search_tool.CLIENT = client          # 8.4.4 留的那个口子，这儿接上
    log = SessionLog()
    answer = asyncio.run(run_turn(question, build_registry(), log))
    rounds = sum(1 for e in log.events()
                 if e["kind"] == "tool_result" and e.get("name") == "search_docs")
    return answer, rounds


def score(answer: str, case: dict) -> dict:
    """最朴素的评分：关键词是否出现 + 期望来源是否都引到。"""
    if not case["must"]:
        return {"answer_ok": True, "cited": None}
    sources = case["source"] or []
    return {
        "answer_ok": case["must"] in answer,
        "cited": all(s in answer for s in sources) if sources else None,
    }
```

这里只有两个外部输入：`client`（能算向量的那个）和 `search_tool.INDEX`（8.2 灌好的索引，8.4.4 那两行接上）。其余全是前面章节的原件——`embed` / `top_k` 出自 8.2，`run_turn` / `SessionLog` / `build_registry` 出自第 3、6、4 章。import 推迟到真跑，这样没配 key 也能先改题库。

`score()` 里那个 `all(...)` 值得多看一眼：多跳题少引一篇就算没引对。这恰好是模型最爱偷懒的地方——引了一篇，就敢拿它把三篇的结论都说了。**它到底只是字符串匹配**，判不了「引的那篇撑不撑得起那句话」；可「有没有引全」这一层，它拦得住。

`strategy_agentic` 里没有一行是自己写的循环：`search_docs` 进了注册表，剩下的就是那个循环自己在跑，它只多数了一件事——日志里调了几次检索。**这是「把检索变成技能」的顺带好处**——评测 Agentic 不用另写执行代码，换个工具集就行。

评四件事：

| 维度 | 怎么判 |
| --- | --- |
| 检索命中 | 期望来源是否都出现在召回结果里 |
| 答案正确 | 答案是否包含 `must` 的关键词 |
| 引用正确 | 答案里是否引全了期望来源（多跳题要几篇都到） |
| 成本 | 用了几轮检索 |

四件事里，`score()` 只管第 2、3 件；命中率得去检索日志里数，用了几次检索由策略函数自己交回来。命中率能数，是因为索引每块都带着 `source`（8.2 的 `index_docs` 写进去的文件名）——命中了哪几篇是查出来的，不是猜的。

`must` 为 `None` 的那几道题，`score()` 判不了——它们要判的是「答案有没有被检索带偏」，只能人看。这也是这一节叫「手工评分」的原因：能自动判的（关键词、来源）先自动判，剩下的交给一双眼睛。

## 8.6.5 结果怎么看

跑十道题，会得到这样一张表（数值示意）：

| 题目类型 | 朴素 RAG 正确 | Agentic 正确 | 平均轮数（朴素 / Agentic） |
| --- | --- | --- | --- |
| 单跳（3 题） | 3 | 3 | 1.0 / 2.0 |
| 多跳（3 题） | 1 | 3 | 1.0 / 3.3 |
| 不该检索（4 题） | 1 | 4 | 1.0 / 0.0 |

表里的「轮」只数检索，不含最后那次作答——不然「0.0 轮」就说不通了。

三条结论，方向完全不同：

- **单跳题上两者打平**，但 Agentic 的轮数翻倍——**它在简单的题上是纯成本**。真实系统里多数请求都是单跳事实题，无差别上 Agentic 就是亏的。
- **多跳题上差距明显**。朴素 RAG 那个「1」大概是蒙对的，它结构上就没有拿全信息的机会。
- **「不该检索」组上 Agentic 全对。** 0.0 轮的意思是它一次都没查。这一组里朴素 RAG 必然去查库：连「谢谢你，先到这里」也走一遍检索，不仅浪费，还会把无关段落拉进上下文，把一句简单的对话带偏。

**所以 Agentic RAG 的收益不是「更准」，是「把该不该做这件事的判断也交了出去」。** 问题越复杂，收益越大，成本也越高。它值不值，取决于你自己的问题长什么样——而这件事只能在你的数据上量。

## 8.6.6 和第 13 章的关系

10 道题、2 个策略、20 次手工判断——这就是这一节的上限。

一旦题库长到几百题、策略多到十几种，「跑一遍 + 人看一遍」就不可行了。那时要的是另一套东西：**题库要版本化**（不然改了题就没法和过去比）、**评分要自动化**（关键词和引用这些能自动判）、**要能做回归对比**（改了切块策略，哪几道题从对变错了）。这些是第 13 章的主题。

所以这一节的目标不是搭一套评测系统，而是**先体会一次「没有度量就没有方向」**。你现在手里有了一份最小的评测：只有十道题，但已经够你在两个方案之间做一次有依据的选择，而不是靠感觉。
