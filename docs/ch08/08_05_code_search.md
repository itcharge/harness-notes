# 8.5 代码库检索：Harnex 的专属用法

## 8.5.1 代码和普通文档不同

前面几节的默认场景是 **文档**：一份手册、一批笔记。同一套做法搬到代码库上，会立刻不灵。原因不在「代码更难懂」，而在代码的两个性质。

**代码是结构化的。** 命名、缩进、import 关系、目录层级都在表达结构。一段代码的意思有一大半不在字面里，而在「它在哪个文件、属于哪个类、被谁引用」里。

**代码是高冗余的。** 一个 `def get_user(...)` 可能在十几个文件里出现，长得都很像。向量检索会把这一堆「都很像」的块一起召回——它分不清「这里定义了一个用户获取函数」和「这里调用了它」。冗余会让语义检索的精度反而下降。

更根本的一点：**代码库上的大量问题，问的是位置，不是意思。**

「`parse_config` 在哪里定义的？」——这是个**精确匹配**问题。答案是一个文件加一个行号。语义检索再准，也只能给你「几个最像的段落」，而你要的是**唯一确定的那一处**。

## 8.5.2 三种检索各做什么

代码库检索不是一种方法，是三个方法的组合，按问题的类型分派：

| 你的问法 | 该用什么 | 例子 |
| --- | --- | --- |
| 精确符号在哪 | 文本搜索（ripgrep） | 「`parse_config` 定义在哪」 |
| 谁用了它 / 结构关系 | 符号索引（ctags、LSP） | 「谁调用了 `parse_config`」 |
| 意图 / 语义 | 向量检索 | 「哪里处理了超时重试」 |

**第一行覆盖了绝大多数日常问题，而且它最便宜。** `rg` 扫一遍几万行的仓库只要几百毫秒，不用切块、不用嵌入、不用建任何索引——这三样恰恰是向量检索开张前要先付的钱。这就是为什么「先 grep 再读文件」经常比向量检索更准：它不是更聪明的检索，它是**用对了方法的检索**。

不过第 7 章那份白名单里没有 `rg`，收的是 `grep`、`ls`、`head` 这些。`grep` 也能凑合，但 `rg` 更快、默认带行号、默认尊重 `.gitignore`——代码检索最需要的恰好是这三样。所以本章不给 `shell` 开口子，而是另加一个 `code_search` 工具。理由有两条：权限能分开——`repo:search` 和 `kb:read` 各管各的，正是 8.4.4 那笔账；**而且「怎么拼参数、怎么读 `rg` 那种三段式输出」这些活，不必每轮都让模型现场发挥。**

## 8.5.3 先精确搜，再读原文

把这条路走完整，就两步：**用 `rg` 定位文件和行号，再读那一段。**（`rg` 就是 ripgrep，机器上没有的话 `brew install ripgrep` 一行装好。）

```python
# harnex/retrieval/codesearch.py —— 精确搜索优先
import subprocess

ROOT = "."


def code_search(args: dict) -> str:
    """用 ripgrep 在仓库里精确搜索。args: {pattern: str, glob?: str, max_results?: int}"""
    pattern = str(args.get("pattern", "")).strip()
    if not pattern:
        return "错误：pattern 不能为空。"
    max_results = int(args.get("max_results", 30))
    argv = ["rg", "--line-number", "--no-heading", "--color", "never", pattern, ROOT]
    glob = args.get("glob")
    if glob:
        argv += ["--glob", str(glob)]
    try:
        proc = subprocess.run(argv, cwd=ROOT, capture_output=True, text=True, timeout=10)
    except subprocess.TimeoutExpired:
        return "错误：搜索超时（10 秒）。请把 pattern 写得更具体。"
    if proc.returncode == 1:
        return (
            f"没有匹配 {pattern} 的内容。"
            "可以换一个关键词、去掉 glob 限制，或先用 fs_read 看一下目录结构。"
        )
    if proc.returncode != 0:
        return f"错误：搜索失败（退出码 {proc.returncode}）：{proc.stderr.strip()[:200]}"
    lines = proc.stdout.splitlines()
    body = "\n".join(lines[:max_results])
    if len(lines) > max_results:
        body += f"\n（共 {len(lines)} 处匹配，此处显示前 {max_results} 处）"
    return body
```

`rg` 的输出格式是 `路径:行号:内容`——**这正好是下一步需要的东西**。模型从里面挑一行，把路径交给 `fs_read` 就能打开那个文件；几百行的文件整份读进来也不贵。真撞上几千行的大文件，用 `shell` 里的 `head` / `tail` 先截一段就够。

六处细节值得留：

- **搜索路径一定要写出来。** 不给路径时，`rg` 会去读标准输入。在终端里手敲没问题——它检测到那是终端，会自己搜当前目录；可被 Harnex 当子进程起的时候，标准输入是空的，于是**每一条搜索都返回「没有匹配」**。同一行命令，在终端里对、在程序里错，这类坑只能靠「装进工具跑一次」暴露出来。
- **`rg` 默认跳过 `.gitignore` 里的文件，也跳过隐藏文件。** 平时这是好事——`node_modules`、构建产物、`.env` 不会来搅局；可它也会让「明明在仓库里」的文件搜不到。返回空结果时先想一下这一层，该搜的时候加 `--no-ignore` 或 `--hidden`。
- **`returncode == 1` 不是错误**，是「没有匹配」。`rg` 用它表示搜过了但没找到，这和「命令执行失败」是两码事——不跟模型说清这一点，它会把「没找到」当成「搜索坏了」。这正是 7.1.3 讲的「把返回码变成一句给模型的判决」。
- **退出码 2 也得说清**，那是正则写错了。要是把它当成「没匹配」返回一个空串，模型会以为自己搜过了却什么都没有——**「搜坏了」和「没搜到」返回的东西长得一模一样**，它只会按「没有」往下答。
- **`max_results` 封顶**。一个常见词（`config`、`data`）可能命中几千处，全扔给模型就又回到了 7.2 的大输出问题。
- **超时和带下一步的拒绝理由**，都是第 4、7 章沿用下来的老规矩。

## 8.5.4 什么时候才用向量

三个方法里，向量排在最后。不是因为它差，是因为它最贵：要先切块、嵌入、建索引，查询时还得算一遍相似度。它真正不可替代的场景只有一个——**你说不出该 grep 什么词。**

「哪里处理了超时重试」——你没法规规矩矩地 grep，因为代码里可能写的是 `retry`、`backoff`、`retries`、`tenacity`，还可能是某个叫 `_with_retries` 的私有方法。这时向量能帮上忙：它从「语义」这一侧找到那片区域，返回几个候选文件。**但它的输出也只是「候选」**——找到之后还得读原文确认。

所以代码库检索的默认策略是一条降级链：

1. **能说清符号名** → `rg` 直接定位
2. **只能描述意图** → 向量召回几个候选文件
3. **拿到候选** → `fs_read` 读原文，确认是不是要找的

每一环都是「粗到细」，终点永远是精确的原文，而不是最像的段落。这和 8.3 的重排是同一个思路：**先便宜地缩小范围，再用贵的方法确认。**

## 8.5.5 这个办法的限度

「谁调用了 `parse_config`」这类问题，`rg` 答不准。它会把所有出现过这个词的地方都列出来——定义处、注释里提到的、字符串里的——分不清哪一处是调用。要分清，得靠**符号索引**：`ctags` 建一张「符号在哪定义、在哪被引用」的表，或者语言服务器（LSP）实时回答。

那是另一道专门的题，要的是把代码**解析成结构**，不是搜索文本。本章不展开，也不影响主线——8.5.2 那张表的第一行，就能解决日常问题里的八成。

## 8.5.6 到这里就会查了

把这一章给 Harnex 装的东西合起来看：

- **文档问答**：`search_docs` 让它能在自己的资料里找段落，带来源和引用
- **多跳检索**：模型自己决定查几轮、用上一轮的关键词构造下一轮
- **代码定位**：`code_search` 让它能在仓库里精确找到「这一处在哪」，再读原文

它现在能回答的问题，比上一章宽得多。但这也带出一个新的、必须回答的问题：**这套东西到底好不好用？** 「感觉比之前准」不算数。下一节给出一份只有 10 道题的评测——小，但它是第 13 章那套正式评测的雏形。
