# 8.2 向量检索的最小工作集

## 8.2.1 三个零件

向量检索拆开只有三个零件：**切块**、**嵌入**、**相似度**。顺序就是它们干活的顺序，下面三小节一节讲一个。

三样里只有切块由你定：嵌入是现成模型，相似度是一行公式。后面所有调优，大半落回切块。

## 8.2.2 切块：拆分文档

起步配置：**每块 256–512 字。** 256 字差不多两三个自然段，正好把一件事说完；512 字是上限，再往上，一块里就会混进两三个话题，向量也就糊了。

切法只有一条规矩：**先用最大的边界切；切出来的块还超过 512 字，才换小一号的边界。** 这套做法有个现成的名字，叫 **递归切分**——名字不用记，记住四步就行。

1. **有标题或表格**：一个标题底下的内容算一块；表格整张算一块，超长也不劈。
2. **没标题，有空行**：一个自然段，算一块。
3. **一个自然段超过 512 字**：在句号处断开。
4. **连句号都没有**（日志、代码、一大段流水账）：只能数着字数，在 512 字处剪断。

判据是数字，不是感觉：除表格外，每一步都问**这块超过 512 字了吗**——没超就停，超了才往下走。凭「感觉有点长」往下走，块只会越来越碎。

只有第 4 步要补一手：**相邻两块留 10–20% 的重叠**，512 字的块就是 50–100 字，差不多一句话。因为按字数剪不认句子，一刀下去常常正落在句子中间：

```text
块 1   …默认限流是每分钟 500 次，超过后返回 429；该限制已提升到 10000
块 2   次/分钟，需要联系平台申请…
```

块 1 收在半个句子上，「10000」后头没了；块 2 开头「次/分钟」不知所云。留了重叠，这句话在两块里各完整出现一次。前三步不用留——按标题、段落、句号切开的地方本来就是完整边界。

按结构切比按字数切，差多少？一项针对临床决策支持系统（给医生查指南、查药品说明书的那种）的研究量过：同一批问题、同一个模型，别的没动，只把切块换成按结构，检索 F1 从 0.24 涨到 0.64。F1 同时看「找得全」和「找得准」，满分 1：0.24 是找回来的大半不相关、该找的还漏着。**这一截不是调参调出来的，是换切法换出来的。**

所以顺序是固定的：**有结构就用结构，没结构才退到字数。** 标题、表格、自然段、句号都是现成的边界，只有纯散文什么都没得靠，才轮到数字——一个完整表格被劈成两半，检索到也答不对。

按字数切不丢人——便宜、几分钟就能跑起来，只是垫底那一档。切完抽五块看看：有没有以半句话开头、有没有半个表格、有没有一块里塞了两个话题；占一样，就换大一点的边界。

## 8.2.3 嵌入：把文本变成坐标

切完块，机器还是比不了两段文字——它只会算数。所以得先把文字换成数。

做法就一步：把一段文本送进嵌入模型，它吐出一串数——这串数就叫 **向量**。`text-embedding-3-small` 不管输入多长，吐出来的都是 1536 个数，所以叫「1536 维」：数的个数就是维数。

它不是 1536 个标签，是一个点的 1536 个坐标。经纬度两个数可以确定地球上的一个位置，这里 1536 个数确定一段话的位置，这个位置也是这段话的意思。没有哪一位单独有意义（不是「第 7 位代表情感」「第 12 位代表价格」），人读也读不懂；机器不用读懂，它只要拿两个位置比远近。

**嵌入要做两遍。** 建索引时，每块都过一遍模型，于是摆进同一个空间：讲超时的挤在一处，讲计费的挤在另一处，讲部署的挤在第三处。查询时，问题也过一遍**同一个**模型，换回同样 1536 个数，落在同一个空间里——检索就是看它落在哪一堆附近，把那一堆捞出来（8.2.5 里 `top_k` 的 `qv` 就是问题那串数）。

1536 维画不出来，但「两点隔多远、两个方向夹角多大」的公式照搬三维那套，短到一眼看完（8.2.5 的 `cosine()` 就五行）。

位置凭什么叫意思？因为**「意思」没法标注**——你没法拿两段话给人看，让他报个相似度：0.7 还是 0.8？但有一件事能观察：**一段话周围常站着哪些词。**

训练就是这么做的：成对的文本喂进去，每对只回答一句——**这两个该靠近，还是该推开**。同一句话的几种改写、一问一答、相邻的两段，靠近；不相干的两段，推开。见得够多，规律就落下来了：语境相近的，位置也相近。

于是「测试」和 `pytest` 一个字都不重合，坐标却贴在一起——6.6 结尾说 `keywords()` 抓不住这类关系，说的就是这个。

也别把它想得太神。坐标记的就是「周围站着哪些词」，所以它比的是 **语境像不像**，不是 **事实对不对**。「这个接口能用」和「这个接口不能用」，周围的词几乎一样，坐标也就几乎一样——否定、精确数字、订单号，它分不出来。这个洞由 8.3 那一路关键词检索来补。

**两遍得用同一个模型。** 不同模型的坐标不在同一个空间，混着比等于拿经纬度比温度计；换模型就得重建整个索引，只换查询那一头等于白换。代码是 8.2.5 的 `embed()`，一批送比一条条送快得多（`input=texts`）。

## 8.2.4 相似度：怎么量「近」

手里于是有两串数：问题的、每块的。剩下只有一个问题：**这个「近」怎么算。**

常见的两种：欧氏距离量直线距离，余弦量夹角。

检索里几乎一律用余弦，原因一句话：**我们关心方向，不关心长度。** 它的取值落在 −1 到 1：同向为 1，垂直为 0，反向为 −1，越接近 1 越像。

50 字的退款说明和 500 字的退款细则讲的是同一件事，方向该一致。可后者信息更密，向量往往被拉得更长；欧氏距离把长度差也算进去，就判成「不太像」。余弦先把两串数各自缩到长度 1，再比夹角——长短跟着信息密度走，本来就是噪声。

## 8.2.5 向量先存在文件里

```python
# harnex/retrieval/rag_min.py —— 最小工作集：切块、嵌入、余弦检索
import json
import math


def chunk(text: str, size: int = 400, overlap: int = 60) -> list[str]:
    """先按空行切段，再把小段合并到接近 size；超长段硬切并保留 overlap。"""
    size = max(1, size)                        # 块大小给 0 会切不动，这里兜住
    overlap = min(max(overlap, 0), size - 1)   # 重叠顶满整块时 p[size-overlap:] 原地不动
    paras = [p.strip() for p in text.split("\n\n") if p.strip()]
    chunks: list[str] = []
    buf = ""
    for p in paras:
        while len(p) > size:
            chunks.append(p[:size])
            p = p[size - overlap:]
        if len(buf) + len(p) + 2 <= size:
            buf = f"{buf}\n\n{p}".strip()
        else:
            if buf:
                chunks.append(buf)
            buf = p
    if buf:
        chunks.append(buf)
    return chunks


def embed(client, texts: list[str], model: str = "text-embedding-3-small") -> list[list[float]]:
    """把一批文本转成向量。批量送比逐条送快得多。

    DeepSeek 没有 embeddings 接口，这个 client 得另找一家（任何 OpenAI 兼容、
    带 /embeddings 的都行）。建索引和查询用同一个模型，两串数才在同一个空间。
    """
    resp = client.embeddings.create(model=model, input=texts)
    return [item.embedding for item in resp.data]


def cosine(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(y * y for y in b))
    return dot / (na * nb + 1e-9)


def item_score(item: dict) -> float:
    return item["score"]


def top_k(qv: list[float], index: list[dict], k: int = 3) -> list[dict]:
    """暴力算相似度，取前 k。index 里的每条记录都带上自己的 score。"""
    scored = [dict(it, score=cosine(qv, it["vec"])) for it in index]
    scored.sort(key=item_score, reverse=True)
    return scored[:k]


def index_docs(client, docs: dict[str, str]) -> list[dict]:
    """docs: {文件名: 全文} → 一条条带来源的索引记录。"""
    items: list[dict] = []
    for name, text in docs.items():
        for piece in chunk(text):
            items.append({"source": name, "text": piece})
    vecs = embed(client, [it["text"] for it in items])
    for it, v in zip(items, vecs):
        it["vec"] = v
    return items


def save_index(index: list[dict], path: str = "index.json") -> None:
    with open(path, "w", encoding="utf-8") as f:
        json.dump(index, f, ensure_ascii=False)
```

五十来行，一个完整的向量检索就在这儿了。`index_docs` 把三件事串起来：切块 → 嵌入 → 存进记录。查询侧也只有两步：先把问题喂给 `embed` 拿到 `qv`，再交给 `top_k` 比一遍。

`chunk()` 只做了 8.2.2 那四步里的**第二步和第四步**：按空行切段、把小段合到接近 400 字，段落本身超长才硬切（带 60 字重叠，正好落在 10–20% 里）。小标题得先把 markdown 拆开再喂进来，句号是在那个 `while` 里加几十行的事——多数文档按段落就切得动。

`index_docs` 里那个 `source` 字段是**故意的**——它不是给相似度算的，是给人看的。检索结果要能指回原文（8.3、8.4 都会用到），所以建索引时就得把来源带上，事后补不上。

## 8.2.6 以后再换向量库

存成 JSON、在内存里暴力算余弦，这套能撑到多大？**几千块以内，它比任何向量数据库都快、都简单。** 一块 1536 维向量约 6 KB，一千块不过 6 MB，全塞进内存，查一次几千次点积——毫秒级。

换成真正的向量库，有两个信号：

| 出现什么信号 | 换成哪一类 | 具体选型 |
| --- | --- | --- |
| 块数上万，暴力算开始变慢 | 本地索引库 | FAISS（本地、无服务）、Chroma（本地、带元数据过滤） |
| 需要「先按条件过滤，再检索」 | 带过滤的库 | 只查某个项目 / 某段时间的文档时，Postgres + pgvector 最省事 |

更常见的动因是第二行：不是嫌余弦慢，是嫌它**不能先筛**——「只在这个季度的合同里找」，靠元数据过滤比靠语义靠谱。

在那之前，`index.json` 就是你的向量库。

## 8.2.7 一个常见失败

把上面的 `index_docs` 和 `top_k` 连起来跑，你会很快撞上第一个坑：**明明库里就有答案，检索却没把它召回。**

原因通常不在模型，在切块——那句话被切断了、那个表格被劈开了、那块内容没带上「它在讲什么」的线索。这不是调大 `k` 能解的：塞更多块，只会让更相关的那块埋得更深。
