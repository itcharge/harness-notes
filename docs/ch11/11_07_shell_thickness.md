# 11.7 外壳能长多厚：从 80 行到能天天用

## 11.7.1 八十行撑了不到一周

上一节收尾时，那个页面已经能发给同事了。真用了一周，他回来提的问题，没有一条是「功能没做」：

- 他记得上周三问过报销流程，可会话列表按文件时间排，只能一个个点开找
- 一次 `pytest` 吐出两百多行，全摊在时间线上，把前后的话冲出屏幕
- 那边在出字，这边输入框跟着往下蹦，打到一半的词被顶走
- 他把截图拖进去，Harnex 回一句「看不到图片」

四条反馈，指向四个方向：找得到、看得清、坐得稳、进得来。

11.5 定过一条纪律：四件事（发消息、收流、画清单、弹审批框）八十行就该够，超过就说明内核漏了东西。这句要补个限定。它管的是**内核漏没漏**，不是**界面只能这么大**。八十行对的是四件事，而「天天用」会自己长出第五件、第六件。界面变长是必然的。

变长不可怕。可怕的是长出来的那些东西里，混进了不该它管的判断。

## 11.7.2 厚度不看行数，看它知不知道

判断一段界面代码有没有越界，不看它有多少行，看它有没有在做「决定」。越界就是干了不该它干的活。四个信号，出现一个，就已经越了：

| 界面上写了什么 | 为什么越界 | 该在哪 |
| --- | --- | --- |
| `if (cmd.includes("rm")) askUser()` | 危险与否写在界面上 | 第 15 章的策略层 |
| `catch (e) { setTimeout(retry, 1000) }` | 自己决定重试，绕过退避与熔断 | 第 10 章 |
| 把用户输入拼成 `grep …` 的整条命令 | 绕开了命令白名单 | 第 7 章 `shell.ALLOWED` |
| 本地存一份清单，收到推送再合并 | 造出第二个真相 | 9.2 的日志投影 |

表里第二行那个「退避与熔断」，指第 10 章那套规矩：失败后等一会儿再试，连着失败就停手。

四条的共同点不在技术上，在后果上：**它们都会让「再做一个客户端」变成重写一遍。** 今天在网页里判了危险，明天做桌面端、后天做手机端，这套判断要再写两遍。三份代码迟早对不上，而只要有人用的是对不上的那份，判断就等于没做。

所以纪律换个说法，比八十行那条更硬：

> **外壳可以三千行，但不能有一行知道「该不该做」。**

仪表盘可以有速度、油量、水温、胎压，表越多越好。但没有一块表能替你打方向盘。

## 11.7.3 协议表就是组件清单

界面从四件事长到十几件，不需要新的设计方法。11.5 那张协议表已经把清单写完了：**每个事件，对应界面上一块东西。**

| 事件 | 界面上长成什么 |
| --- | --- |
| `user_message` | 一条用户消息 |
| `assistant_delta` | 追加到正在写的那段回答里 |
| `tool_start` | 一张卡片：标题是工具名，状态「进行中」 |
| `tool_output` | 卡片内部滚动的执行日志 |
| `tool_result` | 卡片收起，标题右侧一个勾或一个叉 |
| `todo_update` | 侧栏那张清单重画 |
| `approval_request` | 审批卡片，带三要素（11.4） |
| `approval_denied` | 那张卡片标灰，补一句「已拒绝」 |
| `turn_done` | 停表，输入框解禁 |

九个事件，九块界面，没有第十块。这句话不只是一句口号：**界面上还需要别的东西，说明协议缺了一条，不是前端该自己造。**

举个正在发生的例子。界面想显示「这段回答花了多少 token」，可协议里没有这个字段。正确做法是回内核加一条事件，前端等着。错误做法是前端自己数字符，再除以四，估一个。估出来的也能跑，但那个数永远不可信，而且过两天没人记得它是估的。

11.5 说「协议是内核和外壳之间唯一的接口」。落到实处就是这张表：**表里没有的，界面上就不该有。**

## 11.7.4 状态只有一个来源

九块界面各自得记住自己长什么样。这些「记住」放在哪里，是外壳工程里最容易搞错的一件事。

规矩只有一条：**界面不持有自己的状态，它只是日志的一种投影。** 投影的意思是：界面上每一样东西，都能从日志里算出来，别处不另存一份。

11.6 那张清单里有一条「刷新页面，历史与清单从日志重建」。那不是体验要求，是给架构做体检：刷新就丢，说明有东西还留在内存里，没落盘。

唯一的例外叫**乐观更新**：用户按下回车，消息立刻上屏，不等服务端确认。「乐观」是说，先假定这件事会成。这个例外安全，因为它只让「显示得快一点」，不让界面决定「事实是什么」。服务端回执一到，以回执为准；对不上就改回来。

断线也归这条规矩管。11.5 的边界写着「没有增量补偿」，所以重连的动作是**重放整屏**，不是「接着上次继续流」。看着笨，但它保住了一件事：**你看到的，永远是日志里有的。**

跟着来一个容易被问到的情形：两个窗口同时看一个会话，会怎样？答案是——**增量只到发起的那一次连接。** 另一个窗口要看新内容，只能重连、重放。这是同一条边界的另一面，也是多端真正的难点。本章没有解决它，但要知道它没被解决。

把这些收成一张表，就是下面这二十来行：

```javascript
// harnex/apps/server/static/render.js —— 事件到组件：一张表就够了，没有第十种东西
// 右边那些 renderXxx 都在本文件里，各画各的一块。这张表只是「类型 → 画法」的对照。
const RENDERERS = {
  user_message:     renderUser,
  assistant_delta:  renderDelta,
  tool_start:       renderToolStart,
  tool_output:      renderToolLine,
  tool_result:      renderToolResult,
  todo_update:      renderTodos,
  approval_request: renderApproval,
  approval_denied:  renderDenied,
  turn_done:        renderTurnDone,
};

function render(event) {
  const handler = RENDERERS[event.type];
  if (!handler) {
    // 内核加了新事件、界面还没跟上：记一笔，别让整屏崩掉
    console.warn("不认识的事件", event.type);
    return;
  }
  handler(event);
}

// 跑起来看到：控制台一条警告都没有，说明九个事件都被这张表接住了。
// 哪天内核多出一个事件，这里会立刻报出它的名字——这就是这张表的用处。
```

一张表，把「界面要画什么」从散落各处的 `if` 里收回到一处。加一个新事件，只加一行；漏了一个，控制台会告出来。

**11.5 那条纪律真正想要的东西，就是这里**——不是代码少，是每一块都有出处。
