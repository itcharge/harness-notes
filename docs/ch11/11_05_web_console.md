# 11.5 全端第一步：Web 控制台（协议优先）

## 11.5.1 为什么离开终端

到上一节为止，Harnex 一直住在终端里。终端就是那个只能打字、只能看字的黑框框。它能跑通，但有三件事做不到：

- **分享不了。** 想让同事看一眼待办清单，只能截图。
- **界面做不了。** 11.4 的审批框在终端里只能压成一行 `允许？[y/N]`。「影响什么」那半句没地方摆。
- **手机上看不了。** 终端基本只活在电脑上。

前几章一直守一条纪律：**harness 内核是主角，客户端是外壳。** 内核负责想和做，客户端是人看着、点着的那一层。换一层界面，不该回头改内核的代码。

这一章是这条纪律第一次受真考验，因为这回真要换客户端了——从终端搬到浏览器。

## 11.5.2 先定消息格式，再写页面

搬进浏览器，得写两半代码。跑在浏览器里的那半叫前端（frontend）。跑在服务器上的那半叫后端（backend）。平时做产品，先搭页面，再往后接数据。

这里反过来：

> **先写清「运行时往外发什么事件、客户端往里发什么指令」，再写两边。**

理由很实际。**协议是内核和外壳之间唯一的接口。** 协议就是两边约好的消息格式：谁发、发给谁、里面装什么。

协议稳了，前端可以随时重写，甚至同时开三个。协议没定，每加一个界面功能都要回头改内核。那等于内核跟某一个界面绑死了。

11.2 那张表只写了「服务端往客户端推」，是协议的一半。补齐两边：

| 方向 | 消息 | 载荷 |
| --- | --- | --- |
| 客户端 → 服务端 | `user_message` | 用户输入文本 |
| | `confirm` | 审批的 `key` + 布尔值 |
| | `cancel` | 中断当前这一轮 |
| 服务端 → 客户端 | `assistant_delta` | 一段文本增量 |
| | `tool_start` / `tool_output` / `tool_result` | 工具执行过程 |
| | `todo_update` | 整张清单快照 |
| | `approval_request` | 要问的 `key` 与三要素摘要 |
| | `approval_denied` | 被拒的 `key`，界面标成「已拒绝」 |
| | `turn_done` | 这一轮结束 |

第三列的「载荷」指一条消息里带的具体内容。第一列空着的行，方向和上一行相同。

这里有个看着无所谓、其实很省事的决定：**协议里的 `type` 和日志里的 `kind`，用同一套词表。** `type` 是一条消息的种类，`kind` 是一条日志的种类。名字取成一样，两边就不用互相翻译。

好处有三条。前端不用做两套对照表。**日志回放能直接喂给同一个渲染器**，渲染器就是把事件画成界面的那段代码，看历史和看实时走同一段。新增一种事件只要起一个名字，两边同时生效。

有两个例外，只在界面上跑，不写进日志。`assistant_delta` 是展示用的碎片，日志里没有对应物——这印证了 11.2 那条决定：**日志存整段，不存增量。** `turn_done` 也不用单独记。下一轮那条新的 `user_message`，已经说明上一轮结束。

## 11.5.3 后端怎么接

协议定了，后端只剩一件事：把它接到内核上。代码用 FastAPI 写，那是一个做网页服务的 Python 框架。没写过网页服务的，先看下面四条，够用了：

```python
from fastapi import FastAPI, WebSocket          # 1. 导入两个东西

app = FastAPI()                                 # 2. 一个 app 就是一个服务，网址都挂在它身上


# 3. @ 打头这行叫装饰器，意思是「下面这个函数，挂在 /ws/xxx 这条路上」
# 括号里两个类型注解不能省：FastAPI 靠它认出第一个参数是连接对象
@app.websocket("/ws/{session_id}")
async def ws_chat(ws: WebSocket, session_id: str):
    await ws.accept()                           # 4a. 先把连接接住
    frame = await ws.receive_json()             # 4b. 收一条 JSON（页面发来的话）
    await ws.send_json({"type": "turn_done"})   # 4c. 回一条 JSON

# 跑起来看到：页面连上 /ws/demo，发一句话，服务端回一条 {"type": "turn_done"}。
# 这段只证明「连得上、收得到、发得出」，内核还没接上。
```

`{session_id}` 是路径参数，指网址里那段会变的部分，名字对上就自动传进函数。`async def` 是因为这几步都在等网络，等的工夫要让出去给别人跑。启动用 `uvicorn harnex.apps.server.app:app --reload`。`uvicorn` 是启动这个服务的小程序。然后在浏览器里访问 `http://127.0.0.1:8000`。

四条拼起来就是这个：

```python
# harnex/apps/server/app.py —— Web 控制台后端：一条 WebSocket 接一个会话
# 依赖：pip install fastapi uvicorn。不用 API key 也能起服务，
# 只是真的发一句话之后，模型那一步会报错。
from fastapi import FastAPI, WebSocket, WebSocketDisconnect

app = FastAPI()


@app.websocket("/ws/{session_id}")
async def ws_chat(ws: WebSocket, session_id: str):
    await ws.accept()

    log = SessionLog.load(session_id)              # 第 6 章：状态从日志读，不存内存
    registry = build_registry()                    # 第 4 章：工具装配线
    gate = ApprovalGate(log, ask=make_asker(ws))   # 11.4 的闸门，问法换成网页

    # 推一条事件给前端。type 和日志的 kind 同名，前端不用再翻译一遍
    async def emit(event):
        await ws.send_json(event)

    try:
        while True:
            frame = await ws.receive_json()

            if frame["type"] == "user_message":
                await run_turn(frame["text"], registry, log, gate, emit)
                await emit({"type": "turn_done"})

            elif frame["type"] == "confirm":
                resolve_approval(frame["key"], bool(frame["verdict"]))

    except WebSocketDisconnect:
        # 断开不等于任务失败：日志已落盘，接着跑靠 10.4 的 resume
        pass

# 启动：uvicorn harnex.apps.server.app:app --reload
# 跑起来看到：浏览器打开 http://127.0.0.1:8000，发一句话，字一段一段冒出来。
# 关掉标签页、再打开同一个会话，历史还在——因为它是从日志重放出来的。
```

三处值得停下：

- **`SessionLog.load(session_id)` 就是会话路由。** 一个 id 对应磁盘上一份 JSONL，一种一行记一件事的文本文件。两个客户端连同一个 id，看到的是同一份记录。**多会话不需要额外的会话管理模块**，第 6 章「日志是真相源」在这里直接兑现。
- **`except WebSocketDisconnect: pass`。** 关标签页太常见，它不该让任务变成「失败」。保证正确性的是日志。客户端只是看客，**看不看得见都不影响记录**。
- **审批的 asker 是回调。** 回调就是先把一个函数交给别人，等事情到了再叫他。`make_asker(ws)` 先发 `approval_request`，等 `confirm` 回来。这就是 11.4 那个 `self.ask`：**机制在内核，通道由客户端提供。**

## 11.5.4 用长连接，不反复询问

一个自然的疑问：做个 HTTP 接口，让页面每秒问一次「有新事件吗」，不是更简单？HTTP 是网页里最常见的那种「你问一次、我答一次」。三个理由，第一个就够：

- **服务端要主动推。** 流式增量、审批请求、清单变更何时发生，由 Harnex 决定，不由浏览器决定。改成定时问，就得先替它定「多久问一次」。这个数字没有好答案：问得密，多半白问；问得疏，界面卡顿。
- **一次任务几十到几百条事件。** 定时问，绝大多数请求拿回来是空的。**白问本身也是成本。**
- **双向是真实需求。** 审批要浏览器往回送东西。硬用 HTTP，得拆成「发消息」和「拉事件」两套接口，反而不省事。

一条 WebSocket 全包了。WebSocket 是一条一直开着、两头都能随时说话的网络连接。FastAPI 内置支持：`@app.websocket` 加 `await ws.receive_json()`，就是全部。

**一个要留意的细节：** WebSocket 连接本身不保存会话信息。这正是想要的——**会话状态在日志里，不在连接里**。断线重连时，拿着 `session_id` 连上、重放日志，界面就回来了。

## 11.5.5 页面只做四件事

前端只做四件事：发消息、把增量接在当前气泡后面、画待办清单、弹审批框。气泡就是对话框里那一块一块的说话框。

第三件是白送的。清单在日志里（9.2），推过来的 `todo_update` 就是现成的列表数据，画成列表不用任何判断。第四件也简单：`approval_request` 到了就显示框，用户一点就把 `confirm` 发回去。

**四件事加起来，用原生 JS 写，大约八十行。** 原生 JS 指不装前端框架、直接用浏览器自带的那套 JavaScript。八十行不是巧合，是一条能检验的纪律：

> **如果前端要上百行才能把这些事做出来，说明有东西本该在内核里，却被漏到了界面上。**

反过来说，八十行能跑起来，就证明「内核与外壳分开」做到了。

## 11.5.6 页面不决定能不能执行

这里有一条铁律，也是本章错误模式里记着的那条：

> **权限判断不能写在前端。**

原因不是「前端代码不好看」，而是 **它根本不可信**。绕开界面，直接往 WebSocket 上发一条 `{"type": "confirm", "key": "…", "verdict": true}`，前端那些 `if` 一行都不会跑。

但话说完整：**审批放在服务端，也还不是安全边界。** `decide()` 会查这个 key 有没有被批过。它挡住「同一件事做两遍」，也挡住「随手批一个不存在的 key」。它挡不住**「连着 WebSocket 的人假扮成你」**。

所以立场说清楚：

| 问题 | 这一章的答案 |
| --- | --- |
| 前端能决定允不允许吗？ | 不能，它只是显示和转达 |
| 服务端能挡住伪造的批准吗？ | 挡得住「批过又批」，挡不住「假扮成你」 |
| 那谁来解决「假扮成你」？ | 认证与多用户隔离——第 16 章；沙箱边界——第 15 章 |

**本地跑、只有一个用户时，这套是够的。** 一旦放到公网上，认证就是必需项，不是加分项。认证就是先让你证明「你是你」，再放你进门。

## 这一节的边界

- **没有认证，没有多用户隔离。** 上面那张表说清了。
- **没有断线续传的增量补偿。** 重连靠日志重放整屏，不是「接着上次继续流」。
- **没有真正的移动端。** 下一节做出来，但只到「能用」，不到「好用」。

到此为止，Harnex 第一次有了一个网址。你甚至能发给朋友，但你还不敢。界面上那些没处理的地方，一落到别人手里就立刻露出来：点了没反应、出错没提示、卡住了也不知道。下一节收尾。
