# 11.2 流式的实现与两条流合成

## 11.2.1 写到一半要去调工具

上一节讲的是「边生成边送」：模型吐一段，屏幕就显示一段。可真接进 Harnex，这个办法立刻撞上一个坎。

Harnex 的回复不总是纯文字。它常常先说一句「我先看一下这个文件」，再发起一次 `fs_read` 调用。拿到内容之后，接着说下一句。

`fs_read` 是一次工具调用。工具调用里，动手的不是模型。模型只输出一句话，意思是「我要用某个工具办某件事」，后面跟着工具名和参数。真正去读文件、去跑命令的，是 Harnex 这边的代码。

流式下，这段过程是一块一块到达的：

```text
块 1   "我先"
块 2   "看一下"
块 3   "这个文件"
块 4   tool_calls: [{index: 0, function: {name: "fs_re"}}]
块 5   tool_calls: [{index: 0, function: {arguments: "{\"pa"}}]
块 6   tool_calls: [{index: 0, function: {arguments: "th\": \"src"}}]
块 7   tool_calls: [{index: 0, function: {arguments: "/a.py\"}"}}]
块 8   （结束）
```

问题在第 4 块到第 7 块：**工具名和参数是分批送来的，而且每一批只有半截。** 第 5 块那个 `{"pa` 单独拿出来，不是一段完整的 JSON。

JSON 是程序之间传数据用的一种文本格式。长这样：`{"path": "src/a.py"}`。`json.loads` 就是把这种文本读成程序能直接用的数据。半截的文本喂给它，它读不懂，会直接报错。程序里管这种「跑到这里出错、把控制权交出去」叫抛异常。

所以第一条规矩：

> **工具调用的参数必须缓冲到完整，才能解析。不能边收边 `json.loads`。**

缓冲就是先攒着，攒齐了再动。第二条规矩不同，它管的是文字。模型说「我先看一下这个文件」的时候，它其实还没看到文件。这句话可以立刻显示给用户，因为用户看的就是这个过程。但 **Harnex 不能拿它做决定**。真正要做的事，要等第 8 块之后才定下来。

一句话：一路是文字，边收边拼。另一路是工具调用，攒齐了才能解析。两路要分开处理：

```python
# harnex/llm/stream.py（续）—— 把一次流式响应拆成文本与工具调用两路
# 只用标准库；不需要联网，喂一串事先攒好的块就能跑。
import json


def consume_stream(stream):
    """收完一次流式响应：文字边收边拼，工具参数攒齐了再解析。"""
    text_parts = []
    calls = {}          # 按 index 攒：{0: {"name": "fs_read", "args_buf": "..."}}

    for chunk in stream:
        # extract_deltas 是它的「一次可能几段」版本：统一成列表，调用方不用分支
        for delta in extract_deltas(chunk):
            content = delta.get("content")
            if content:
                text_parts.append(content)      # 文字可以来一段拼一段

            for tool_call in delta.get("tool_calls", []):
                index = tool_call["index"]
                if index not in calls:
                    calls[index] = {"name": "", "args_buf": ""}
                slot = calls[index]             # 同一个 index 就是同一次调用

                func = tool_call.get("function", {})
                if func.get("name"):
                    slot["name"] = func["name"]
                slot["args_buf"] += func.get("arguments", "")

    # 循环走完，参数才算齐。边收边解析会拿到 `{"pa` 这种半截 JSON
    parsed = []
    for index in sorted(calls):
        slot = calls[index]
        try:
            args = json.loads(slot["args_buf"])
        except json.JSONDecodeError as exc:
            # 参数不是合法 JSON：留一条带错误的记录，不要整轮丢异常
            parsed.append({"name": slot["name"], "args": None, "error": str(exc)})
            continue
        parsed.append({"name": slot["name"], "args": args, "error": None})

    return {"text": "".join(text_parts), "calls": parsed}

# 跑起来看到：{"text": "", "calls": [{"name": "fs_read", "args": {"path": "src/a.py"}, "error": None}]}
# 参数是一点一点到的，所以 args 只能是攒完之后的结果。
```

三个细节。

- **`calls` 用 `index` 做键，不是用 `name`。** `index` 是这一轮里第几次调用。一轮里可能两次调用同一个工具，比如同时读两个文件。用名字做键，这两次会被并成一条。
- **`slot["name"] = func["name"]` 是覆盖不是拼接。** 工具名通常一次送全，只是送来的时机不固定。真正需要拼的是参数（`arguments`），所以只有它用 `+=`。
- **解析失败不抛异常，记进 `error` 字段往下传。** 这是 10.2 那条「失败是一种返回值」的第三次出现。**流式的边界同样不能是一个异常终止点。**

## 11.2.2 模型输出和命令输出

到这里，`consume_stream()` 管的是第一条流：**模型输出流**。

第二条流在 7.2 就埋好了。它是 `run_streaming()` 的 `on_line` 回调。回调是这么个东西——你把一个小函数交给别人，事情发生时它替你去叫那个函数一次。命令每输出一行，`on_line` 就被叫一次。命令一行一行往外滚，这就是 **命令输出流**。7.2 当时留了一句「接口先定下来，接线以后再说」。现在到了接线的时候。

两条流在时间上交错，还会互相嵌套：

```text
模型流   "我先跑一下测试"
命令流   $ pytest -q
命令流   .....F....
命令流   1 failed, 3 passed in 0.4s
模型流   "有一个用例挂了，我看下原因"
```

用户看到的应该是**一条时间线**，不是两块割裂的框。

要在界面上做出这条时间线，靠的不是前端排版的手艺，是**协议**。协议是双方事先约好的消息格式：谁先说、用什么名字说，都写死。

> **别让前端去猜「现在该显示什么」。让运行时把发生的每一件事，都翻译成一个带类型的事件推出去。**

事件就是「发生了一件事」的通知，带一个类型标签。前端收到一条，就知道该画什么。

具体做法，是给运行时加一个统一的事件出口：

```python
# harnex/protocol/events.py —— 所有要推给客户端的东西，统一成带 type 的事件
def emit(kind, **payload):
    """拼一条事件。type 和日志里的 kind 同名（展示专用的事件除外）。"""
    return {"type": kind, **payload}


def on_tool_line(name, line):
    """7.2 的 on_line 回调：命令每打印一行，就变成一条事件推出去。"""
    # push 是「把事件送出去」的出口，由客户端那一层提供（11.5 会看到它的用法）
    push(emit("tool_output", tool=name, line=line))

# 跑起来看到：{"type": "tool_output", "tool": "pytest", "line": "1 failed, 3 passed"}
```

事件类型就那么几种，一张表说得清：

| 事件 | 什么时候发 | 客户端拿它做什么 |
| --- | --- | --- |
| `assistant_delta` | 模型吐出一小段文本 | 追加到当前气泡 |
| `tool_start` | 一次工具调用开始 | 显示「正在执行 pytest…」 |
| `tool_output` | 命令流吐出一行 | 追加到折叠的执行日志里 |
| `tool_result` | 一次工具调用结束 | 收起「正在执行」状态 |
| `todo_update` | 清单变了（9.2） | 重画侧栏那张清单 |
| `approval_request` | 有危险动作要问（11.4） | 弹一个审批框 |
| `approval_denied` | 用户拒了（11.4） | 把审批框标灰，补一句「已拒绝」 |
| `turn_done` | 这一轮结束 | 停止加载动画 |

表里的「客户端」指外面那层界面，浏览器页面、桌面窗口都算。表里的「气泡」指对话里一块一块的框子。

**`tool_start` 是这一节新加的。** 前面几章的工具执行只有「调用」和「结果」两个时刻，因为没人看中间。现在有人看了。不告诉客户端「开始了」，那个「正在执行 pytest…」就永远显示不出来。

## 11.2.3 假装在流式，中间仍空白

`tool_start` 这条事件，还牵出一个体验上的关键点。

流式解决了「模型在想」那段空窗，没解决「工具在跑」那段。一次 `npm install` 跑三分钟。这三分钟里模型不吐任何字，界面上又安静下来。**用户刚从非流式的坑里爬出来，又掉进另一个。**

所以 `tool_start` 要立刻发。就像仪表盘上先亮一盏「正在跑」的灯，人看见灯亮着，就知道车在动。客户端还要拿它做一件事。**在没有真实增量的时间里，填一个假的、但在诚实描述状态的东西。**

```text
正在执行 pytest…（已 3.2s）
```

这句话不是「假装有输出」。它说的全是真话：真在跑 pytest，真过了 3.2 秒。它填的是**感知空窗**，也就是用户看不到任何反馈的那段时间。它填的不是内容。这条线要划清。11.6 的验收里还会出现同一句话：**填充物必须描述真实状态，不许编。**

## 11.2.4 边出字不改日志

最后一个决定，也是这一节最重要的一条。

流式产生了大量的增量块。要不要把它们全写进会话日志？

会话日志是一路聊下来的流水账，回放、排查都靠它。

**不写。** 那条 `assistant_message` 存的仍然是**整段结果**。不是几百个碎片。三条理由：

- **日志是真相源，不是展示缓冲区。** 真相源就是「起争议时以它为准」的那一份。屏幕上那个逐字动画只是一次显示，增量是显示用的零件，不是事实本身。
- **它会让日志膨胀几十倍。** 一条 500 字的回复会变成上百条事件，而它们的信息量加起来等于一条。
- **它不可读。** 三天后你想看「它当时怎么说的」，不想读一百行碎片。

这里有一处必须交代清楚的矛盾。第 6 章的不变式一说「模型可见即已记录」。不变式是一条任何时候都得成立的规定。那如果进程在**流到一半**时崩了，已经显示给用户的那半段文字怎么办？它确实没进日志。

答案是：**那半段没有进入任何后续依赖。**

不变式一之所以重要，是因为模型下一轮会看到这些内容。而你需要能回答「它当时看到了什么」。但一段还在生成中的文字，还没被任何工具结果或后续推理引用过。它是可以丢的中间状态，不是需要重建的历史。**重做一次，得到的还是同一件事。**

所以处理很简单。流式只在内存里拼。`assistant_message` 在流结束时一次性写进磁盘。**崩在中间，丢的是一段动画，不是一条记录。**

## 这一节的边界

- **它没解决「工具慢」。** 它只保证慢的过程看得见。
- **它没做断线重连。** 客户端断开了，这段增量就没了。要接着看，得靠日志重放，11.5 会用上。
- **它没碰危险动作。** 现在接口变快了。`rm -rf build/` 一样畅通无阻，那要等 11.4 的刹车。

顺带说一件顺手拿到的事。一轮里如果模型同时发起了好几个互不依赖的调用，上面这段代码仍然是 **一个接一个地等**。下一节把这条也拆掉。
