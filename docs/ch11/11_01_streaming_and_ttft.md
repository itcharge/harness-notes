# 11.1 流式输出：体感速度与首字时延

## 11.1.1 三种等待

先做一个最小实验：同一个问题，问 Harnex 两次。

第一次用现在这套代码。`chat()` 会把整段回答生成完，再一次性返回。你按下回车，盯着空屏。到第 8 秒，整段话「唰」地出现。

第二次改成流式（`stream=True`）。模型每生成一小段，就往外送一小段。同样在第 8 秒结束。但从第 0.6 秒开始，字就在往外跳。

**总耗时一模一样。你却说第二次「快多了」。**

这就是第一个结论：**「快」不是一个指标，是两个。**

| 指标 | 含义 | 谁在感受它 |
| --- | --- | --- |
| **TTFT**（Time To First Token，首字时延） | 从发出请求，到第一个**可见**的字出现 | 人。它决定「有没有在理我」 |
| **E2E**（End-to-End，端到端耗时） | 从发出请求，到整段输出结束 | 人靠它估还要多久；它也算成本和吞吐（同一时间能服务多少人）的账 |

后面会反复提到 token。它是模型处理文本的最小单位。**粗略当成「一小段字」就够用。**

这两个数像仪表盘上的两块表。非流式下读数一样，流式把它们拆开。你几乎只盯第一块——**人只对第一个敏感**。

## 11.1.2 人能等多久

TTFT 要压到多少才够？人机交互（研究人和机器怎么配合的学问）里有一条几十年的经验线。三个阈值是 Jakob Nielsen 1993 年整理的。最早的数据可以追到 1968 年 Robert Miller 的研究：

| 阈值 | 人的感受 |
| --- | --- |
| **0.1 秒** | 像「我一按就出来了」，不觉得是机器在算 |
| **1 秒** | 思路不断。他能觉出一点慢，但还觉得自己在掌控 |
| **10 秒** | 注意力跑掉了。他会去想别的事，回来很难接上 |

这三个数不是绝对线，但方向清楚。**1 秒是「还在一起干活」的界限，10 秒是「人已经走了」的界限。**

放到 Agent 上还更严。非流式请求很容易撞到 10 秒——一次工具调用加一次推理就超了。这时 TTFT 几乎等于整段回答的时间。流式能把它压回「prefill 加第一个 token」。通常落在几百毫秒到两秒，正好压在 1 秒附近。

给 Harnex 定一条基线：

> **TTFT 的 P95（95% 的请求比它快）不超过 2 秒。任何超过 2 秒的无反馈空窗，都要有东西填。**

「无反馈空窗」是本章反复出现的词。11.2 与 11.6 各补一半。

## 11.1.3 边出字会让总时间略长

流式不是白给的。一次大响应被拆成几十上百个小块，每块都要过一遍网络、过一遍解析。工程上，它的 E2E 通常比非流式**长一点点**，几个百分点到十几个。原因有三条：

- **多了协议开销。** 每块都要包成一个 SSE 事件。SSE 全称 Server-Sent Events，是服务端一条条往外推的格式。客户端还要一块块解析。
- **少了一次性优化。** 非流式可以在整段生成完之后统一压缩、统一发送。
- **早停的机会被花掉了。** 有些提速手段依赖「提前知道要写多长」。流式下这个信息只能一点点确定。

**这点代价值。** 省下的不是时间，是「用户盯着屏幕、怀疑它死了」的那一段。那一段不是成本，是用户还愿不愿意继续用。

## 11.1.4 第一个字慢在哪

要压 TTFT，先看它花在哪。一次调用粗分两段：

- **prefill（预填充）**：把全部输入读一遍、算出内部状态。耗时和**输入多长成正比**。
- **decode（解码）**：一个 token 一个 token 往外吐。耗时和**输出多长成正比**。

TTFT 由 prefill 加「第一个 token 的 decode」组成。**在 Agent 场景里，prefill 才是大头。** Harnex 每轮输入都塞得很满：

```text
系统提示 + 技能清单（第 5 章）+ 待办清单（第 9 章）+ 全部历史 + 工具定义
```

这几块最短的也有几百 token，历史稍长就上千。用户那句话只有十几个 token。

最直接的一刀是前缀缓存。主流模型 API（调用模型的接口）都支持。开头和上次**一个字节都不差**时，服务端能复用算好的内部状态。重复的 prefill 就跳过了。Anthropic 公布的实测数字如下：

| 场景 | 无缓存 TTFT | 有缓存 TTFT | 成本变化 |
| --- | --- | --- | --- |
| 一段 10 万 token 的长文档问答 | 11.5s | 2.4s（−79%） | −90% |
| 多轮对话（长系统提示） | ~10s | ~2.5s（−75%） | −53% |
| many-shot 示例（1 万 token） | 1.6s | 1.1s（−31%） | −86% |

（数据出自 Anthropic 2024 年 8 月的提示缓存公告。同年 12 月转正式可用。缓存写入按 1.25 倍计价，读取按 0.1 倍。最小生效前缀 1024 token。）

最该记住的是第二行：**多轮对话的 TTFT 掉了七成五。** Agent 干的就是多轮对话。

但缓存有一条硬规矩：**前缀必须一个字节都不差，改一个字符整段作废。** 所以那份输入清单不能乱序，不能夹时间戳，也不能每轮把工具定义重新拼一遍。

第 5 章「技能清单要精简」在这里有了第二个理由。当时说的是省 token，现在多一条：**系统提示和技能清单都在前缀里。它们越稳、越短，命中率越高，TTFT 越短。** 技能描述里塞一句「当前时间 2026-10-11 20:11」看着无害。可它会让整个前缀每轮都变，缓存永远打不中。

## 11.1.5 从哪一刻开始计时

第一次量 TTFT，容易量出一个漂亮得可疑的数。原因通常是**计时点标在了「收到第一个字节」上**。

流式连接里，服务端常常先发一个心跳包，确认通道是通的。有的 SDK 还会先送一个块，里面只有 `usage`（用量统计）。SDK 就是调用模型服务的那套工具包。这些「第一个字节」到的时候，屏幕上什么都还没有。**它们既不是 prefill 结束，也不是用户看到东西的时刻。**

正确的计时点，是 **第一个装着可见内容的增量**：

```python
# harnex/llm/stream.py —— TTFT 计时：从「首个可见 token」算起，不是从首字节
# 只用标准库，不需要 API key：喂它一串现成的块就能跑。
import time


def measure_stream(stream):
    """收完一个流式响应，返回文本和两个延迟指标。"""
    started = time.monotonic()      # 起点只取一次，TTFT 和 E2E 都从它算起
    ttft = None
    parts = []

    for chunk in stream:
        # extract_delta 是正文下面讲的那个小函数：把一块 chunk 翻成看得见的文字
        delta = extract_delta(chunk)
        if not delta:
            continue                # 心跳包、usage 块：屏幕上还什么都没有

        if ttft is None:
            # 只在第一段可见文字到达时记一次，后面的块不再覆盖
            ttft = time.monotonic() - started

        parts.append(delta)

    return {
        "text": "".join(parts),
        "ttft": round(ttft or 0.0, 3),
        "e2e": round(time.monotonic() - started, 3),
    }

# 跑起来看到：{"text": "我先看一下这个文件", "ttft": 0.4, "e2e": 1.3}
# 三个数里只有 ttft 会因为「早一点开始出字」而变小；e2e 基本不动甚至略涨。
```

`extract_delta()` 从一个块里取出「给用户看的那部分文本」。取不到就返回空串。它把「协议层的字节」翻译成「用户层的字符」。**这条区分，就是计时点标在哪的分界线**。

## 11.1.6 看中间值和偏慢的那档

延迟数据是 **长尾分布**：大部分请求很快，少数极慢，极慢的几次最让人记住。

平均值在这里几乎没有信息量。一次 30 秒的卡顿，混进 100 次 1 秒的请求里。平均值只涨到 1.3 秒，看着完全正常。

所以延迟一律报 **分位数**——把数据从小到大排好，看某个位置上的数：

| 指标 | 看什么 | 对应体验 |
| --- | --- | --- |
| **P50** | 一半的请求比它快 | 一般情况有多顺 |
| **P95** | 95% 的请求比它快 | 用户「偶尔卡一下」的那一下，有多卡 |

P95 才是对得上基线的那一个数。它不温柔，但诚实。

## 这一节的边界

三件流式解决不了的事：

- **它不能让模型本身变快。** prefill 和 decode 是模型那边的成本。流式只是把等待摊开，让等待里有东西看。
- **它不能省 token。** 输出还是那么多。
- **它只是展示层的改动。** 下一节展开：流式改的是「数据怎么到用户眼前」，不该改「日志里记什么」。

到这里只解决了「压哪个数、量哪个数」。真接进 Harnex 还有个问题：**流到一半，模型说要调工具，怎么办？** 下一节处理它。
