# 11.4 审批中断：让人在流程中间插手（human-in-the-loop）

## 11.4.1 动手前先问一声

上一节结尾留了一句话：Harnex 现在仍然可以毫不犹豫地删掉你的目录。这一节装的就是那道刹车。

场景还是章首那个。Harnex 打算删 `build/` 这个目录。一条命令下去，你连插话的机会都没有。

第 7 章的 `guard()` 已经拦住一部分。`guard` 是守卫的意思，它专门检查一条命令能不能跑。不在白名单里的，一律不给跑。`rm` 就不在名单里，直接调它会被拒。

但它拦的是**「这条命令叫什么」**，拦不住**「这条命令要干什么」**。白名单里有 `python`，一门编程语言。它跑起程序来，能干的事很多。删文件、删目录，根本不用打 `rm` 这两个字。

所以一个动作能不能过 `guard()`，和它该不该做，是两回事。删构建产物，技术上完全合理。**只有你知道此刻不该删它**，因为你正准备拿这份产物做一次离线对比。

这一类要人来拿主意的，得换一种拦法：**停下来，问。**

第 7 章留过一个 `dry_run` 开关。当时讲明了：它只是一层「交互礼貌」，模型可以不理它，直接跑。真正要做到「跑之前必须有人点头」，得另有一套东西。这一节做的就是它。

## 11.4.2 同意或拒绝写进日志

停下来问了，问出来的答案存在哪？这是这一节最要紧的一个决定。

最直觉的做法，是在内存里放个变量。用户一点「同意」，就把这个值改成同意，循环接着往下跑。内存是程序跑起来时临时放东西的地方，程序一退出就没了。

这个做法和 9.2 那个「清单放局部变量」是同一个错。而且后果更重：

- **进程一崩，审批状态就没了。** 用户明明批过的那次删除，恢复以后得再问一遍。
- **事后查不到。** 三天后想问「这次操作是谁批的、什么时候批的」，答不上来。**审批记录是安全审计的一部分**，不能只活在内存里。

所以按第 6 章的老规矩办：**审批记成一条日志。当前是批了还是没批，从日志里算出来。**

事件就三个：`approval_request`（要问）、`approval_granted`（批了）、`approval_denied`（拒了）。每个都带一个 `key`。**这个 key 就是 10.4 的幂等键**，标识的是「这一件具体的事」。不是「这一类事」。

```python
# harnex/approval/gate.py —— 审批闸门：动手前问人，答案写进日志
# 这里第一次用 class：它只是把两样东西捆在一起——日志，和「怎么问人」。
# self 指「这一个闸门自己」；__init__ 是造它的时候跑一次，把两样存进去。
class ApprovalGate:

    def __init__(self, log, ask):
        self.log = log
        self.ask = ask          # 「怎么问用户」的回调：终端和网页问法不一样

    def decide(self, key, summary):
        """需要审批的动作先过这里。返回 True 才允许执行。"""
        # 先翻日志。崩溃重启后，同一个 key 不能问第二遍
        for event in self.log.events():
            if event["kind"] == "approval_granted" and event["key"] == key:
                return True
            if event["kind"] == "approval_denied" and event["key"] == key:
                return False

        # 日志里没有这个 key，才真的去问人
        self.log.append("approval_request", key=key, summary=summary)
        verdict = bool(self.ask(summary))        # 卡在这里，等用户点按钮

        if verdict:
            self.log.append("approval_granted", key=key)
        else:
            self.log.append("approval_denied", key=key)
        return verdict

# 跑起来看到：问一次 → 日志里多两条（request + granted）。
# 第二次拿同一个 key 进来，loop 在日志里命中，直接返回，不再问。
```

代码开头那个 `for` 循环，是全篇最要紧的几行。它干的事是：**程序恢复的时候先翻日志，翻到批过的记录就直接放行，不问第二遍。**

这一下就把 10.4 那套东西接上了。回想 `run_effect()` 的顺序。它先 `begin`，再执行，最后 `commit`：

```text
begin(key)  →  decide(key)  →  执行  →  commit(key)
   记账          问人           动手       销账
```

审批闸门插在中间。崩溃卡在任何一个箭头上，恢复时的行为都是定死的。**账本上没有 `commit` 的，按「没做过」处理。`decide()` 会自己去日志里找批准记录。** 批过的不会再问，没批过的重新问一次。这两种情况，都不会出现「删了两遍」或「批了却没删」。

## 11.4.3 和断点记在同一个位置

答案存进日志这件事，10.4 已经干过一次，只是防的东西不一样。

| | 10.4 检查点 | 11.4 审批闸门 |
| --- | --- | --- |
| **位置** | 动手之前 | 动手之前 |
| **问谁** | 磁盘上的日志 | 人 |
| **回答什么** | 「这件事可能正在做，恢复时核对」 | 「这件事允许做 / 不允许做」 |
| **防的是什么** | 崩溃后重复执行 | 执行了不该执行的 |
| **答案存在哪** | `effect_begin` 事件 | `approval_granted` / `approval_denied` 事件 |

两把锁都装在同一道门上。因为它们防的是同一件事：**在动手之前，留下一条能查的记录。**

这也是第 6 章那条「先落磁盘，再回内存」的又一次出现。只不过那次的「磁盘」是 JSONL，一种一行记一件事的文本文件。这次的「磁盘」，是另一个人的脑子。

## 11.4.4 提问要一眼看懂

闸门装好了，接下来的问题是它开口说什么。

一个糟糕的弹窗长这样。弹窗就是屏幕上冒出来、专门问你话的那个小框：

```text
是否允许执行 execute_shell？
[允许] [拒绝]
```

这等于把模型原本发的那句话原样甩给用户。用户看到的是一个函数名，加一句「是否允许」。他不知道要跑什么命令、为什么要跑、跑完会怎样。**这种弹窗的下场只有一个：用户开始闭着眼点「允许」，审批就变成了走过场。**

好审批要一次说清三件事：

| 要素 | 为什么要它 | 从哪来 |
| --- | --- | --- |
| **要执行什么** | 用户得看见那条真实命令 | 工具名 + 参数原文 |
| **为什么要它** | 这是当前任务里的哪一步 | 上下文里模型的最近一句意图 |
| **影响什么** | 出事了会波及什么、能不能撤销 | 需要 harness 自己算 |

第三条最难，也最值钱。它是 4.2 那个「好错误」翻过来说的样子：

> **好错误告诉模型「下一步该做什么」；好审批告诉人「这一步会波及什么」。**

两者干的是同一件事：把「原始细节」翻译成「对方能用的话」。只是读者不一样。对比一下：

```text
差：rm -rf build/
好：删除目录 build/（约 1200 个文件，是构建产物，可重新生成）
```

这两行只是举例。`rm -rf build/` 在 Harnex 里连 `guard()` 都过不去——11.4.1 说过 `rm` 不在白名单。真正动手删目录的，可能是一句藏在 `python` 里的脚本。**但弹窗要做的事不变**：不管模型发来的原文长什么样，都得把它翻成人话。

后半句里每个字都得 Harnex 自己去拿。目录里有多少文件，要用 `os.walk` 一个个数过去。`os.walk` 是程序里一个「把目录翻一遍」的函数。「是构建产物」得靠目录名，加上 `.gitignore` 里的记录来判断。`.gitignore` 是一个文件，里面写着「这些文件不用管」。「可重新生成」是从前两句推出来的结论。

**这些都不该指望模型自己说。** 它说的时候，你就得怀疑它在编。

算这些要花时间，所以有一道取舍：**只给真正危险的动作算。** 判据是「这个操作能不能撤销」。读文件、跑测试、查状态——撤销成本为零，不问。写文件、删目录、提交、推远端、发请求——撤销成本不是零，问，并且把影响算清楚。

## 11.4.5 用户拒绝之后

用户点了「拒绝」。然后呢？

这里有两个方向。

**一条是到此为止。** 循环退出，任务结束，烂摊子留给用户。

**另一条是把「不行」当成一条消息，交给模型。** 模型收到「用户拒绝了这次删除，原因：这份产物还要用来做对比」。它就有机会换一条路——比如先复制一份再删，或者干脆跳过这一步。

选第二条。理由是它和全书那条主线对得上：**把判断交出去，但把处理留着。** 人只管说「不行」，「那怎么办」是模型该干的活。这正是 9.3 讲的中途修正，只不过触发信号从「工具报错」换成了「人说不行」。

拒绝的那段话要按 4.2 的要求写：

```text
用户拒绝了这次操作（rm -rf build/）。
原因：这份构建产物还要用于离线对比。
请不要重试同一操作。可以换一条路，或者把这个目标交回给用户。
```

最后那句「不要重试同一操作」最关键。少了它，模型很可能礼貌地道个歉，然后换个写法再试一次。**用户看到的就是：我说了不行，它换个写法照做。**

## 这一节的边界

**第一，审批不负责拦住坏人。** 它能防的是「模型判断失当」，防不了「模型存心要绕」。一个足够坏的模型，可以想办法哄用户点同意。真正的安全边界在沙箱里，也就是 7.4 与第 15 章讲的把程序关起来跑。**审批是加在沙箱之上的第二层，不是替代。**

**第二，问得多细，上限是「人愿意点几次」。** 每一步都弹窗，用户第三天就闭着眼点允许了。所以光有「问」这个动作不够。还得定清楚：哪些必须问、哪些问一次就够、哪些根本不用问。**这一节做的是机制；策略是第 15 章那三档审批的活。**

**第三，没人看着的时候，它得有个退路。** 半夜跑的定时任务，没有人可以问。这时审批闸门要么按预设策略自动放行，要么停在「等待批准」上等人早上来处理。**不能悄悄跳过——那等于没装。**

到这里，Harnex 会流式了、会并行了、也会刹车了。但这一切都发生在终端里，也就是那个只能打字、只能看字的黑框框。下一节把它搬进浏览器。而搬的过程会冒出一个更要紧的问题：**这些东西怎么组织成一套接口。**
