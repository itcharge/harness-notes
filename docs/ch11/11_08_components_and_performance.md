# 11.8 组件、富内容与两处性能

## 11.8.1 五块组件，状态住在最上面

上一节那张表说的是「界面上有什么」。这一节说的是「这些东西摆在哪，谁替谁记事」。

先把「组件」这个词说清。组件就是界面上能单独拎出来的一块。输入框是一块，一条消息是一块，问你要不要放行的那张卡也是一块。界面一大，就得拆块。拆开以后，改一块不用碰别处。

Harnex 的界面拆成五块：

- **Sidebar**：侧边栏。放会话列表和待办清单。
- **Timeline**：时间线。一条从上往下排的事件流，说到哪儿排到哪儿。
- **Item**：时间线里的一条。一条消息、一张工具卡片、一张审批卡，都算一条。
- **Composer**：输入框。把话组织起来发出去的那一块。
- **Approval**：审批卡。就是问你要不要放行的那一块。

五块里只有 Timeline 的上一层存着东西：**这一轮收到的事件数组**。数组就是一串排好序的东西。其余四块只管画——给什么画什么，自己不记事。

「状态」指界面此刻得记住的东西：滚到哪儿了，哪张卡展开了，这一轮收到了几条事件。状态放在哪一层，是外壳工程最容易搞错的一件事。11.7.4 已经给过判据：一块界面只要自己存了东西，就有第二个真相的风险。落地到具体某一处，办法很朴素：**它需不需要知道「我是第几条」？** 需要，多半说明状态放错了层。

审批卡换位置，是这一节最直观的改动。11.4 那个弹窗是单独冒出来的一块，跟时间线不在一处。答完它，还得自己回想「刚才说到哪一步了」。放进时间线，它就落在「要动手的那一步」旁边，上下文就在隔壁。

## 11.8.2 富内容：谁来把文字变成界面

「富内容」是相对纯文字说的：带加粗、带表格、带颜色、能点开的，都算。

时间线里会出现三种东西：模型说的话、命令吐出来的字、代码改动。

三种里只有第一种带格式。模型的话用 Markdown 写。Markdown 是一种「用几个符号表示格式」的写法。两个星号包住就是加粗，三个反引号包住就是一段代码。写的时候像纯文字，看起来才有格式。

浏览器只认 HTML，不认 Markdown。所以 `**` 不会自己变粗，中间得有人转一道。

三条路：自己写解析器、用现成的库、让服务端先转好。解析器就是「把一种写法翻成另一种写法」的那段程序。**推荐第二条**，因为 Markdown 的边角比看着多。表格、套着的列表、行内代码里的星号，都是坑，自己写迟早出岔子。

不管走哪条路，有一件事不能省。**工具输出是外部内容，不能直接塞进 `innerHTML`。** 外部内容指这段字不是 Harnex 写的，而是从别处来的。可能是一个网页、一份日志、一次报错。`innerHTML` 是「把一段 HTML 原样插进页面」的写法。这段字里写着 `<script>`，是完全合法的。塞进去，等于让写这段字的人在你的页面上跑程序。这类攻击有个名字，叫 XSS（跨站脚本）。「跨站」是说，攻击从另一个站点过来。

隔离分三层，从轻到重。一是转义。转义是把 `<` 这类符号换成「只是文字」的写法，浏览器看见它就不再当标签。二是用 `textContent`，只把这段字当文字放进去，不当代码。三是放进 `iframe`——页面里再开一个小页面，四面封起来，一块权限都不给。还有第四层：干脆不渲染，只显示「点开看原文」。

代码改动走另一条路。它来自工具结果里的补丁。补丁记的是「哪几行删了、哪几行加了」。按固定的颜色规则画就行——**别让模型自己生成 HTML**。第 12 章的轨迹视图要用同一套渲染，到时候不必重写。

## 11.8.3 工具卡片：三个状态，一个时间

时间线里数量最多的是工具卡片。一次任务几十次调用，一屏上大半是它们。它们决定这一屏读起来累不累。

三个状态：**进行中、成功、失败**。11.6 说的「正在执行 pytest…（已 3.2 秒）」就是第一个状态。

那个 3.2 秒从哪来？**从 `tool_start` 到达那一刻起算**，不用模型自报。模型说「大约 5 秒」不能信。它说的是估计，不是实际花了多久。事件到达的时刻是硬事实，记在日志里。

卡片默认收起，只留一行：工具名、状态、耗时。点开才看得到输出。理由很实际——一次 `pytest` 两百行，全展开就把对话顶出屏幕。11.6.4 那个轨迹视图就是「全部展开」的版本：同一个组件，两种密度。

建卡片这一步要守住 11.8.2 那条。

```javascript
// harnex/apps/server/static/card.js —— 工具卡片：三个状态，耗时从事件到达时起算
// timeline 是页面上那条时间线，整页只有一个（11.5 建的）
function openCard(event) {
  const card = document.createElement("div");
  card.className = "card running";
  card.dataset.id = event.tool_call_id;
  card.dataset.group = event.group || "";
  card.dataset.since = String(Date.now());   // 起算点：事件到达这一刻，不用模型自报

  const title = document.createElement("span");
  title.className = "name";
  title.textContent = event.name;            // 外部内容一律 textContent，不拼 HTML
  card.append(title);
  timeline.append(card);
  return card;
}

// 跑起来看到：时间线上多出一张卡片，标题是工具名——名字来自事件，不是模型嘴上说的。
// 卡片一开始带 running（黄），收到 tool_result 之后由另一个函数改成 ok 或 fail。
```

`dataset` 是往这个元素身上贴标签的写法，贴上去以后能再查出来。这里贴了三样：哪次调用、属于哪一批、什么时候开始的。

并行的那两条腿要并排。11.3 给每次调用打了 `group` 标记。同一个 `group` 的卡片摆成两栏，而不是前后脚排成一列。**时间线上的一前一后，会让人以为是串行的。** 串行就是一件干完再干下一件。

## 11.8.4 两处性能：按帧合并，只画看得见的

界面长到这一步，会撞上两个数。

第一个数是**流式的段数**。模型一秒能吐三四十段，每段来了就改一次页面，一秒钟重排四十次，滚动就开始抖。重排是浏览器重新算一遍每样东西该在哪、再重画。解法是**攒一帧**：事件照收，渲染排到下一帧，一帧只画一次。屏幕一秒换六十次画面，每次叫一帧。人看不出差别，浏览器省下三十九次重排。

第二个数是**事件总数**。会话跑几天就是几千条，全画出来，光建节点就要几百毫秒。节点是页面上一个实实在在的元素，一条消息、一张卡片都算一个。解法是**只画视口里的**。算出滚动位置对应第几条到第几条，两头各多留一屏当缓冲。上下用空白撑住高度，滚到哪儿再换一批。视口就是屏幕上真正看得见的那一块。

两处都不改协议，也不改内核。它们只跟「屏幕上放多少东西」有关，是外壳自己的账。

```javascript
// harnex/apps/server/static/paint.js —— 两处性能：一帧画一次，只画看得见的
// 依赖 render.js 里的 render()：这里只管「什么时候画」，不管「怎么画」
let queued = [];          // 排着队、等这一帧画的事件
let scheduled = false;    // 这一帧的活是不是已经排上了

function schedule(event) {
  queued.push(event);
  if (scheduled) {
    return;               // 已经排过一帧，这一帧不再排第二次
  }
  scheduled = true;
  requestAnimationFrame(function () {    // 浏览器画下一帧之前会叫我们一次
    scheduled = false;
    const batch = queued;
    queued = [];
    batch.forEach(render);               // 一帧内来多少条，都在这里画完
  });
}

function visibleRange(scroller, rowHeight) {
  const top = scroller.scrollTop;
  const height = scroller.clientHeight;
  const first = Math.max(0, Math.floor(top / rowHeight) - 20);   // 上面多留 20 行
  const last = Math.ceil((top + height) / rowHeight) + 20;       // 下面也多留 20 行
  return [first, last];
}

// 跑起来看到：模型吐字时页面不再一跳一跳，输入框里的字也不会被顶走；
// 三千条的会话一次 DOM 只建十几行，滚动条长度照旧对得上。
```

## 11.8.5 为什么它天生能装进一个桌面窗口

最后剩一个问题：这个页面凭什么能变成 WorkBuddy 那样的桌面应用。

因为桌面端的外壳，就是**一个浏览器窗口，外加一层能调系统接口的东西**。网页跑在里面，协议照旧，渲染照旧——换的是窗口，不是协议。上一节说过「每一块都有出处」，到了桌面端还成立：出处没变，只是换个地方显示。

多出来的部分都是跟系统打交道：托盘图标、全局快捷键、把文件拖进来、发通知。还有两件最容易被忽略的：**签名**和**自动更新**。签名是给安装包盖一个能验的章，它回答「用户凭什么信任这个安装包」。自动更新是让旧版本自己换成新版本，它回答「新版本怎么悄悄换上去」。这两件做不好，前四项做得再顺也没人敢装。

它们不在本章。它们属于「把东西送到别人机器上」，是第 20 章的事。

本章到这里，外壳从八十行长到了能天天用的样子。内核那行代码一行没动——**这句话才是这八节真正要证明的东西。**
