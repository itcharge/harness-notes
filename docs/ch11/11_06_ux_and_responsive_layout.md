# 11.6 体验清单与响应式布局

## 11.6.1 别人打开网页之后

上一节结束时，Harnex 有了一个网址。你把它发给了同事。

十分钟后他回你一句：「你这个东西是不是坏了？」

你打开他的截图，明白了。他点进去，输入一句话，然后屏幕上什么都没有。因为第一轮要先花 1.8 秒把输入读一遍，才轮到吐字。这段「只读不写」的时间叫 prefill，11.1 讲过。而你那套前端在收到第一个字之前，什么状态都不显示。他等了 3 秒，下了结论。

**功能都对了，体验全丢了。**

这一节要收掉的，就是这些「朋友一眼就能挑出来」的问题。做法不是把界面做漂亮。**重点是处理好「沉默」和「出错」这两种情况**——体验差的地方，九成都出在这两处。

## 11.6.2 三处空白怎么填

先接回 11.1 那条基线：**任何超过 2 秒的无反馈空窗，都要有东西填。**

界面上有三处空窗，来源各不相同。它们都不算出错，只是「还没轮到说话」：

| 空窗 | 什么时候 | 填什么 |
| --- | --- | --- |
| **首字之前** | 用户按了回车，模型还在 prefill | 立刻显示用户消息 + 一个「思考中」指示 |
| **工具执行中** | 模型不吐字，命令在跑（11.2） | `tool_start` 触发的状态条：正在执行什么、已多久 |
| **审批等待中** | 弹了框，等你点（11.4） | 状态条切换成「等待你的确认」，并把那条命令再贴一次 |

三处的填充物守着同一条纪律：**必须描述真实状态，不许编。**

「正在执行 pytest…（已 3.2 秒）」是真的。「正在思考…」在真的思考时也是真的。但「马上就好」不是——你并不知道马上是多久。**填充物是为了让人停止瞎猜。编出来的话，只是把瞎猜换了个说法。** 一旦用户发现那句安慰是假的，下次连真的提示他也不信了。

工具执行那一处还有个朴素的办法：一个看门狗计时器。看门狗就是门口那条狗：有动静它不出声，长时间没动静它就叫一声。**没有新事件的时间超过阈值，就把当前状态再强调一遍。**

```javascript
// harnex/apps/server/static/console.js —— 空窗看门狗：沉默超过阈值就再报一次当前状态
let watchdog = null;      // setTimeout 给的编号，用来取消上一次的闹钟

function armWatchdog(label, seconds) {
  if (watchdog) {
    clearTimeout(watchdog);      // 先撤掉上一次，否则闹钟会叠好几个
  }
  watchdog = setTimeout(function () {
    showStatus(label + "……（已 " + seconds.toFixed(1) + " 秒）");
    armWatchdog(label, seconds + 1);     // 还在沉默，就加一秒再报
  }, 1000);
}

// 每收到一个事件就调它：有动静了，「正在执行…」就该消失
function disarmWatchdog() {
  if (watchdog) {
    clearTimeout(watchdog);
    watchdog = null;
  }
  clearStatus();
}

// 跑起来看到：工具跑着不吭声时，状态条每秒换一次「……已 N 秒」；
// 一有输出进来，disarmWatchdog 被叫一次，这条提示立刻消失。
```

它的逻辑很直白：**只要还有事件进来，就一直不出声。一旦断了，就每秒提醒一次「我还在做这件事」。**

## 11.6.3 出错时用白话

第二类问题：出错。

第 4 章给模型设计过一套「好错误」：短、带路径、指向下一步动作。那是写给模型看的。**界面上的错误有两套读者。** 这是 10.5 讲过的拆法，到这里才有了具体样子：

| | 给模型的错误 | 给界面的错误 |
| --- | --- | --- |
| 读者 | 模型 | 使用者 |
| 内容 | 精确到字段的错误原文 | 发生了什么、可以怎么办 |
| 长度 | 越短越好 | 允许长，但要求有结构 |
| 要不要技术细节 | 必须要有 | 折叠起来，默认不显示 |

界面上那条错误，最少要有三块：

```text
这次没有完成。
发生了什么：执行 npm install 时网络超时（已重试 2 次）。
你可以：点「再试一次」，或者把网络代理配置告诉它。
[查看详情]        ← 折叠区里放退出码、原始输出、轨迹路径
```

「你可以」那一栏是关键。**少了它，用户唯一能做的就是把同一个按钮再点一次。** 这和 10.5 那份失败报告说的是同一件事：报告只摆事实和范围，不替人下结论。界面把它又往前推了一步，把那个范围翻成几个能点的选项。

顺带说个反例：**别把 traceback 直接摊在界面上。** traceback 是程序出错时打出来的一大段内部调用记录。它不解决问题，只让人觉得自己拿到的是半成品。折起来就够了，真想看的人会点开。

## 11.6.4 能看历史和过程

第三件事：**能回去看。**

因为会话记在日志里（第 6 章），这件事几乎是白送的。一个会话列表，就是一列 JSONL 文件：

```text
sessions/20261011-091233.jsonl
sessions/20261011-134501.jsonl
```

点开任意一份，把事件按 `seq`（每条记录自带的顺序号）重放给渲染器。**还是 11.5 那同一个渲染器**，因为协议 `type` 与日志 `kind` 同名。列表里再带两个小字段：会话开头那句话，拿来当标题；最后一条事件的时间，拿来当「上次用过」。

轨迹就是这次任务从头到尾每一步的记录，轨迹视图比会话视图细一层。它把 `tool_start` / `tool_output` / `tool_result` 一并摊开，还能显示 11.3 那个 `group`。**并行的两条腿，在界面上应该并排站两栏，不该挤成交错的一行。** 这是 11.3 那个字段第一次真正派上用场。

## 11.6.5 手机上也能看

第四件事：手机上能用。

这件事能做得很小。Agent 的界面天生适合小屏。**它本来就是一条从上往下的时间线**：消息、工具执行、清单、审批框，全挤在一列里。要动的只有两处：

```css
/* harnex/apps/server/static/console.css —— 窄屏下把侧栏收起来，让时间线占满 */
.console { display: grid; grid-template-columns: 260px 1fr; height: 100vh; }

@media (max-width: 720px) {
  .console { grid-template-columns: 1fr; }      /* 侧栏收起，改从顶部抽屉打开 */
  .sidebar  { display: none; }
  .composer { position: sticky; bottom: 0; }    /* 输入框常驻底部 */
}
```

两点就够了：**窄屏把侧栏收起来**，待办清单和会话列表改从顶部抽屉进。**输入框钉在底部。** 剩下的交给浏览器自己折行。时间线本来就是流式布局——元素按顺序往下排，一行装不下就换行，不需要另写规则。

这一步还有个不显眼、却要提前做的准备。**PWA 是让网页像 App 一样装到手机桌面上的一套做法**，给界面留这么个「装到桌面」的入口，是第 20 章的活。而这节做的响应式布局，是那次安装的前提。一个在小屏上没法用的站点，装到桌面上也还是没法用。

## 11.6.6 一页检查清单

把上面这些收成一份清单。用法是：**每次给 Harnex 加了新能力，拿它过一遍。**

| 场景 | 要求 |
| --- | --- |
| 用户按下回车 | 消息立刻上屏，并出现「思考中」状态 |
| 模型开始输出 | 第一个字到达时切换成实时流，状态条消失 |
| 工具开始执行 | 显示工具名与「已用多久」，命令输出实时滚动 |
| 工具执行超过 5 秒 | 状态条持续更新，不静默 |
| 出现危险动作 | 弹审批框，含「做什么 / 为什么 / 影响什么」三项 |
| 用户拒绝 | 模型换一条路，且界面明确显示「已拒绝，它正在换方案」 |
| 出错 | 显示「发生了什么 + 你可以怎么办」，技术细节折叠 |
| 任务结束 | 加载动画停止，清单显示最终进度 |
| 刷新页面 | 历史与清单从日志重建，界面与刷新前一致 |
| 手机打开 | 无横向滚动，输入框可达 |

清单里「刷新页面」那一条值得多看两眼：**它是对整套架构的一次压力测试。** 刷新之后界面能自己回到原样，说明状态真的在日志里。一刷就丢，说明有东西还留在内存里，没落盘。

本章的验收标准里有两条延迟指标，这里明确它们怎么量：

- **TTFT P95 ≤ 2 秒**——P95 指 95% 的请求都比这个数快。计时点按 11.1 的规矩，从**首个可见增量**算起，不是从首字节。
- **任何超过 2 秒的无反馈空窗清零**——这条比上一条更严。它管的是「工具执行中」「审批等待中」这些流式管不到的地方。

两个数都要进轨迹（12.1 会讲怎么落）。**没有数字，「体验变好了」就只是一种印象。**

## 这一节的边界

- **没有做无障碍**（键盘导航、屏幕阅读器标签）——让看不见屏幕的人、只用键盘的人也能把界面用下来。它是真实需求，但不在本章范围。
- **没有做主题、国际化。** 它们不影响「用得下去」这个目标。
- **前端仍然不是安全边界。** 这一节一个字都没改这条结论。

到此，Harnex 有了仪表盘和刹车，也有了一个能发给别人看的网址。你甚至可以让朋友真的用它。**但他用不了多久就会问第二个问题：**

> 能不能把刚才那次任务的执行过程给我看看？

而你现在只知道它「做完了」或者「失败了」，还不知道它怎么一步步走到那个结果。那是第 12 章的事。
