# 11.3 并行工具调用

## 11.3.1 两次等待并成一次

用户问了一句很普通的话：

```text
你> 这个项目现在什么状态？
```

模型要两样东西。一样是当前目录下有哪些文件，用 `fs_list` 去问。另一样用 `shell: git status` 问：git 里有没有未提交的改动。

git 是管代码版本的工具。`git status` 把「哪些文件改过、还没提交」列出来。

一句话里要两样东西，模型就在一轮里发起了两次调用。

现在这套 `run_turn()` 是一个简单的 `for` 循环。循环就是「把同一件事一件一件做下去」，写成代码就是一个 `for`：

```python
# 串行版：上一条的结果回来了，才轮到下一条
async def run_turn(msg):
    for call in msg.tool_calls:
        # args 就是第 3 章那行 json.loads(call.function.arguments) 的结果
        result = await registry.call(call.function.name, args)
```

第一个跑完，再跑第二个。这叫串行，意思是排队，一个做完才轮到下一个。两次各花 1.2 秒和 1.5 秒，用户等了 2.7 秒。

**但这两件事之间没有任何关系。** `fs_list` 不需要 git 的输出。`git status` 也不关心目录里有什么。它们唯一的共同点是「都还没做」。

如果同时发起，这叫并行，意思是两件事一起做。用户等的就变成两者里更慢的那个。`max(1.2, 1.5)` 就是取两个数里大的那个，答案是 **1.5 秒**。省下的 1.2 秒不是挤出来的，是本来就白白浪费掉的。

## 11.3.2 一起等这几个调用

要同时发起，得先有「同时」这件事。Python 里的 `asyncio` 就是干这个的。它让程序在等某件事的时候，先去干别的。

它有个很实用的小工具，正好办这件事，叫 `asyncio.gather()`。它接收一堆可以「先挂起、等会儿再接着做」的活，然后一起等。这种活叫协程，写起来像普通函数，只是前面加个 `async`。

```python
import asyncio


async def fetch_all():
    # gather 收一串「还没跑的函数调用」，把它们同时放出去，再一起收结果
    return await asyncio.gather(task_a(), task_b(), task_c())

# 三个任务各等 1 秒，总耗时约 1 秒，不是 3 秒。
```

`gather()` 返回一个列表，**列表的顺序和你传进去的顺序一样**。三个要点：

- **它不会卡住整个程序。** 卡住是这么回事：一个任务在等，别的任务一步也走不了。`await` 的规矩是「等到这里，先把控制权让出去」，所以几个任务真的在重叠。
- **结果的顺序是传入顺序，不是完成顺序。** 第二个先跑完，结果还在列表第二位。这一点省心，不用自己配对。
- **默认一个出错，整批都算失败。** 只要有一个抛异常，`gather()` 就把那个错抛出来，别家的结果也不要了。**别家的活不会跟着停。**它们照样跑到结束，只是结果没人接了。不过 Harnex 的工具层早就把报错兜成了文本，4.2 那条铁律讲的就是这个。所以这里一般碰不到。`return_exceptions=True` 可以再兜一层。报错也会变成列表里的一个值。

## 11.3.3 看它们是否互相依赖

并行这么好用，但不是所有调用都能并行。判据只有一条，而且它比听起来更严：

> **两个调用能并行，当且仅当「谁也读不到谁的结果」。**

换句话说：**一个调用的参数，是不是用另一个的输出算出来的。**

对照几个例子：

| 调用 A | 调用 B | 能并行吗 | 为什么 |
| --- | --- | --- | --- |
| `fs_list(path="src")` | `shell("git status")` | 能 | B 的参数里没有 A 的结果 |
| `fs_read(path="src/a.py")` | `fs_read(path="src/b.py")` | 能 | 目标文件是硬编码的，互不依赖 |
| `search_docs(query="重试策略")` | `fs_read(path=x)` | **不能**（除非 x 已知） | 如果 x 是搜出来的第一条命中，B 就在等 A |
| `apply_patch(path=p, ...)` | `shell(f"pytest {p}")` | **不能** | 测试目标要等写完之后才成立 |

这张表里藏着一个容易犯的错：**用「任务像不像一类」来判并行。**「读两个文件」看起来是一类，「读文件 + 查 git」看起来不是一类。可真正决定能不能并行的，是**数据依赖**——一个的输出是不是另一个的输入。它跟任务分类没关系。

「读 a.py 和读 b.py」能并行，是因为文件名都已知。已知的意思是名字直接写在代码里，行话叫硬编码。如果第二个文件名要从第一个的内容里解析出来，那就是有依赖。哪怕两个都是 `fs_read`，也照样串行。

## 11.3.4 把一批调用拆开跑

```python
# harnex/tools/parallel.py —— 同一轮里的多个工具调用：能并行就并行
# 只用标准库；registry 和 log 都从前面的章节来（工具注册表、会话日志）。
import asyncio


async def run_calls(calls, registry, log):
    """把一轮里的多个调用发出去：互不依赖的同时跑，各自记各自的日志。"""
    # 这一批共用一个并发标记，事后靠它把交错的事件还原成两条腿
    group = "p" + str(next_seq(log))

    async def run_one(call):
        """一条腿：开工记一笔，收工记一笔。"""
        log.append("tool_start",
                   tool_call_id=call["id"],
                   name=call["name"],
                   group=group)
        result = await registry.call(call["name"], call["args"])
        log.append("tool_result",
                   tool_call_id=call["id"],
                   name=call["name"],
                   group=group,
                   content=result)
        return result

    tasks = []
    for call in calls:
        tasks.append(run_one(call))

    results = await asyncio.gather(*tasks)
    return list(results)

# 跑起来看到：两个调用总耗时约等于「最慢的那一个」，不是两个相加。
# 日志里两条 tool_start 挨着出现，两条 tool_result 的先后可能反过来。
```

`next_seq(log)` 只是个取当前事件条数的函数，用来拼一个不重复的组名。真正值得说的是 `group` 这个字段。

组名是给日志看的，理由在下一小节。

## 11.3.5 同时跑时输出会交错

**并行不是免费的，它的账单开在日志上。**

一件一件做的时候，事件流就是真实时序。`seq` 从 0 一排到底，每条接着上一条。`seq` 是日志给每条事件编的号。

并行之后，这个号的含义悄悄变了。6.1 的 `append()` 每写一条就把 `seq` 加一。并发时谁先写完谁先拿号，**所以 `seq` 是完成顺序，不是开始顺序。**

一次并行的轨迹落进日志会是这样：

```text
{"seq":7,  "kind":"tool_start",  "name":"fs_list",  "group":"p7"}
{"seq":8,  "kind":"tool_start",  "name":"shell",    "group":"p7"}
{"seq":9,  "kind":"tool_result", "name":"shell",    "group":"p7", ...}
{"seq":10, "kind":"tool_result", "name":"fs_list",  "group":"p7", ...}
```

`fs_list` 从第 7 条开始、第 10 条结束，中间隔了三条。`shell` 从第 8 条开始、第 9 条结束。**光看 `seq`，会以为 `fs_list` 一直在跑。其实它只是先发出去、后回来。**

所以给轨迹加两样东西：

- **`group` 字段**：同一个组名的事件，属于同一批并发调用。看轨迹时，先把同组的事件挑出来，再看组内怎么交错。
- **每条事件本来就有的 `ts`**（6.1 的 `append()` 就在写）。`ts` 是时间戳，记的是这件事真正发生的时刻。`seq` 说「第几个落盘」，`ts` 说「什么时候真的发生」。**并行的轨迹必须看 `ts` 和 `group` 才读得对。**

这里要提醒一个陷阱：出错时找原因会变难。串行时，「上一条是什么」通常是解释「这条为什么错」的最近线索。并行时这条线索断了。报错的那条 `tool_result`，前一条 `seq` 很可能是**另一条腿**的事。

排错时只有一条可靠的路子。按 `group` 分组、按 `ts` 排序，把每条腿单独拉出来看。

## 11.3.6 什么时候必须一个个来

两类情况，一条判据管不住全部。

**第一类，有依赖的链条。** 就是上面那张表说的：B 的参数要从 A 的输出里取。这类不能并行，也不需要特别处理，顺序执行本来就是对的。

**第二类，有顺序语义的动作。** 这类容易漏。两个调用之间没有数据依赖，但 **顺序本身有意义**。

- 两次写 **同一个文件**：一起写的结果取决于谁先落盘，而且下次重跑未必一样。
- 「提交」和「推送到远端」：第二个的参数不依赖第一个的结果。但换了顺序，整件事就不成立。

这类动作必须显式串行，也就是排好队、一个一个来。判据是对 11.3.3 那条的补充：

> **没有数据依赖的调用可以并行；但改变外部世界的动作，还得看顺序本身有没有意义。**

工程上的稳妥做法是：**只读的操作放心并行；写操作默认串行。** 读多写少是 Agent 任务的常态，这一刀切下去就够用了。

有个容易含混的地方要说明白。**一轮里发几个调用，是模型的决定。这几个调用怎么跑，是 Harnex 的决定。**

模型可能在一次回复里给出三个 `tool_calls`，也可能老老实实一个一个来。它给的这三个，你没法要求它们必须独立。它有时候会给出一个依赖链。

所以 `run_calls()` 应该做的判断是**保守的**。默认并行，遇到上面两类情况退回串行。真要做细，可以在参数里找线索，比如某个调用的参数值恰好是前一个调用结果的片段。但那只是猜，行话叫启发式，会误判。

**更稳的做法是把这条规矩写进提示。**告诉模型「一次回复里只放互不依赖的调用，有依赖的等拿到结果再发下一批」。模型的服从度不低，Harnex 只需对「它没听话」兜底。

## 这一节的边界

并行省下的是 **等待**，不是 **思考**。模型推理那段时间一动不动，不会因为你并行了两条腿就变快。

所以收益有个明确上限：**只有当任务里存在多个互相独立的 IO 等待时才兑现。** IO 等待就是等外面回话——等磁盘读完一个文件、等网络把结果送回来。

一个纯靠模型推理的问答任务，并行做了也白做。
