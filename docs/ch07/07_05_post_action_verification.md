# 7.5 动作后验证：退出码 0 ≠ 任务成功

## 7.5.1 返回成功，事却没做成

7.1 花了一整节讲「返回码是唯一硬信号」。现在要给它划一条边界：

> **退出码只回答「这个程序正常结束了没」，不回答「你要的事情办成了没」。**

这两件事在大多数情况下重合，在关键时候分开。

看三个真实场景。

**场景一：名字写错了，但命令没错。**

```text
$ mkdir build
命令成功（exit 0），耗时 0.01s
```

命令一点毛病没有，可你要的是 `dist`。目录建好了，只是名字不对——**命令对结果一无所知，它只知道自己建了个目录。**

**场景二：跑完了，但什么都没干。**

```text
$ npm run build
> build
> tsc
命令成功（exit 0），耗时 12.4s
```

干净利落，退出码 0。可如果 `tsconfig.json` 里的 `outDir` 指向了别的目录，`dist/` 就是空的。`tsc` 确实成功了——它成功地把产物写到了另一个目录。

**场景三：提交成功了，但你要的文件没进去。**

```text
$ git commit -am "fix parser"
命令成功（exit 0），耗时 0.06s
```

`-a` 的意思是「把已跟踪文件里的改动全部暂存上」。可你新写的 `parser.py` 还没 `git add` 过，不在已跟踪名单里——**`-a` 根本看不见它。** 于是这次提交只带上了 `README.md`，而 git 一声没吭。

顺带纠正一个常见误会：**暂存区空的时候 `git commit` 是直接报错退出的**（`nothing to commit`，退出码 1）。恰恰是 `-a` 让暂存区不空，这条错误才被盖住——**它不是「提交成功」的证据，只是「有东西可提交」的证据。**

三个场景的共同点：**每条命令都把自己的活干对了，可你要的那件事没办成。** 退出码检查的是前半句，我们关心的是后半句。

## 7.5.2 模型为什么会相信返回码

人类工程师遇到这三种情况，通常会顺手再看一眼。**模型不会——除非你让它看。**

原因不复杂：模型能看到的全部信息，就是工具返回的那段文本。文本上写着「命令成功（exit 0）」，而它的任务是「建一个叫 `dist` 的目录」——这两件事在它眼里很容易**合并成一件**，于是它宣布完成。

这不是模型笨，是**信息不足**。它手上的证据只有「exit 0」，而「`mkdir` 成功 ≠ 目录名对」这条经验，不在它的输入里。

而且这个坑会**级联**：它以为目录建好了，下一步就去 `cd dist`，报错，然后开始一轮新的困惑。**一个没验证的假设，会在三步之后变成一次莫名其妙的失败。**

## 7.5.3 做完再看一眼现场

解法不复杂，就一句话：**执行之后，回头看一眼世界变成了什么样。**

把「我以为成了」变成「我看到成了」：

| 你要的结果 | 回读什么 |
| --- | --- |
| 文件 / 目录建好了 | 它存在吗？名字对吗？ |
| 文件内容改了 | 改的那段在吗？旧的那段走了吗？ |
| 提交成功了 | `git status` 干净吗？那次提交里有你要的文件吗？ |
| 服务起来了 | 端口通吗？进程还在吗？ |
| 构建产物生成了 | 目录非空吗？关键产物在吗？ |

落成代码，可以是一个小工具：

```python
# harnex/exec/verify.py —— 执行后回读：把「我以为成了」变成「我看到成了」
from pathlib import Path

WORKDIR = Path.cwd().resolve()


def _resolve(rel: str) -> Path:
    """复用第 4 章的路径边界：越界直接抛 ValueError。"""
    target = (WORKDIR / rel).resolve()
    if target != WORKDIR and WORKDIR not in target.parents:
        raise ValueError(f"路径越界：'{rel}' 不在工作目录内")
    return target


def expect_exists(args: dict) -> str:
    """检查路径是否存在。用于验证「产物应该已经生成」这类动作。"""
    rel = args["path"]
    target = _resolve(rel)
    if target.exists():
        return f"已确认：'{rel}' 存在。"
    return (f"未确认：命令虽然成功了，但 '{rel}' 并不存在。"
            f"退出码只能说明命令正常结束，不代表产物真的生成了。"
            f"请检查构建配置、输出目录，或上一步的输入是否正确。")


def expect_contains(args: dict) -> str:
    """检查文件里是否包含指定文本。用于验证「内容改对了」。"""
    rel, keyword = args["path"], args["keyword"]
    target = _resolve(rel)
    if not target.exists():
        return f"未确认：'{rel}' 不存在，无法检查内容。"
    text = target.read_text(encoding="utf-8", errors="replace")
    if keyword in text:
        return f"已确认：'{rel}' 里包含 '{keyword}'。"
    return (f"未确认：'{rel}' 里没有找到 '{keyword}'。"
            f"可能是写错了位置，或者那段文本已经被改掉了。")
```

`expect_exists` 的失败返回值得注意：它没有停在「不存在」，而是 **主动把「退出码 ≠ 结果」这件事讲给模型听**。因为大多数时候，模型不是不想验证，是不知道「退出码 0」和「目标达成」之间还有一道缝。**把这道缝写进工具的返回里，等于把这条经验装进了上下文。**

两个检查工具也进装配线，回读类单独一组。它们只读不写，`fs:read` 就够——**权限范围要贴着工具真正干的事写，不是给得越多越保险**：

```python
# harnex/tools/build_registry.py 片段 —— 7.5：回读类工具归一组
def verify_tools(add) -> None:
    """两个回读工具：确认「我以为成了」变成「我看到成了」。"""
    add(_tool(
        name="expect_exists",
        description=("回读：确认某个路径真的存在。建目录、生成产物、写文件之后用它验收——"
                     "命令退出码为 0 不代表文件真的在那个位置、那个名字上。"),
        properties={"path": {"type": "string", "description": "相对工作目录的路径"}},
        handler=expect_exists,
        scopes=["fs:read"],
        required=["path"],
    ))

    add(_tool(
        name="expect_contains",
        description=("回读：确认某个文件里真的包含一段文本。改完文件之后用它验收——"
                     "确认改对了位置，而且旧内容确实被换掉了。"),
        properties={"path": {"type": "string", "description": "相对工作目录的路径"},
                    "keyword": {"type": "string", "description": "应当出现的文本"}},
        handler=expect_contains,
        scopes=["fs:read"],
        required=["path", "keyword"],
    ))
```

装配线里再加一行 `verify_tools(add)`。

## 7.5.4 三种检查放法

小工具是一种落法，但不是唯一的，也不总是最好的。三种落法，区别只在于 **这条判断写在哪**——写进工具、写进描述、写进流程。

**第一种，写成工具。** 像上面这样，给一类判断（存在、包含、端口通）做一个专门的工具：名字叫得准、参数就那两三个，模型想漏都难。适合高频、判断标准明确的验证。

**第二种，写进描述。** 不加新工具，只在 shell 的 description 里加一句话：

```text
涉及文件产出的任务，命令成功之后请用 fs_read 或 shell 回读一次，
确认产物真的生成了——命令的退出码只说明它正常结束。
```

成本几十个 token，收益是让模型**自发**去做回读。4.2.2 那句「把用法写进描述」，在这里又一次派上用场。

**第三种，写进技能包的流程。** 如果一个任务有固定的验收标准（发布、打包、迁移），把它写进第 5 章那种技能包的一个步骤：

```text
## 发版前检查
1. 跑 scripts/check_versions.sh，确认版本号一致
2. 跑构建，确认 exit 0
3. 看 dist/ 是否非空——build 成功而产物为空是常见事故
4. 只有前三条都过，才继续下一步
```

**怎么选？看两条**：判断越明确、越高频，越该做成工具；越依赖上下文、越不像一个「通用动作」，越该写进描述或技能包。第三种还多一层价值——它把验收标准**固化成了流程**，下次不用重新想。

## 7.5.5 后面还会用到这个办法

「动作后验证」不是这一章独有的技巧，它是 Agent 工程里反复出现的一条主线：

- **第 9 章 9.4「可检验性」**：做规划时，清单里每一项都得写得出「怎么知道它成了」。这一节是它在单条命令上的最小版本。
- **第 19 章 GUI Agent**：屏幕上点了一个按钮，怎么知道点中了？**每一步都要看一眼截图**——和这一节「跑完命令回读一次」是同一个动作，只是「回读」的对象从文件系统变成了屏幕。

往回看，第 6 章的会话日志也在同一条线上：**「模型可见即已记录」是为了让「它当时看到了什么」可被检查**，而验证是为了让「它做成没做成」可被检查。两件事干的是同一个活——**把 Agent 的自信，换成可核对的事实。**
