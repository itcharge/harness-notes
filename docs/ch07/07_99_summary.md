# 小结与验收

## 本章小结

1. **shell 工具的第一个职责，是把成败判断从模型手里拿走。** 一个命令跑完至少有四样东西值得回传：`exit_code`、`stdout`、`stderr`、`duration`。少回 `exit_code`，等于要求模型从自然语言里猜成败。
2. **退出码是机器对机器说的语言。** 0 与非 0 没有歧义、不需要理解、不受语言风格影响。它是「过没过」这个问题的唯一硬信号。
3. **返回给模型的文本要先给判决、再给证据。** 开头一句「命令成功（exit 0）」或「命令失败（exit 1）」，替模型省掉一整轮猜测。
4. **超时是 shell 工具的必需组件，不是兜底。** 等输入的、不会结束的、真卡住的命令，对模型的呈现都是同一个「不返回」。超时把它变成一条可读、可诊断的结果。
5. **流式执行要把「读」和「等」分成两条线。** 同一个线程里既读又等，超时根本轮不到执行。`on_line` 回调是命令输出流的数据源，第 11 章会把两条流接到界面上。
6. **工具返回的内容必须有上限。** 三万行编译日志约 37 万 token，一次就能把上下文撑爆四倍。默认保尾 40 行，同时用行数与字节数两道闸封顶。
7. **截断必须显式告知。** 那句「共 31284 行，以下只显示最后 40 行」让模型知道输出被截了、以及可以用更精确的命令再问一次。
8. **shell 是能力放大器。** 它的能力不是「某一种动作」，而是「其他所有工具的集合」。它带来的最大破坏，从「改错一个文件」升级成了「删掉整个项目」。
9. **白名单的问题出在粒度，粒度一细就退化成黑名单。** `python`、`git` 这类驱动型命令把真正行为藏在参数里，看第一个词等于什么都没看；想把粒度做细到参数，就得逐条枚举组合——那其实就是一张黑名单。
10. **黑名单拦不住恶意，因为它验证的是「写法」而不是「动作」。** 换写法、换载体、借道下载、编码混淆——绕过它不需要攻破任何东西。它的正确位置是「减少手滑」，不是「安全边界」。
11. **真正的边界在进程之外。** 文件系统隔离、网络隔离、权限隔离、资源限制——沙箱不识别任何东西，它让危险的事**根本做不到**。让危险做不到，只要四层；识别危险写法，永远列不完。
12. **退出码 0 不等于任务成功。** 它只回答「程序正常结束了没」，不回答「你要的事情办成了没」。名字写错、什么都没干、漏了一步——三种情况下退出码都是 0。
13. **验证就是把「我以为成了」换成「我看到成了」。** 执行后回读一次状态；失败返回里主动讲清「退出码 ≠ 结果」这道缝。
14. **不是所有命令都能「跑完就结束」。** 交互式命令靠 `DEVNULL` + 参数约束让它早点失败；长驻进程需要持久终端（PTY），那是第 19 章的事。

## 动手任务

1. **亲手看一次「只回 stdout」的后果。** 把 7.1 的 `format_for_model()` 改成只返回 `stdout`，然后让 Harnex 跑一条不存在的命令（比如 `pytest --nope`）。**看它怎么描述这次失败**——再改回带判决的版本跑一次，对比两段回复。

2. **量一次大输出。** 找一个真实项目跑 `npm run build` 或 `pytest -q -v`，记录总行数；把完整的 `stdout` 按 1 行 ≈ 12 token 粗算总 token 数。**然后对比 `tail_lines=40` 的版本**，算出这一刀省了多少。

3. **徒手绕一次自己的白名单。** 用 7.3 的 `guard()`，试着构造三条能通过检查、却能造成破坏的命令。**写下来，再看 7.4 列的四种绕法**——你大概会命中其中两三种。

4. **给 `guard()` 补一条真正的白名单式过滤。** 挑一条你白名单里的驱动型命令（`git` 或 `python`），把它拆成「允许的组合」而不是「允许的程序名」。**然后统计你写了多少条规则**——这个数字就是「白名单退化成黑名单」的实测证据。

5. **演示一次「动作后验证」。** 让 Harnex 完成「建一个 `dist/` 目录并确认存在」。先给它一个会失败的任务（比如让它建 `build/` 而你要的是 `dist/`），看它会不会自己发现；再用 `expect_exists` 跑一次，对比差别。

6. **把后台任务接进会话日志。** 用 7.6 的 `start_background()` 起一个 `python -m http.server`，然后用第 6 章的 `SessionLog` 查一件事：**用户问「刚才那个服务起来了吗」，`overview()` 能不能答上来？** 不能的话，你觉得该记一条什么样的事件。

## 验收清单

- [ ] shell 工具跑通 `ls` / `grep` / `python -c` 三类命令，返回结构含 `exit_code` / `stdout` / `stderr` / `duration`
- [ ] 返回给模型的文本以判决开头（`命令成功（exit 0）` / `命令失败（exit N）`）
- [ ] 编译类大输出只把尾部内容交给模型，且明确写出「共 N 行，此处显示最后 40 行」
- [ ] 一条不会结束的命令（`tail -f`）在超时后被终止，模型收到可诊断的超时说明
- [ ] 危险命令（`rm`、`sudo`、`curl`）被白名单拦下，模型收到「可用命令是……」这类可读理由
- [ ] `cwd` 越界与参数里明写的绝对路径 / `..` 被拒绝
- [ ] 交互式命令（不带 `-m` 的 `git commit`、不带 `-y` 的 `npm init`）拿到明确报错而不是挂起
- [ ] （里程碑）至少一个任务演示「动作后验证」：命令成功但结果不符，被检出并纠正
- [ ] 后台任务能起、能读、能停，输出落在 `sessions/` 下的文件里
- [ ] 命令的拒绝理由与结果都进了会话日志（第 6 章），能事后回看「它跑过什么」

## 本章的常见误区

- **只返回 `stdout`**：模型看不到退出码，把失败当成功继续往下做。
- **没有超时**：一条 `tail -f` 样的命令永久挂起，整条链路卡死。
- **大输出直灌上下文**：编译日志几万行进 prompt，一次烧掉半个窗口。
- **截断但不告知**：模型以为 40 行就是全部，在残缺信息上做判断。
- **依赖黑名单**：`rm -rf` 被拦了，`find . -delete` 却放行——字符串过滤必然漏。
- **把白名单当成安全边界**：白名单里的 `python -c` 能做任何事；以为它安全，比知道它不安全更危险。
- **`shell=True` 直接拼用户输入**：命令注入的经典入口，也是提示注入落地成真实动作的通道。
- **交互式命令不加约束**：不带 `-m` 的 `git commit` 让循环挂到超时，模型还看不懂为什么。
- **把长驻进程塞进主循环**：`npm run dev` 永不结束，主循环等它 = 永久卡死。
- **相信退出码就是结论**：`mkdir build` 成功而你要的是 `dist`——成功退出但没做成。

## 本章术语速查（中英对照）

| 中文 | 英文 | 一句话解释 |
| --- | --- | --- |
| 退出码 | Exit Code | 进程结束时的整数，0 = 正常，非 0 = 出错 |
| 子进程 | Subprocess | 由 harness 启动、与它并行的另一个程序 |
| 标准输出 / 标准错误 | stdout / stderr | 命令的两条输出通道；结果与报错分开 |
| 流式执行 | Streaming Execution | 边跑边读输出，而不是跑完再取 |
| 输出截断 | Output Truncation | 只把一部分输出交给模型，默认保尾 |
| 能力放大器 | Capability Amplifier | shell 的本质：它能做其他工具能做的全部事情 |
| 白名单 | Allowlist | 只允许清单内的程序；默认拒绝 |
| 黑名单 | Denylist | 禁止清单内的写法；注定不完备 |
| 纵深防御 | Defense in Depth | 多层边界叠加，不靠单点 |
| 沙箱 | Sandbox | 进程级隔离：文件系统 / 网络 / 权限 / 资源 |
| 动作后验证 | Post-action Verification | 执行后回读状态，确认结果真的达成 |
| 「退出码 0 ≠ 成功」 | Exit Code ≠ Success | 命令正常结束不代表目标达成 |
| 交互式命令 | Interactive Command | 等待标准输入的命令，无人值守时会挂起 |
| 长驻进程 | Long-running Process | 设计上就不退出的进程（dev server 等） |
| 伪终端 | PTY | 让程序以为自己连着真终端的接口 |
| 后台任务句柄 | Background Handle | 后台进程的名字，供后续读取与停止 |
