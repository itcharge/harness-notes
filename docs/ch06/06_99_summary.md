# 小结与验收

## 本章小结

1. **`messages` 是投影，会话日志是记录。** 前者是「这一轮要发给模型的东西」，会被裁剪替换；后者是「这件事到底发生过什么」，只增不减。**日志不从 `messages` 反推，`messages` 从日志投影出来。**
2. **两条不变式撑起了整个数据层。** 「模型可见即已记录」把「它看到了什么」变成可检查的问题；「状态由日志投影得出」让状态不会漂移、可回放、可换投影。
3. **日志的基本单位是事件，不是消息。** `user_message`、`assistant_message`、`tool_result` 只是事件的一类；`user_interrupt`、`compaction`、`error` 这些不是消息，但少了它们就没法解释模型为什么那样想。
4. **上下文是一块会被耗尽的公共资源。** 六块内容抢同一个窗口，只有轨迹投影没有天然上限——所以「上下文爆了」几乎等同于「历史太长了」。
5. **预算表是上下文工程的操作面板。** 给每块划额度、让输入别超过窗口的 70%、发现轨迹压不住时先回头看看技能清单和工具清单。**技能清单和历史抢的是同一块地。**
6. **压缩要问「什么时候」和「压什么」，而不只是「怎么压」。** 三个触发时机里，任务阶段切换最容易被忽略、价值最高。判断能不能压的规则是**可重建性**：模型能低成本重建的可以压，重建不出来的必须留。
7. **忘了比记着更危险。** 错误记忆会露馅，遗忘不会——它表现为一个自信的错误决定，而且会连锁：丢掉的往往是某个判断的前提。
8. **压缩只能删投影，绝不能删日志。** 有了这条边界压缩才敢做；否则删错了就再也还不了。
9. **长期记忆按 `key` 更新，不按内容新增。** 同一件事记两条矛盾的，检索时挑中哪条全看运气。用户的纠正置信度给满，优先级高于任何推断。
10. **记忆要有 `source` 和 `confidence`。** 一个用于追溯错的记忆从哪来，一个用于决定哪些可以淘汰——**隐式写入宁缺毋滥。**
11. **相关性和数量无关。** 全量注入 200 条不会让相关的那 5 条更容易被找到，只会稀释。记忆少于 20 条时全量注入更简单；超过、且长期不清理时，检索从优化变成必需。
12. **能回看的最低标准是「把日志还原成人能读的东西」。** 这一章三十来行的脚本是第 12 章 trace 看板的用户侧版本，也是第 20 章「查看任务」的数据来源。

## 动手任务

1. **把一次会话落成 JSONL 再重启恢复。** 用 6.1 的 `SessionLog` 跑一次任务，关掉进程，再用 `SessionLog.load()` 把它读回来，确认 `project()` 出来的消息和关闭前一致。**然后手动删掉日志里最后一条事件再读一次**，看投影出来差了什么——亲手体会一次「日志即真相源」。

2. **给自己的 harness 做一张预算表。** 用 6.2 的 `budget_report()`，在一个真实任务上每 5 轮报一次。**记下轨迹投影第一次超过 70% 是哪一轮**——那个数字就是你现在的压缩触发点。

3. **对比三种压缩策略。** 拿一个 40 轮以上的长会话，分别只用滑动窗口、只用摘要、用 6.4 的组合式 `compact()`，各跑一次压缩，记录压缩后的 token 与「问同一个关键事实能否答对」。**把三张结果表放在一起**——你会看到为什么顺序是「先瘦身、再分堆、最后摘要」。

4. **写一条会过期的记忆。** 让 Harnex 记住「这周在做登录重构」，把 `expires_at` 设成 7 天后。到期后再问，确认它不再被召回。**然后故意设一条 `confidence=0.3` 的推断记忆**，看它在正常情况下会不会挤掉置信度更高的事实。

5. **造一次记忆冲突再解决它。** 先让系统记住「用 unittest」（显式），再让它从对话里推断出「用 pytest」（隐式），看检索会返回哪条。然后按 6.5 的规矩，用用户明确纠正的方式把 key 覆盖掉，确认 `active()` 里只剩一条。

6. **给回看脚本加一个筛选。** 在 6.7 的 `overview()` 上加一个参数：只列出「发生过压缩」或「工具调用超过 N 次」的会话。**这是你第一次在轨迹上做查询**，也是第 12 章那些筛选器的雏形。

## 验收清单

- [ ] 会话以 JSONL 事件流落盘，**进程重启后能恢复并继续同一会话**
- [ ] `project()` 能只凭日志重建「某一轮模型看到的全部内容」
- [ ] 预算表能跑出四行占用（系统提示与技能清单合成一行），轨迹投影超过 70% 时会告警
- [ ] 长会话压缩后 token 明显下降，且**关键约束与未完成事项不丢**
- [ ] 压缩发生时日志里新增一条 `compaction` 事件，**原有事件一条未改**
- [ ] （里程碑）新会话里问「我的技术栈偏好是什么」，能答对
- [ ] 记忆按 `key` 更新：用户纠正后 `active()` 里只剩最新一条
- [ ] 记忆条目带 `source` 与 `confidence`；过期的被 `active()` 滤掉，低置信度的在 `recall()` 里排到后面
- [ ] 能点开任意历史会话，看到逐事件的完整轨迹；能列出所有会话的一行摘要
- [ ] 敏感的字符（token、密码）**不出现在日志与记忆**里（第 15 章会回收这条伏笔）

## 本章的常见误区

- **只存 `messages` 不存事件**：想回放时只剩最终对话，中间的工具结果与失败全丢了——因为 `messages` 本来就是给模型看的投影。
- **把状态另存一份**：又存日志又存「当前状态」，两者一旦不同步就永远对不上。状态该由日志投影得出。
- **压缩掉证据**：把工具返回的关键数据摘要掉，导致后续步骤重复劳动或重复报错。
- **直接改日志来压缩**：删错了就还不了。压缩改的是投影，日志只追加。
- **用轮数而不是 token 触发压缩**：第 3 轮可能塞进一个 5000 行的文件，第 20 轮可能只是「好的」。
- **在摘要时把老约束当噪声丢掉**：「config 不要动」这种话，压掉之后模型会自信地违反它。
- **记忆全量注入**：200 条全塞系统提示，每轮白烧 5000 token，还把相关的几条淹没掉。
- **错误记忆不更新**：用户早已纠正过，harness 仍在推荐旧路径——因为没有按 `key` 覆盖。
- **只相信隐式推断**：猜错的记忆会参与每一轮决策，还可能顶掉正确的信息。隐式写入宁缺毋滥。
- **把机密写进日志**：token、密码被记入轨迹并随日志长期留存——日志要留全，但**不该留的东西一开始就不该进来**。

## 自测题

1. 「模型可见即已记录」这条不变式保证了什么？破坏它会付出什么代价？
2. 为什么状态要从日志投影，而不是直接存一份当前状态？请说出至少两个理由。
3. 压缩的三类策略各适合什么场景？为什么建议的顺序是「先瘦身、再分堆、最后摘要」？滑动窗口又该在什么位置上？
4. 压缩前必须做什么？如果压缩直接改了日志，会带来什么后果？
5. 记忆条目为什么需要「来源」和「置信度」字段？分别用在什么环节？
6. 用户纠正一条旧记忆时，正确的处理是新增还是覆盖？为什么？
7. 什么情况下全量注入记忆反而比检索更合适？判断的界线在哪？
8. 哪类信息绝对不该进入会话日志与长期记忆？

## 本章术语速查（中英对照）

| 中文 | 英文 | 一句话解释 |
| --- | --- | --- |
| 会话日志 | Session Log / Trajectory | 只追加的事件流，harness 的真相源 |
| 事件 | Event | 日志的基本单位；有类型与时间，负载可不同 |
| 投影 | Projection | 从日志得出「本轮要发给模型的消息」的过程 |
| 不变式 | Invariant | 必须始终成立的性质；本章两条撑起整个数据层 |
| 上下文窗口 | Context Window | 输入与输出共用的资源，会被耗尽 |
| 上下文工程 | Context Engineering | 决定哪些内容、以什么形式进入窗口 |
| 预算表 | Token Budget | 给每块内容划额度的操作面板 |
| 压缩 | Compaction | 收缩投影的手段总称；只动投影，不动日志 |
| 滑动窗口裁剪 | Sliding Window | 只留最近 N 条消息的裁剪方式 |
| 摘要压缩 | Summarization | 让模型把老消息总结成一段 |
| 工具结果瘦身 | Tool-result Trimming | 大输出只留用过的部分 |
| 长期记忆 | Long-term Memory | 跨会话保留的画像、事件与程序性记忆 |
| 画像 / 事件 / 程序性 | Profile / Event / Procedure | 记忆的三种类型：你是谁、你做过什么、怎么服务你 |
| 置信度 | Confidence | 记忆的可信程度，用于写入与淘汰策略 |
| 相关性与稀释 | Relevance / Dilution | 塞得越多，真正相关的那几条越难被挑中 |
| 轨迹浏览 | Trajectory Viewer | 把日志还原成人能读的界面 |
