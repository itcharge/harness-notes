# 6.2 上下文预算的分配：谁在吃你的 token

## 6.2.1 六块内容抢同一块地方

第 2 章讲过上下文窗口是什么，那时它只是个概念。现在它能变成一张账单了。

Anthropic 讲上下文工程时有一句话：**上下文是一种有限的资源，而且边际收益递减。** 大白话就是——窗口就这么大，谁多占一块，别人就少一块。系统提示、技能清单、记忆、历史对话，全在抢这同一块地方。

数一数往里塞东西的有几路。一次请求真正发给模型的内容，由六块拼成：

| 区块 | 来自哪 | 增长速度 |
| --- | --- | --- |
| 系统提示 | 你的 `BASE_PROMPT` | 常驻，固定 |
| 技能清单 | 第 5 章 `loader.catalog()` 的输出 | 随技能包数量 |
| 工具清单 | `registry.schemas()` 的 JSON Schema | 随工具数量 |
| 记忆注入 | 长期记忆里挑出的条目（6.5 节） | 随注入条数 |
| 轨迹投影 | 6.1 那些事件投影出的消息 | **随轮数线性增长** |
| 当前输入 | 用户这一句 | 每次一点点 |

这六块里，前四块都有天花板：技能包加到三十个你会停手，工具加到二十个你会嫌多，记忆注入有配额，系统提示翻来覆去就那几句。**只有轨迹投影没有天花板。** 它每转一轮多两条消息，工具返回动辄几千 token；一个查数据库的任务跑四十轮，光历史就能吃掉十几万 token。

所以上下文工程的重心，从来都是「历史」。

## 6.2.2 先给每块分额度

最实用的做法是**预算表**：给每块划一个额度，超了就去压对应那块，而不是等窗口爆了才手忙脚乱。

拿 128k 窗口举例，一个合理的初分配：

| 区块 | 额度（token） | 约占 | 超了怎么办 |
| --- | --- | --- | --- |
| 系统提示 | 2 000 | 1.6% | 精简措辞 |
| 技能清单 | 5 000 | 3.9% | 减少常驻技能包（第 5 章） |
| 工具清单 | 4 000 | 3.1% | 拆注册表、按场景分装 |
| 记忆注入 | 3 000 | 2.3% | 改成检索式注入（6.6 节） |
| 轨迹投影 | 70 000 | 54.7% | **压缩（6.3 / 6.4 节）** |
| 当前输入 | 2 000 | 1.6% | —— |
| 留给输出 | 42 000 | 32.8% | —— |

这张表最该看的是最后一行：**你必须给模型的输出留出空间。** 窗口是「输入 + 输出」共用的。历史把 128k 占满，模型连一句话都说不完——要么报错，要么被迫把回答压成两三个字。

> 一条经验：**让输入别超过窗口的 70%。** 剩下 30% 留给输出和推理。这个比例不是精确值，但它是一条线，比「等报错了再说」靠谱得多。

## 6.2.3 技能多了，历史就少

预算表暴露的第一件事，是第 5 章那个「零成本」印象的代价。

第 5 章说，装 50 个技能包只花约 5 000 token 常驻——听起来很便宜。可那是**跟「把正文全塞进系统提示」比便宜**。放进预算表里，它是实打实占掉 5 000 token 的：这 5 000 不拿来放技能清单，就能多放好几轮带着工具结果的历史。

**技能清单和历史抢的是同一块地。** 装到 100 个技能包，光清单就吃掉近 1 万 token，而九成九的对话只会触发其中一两个。

这不是说第 5 章错了——它仍然远好过把正文全塞进系统提示。它只是提醒你：**「便宜」是相对的，预算表才是绝对的。** 当你发现轨迹投影总是压不住，先别急着调压缩策略，回头看看技能清单和工具清单是不是在偷偷加税。

## 6.2.4 把占用算成数字

概念讲完，落成一段能跑的代码：一个 token 估算，一个报告函数。

```python
# harnex/context/budget.py —— 上下文预算表：一段一段量出谁在吃 token
def rough_tokens(text: str) -> int:
    """粗略估 token：中日韩字符约 1 字 1 token，其余约 4 字符 1 token。"""
    cjk = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")
    return cjk + (len(text) - cjk) // 4


def budget_report(system: str, tools_json: str, memory: str,
                  messages: str, limit: int = 128_000) -> str:
    rows = [("系统与技能清单", rough_tokens(system)),
            ("工具清单", rough_tokens(tools_json)),
            ("记忆注入", rough_tokens(memory)),
            ("轨迹投影", rough_tokens(messages))]
    total = sum(n for _, n in rows)
    lines = [f"{'区块':<16}{'token':>8}{'占比':>8}"]
    for name, n in rows:
        lines.append(f"{name:<16}{n:>8}{n / limit:>7.1%}")
    lines.append(f"{'合计':<16}{total:>8}{total / limit:>7.1%}")
    if total > limit * 0.7:
        lines.append(f"⚠️ 已超过 {limit * 0.7:.0f} token 警戒线，该压缩了")
    return "\n".join(lines)
```

注意这张报告只有四行，不是六行：系统提示和技能清单合并成一行（都是常驻文本），当前输入也没算——它就是这一轮刚发的那句话，有多长你自己看得见。

`rough_tokens` 只是估计，不是精确计数——但它的用途恰恰不要求精确。你需要知道的不是「38 421 还是 38 517」，而是「几千还是几万」。**量级对了，决策就对了一半。**

在一个装了 5 个技能包、跑了 20 轮的小任务上跑一次：

```text
区块                 token      占比
系统与技能清单              742   0.6%
工具清单                1180   0.9%
记忆注入                 386   0.3%
轨迹投影               21450  16.8%
合计                 23758  18.6%
```

看轨迹投影这一行：**它一个人占了全部的九成。** 这 20 轮里，其他三块加起来一直不到 2 400 token，稳得像块石头；轨迹投影却从第 1 轮的两条消息，一路涨到两万多。

这就是为什么下一节直接谈压缩——绝大多数任务里，**「上下文爆了」几乎等同于「历史太长了」**，其余几块你早就管住了。

## 6.2.5 预算和日志各管什么

最后交代两节的分工，免得混淆。

日志（6.1）管**「记得全」**：发生过的事一条不丢。预算表管**「发得省」**：每轮只把该发的发出去。两者不冲突——**正因为日志全，投影才敢省。**
