# 6.3 压缩（一）：什么时候该忘

## 6.3.1 先决定什么时候该忘

压缩这件事最容易走错的一步，是把它当成定期任务：「每 20 轮压一次」「超过 5 万 token 就压」。这两个标准都太钝——只看量，不看内容。

真正该触发压缩的是 **三个时机**，每个都对应一种具体的危险：

| 时机 | 信号 | 不压会怎样 |
| --- | --- | --- |
| 接近窗口上限 | 预算表超过 70% | 报错，或输出被挤成一句话 |
| 任务阶段切换 | 一个子目标完成了、开始下一个 | 上一阶段的过程细节白占地方 |
| 长时间空闲 | 用户离开几小时又回来 | 中间那段等待和来回试探毫无价值 |

**第二个时机最容易被忽略，价值却最高。** 一个「改登录 bug」的任务，前半段在定位，后半段在改代码。前半段的 `grep`、`fs_read`、失败的重试全都有用——但只在定位阶段有用。一旦「问题出在 token 校验那行」这个结论已经写进上下文，前面那几千 token 的过程细节就成了纯粹的负担。

在阶段切换点压缩，比在「满了」的时候压缩更好，原因有两条：

- 阈值还没到，你有空间写一段从容的摘要，而不是被迫丢东西
- 压缩的边界是**语义边界**，而不是「第 N 条消息」

**第三个时机，「空闲」**，指的是用户此刻不在乎速度，你可以慢慢压。这也是最从容的那一刻——「让模型总结」这种较贵的手段，放在这里才不心疼。

## 6.3.2 什么能忘，什么不能忘

压缩的难点从来不是「怎么压」，而是「压掉哪部分」。一份能直接照着做的清单：

**必须保留（丢了就出错）：**

- 当前任务的 **目标** 和 **约束**（「只改测试，不许动源码」）
- 用户 **明确说过的** 偏好与纠正（「用 pytest，不要 unittest」）
- **未完成事项**（「还差一个测试没补」）
- **关键的确定性事实**：路径、ID、版本号、错误码

**可以压缩（压掉只是啰嗦，不影响正确性）：**

- 工具返回的 **完整长输出**，如果其中只有一小部分被用到
- 已经得出结论的 **中间探索**（读过的文件、搜过的关键词）
- 重复的 **失败重试**（保留最后一次的结论即可）
- 模型的 **冗长解释**，只留它的决定性句子

有一条判断规则特别好用：**「这件事再发生一次，模型能不能自己重新推出来？」** 推得出来的（某个文件的内容，它随时能再读一遍）可以压；推不出来的（用户随口说的一句偏好、一次失败的教训）必须留。

这条规则的底层是**「可重建性」**：能低成本重建的信息不值得常驻；重建不出来的，它就是唯一的一份。

## 6.3.3 忘错比全记住更糟

直觉上「记着」更安全，其实反过来。多记一点，代价是钱；忘掉一点，代价是**错**。

举个具体的：

> 你在第 3 轮说过「`config` 目录不要动，那是自动生成的」。
> 第 30 轮触发了一次压缩，这句约束在摘要时被当成「已完成的背景」丢了。
> 第 35 轮，Harnex 为了「让配置生效」，顺手改了 `config/app.yaml`。

整个过程它不报错，还觉得自己做得挺对。**错误记忆会露馅，遗忘不会——它表现为一个自信的错误决定。**

更麻烦的是遗忘会 **引发连锁反应**：丢掉的往往不是一条孤立信息，而是某个判断的前提。前提没了，结论还在，模型就会在错误的地基上继续往下推，而且越推越远。上面那个例子里，它甚至可能接着把 `config` 里其他文件也「顺手优化」一遍。

所以压缩的第一原则不是「尽量多压」，而是：**宁可保守，先在日志里留全，再决定投影里留哪些。** 这条原则下一节会落成具体的不可逆性约束。

## 6.3.4 两种常见错误

**反模式一：定时压缩。** 「每 20 轮压一次」，不管这 20 轮是一堆废话，还是一个正在成形的复杂推理。后者被拦腰截断，会丢掉正在建立的心智模型——它刚把问题想清楚，你把它的草稿纸收走了。

**反模式二：按轮数而不是按 token 压。** 轮数和占用没关系：第 3 轮可能塞进一个 5000 行的文件，第 20 轮可能只是「好的」。**该看的是预算表，不是计数器。**

## 小结一段

这一节定的是「什么时候压、压什么」；下一节定「怎么压」。顺序不能反——**先想清楚要丢什么，再挑工具，比反过来稳得多。** 手里有了一把压缩的锤子，看什么都想砸，往往就是这么砸出事的。
