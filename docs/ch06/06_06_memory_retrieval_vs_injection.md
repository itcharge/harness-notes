# 6.6 检索式记忆 vs 注入式记忆

## 6.6.1 全部塞进去的上限

先看把记忆全量注入会怎样。假设记了 200 条：

```text
200 条 × 平均 25 token ≈ 5000 token，每一轮都发
```

5000 token 本身不算致命，要命的是它**每轮都花一遍**：跑 30 轮，就是 15 万 token 的输入，其中绝大多数和当轮任务无关。更糟的是 **稀释**——上下文里塞着 200 条「可能相关」，模型得从里面挑出真正相关的那三五条，挑错的概率随条数往上走。

所以全量注入的问题不在成本，而在 **相关性和数量无关**：相关的那几条，不会因为你多塞了 195 条而更容易被找到。

## 6.6.2 按相关程度挑

换个做法：**只把和当前任务相关的记忆挑出来注入。** 判断相关性的信号有几个层次：

| 信号 | 做法 | 强度 |
| --- | --- | --- |
| 关键词重合 | 任务文本和记忆内容的词是否重叠 | 弱 |
| 类型匹配 | 涉及代码的任务，优先取「技术栈」类 | 中 |
| 时间接近 | 越近的记忆越可能相关 | 中 |
| 语义相似 | 用向量算相似度 | 强（第 8 章） |

这一章先用前三个——它们不需要任何模型，几行代码就能跑，而且覆盖大多数场景。**第四个「语义相似」是第 8 章 RAG 的主角**，那时你会看到同一件事用向量做得更好。

## 6.6.3 不用模型也能检索

```python
# harnex/memory/recall.py —— 按相关性挑记忆，而不是全量注入
import re
import time

STOP = {"the", "a", "an", "of", "to", "and", "or", "in", "on"}


def keywords(text: str) -> set[str]:
    """粗糙分词：英文按词切，中文切成二字组。够用，且不依赖分词库。"""
    words = re.findall(r"[A-Za-z_][A-Za-z0-9_]*", text)
    han = re.findall(r"[\u4e00-\u9fff]+", text)
    bigrams = [h[i:i + 2] for h in han for i in range(len(h) - 1)]
    return {t.lower() for t in words + bigrams if t.lower() not in STOP}


def _by_score(pair: tuple) -> float:
    return pair[0]


def recall(query: str, items: list, k: int = 5) -> list:
    """给每条记忆打分：关键词重合 × 置信度 × 时间衰减，取前 k 条。"""
    q = keywords(query)
    now = time.time()
    scored = []
    for it in items:
        overlap = len(q & keywords(it.content))
        if overlap == 0:
            continue
        age_days = (now - it.created_at) / 86400
        recency = 1.0 / (1 + age_days / 30)          # 越近越高，30 天衰减一半
        score = overlap * it.confidence * recency
        scored.append((score, it))
    scored.sort(key=_by_score, reverse=True)
    return [it for _, it in scored[:k]]


def memory_prompt(items: list) -> str:
    """把挑出的记忆拼成一段注入文本。全空时不占位。"""
    if not items:
        return ""
    lines = ["关于当前用户，你记得这些（不一定都和本次任务有关）："]
    lines += [f"- {it.content}" for it in items]
    return "\n".join(lines)
```

三处设计：

- **完全没重合的直接跳过**，而不是给它一个低分——省得一堆弱相关记忆挤进前 k。
- **`recency` 用 30 天半衰期。** 这个数可以调，重点是 **让旧记忆自然退场，而不是靠人手动清理。**
- **注入文本带一句免责。** 「不一定都和本次任务有关」——检索必然会有错配，这句话让模型知道这些是 **参考**，不是 **指令**。

跑一遍：库里躺着 200 条记忆，一次「帮我改下 parser 的测试」的查询，召回的是「测试框架：pytest」「parser 模块是上周重构的」「偏好：测试文件放 tests/ 下」这几条，剩下的 197 条一个 token 都不占。

## 6.6.4 把记忆做成技能包

到这里，还有一个更省的设计。既然第 5 章刚学会了技能包，而「记忆」这件事本身就是一套方法论——什么时候记、记成什么格式、怎么取——那它完全可以是一个技能包。

把记忆技能放进 `skills/memory/SKILL.md`：

```markdown
---
name: memory
description: 记住用户的长期偏好与事实，或回忆之前记住的内容。当用户说「记住」「以后都」「我们项目用」「上次我提到」时使用。
---

## 记住
当用户表达一条稳定事实或偏好时（比如「我们项目用 pytest」），
调用 shell 执行 `harnex memory set <key> "<内容>"`。
key 用简短英文，如 `test_framework`。

## 回忆
需要用户的偏好或历史信息时，先执行 `harnex memory get`，
不要凭空猜测用户的习惯。

## 边界
不要把一次性的、临时的事当成长期记忆（「今天改登录」不进库）。
用户的明确纠正优先级最高，直接覆盖旧 key。
```

这么一来，「记忆」就从 harness 的硬编码逻辑，变成了一个**可读、可改、可分发**的约定。想改记忆策略，改这个 Markdown 就行，不用动 Python。（技能包里那两条 `harnex memory set/get`，就是给 6.5 的 `MemoryStore` 套一层 argparse——十来行，留给你补。）

**这就是「记忆也是一种技能调用」的意思**：它和「提交代码」「发版」是同一类东西——一套做法，装成知识包，按需生效。

注意这一节的 `recall()` 和这个技能包是**互补**的：`recall()` 负责「把相关的几条自动挑进上下文」，技能包负责「模型主动去记、去查」。前者是自动注入，后者是显式调用——真实系统里两者都要，各管一段。

## 6.6.5 什么时候该全部塞进去

检索不是永远更优。有一条朴素的分界线：

**记忆条数少于 20 条时，全量注入更简单，也够用。**

三个理由：20 条 × 25 token = 500 token，成本可以忽略；没有检索，就没有「该召回却没召回」这种失败模式，少一层会出错的东西；代码量少一半，调试路径也短。

检索的价值随记忆条数增长——条数越多，全量注入的稀释效应越明显，检索的收益越大。**不要在只有 20 条记忆的时候就去搭一套向量库**，那是第 8 章的工具，也是第 8 章才需要面对的规模。

反过来，一旦记忆上百条、又长期不清理，检索就从「优化」变成了「必需」：此时不检索，模型每轮都在 200 条里挑，挑错率高到让记忆变成负资产——**记了还不如不记**。

一条可操作的切换经验：**先用全量注入跑通。等到「记忆注入」这一行顶到 6.2 给它划的额度（3 000 token，大约 120 条）时，再引入检索。** 这样你手里有对比数据，知道检索究竟改善了什么。

## 6.6.6 和资料检索的关系

你可能注意到，5.7 节讲过技能包的触发测试，而这一节讲记忆的召回——两者是同构的：**都是「给一个 query，从一堆候选里挑出该用的那几个」。**

这一章的 `recall()` 用关键词做这件事；第 8 章的 RAG 会用向量把它做扎实。**记忆检索是 RAG 在「关于你自己」这个特定领域里的一次预演。** 等你在第 8 章学会向量检索，回头看这一节的 `keywords()`，会很清楚它为什么不够用——比如「测试」和「pytest」两个词面不重合，关键词方法就抓不住它们的关系。
