# 小结与验收

## 本章小结

1. **工具不是一个函数，是一份带说明书的记录**：名字、描述、参数 schema、执行函数、权限声明。少一样都不完整。
2. **注册表让循环和工具解耦。** 循环只知道「把名字和参数交给注册表」——加工具、换实现、搬到别的进程，循环都不用改。
3. **默认拒绝**：工具不声明权限就拒绝加载。工具是唯一能产生副作用的地方，默认允许等于给每个新工具自动发全部权限。
4. **粒度法则**：一个工具 = 模型能独立判断成败的一个动作。拆得太细，等于把「定位」和「内部状态」的猜谜工作推给模型。
5. **description 是写给模型的文档**：什么时候该用、什么时候不该用、参数怎么填、返回什么。指令式的句子（「必须先调用它」）是性价比最高的投入。
6. **异常绝不抛穿循环。** 失败要转成「发生了什么 + 可能原因 + 下一步怎么做」的文本——错误信息是喂给模型的输入，它的质量决定 Agent 的下一步质量。
7. **补丁优于全量覆写**：省 token、可审、失败面小。改已有文件用 `apply_patch`，`fs_write` 只留给新文件。
8. **MCP 把工具搬进独立进程**：进程隔离、语言无关、可复用生态，代价是每次调用多一次跨进程往返。权限的判断权永远留在 harness 一侧。

## 动手任务

1. **数一数「循环有没有变」**：把第 3 章的 `loop/agent.py` 和本章的版本放在一起 diff。确认**循环内核（熔断、追加顺序、终止判断）一字未动**，改的只是工具从哪来、怎么调。把 diff 输出留在仓库里。
2. **观察一次好错误的作用**：把 `delete_note` 注册进去，然后让 Harnex 「把日记删掉」。看它拿到错误后会不会按提示走——**把它读到的原始错误文本和它接下来的动作都打印并留存**（第 12 章的 trace 做的正是这件事）。
3. **写一个会越界的路径测试**：给 `fs_read` 传 `path="../../etc/hosts"`。`_resolve()` 里抛的是 `ValueError`，被 `registry.call()` 的兜底接住才变成文本——确认模型读到的是「路径越界」这句话，既不是文件内容，也不是 traceback。
4. **加第六个工具**：自己写一个 `search_text`（或别的你真正需要的工具），要求：带 `required` 参数、描述包含「什么时候不该用」、失败时返回带下一步的错误。**全程不改循环代码**——这就是本节的验收点。

## 本章的常见误区

- **异常炸穿循环**：一个工具抛异常，整场会话终止。工具必须永远返回字符串。
- **粒度过细**：把「先读再改再写」的内部步骤摊开给模型，它会把这些步骤当作用户需求去执行。
- **参数 schema 缺 `required`**：模型永远漏传参数，然后收到一个 `KeyError`。
- **描述写成实现说明**：写了「内部调用 subprocess 执行」，没写「什么时候该用它」——模型要的是后者。
- **给破坏性工具设默认值**：假如给 `fs_write` 的 `content` 加一个默认值，少传就会把文件清空——这种「方便」是灾难。本章的实现刻意不给默认值，正是为了堵住它。
- **权限由工具自己说了算**：MCP server 自称有权限不等于该给它。判断权必须留在 harness。
- **以为 MCP 是「更高级的写法」**：本地短函数就是最快的，MCP 是为隔离与复用付的代价。
- **把 CRUD 端点原样暴露**：工具数量上升会同时抬高选择成本和误操作风险，按任务语义封装。

## 自测题

1. 为什么报错要转成字符串返回给模型，而不是抛异常？请结合「模型拿到错误后会做什么」回答。
2. 「默认拒绝」和「默认允许」的差别，在工程上具体表现在哪一行代码？各会导致什么事故？
3. 好的工具 description 包含哪四个要素？为什么「内部怎么实现」不属于其中？
4. 修一行代码，用 `apply_patch` 相比 `fs_write` 好在哪里？请说出至少三点。
5. 「核心循环零改动」是靠什么设计实现的？如果直接删除 `ToolRegistry`、「循环里加个 if 判断工具名」，会失去什么？
6. 什么情况下值得把工具搬进 MCP server？什么情况下不值得？
7. 一个工具在 MCP server 侧声明了 `scopes`，harness 的 `granted_scopes` 里却没有它。冲突时谁说了算？为什么？
