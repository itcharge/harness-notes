# 4.2 工具描述工程与错误返回设计

4.1 的工具转成给模型看的清单时，只有三项：`name`、`description`、`parameters`。`name`（名字）只是标识，`parameters`（参数）只规定有哪些字段。模型决定「现在用不用这个工具」，看的是 `description`（工具描述）。

**这段说明写给模型，不是写给程序员看的。** 两边要的东西不一样：

| 受众 | 想知道的 |
| --- | --- |
| 程序员 | 内部怎么实现、调了哪个 API、快还是慢 |
| 模型 | 什么时候该用、什么时候不该用、参数怎么填、返回什么 |

「内部用 subprocess 调用 git」对模型没有用。它需要的是：「用户提到提交、暂存、查看改动时，用这个工具。」

## 4.2.1 描述里的四件事

一条合格的 description 回答四个问题：

1. **什么时候该用它**（触发条件）
2. **什么时候不该用它**（边界，尤其要指出「这件事该用哪个其他工具」）
3. **参数怎么填**（每个字段是什么意思、什么格式）
4. **返回什么**（结果长什么样，好让模型知道下一步怎么用）

先看本章 `fs_read` 的描述。它只回答前两个问题，一句实现细节都没有：

```text
读取工作目录里的文件内容，或列出目录下有哪些文件。
想知道『文件里写了什么』『目录里有什么』时用它。
不要用它试探路径是否存在——路径不对会直接返回错误。
```

第 3 问不写在这段话里，写在 `parameters`（参数）上：

```python
{
    "type": "object",
    "properties": {
        "path": {"type": "string", "description": "相对工作目录的路径；省略则列出根目录"},
    },
}
```

「相对工作目录的路径」是在告诉模型：填 `src/main.py` 这种相对路径，别填 `/Users/...`。第 4 问这个例子没写。返回如果有固定格式，也要在描述里说一句，模型才知道拿到结果之后怎么接着用。

## 4.2.2 把用法写进描述

四个问题里，「什么时候该用」有时不是建议，是硬要求。这种时候直接写成命令句。第 3 章 `get_time` 就是这样：

```text
获取当前日期和时间。凡是涉及『今天 / 现在 / 几号』的问题都必须先调用它。
```

模型读描述，是在决定这一步要不要调用它。「必须先调用它」直接回答了这件事，比多写几条参数约束更管用。

同类的句子还有：

- `在这之前先用 fs_read 确认文件内容。`（先做哪一步）
- `如果用户没有指定目录，不要猜，先问。`（缺了参数怎么办）
- `同一轮里不要重复调用两次。`（别循环绕圈。第 3 章的熔断是次数到了强制停下；这句话是提前告诉模型，别走到那一步）

这些句子不靠代码检查，靠模型读了之后照做。成本是多几十个 token，收益是少一次错误的工具调用。**这是本章性价比最高的一处投入。**

## 4.2.3 三种写法的结果

把同一个工具的 description 换三种写法，你会看到三种典型翻车：

| 写法 | 例子 | 模型会怎样 |
| --- | --- | --- |
| 太含糊 | `操作文件` | 该读文件时想不起来用它，参数也凭习惯乱填 |
| 太宽 | `处理一切与文件相关的任务` | 把 `apply_patch`、`fs_write` 的活也抢过去，要改文件时却去读文件 |
| 刚好 | `读取文件内容或列出目录；想改文件请用 apply_patch` | 该用的时候用，不该用的时候让给其他工具 |

**动手测一次（建议做）**：挑一个工具，把三种写法各写一遍。用同一组 10 个任务（5 个「该用」、5 个「不该用」）各跑一轮，记下两列数字：**该用却没用的次数**，**不该用却用了的次数**。你会看到第三种写法里，两列都会变少。

这一步不白做：下一章的技能包也一样，模型先看到的是它的一句话描述。描述写错，正文根本没机会被读到，这个技能包就等于不存在。

## 4.2.4 报错要写给模型看

描述写清楚，模型还是会叫错：路径不存在、参数名写错、文件被改过。调用失败之后，模型看到的那段文字，决定它下一步怎么改。

### 铁律：异常绝不抛出循环

第 3 章的 `get_weather` 埋着一颗雷。如果模型把 `city` 写成 `cities`，代码去取 `args["city"]`，就会抛出 `KeyError`。从而导致程序退出，会话结束，用户看到一段 traceback。

文件不存在、路径写错、没有权限、网络超时，这些一天会碰上很多次。它们不是程序写错了，是任务做到一半的正常结果。

所以有一条铁律：**工具永远返回字符串，永远不抛异常。** 失败也是一次返回，文字里要写明「这次没成，原因是……」。

4.1 `ToolRegistry.call()` 里的 `try/except` 是这条铁律的最后一道防线：即使某个工具的作者忘了处理，异常也会被兜住，转成文本交给模型。这是最后一道兜底，能说清楚的错误，应该由工具自己返回。

### 坏错误 vs 好错误

同一次失败，两种返回，模型的下一步完全不同：

```text
坏：  error
坏：  Traceback (most recent call last): File "tools_fs.py", line 23, in fs_read ...
坏：  Failed.
```

```text
好：  错误：路径 'src/main.py' 不存在。
     请先用 fs_read(path='src') 看看实际有哪些文件。
```

差别不在写得长不长。**坏错误只说发生了什么，好错误还告诉下一步怎么做。**

一条好错误要有三件事：

1. **发生了什么**（路径不存在 / 原文没找到 / 这段原文出现了多次）
2. **可能的原因**（路径写错了？文件被改过？空格对不上？）
3. **下一步怎么做**（用哪个工具、传什么参数去确认）

`apply_patch` 的三种失败都带了下一步。完整实现见 4.3 节：

```python
# apply_patch 的三条失败分支（完整实现见 4.3 节）
def apply_patch(args: dict) -> str:
    ...
    return f"错误：'{rel}' 不存在。请先用 fs_read(path='{rel}') 确认，或改用 fs_write 创建它。"
    return f"错误：在 {rel} 里找不到要替换的原文。请先用 fs_read(path='{rel}') 核对空格与缩进。"
    return f"错误：要替换的原文在 {rel} 里出现 {hits} 次，无法定位。请在 old 里多带几行上下文。"
```

第三条没有停在「找不到」。它告诉模型：在 `old` 里多带几行上下文，让这段原文只出现一次。模型读到这句，下一轮就会把参数改对。

### 故意报错的工具：本章的教具

这些返回好不好用，要看见模型拿到之后做什么。这里放一个故意失败的工具 `delete_note`。它只做一件事：按文件名删一份笔记。参数只有 `filename`，就是要删的那个文件名。

文件名不是代码里写死的。用户说「把日记删掉」，模型从这句话里读出来，填 `filename="日记.txt"`。

```python
# harnex/tools/misc.py —— 时间工具 + 一个故意报错的教具
from datetime import datetime


def now(args: dict) -> str:
    return datetime.now().strftime("%Y-%m-%d %H:%M:%S")


def delete_note(args: dict) -> str:
    """教学道具：一个一定会失败的工具。"""
    filename = args["filename"]    # 要删的文件名，由模型从用户的话里读出来
    if filename == "日记.txt":
        return ("错误：日记.txt 不能直接删。"
                "请先用 fs_read(path='日记.txt') 看一遍内容，"
                "或改删副本 filename='日记-副本.txt'。")
    raise RuntimeError("删除功能还没接上")
```

`filename` 在参数 schema 里要写成必填。动手任务 2 里注册它时，加上 `required=["filename"]`。这和 4.1 的规矩是同一条：删文件会真的改掉东西，文件名不能靠模型猜。

这个工具故意走了两条路。`filename` 是 `日记.txt` 时，它自己返回一段好错误，里面写了下一步怎么做。换成别的文件名，比如好错误里提到的 `日记-副本.txt`，它就直接抛异常，用来确认注册表会把异常兜成文本。

把它注册进去，对 Harnex 说「把日记删掉」：

```text
① 模型调用 delete_note(filename="日记.txt")
② 工具返回：错误：日记.txt 不能直接删。
   请先用 fs_read(path='日记.txt') 看一遍内容，或改删 filename='日记-副本.txt'
③ 模型读到"下一步怎么做"，于是向用户转述：
   "日记不能直接删。我可以先读一遍内容，或者改去删那份副本，要哪一个？"
```

**第 ③ 步就是好错误的用处。** 如果第 ② 步只返回 `error`，模型只能对你说「删不掉，我也不知道为什么」。错误文本是交给模型的输入，写得好不好，决定它下一步做什么。

> 真实产品里也是这一条。别只回「权限不足」。写成「你要先做 X，才能拿到 Y 权限」，模型就会自己去找 X。
